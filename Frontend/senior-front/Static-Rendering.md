# 🧊 Topic: Static Rendering (SSG)

> [!abstract] Executive Summary (ELI5)
> Статический рендеринг — весь HTML генерируется **во время сборки** (`npm run build`) и остаётся неизменным до следующего билда. Один HTML на всех пользователей. Готовые файлы лежат в статическом хранилище и кэшируются в CDN/Edge-сети максимально близко к пользователю — поэтому **TTFB почти мгновенный**: серверу нечего рендерить, он просто отдаёт файл.

> Источник: глава 1.1 курса, подглава 2 (§2.1–2.4). Якорь: [Pat] patterns.dev, «Rendering Patterns» → Static Rendering.

---

## 🎯 The "Why"

- **Problem Solved:** как отдать контент максимально быстро, если он **одинаков для всех** и меняется редко. Никакой серверной работы на запрос — только раздача готового файла с ближайшей CDN-точки.
- **Критерий пригодности (якорь [Pat]):** страницы «which do not change often and display the same data no matter who requests them» — редко меняются и показывают одни и те же данные независимо от того, кто их запрашивает.
- **Alternatives:**
    - [[SSR-Server-Side-Rendering]] — контент зависит от запроса (персональные данные, cookies);
    - [[ISR-Incremental-Static-Regeneration]] — статика, но данные терпят устаревание и обновляются фоном;
    - [[CSR-Client-Side-Rendering]] — высокоинтерактивное приложение, контент вторичен.
- **Trade-offs:** максимум скорости (TTFB/FCP/LCP) и минимум серверных расходов — но контент **заморожен до следующей сборки**; персонализация невозможна в принципе.

---

## 💡 Mental Model & Analogy

**Напечатанная газета в киоске у дома.** Все экземпляры одинаковы, напечатаны заранее (сборка), лежат максимально близко к покупателю (CDN/Edge). Взял — читаешь сразу. Но вчерашняя газета не знает про сегодняшние новости, и в неё нельзя вписать имя покупателя.

```
npm run build → HTML готов → статическое хранилище → CDN/Edge (близко к юзеру)
запрос → CDN отдаёт готовый файл (TTFB ≈ мгновенно) → браузер рисует → JS гидратация
```

**Ключевое различие с SSR — КОГДА, а не ГДЕ:** оба рендерят на сервере. Статика — один раз при сборке. SSR — на каждый визит.

## 🛠️ Core Principles & Mechanics

### Timeline: что происходит когда

| Момент | Static (SSG) | SSR |
|---|---|---|
| `npm run build` | HTML всех страниц готов | — |
| Запрос пользователя | CDN отдаёт готовый файл | сервер рендерит под запрос |
| Серверная работа на запрос | **нет** | каждый раз |
| Контент персонален | **нет** (один на всех) | да (cookies/headers) |
| Когда контент обновится | следующий деплой | каждый запрос |

### Эффект на Core Web Vitals (§2.2)

- **TTFB сверхбыстрый** — HTML уже готов, «время обработки запроса» стремится к нулю.
- Быстрый TTFB → быстрые **FCP и LCP** (контент приезжает первым же ответом).
- Контент статичен → смещение макета исключено → **CLS отличный**. Статика — лучший паттерн по Core Web Vitals из всей главы.

Но: большинство современных сайтов требуют динамических данных и интерактивности → появляются вариации.

---

## 🔀 Вариация 1: Static Rendering with Client-Side fetch (§2.3)

Статический UI с **каркасом (skeleton)** отдаётся мгновенно, данные запрашиваются **на клиенте** (например, через SWR) из API-маршрута. Подходит, когда нужны самые свежие данные (пример якоря — списки недвижимости).

| Что хорошо | Цена |
|---|---|
| TTFB и FCP отличные (shell статичен) | **LCP страдает**: главный элемент отрисуется только после получения данных с API |
| данные свежие | высокий риск **CLS**, если размер каркаса не совпадает с финальным контентом |
| | API вызывается **при каждом запросе** → серверные расходы |

---

## 🔀 Вариация 2: Static with `getStaticProps` (§2.4, сборка с данными)

Данные запрашиваются **во время сборки на сервере** — HTML сразу генерируется с актуальными данными, каркас не нужен. Цитата якоря: «we can avoid creating API routes to fetch the data on the client» — API-маршруты для клиента не нужны вовсе.

С точки зрения клиента сетевая работа и работа главного потока **идентичны базовой статике** — та же превосходная производительность.

**Trade-off (цена данных при сборке):**
- рост сайта (сотни страниц блога) → многократный вызов метода при сборке → «can result in **long build times**» [Pat];
- можно упереться в **лимиты запросов к внешним API**;
- подходит только там, где данные обновляются **редко** — иначе постоянные пересборки и деплой.

> [!warning] Next.js 16: `getStaticProps` ушли
> Классические `getStaticProps`/`getServerSideProps` (Pages Router, эпоха якоря [Pat]) в Next.js 16 **удалены**. Актуальная модель — Cache Components: `'use cache'` + `cacheLife` рендерит при сборке, `<Suspense>`-границы отдают динамику при запросе (см. [[Partial Prerendering]]). Принцип §2.4 «данные при сборке» жив — изменился синтаксис. Зафиксировано в замечаниях главы 1.1 о расхождениях источников.

## ✅ Production-чеклист

- [ ] контент действительно одинаков для всех (нет cookies/гео/A-B на этапе показа) — иначе [[SSR-Server-Side-Rendering]];
- [ ] данные терпят устаревание до следующего деплоя? если нет — [[ISR-Incremental-Static-Regeneration]];
- [ ] сборка не растёт в десятки минут (лимит билд-минут платформы);
- [ ] для свежих блоков выбрана вариация: client-side fetch (skeleton того же размера, что контент — против CLS) или данные в сборке;
- [ ] CDN-кэш сбрасывается при деплое (новая сборка = новая версия файлов).
