# 🧠 Topic: Islands Architecture (архитектура «островов»)

> [!abstract] Executive Summary (ELI5)
> Islands — это когда страница в основном **статичная** (HTML, контент виден сразу), а **интерактивные блоки** (кнопки, виджеты, карусели) — это отдельные маленькие «острова», каждый со своим JS, которые гидрируются **независимо**. Главная идея: **«что, если платить только за интерактивные части?»** Статика — 0 байт JS, острова — только нужный минимум.

> Источник: глава 1.1 курса, подглава 5. Якорь: [Pat] patterns.dev, «Islands Architecture».

---

## 🎯 The "Why"

- **Problem Solved:** классический SSR (Server-Side Rendering) и CSR (Client-Side Rendering) отправляют «слишком много JS»: SSR — гидрирует всё дерево, CSR — весь интерфейс как JS. Islands: платить JS **только за интерактивные зоны**.
- **Alternatives:**
    - [[SSR-Server-Side-Rendering|SSR]] с Selective Hydration — единое дерево, порядок гидратации;
    - [[React-Server-Components]] — единое дерево, серверные компоненты без JS;
    - Qwik (resumability) — вообще без гидратации;
    - [[CSR-Client-Side-Rendering|CSR]] — весь интерфейс в браузере.
- **Trade-offs:** экстремальная производительность (на 80%+ меньше JS для контентных сайтов) и изоляция сбоев, но ценой разделения ментальной модели и сложности синхронизации состояния между островами.

---

## 💡 Mental Model & Analogy

- **Аналогия:** SPA (CSR) — это один большой шатёр, внутри которого всё живёт в общем пространстве. Islands — это палаточный лагерь: общая поляна (статический HTML), на которой стоят отдельные палатки (острова), каждая со своим оснащением (JS). Палатки не знают друг о друге.
- **Главная интуиция:** «что, если платить только за интерактивные части?» ([Pat]).

```
SSR (одно дерево):              Islands (много деревьев):
┌─────────────────────┐         ┌─────────────────────┐
│  <App>              │         │  статический HTML   │
│    <Header/>        │         │  + [остров: кнопка] │ ← своё дерево
│    <Article/>       │         │  + статика          │
│    <Comments/>      │         │  + [остров: чат]    │ ← своё дерево
│    <Footer/>        │         │  + статика          │
│  </App>             │         │                     │
└─────────────────────┘         └─────────────────────┘
гидрируется ЦЕЛИКОМ              гидрируются ТОЛЬКО острова
```

## 🛠️ Core Principles & Mechanics

### Ключевые свойства (из источника)

1. **Каждый остров — собственный корень.** Острова на одной странице **не имеют общего дерева React**, виртуального DOM или хранилища состояния, если не связать их принудительно. Ошибка в одном острове не сломает другой.
2. **Гидратация параллельна и независима.** Островам не нужно ждать общей нисходящей инициализации; активируются по своему расписанию (`load`, `idle`, `visible`, при первом взаимодействии).
3. **Статический контент = чистый HTML.** Источник истины — HTML. 0 байт JS.

### Главная техническая разница со SPA

| | SPA (CSR) | Islands |
|---|---|---|
| Деревьев на странице | **одно** | **много** (по одному на остров) |
| Общий стор | есть (Redux, Zustand, Context) | нет общего |
| Гидратация | всего дерева сверху вниз | только островов, по расписанию |
| Статический контент | рендерится JS | чистый HTML |

## 💧 Частичная гидратация (Astro-синтаксис)

### Отличие от прогрессивной гидратации (Selective Hydration)

- **Прогрессивная гидратация (Selective Hydration, React 18+):** страница — **единое дерево**, просто определяется порядок активации ветвей.
- **Частичная гидратация (Islands):** единого дерева **нет вообще**. Клиентское дерево компонента никогда не собирается целиком на стороне пользователя.

### Astro-директивы

```jsx
<article>
  <h1>Why your bundle is too big</h1>

  {/* Hydrates immediately - над первым экраном, юзер кликнет сразу */}
  <LikeButton client:load count={142} />

  {/* Hydrates only when it scrolls into view - внизу страницы */}
  <Comments client:visible postId="123" />

  {/* Hydrates when main thread is idle - не срочный */}
  <VideoPlayer client:idle src="/intro.mp4" />

  {/* No directive - server-rendered HTML, zero JS shipped */}
  <RelatedArticles posts={posts} />
</article>
```

| Директива | Когда гидрируется | Когда использовать |
|---|---|---|
| `client:load` | сразу при загрузке | компонент **над первым экраном**, кликабелен сразу |
| `client:idle` | когда main thread свободен | важен, но не срочен |
| `client:visible` | при прокрутке в зону видимости | компонент **ниже первого экрана** |
| _(без директивы)_ | никогда | статический контент — **0 байт JS** |

### Fresh (Deno) — иной синтаксис

Astro: директива в JSX (`client:load`). Fresh: **расположение файла** (`islands/` папка).

```
Astro:  <LikeButton client:load />     ← директива решает
Fresh:  islands/LikeButton.tsx          ← папка решает
```

## 🌐 Server Islands (серверные острова)

> Появились в Astro в конце 2024 года. Снимают ограничение классической модели: страница больше не обязана рендериться целиком, если часть требует персональных данных.

### Какую проблему решают

**Проблема классических островов с персональными данными:** если в острове есть персональные данные (аватар, корзина), они попадают в **основной рендер страницы** → весь HTML становится персональным → **нельзя кэшировать на edge**.

**Решение Server Islands:** статическую часть страницы кэшируем на edge, персональные фрагменты рендерим по требованию и подменяем плейсхолдеры.

```jsx
// server:defer — рендер ВЫНЕСЕН в отдельный запрос
<Avatar server:defer>
  <GenericAvatar slot="fallback" />   {/* серый кружок в основном HTML */}
</Avatar>
```

### Что приезжает на клиент

```html
<!-- Основной HTML — кэшируется на edge (один на всех, без userId) -->
<div data-server-island="Avatar">
  <div class="generic-avatar">○</div>   <!-- плейсхолдер -->
</div>

<!-- Фрагмент приезжает позже, по требованию (с userId=42) -->
<img src="/avatars/user-42.jpg" />
<span>Привет, Павел!</span>
```

### Ключевое различение: две оси оптимизации

> **Классический остров разделяет JavaScript** (какой JS грузить).
> **Server Island разделяет рендер** (какую часть страницы рендерить при запросе, а какую — закэшировать).

| | Классический остров | Server Island |
|---|---|---|
| Что едет на клиент | HTML + **JS-чанк** острова | HTML страницы + позже **HTML-фрагмент** |
| Где работает «остров» | **в браузере** (гидратация) | **на сервере** (рендеринг по требованию) |
| Зачем | меньше JS → лучше INP | персональные данные **не ломают edge-кэш** |
| Кэшируется ли страница на edge | только если вся страница статична | **да** |

### Server Island — это НЕ интерактивность

Server Island решает смысл №1 («показать правильные данные»), а не смысл №2 («реагировать на клики»). Аватар без кликов = Server Island (0 JS). Карусель с кликами = классический остров (JS + гидратация).

### Комбинация: персональные данные + интерактивность

Когда нужны ОБА — **серверный остров вкладывается** в классический:

```astro
<!-- CartShell.astro — серверный остров -->
---
import CartInteractive from "./CartInteractive.tsx";
const { userId } = Astro.props;
const cart = await getCart(userId);   // персональные данные на сервере
---
<!-- Внутри — классический остров с гидратацией -->
<CartInteractive client:load initialCart={cart} />
```

```astro
<!-- page.astro -->
<CartShell server:defer userId={Astro.cookies.get("uid")}>
  <div slot="fallback">Загрузка корзины...</div>
</CartShell>
```

> **Важно:** `server:defer` и `client:load` **не смешиваются на одном компоненте**. Серверный остров рендерит HTML, а классический остров вкладывается внутрь него и гидрируется.

### Откуда берётся бандл для классического острова внутри Server Island

Серверный фрагмент — это не «голый HTML». В нём, кроме контента, лежит **МЕТКА**:

```html
<div data-island="CartShell">
  <div>3 товара: телефон, чехол, кабель</div>
  <div data-client-island="CartInteractive"
       data-component="/assets/CartInteractive-a1b2c3.js">  <!-- МЕТКА -->
    <button>Корзина (3)</button>
  </div>
</div>
```

Astro-runtime (маленький JS на странице с самого начала) видит метку `data-component="..."` и **по ней** скачивает бандл — ровно как браузер качает `<script src="...">` по ссылке в HTML. Бандл лежит отдельно как статический ассет.

## 🔍 Сравнение с RSC (React Server Components) и Qwik

Цель «отправлять меньше JavaScript» разделяют несколько подходов, но механизмы разные:

| Паттерн | Структура дерева | Гидратация | Общее состояние |
|---|---|---|---|
| **Islands** | много независимых деревьев | только острова, по расписанию | нет общего (надо явно связывать) |
| **RSC** | **единое** дерево React | серверные — нет, клиентские — да | есть (Context, стор) |
| **Qwik** | единое (но resumable) | **нет** (resumability) | есть, сериализовано в HTML |
| **Классический SSR** | единое дерево | **всё**, сверху вниз | есть |

- **Islands:** JS только для интерактивных зон. Идеально для контентных сайтов (блоги, маркетинг, документы, e-commerce).
- **RSC:** сохраняет единое дерево React, серверные компоненты не отправляют JS и читают данные напрямую из БД. Требует «один большой React runtime».
- **Qwik (Resumability):** вообще отвергает гидратацию. Слушатели встроены в HTML, один глобальный слушатель подгружает код по требованию при клике. «Каждое событие — свой собственный остров», но без явных границ.
- **Классический SSR:** всё дерево + нисходящая гидратация (топорный подход для SPA).

## ✅ Преимущества

1. **Экстремальная производительность.** Astro отправляет на **80% и более меньше JS**, чем Next.js/Nuxt для контентных сайтов.
2. **SEO и доступность.** HTML-first — отлично для поисковиков и скринридеров.
3. **Изоляция сбоев.** Баг в одном острове не обвалит всю страницу (нет общего дерева).
4. **Стратегия загрузки.** Гибкий контроль через `client:load` / `client:idle` / `client:visible`.

---

## ⚠️ Недостатки и trade-off

1. **Разделение ментальной модели.** Нет простоты «одно дерево, один стор».
2. **Сложность коммуникации.** Острова не могут напрямую делиться состоянием. Нужны: URL-параметры, куки, кастомные DOM-события, микро-стор. **Сигнал:** если постоянно нужно делиться состоянием — ты вышел из зоны «в основном статичный контент».
3. **Ограничения экосистемы.** Фреймворки островов моложе React/Vue; крупные UI-библиотеки пишутся под SPA.
4. **Сложность миграции.** Перенос SPA → Islands — переписывание архитектуры, обычно проще начать с нуля.

### Синхронизация состояния между островами (главный trade-off)

```jsx
// Остров 1: кнопка "добавить в корзину"
function AddToCart() {
  return <button onClick={() => {
    window.dispatchEvent(new CustomEvent('cart:add', { detail: { id: 42 } }));
  }}>Add</button>;
}

// Остров 2: бейдж корзины в хедере
function CartBadge() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const handler = () => setCount(c => c + 1);
    window.addEventListener('cart:add', handler);
    return () => window.removeEventListener('cart:add', handler);
  }, []);
  return <span>{count}</span>;
}
```

Работает, но сложнее, чем `useState` в общем родителе SPA.

## 🎯 Когда использовать, а когда нет

### ✅ Практически идеальный выбор

Страница преимущественно статична, интерактивные части локализованы:
- документация, новости, блоги, лендинги;
- страницы товара в e-commerce (JS — галерея + «в корзину»);
- дашборды с преимущественно читаемыми данными.

### ❌ Плохой вариант

Интерактив глобален — общее состояние пронизывает множество виджетов, смена маршрута обновляет половину экрана, «фундаментально одна большая интерактивная поверхность»:
- совместный редактор кода;
- canvas-приложение типа Figma;
- интерфейс видеоконференций.

→ В этих случаях — единое дерево (SPA, SSR с гидратацией или RSC).

> **Резюме источника:** для контентных сайтов в 2025 году острова — базовая архитектура, с которой стоит начинать. Для сложных веб-приложений — лишь инструмент, но не фундамент.
