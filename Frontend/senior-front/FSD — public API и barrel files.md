# FSD — public API и barrel files

> Подглава 6 главы 1.2 курса «Фронтенд senior+ в агентную эру». Якорь [FSD] — Reference → Public API. Продолжает: [[FSD — слайсы и группы слайсов]].

## Executive Summary (ELI5)

Публичный API слайса — это **контракт + ворота**: потребители видят только то, что экспортировано; слайс свободно рефакторится внутри, пока контракт жив. Та же дисциплина, что у npm-пакета (`date-fns` экспортирует `format` — внутренности скрыты), применённая к каждой папке твоего приложения.

Реализация: index-файл с именованными реэкспортами.

## Три цели хорошего public API

1. Остальное приложение **защищено от структурных изменений** слайса (рефакторинг не ломает потребителей).
2. Значимые изменения поведения, ломающие ожидания, **отражаются изменениями API** (честный сигнал breaking change).
3. Экспорт **только необходимого**.

**Wildcard — антипаттерн** (`export * from "./ui/Comment"`):
- рушит discoverability — интерфейс слайса не виден, для интеграции лезешь в код;
- **случайно экспортирует внутренности** — на них полагаются, рефакторинг блокируется (бьёт по цели №1 и №3).

## @x-нотация: легальный кросс-импорт на Entities

Когда слайсу B реально нужен слайс A того же слоя (бизнес-сущности ссылаются друг на друга — лучше отразить, чем хитрить):

**Порядок решения:**
1. **Сначала — рассмотреть слияние** сущностей (кросс-импорты в entities часто следствие слишком мелкой нарезки);
2. если слияние не подходит — `@x`: отдельный публичный API **только для B**.

```
entities/product/
  @x/
    cart.ts     # API только для entities/cart
  index.ts      # обычный API для всех
```

```ts
// внутри entities/cart — абсолютный импорт (другой слайс!):
import type { Product } from "entities/product/@x/cart";
```

Читается «product crossed with cart». Канонический минимум — простой реэкспорт из model (`export type { Product } from "../model/product"`); проекция полей (CartProduct с id/title/price) — опция сверх источника 🟡.

**Две жёсткие рамки:** минимум кросс-импортов; `@x` — только на слое Entities.

## Environment-specific API

Общее правило: API = `index.ts`, свободная кастомизация не рекомендуется. Исключение: модули одного слайса исполняются в **разных средах** — единый index может сломать границу среды или склеить лишний код в бандле → разделить API файлами по среде (пример источника: Server/Client public APIs в Next.js; перекликается с `'use client'` — [[Next.js Server and Client Components]]).

## Проблемы barrel files и решения

**1. Циклические импорты** (`index → HomePage → index`). Анти-циклы:
- внутри слайса — **относительные** импорты с полным путём (`./api/loadUserStatistics`);
- между слайсами — **абсолютные** (alias, `@/features/auth`).

**2. Сломанный tree-shaking в Shared.** `shared/ui`, `shared/lib` — коллекции несвязанных вещей; тяжёлая зависимость одного компонента (подсветчик, drag'n'drop) не должна ехать в бандл страницы из-за кнопки → **поштучные index** на компонент/библиотеку (`@/shared/ui/button`). Классика жанра 🟡: moment, тянувший все локали.

**3. Обход API мимо index** (особенно авто-импорты IDE) → линтер **Steiger**.

**4. Деградация бандлеров** (много barrel files — медленный dev-сервер; TkDodo «Please Stop Using Barrel Files»):
- поштучные index в `shared/ui`/`shared/lib`;
- **не заводить index в сегментах** слоёв со слайсами (`features/comments/index.ts` есть → `features/comments/ui/index.ts` не нужен);
- очень большие проекты — монорепо: пакет = отдельный FSD-корень (мост к главе 1.9).

## Self-check

1. Три цели API? → защита от структурных изменений; заметность поведенческих; экспорт необходимого.
2. Первый шаг перед @x? → рассмотреть слияние сущностей.
3. Анти-циклы? → относительные внутри слайса, абсолютные между слайсами.
4. Почему features/comments/ui без index? → сегмент — деталь реализации; слайсу достаточно одного index.
