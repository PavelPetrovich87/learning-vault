# ♻️ Topic: Incremental Static Regeneration (ISR)

> [!abstract] Executive Summary (ELI5)
> ISR — гибрид статики и динамики: при сборке пререндерится только **часть** страниц, остальные генерируются **по требованию** при первом запросе и кэшируются на Edge. Обновление контента — фоновой регенерацией: по таймеру (`revalidate`) или по событию (вебхук, On-demand). Пользователь всегда получает страницу **мгновенно** — пусть иногда чуть устаревшую, пока в фоне печатается новая версия.

> Источник: глава 1.1 курса, подглава 2 (§2.5–2.6). Якорь: [Pat] patterns.dev, «Rendering Patterns» → Incremental Static Regeneration.

---

## 🎯 The "Why"

- **Problem Solved:** у чистого SSG ([[Static-Rendering]]) два тупика роста: (1) сотни страниц → **долгие сборки**; (2) данные меняются чаще, чем деплоишь → constant rebuild & redeploy. ISR снимает оба: prerender — только то, что нужно, обновление — без пересборки.
- **Гибридность (якорь [Pat]):** «ISR is hybrid in the sense that it allows us to pre-render only certain static pages and render the dynamic pages **on-demand**».
- **Alternatives:**
    - [[Static-Rendering]] — контент меняется реже, чем деплои;
    - [[SSR-Server-Side-Rendering]] — персональный контент, устаревание недопустимо;
    - [[Partial Prerendering]] — эволюция идеи в Next.js 16.
- **Trade-offs:** скорость статики сохранена, но пользователь может увидеть **stale**-версию (окно устаревания = интервал/задержка вебхука); таймерная регенерация может гонять сервер впустую.

## 💡 Mental Model & Analogy

**Кофейня с витриной.** Часть выпечки приготовлена к открытию (prerender при сборке). Позиции, которых нет на витрине, готовят при **первом заказе** — и остаток остаётся на витрине для следующих (кэш на Edge). Обновление ассортимента: по расписанию (таймер `revalidate`) — или звонок поставщика (вебхук), и бармен сразу печёт свежую партию **для всех точек сети**.

```
build:   prerender N важных страниц → CDN/Edge
запрос:  страница есть? → отдаём мгновенно
         страницы нет? → рендерим на лету → кэшируем на Edge → отдаём
обновление: таймер (revalidate: 5m) | вебхук (on-demand) — фоном, без деплоя
```

## 🛠️ Core Principles & Mechanics

### Механика 1: генерация по требованию (§2.5)

Через `getStaticPaths` фреймворку указывается, какие страницы сгенерировать заранее, а какие — **по требованию** при первом запросе пользователя. Неотрендеренные страницы генерируются **на лету** и кэшируются на Edge — следующий запрос получает их уже мгновенно. Сотни страниц больше не требуют сотен рендеров на сборке.

### Механика 2: таймерная регенерация — `revalidate` (§2.5)

Поле `revalidate` задаёт интервал автоматической инвалидации кэша и **фоновой** регенерации. Ключевой UX-инвариант — **stale-while-revalidate**:

```
интервал истёк → пользователь всё равно получает СТАРУЮ страницу (мгновенно)
               → в фоне генерируется новая → подменяет кэш
следующий пользователь → получает новую
```

То есть регенерация **никогда не блокирует** ответ пользователя.

### Механика 3: On-demand ISR — вебхук вместо таймера (§2.6)

Регенерация не по расписанию, а **по событию**: вебхук сигнализирует о появлении новых данных → вызывается метод регенерации конкретного пути. Отличие от таймерной — не просто обновление одной точки:

> «заново распределяет обновлённую страницу по **всей Edge-сети**, so that users worldwide will automatically see the most recent version of the page» [Pat]

### Сравнение режимов

| | build-time (SSG) | ISR по таймеру | On-demand ISR |
|---|---|---|---|
| Когда рендер | сборка | сборка + первый запрос + каждые N | сборка + первый запрос + **событие** |
| Свежесть | до деплоя | окно ≤ N + регенерация фоном | сразу после события |
| Лишняя работа | нет | да: контент редко меняется так часто, как интервал | почти нет |
| Серверные расходы | минимум | ↑ (регенерации + serverless-вызовы) | точечные вызовы |

## ⚖️ Trade-offs таймерного ISR (§2.5)

Решает проблему долгих сборок, но: контент редко обновляется **так же часто**, как заданный интервал → **ненужные регенерации**, инвалидации кэша и вызовы серверлесс-функций → **повышенные эксплуатационные расходы**. На лбу интервала: слишком частый — платишь впустую; слишком редкий — длинное окно устаревания. On-demand ISR снимает дилемму.

---

## 🔮 Куда это эволюционировало (Next.js 16)

Классический ISR с `getStaticPaths`/`revalidate` — API эпохи Pages Router (якорь [Pat]); в Next.js 16 `getStaticPaths` упоминается лишь как источник **сэмплов** для `params` (§8.4). Принцип «статика + точечная регенерация без пересборки» переехал в Cache Components: `'use cache'` + `cacheLife(...)` — кэшированный рендер с управляемой свежестью, а окно устаревания закрывает PPR-стрим динамики. См. [[Partial Prerendering]].

## ✅ Production-чеклист

- [ ] данные **терпят устаревание** (Tolerable Staleness: цены, лента, каталог) — иначе [[SSR-Server-Side-Rendering]];
- [ ] выбран режим обновления: таймер (просто, но платишь пустыми регенерациями) или вебхук (точно, но нужен источник событий);
- [ ] у таймера интервал согласован с реальной частотой изменений данных;
- [ ] fallback первой генерации не двигает layout (CLS);
- [ ] регенерация идемпотентна — вебхук может прийти дважды.
