# Static-Rendering-Flashcards

---

Когда генерируется HTML при статическом рендеринге (SSG) и что это даёт по сравнению с SSR?
?
При **сборке** (`npm run build`), один HTML на всех, неизменен до следующего деплоя. Готовые файлы лежат в статическом хранилище и кэшируются в CDN/Edge максимально близко к пользователю. На запрос серверная работа не тратится вообще — только раздача файла, поэтому TTFB почти мгновенный.

---

Сформулируй критерий пригодности страницы для чистой статики из якоря [Pat] (patterns.dev).
?
«Редко меняются и показывают одни и те же данные независимо от того, кто их запрашивает» («do not change often and display the same data no matter who requests them»). Проверка на пригодность: нет cookies, нет гео, нет A/B на этапе показа → статика годится. Любой из этих трёх → SSR.

---

Почему статический рендеринг даёт лучшие Core Web Vitals из всех стратегий? Разбери по метрикам.
?
HTML уже готов — время обработки запроса стремится к нулю → **TTFB** сверхбыстрый. Быстрый TTFB тянет за собой быстрые **FCP и LCP** (контент приезжает первым же ответом). А поскольку контент статичен и не меняется после отрисовки — смещение макета исключено → отличный **CLS**. Статика — лучший паттерн по CWV из всей главы.

---

Вариация «Static Rendering with Client-Side fetch»: как устроена и чем платим?
?
Отдаём статический UI с **skeleton-каркасом** мгновенно, данные дергаем **на клиенте** (SWR → API-маршрут). Цена: **LCP страдает** — главный элемент отрисуется только после получения данных; высокий риск **CLS**, если размер каркаса не совпадает с финальным контентом; API вызывается **на каждый запрос** → серверные расходы. Хороший TTFB/FCP, но это уже «полу-CSR».
<!--SR:!2026-08-27,1,230-->

---

Вариация «Static with getStaticProps»: что даёт и почему для клиента она выглядит как чистая статика?
?
Данные запрашиваются **во время сборки на сервере** — HTML сразу с актуальными данными, каркас не нужен, API-маршруты для клиента не создаются вовсе («we can avoid creating API routes»). Для клиента сетевая работа и работа главного потока идентичны базовой статике.

---

Назови три trade-off'а статики с данными при сборке (getStaticProps-подход).
?
Три проблемы: (1) рост сайта (сотни страниц блога) → многократные вызовы на сборке → **long build times** («can result in long build times»); (2) можно упереться в **лимиты запросов внешних API**; (3) подходит только для **редко обновляемых** данных — иначе постоянные пересборки и деплои. Ответ на эти проблемы — ISR.
<!--SR:!2026-08-27,1,230-->

---

Ключевое различие статики и SSR — КОГДА или ГДЕ происходит рендеринг? Объясни.
?
**В моменте, а не в месте.** Оба рендерят на сервере. Статика — один раз при **сборке** (build time), один HTML на всех. SSR — на **каждый визит**, под конкретный запрос (персонализация). Из-за этого у статики TTFB ≈ мгновенный (файл готов), у SSR — серверная работа на каждый запрос.

---

Что случилось с getStaticProps/getServerSideProps в Next.js 16 и что заменило «данные при сборке»?
?
Они **удалены** в Next.js 16 (ушли вместе с Pages Router-эпохой; зафиксировано в замечаниях главы о расхождениях). Актуальная модель — Cache Components: `'use cache'` + `cacheLife` рендерит при сборке (аналог «данных при сборке»), а `<Suspense>`-границы отдают динамику при запросе (PPR). Принцип жив, синтаксис сменился.

---

Два вопроса-фильтра, по которым страница уходит на чистую статику (по holotypes-логике главы)?
?
Контент **одинаков для всех** и **терпит устаревание до следующего деплоя** (блог, документация, лендинг, портфолио). Два вопроса-фильтра: (1) есть ли cookies/гео/A-B на этапе показа? да → SSR; (2) меняются ли данные чаще, чем деплоишь? да → ISR. Оба «нет» → чистая статика.

---

Что сделать с skeleton-каркасом в вариации client-side fetch, чтобы не словить CLS?
?
Скелет должен **совпадать по размеру с финальным контентом** — иначе при подмене skeleton → данные контент «прыгнет» и поймаем **CLS**. Плюс помнить, что главный элемент (LCP) отрисуется только после получения данных с API — так что skeleton улучшает ощущение, но не делает контент быстрее.
