## Базовая концепция

Что такое React Server Components (RSC) одним предложением?
?
Компоненты React, которые выполняются **исключительно на серверной стороне** и **никогда не отправляют свой код в браузер** («never ship their code to the browser»). В браузер приходит готовый **результат**, который чередуется с обычными клиентскими компонентами.
#flashcards/frontend/rendering-strategies/rsc/foundations

Что является компонентом «по умолчаниюанию» в RSC-модели — серверный или клиентский? Как изменить?
?
**По умолчанию компонент серверный.** Чтобы сделать его клиентским, нужно явно добавить директиву `'use client'` в начале файла. Это инверсия прежнего мира, где все компоненты по умолчанию были клиентскими.
#flashcards/frontend/rendering-strategies/rsc/foundations

RSC — это замена SSR?
?
**Нет, это совершенно новый слой архитектуры, а не замена SSR.** SSR генерирует HTML для первоначальной отрисовки; RSC позволяет целым частям дерева «never become client JavaScript at all». В Next.js App Router они работают **вместе**: SSR даёт первый HTML, RSC-payload — обновления без перезагрузки.
#flashcards/frontend/rendering-strategies/rsc/foundations

Что отправляется клиенту от серверного компонента — код или результат?
?
Только **результат** (итоговый вывод), а не исходный код и не JS-bundle. Клиентское дерево способно отрендерить этот результат и чередовать его с обычными клиентскими компонентами.
#flashcards/frontend/rendering-strategies/rsc/foundations

## RSC vs SSR

Назови главное отличие RSC от SSR по формату вывода.
?
**SSR** — формат вывода HTML. **RSC** — формат вывода **сериализованное дерево (RSC payload)**, из которого **затем опционально** генерируется HTML. Это ключевая строка таблицы: у SSR вывод — HTML, у RSC — специализированный сериализованный формат описания дерева.
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

Что выполняется на сервере при SSR vs RSC?
?
**SSR:** при каждом запросе рендерится **всё дерево** целиком. **RSC:** только компоненты, помеченные как серверные (остальные остаются клиентскими и не исполняются на сервере).
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

Что отправляется клиенту при SSR vs RSC?
?
**SSR:** HTML + JS для **всего дерева**. **RSC:** HTML + JS **только для клиентских компонентов** (серверные не отгружают свой JS).
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

Затраты на гидратацию при SSR vs RSC?
?
**SSR:** всё дерево целиком гидрируется. **RSC:** гидрируются **только клиентские компоненты** (серверные не имеют JS → не из чего гидрировать).
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

Верно ли утверждение «страница с RSC не гидрируется»?
?
**Нет, формулировка неточная.** «Не гидрируется» применимо к **серверной части**, а не к странице целиком. Страница = микс; гидрируются **только клиентские куски**. Серверные куски не имеют JS — гидрировать нечего.
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

Что означает «первоначальная отрисовка» в определении SSR? Входят ли стримящиеся части?
?
«Первоначальная отрисовка» противопоставляется не «верхней части страницы», а **«обновлению дерева без перезагрузки»** (RSC-payload). Стримящиеся части в Streaming SSR — это **всё «первоначальная отрисовка»**, просто разбитая по времени доставки. Граница: **первый визит vs обновления на живой странице**.
#flashcards/frontend/rendering-strategies/rsc/rsc-vs-ssr

## Преимущества

Назови 3 преимущества RSC.
?
**1. Прямые запросы к БД** — без API-слоя (`await db.users.findUnique(...)`). **2. Безопасность секретов** — env, API keys, URL БД «never be bundled for the browser». **3. Оптимизация bundle** — тяжёлые библиотеки не добавляют ни байта в клиентский код, итог: **«20–40 % reduction in JS shipped to the client»**.
#flashcards/frontend/rendering-strategies/rsc/advantages

Какое числовое сокращение JS даёт RSC (по источнику)?
?
**20–40% reduction in JS shipped to the client** — сокращение JS, отправляемого клиенту, на 20–40%. Достигается за счёт того, что тяжёлые библиотеки (highlight.js, moment, Markdown-рендеры) в серверных компонентах не попадают в клиентский bundle.
#flashcards/frontend/rendering-strategies/rsc/advantages

Почему в серверном компоненте безопасно использовать `process.env.STRIPE_SECRET_KEY`?
?
Потому что код серверного компонента **«never be bundled for the browser»** — он не попадает в клиентский bundle. Переменная окружения остаётся на сервере. Если бы тот же код был в клиентском компоненте (`'use client'`), ключ утёк бы в браузер.
#flashcards/frontend/rendering-strategies/rsc/advantages

## Недостатки

Назови 2 недостатка RSC.
?
**1. Серверные вычисления стоят денег** — то, что раньше клиент делал бесплатно у себя, теперь крутится на ваших серверах → растут траты на «serverless or container minutes». **2. RSC-payload добавляет байты при навигации** — но в большинстве случаев объём сэкономленного JS значительно превышает размер добавленного payload (чистый баланс в плюс).
#flashcards/frontend/rendering-strategies/rsc/disadvantages

## Ограничения

Назови 3 категории вещей, запрещённых в серверном компоненте.
?
**1.** React-хуки жизненного цикла (`useState`, `useEffect`) — на сервере нет жизненного цикла. **2.** Обработчики событий (`onClick`, `onChange`) — сервер не обрабатывает клики пользователя. **3.** Браузерные API (`window`, `localStorage`, `IntersectionObserver`) — на сервере нет браузера.
#flashcards/frontend/rendering-strategies/rsc/limitations

Почему в серверном компоненте нельзя использовать `onClick`?
?
`onClick` — обработчик события, а серверный код не обрабатывает клики пользователя. Обработчики событий — клиентская ответственность. Для интерактивности нужен клиентский компонент (`'use client'`).
#flashcards/frontend/rendering-strategies/rsc/limitations

## Композиция (важнейший раздел)

Может ли серверный компонент рендерить клиентский? Как?
?
**Да, может.** Серверный компонент импортирует клиентский и передаёт ему данные через пропсы. Это **правило 1 композиции** и самый распространённый паттерн: серверный = данные + структура, клиентский = интерактивность внутри.
#flashcards/frontend/rendering-strategies/rsc/composition

Может ли клиентский компонент **прямо импортировать** серверный? Почему?
?
**Нет, не может.** Всё, что импортируется внутри клиентского дерева, также становится клиентским кодом — фреймворк «утянет» серверный код в клиентский bundle. Данные с сервера утекли бы в браузер.
#flashcards/frontend/rendering-strategies/rsc/composition

Какой есть законный способ показать серверный компонент внутри клиентского?
?
**Передать серверный компонент как `children`** (или любой другой пропс) клиентскому. Родительский серверный компонент создаёт оба, оборачивает серверный в клиентский через `children`. Тогда серверный компонент рендерится на сервере и передаётся как готовый элемент JSX, а не импортируется клиентским напрямую.
#flashcards/frontend/rendering-strategies/rsc/composition

Напиши паттерн «серверный как children внутри клиентского» (рабочий пример).
?
```tsx
// Layout.tsx — СЕРВЕРНЫЙ
import ClientWrapper from './ClientWrapper'
import ServerInside from './ServerInside'

export default function Layout() {
  return (
    <ClientWrapper>
      <ServerInside />     {/* ← передаётся как children */}
    </ClientWrapper>
  )
}
```
Серверный `Layout` рендерит `ServerInside` и передаёт его клиентскому `ClientWrapper` как `children`. `ServerInside` **не импортируется** клиентским компонентом — он приходит готовым элементом JSX.
#flashcards/frontend/rendering-strategies/rsc/composition

Какие данные можно передавать через границу сервер→клиент, а какие — нельзя?
?
**✅ Можно (сериализуемые):** числа, строки, массивы, объекты, **промиссы (Promise)**, элементы JSX.
**❌ Нельзя (не сериализуемые):** **функции**, **инстансы классов**.
#flashcards/frontend/rendering-strategies/rsc/composition

Что не так с этим кодом? `&lt;ClientCard handler={() =&gt; ...} user={new User()} /&gt;` (серверский компонент рендерит клиентский)
?
Оба пропса **не сериализуемые**: `handler` — функция, `user` — инстанс класса. Через границу сервер→клиент можно передавать только сериализуемые данные. Код упадёт при пересечении границы.
#flashcards/frontend/rendering-strategies/rsc/composition

## Data Fetching

Какая ключевая возможность data fetching в RSC?
?
Серверные компоненты — **асинхронные функции**, позволяют **`await` прямо в теле функции** («await directly in the function body»). Это устраняет необходимость в `useEffect` для загрузки первоначальных данных. Получение данных — **в том же процессе**, что и рендеринг (а не «клиент скачал JS → пошёл в сеть»).
#flashcards/frontend/rendering-strategies/rsc/data-fetching

Сравни загрузку первоначальных данных в CSR vs RSC.
?
**CSR:** `useEffect` → `fetch('/api/...')` → `setState`. Клиент скачал JS, потом пошёл в сеть за данными, потом установил стейт — «сложные танцы».
**RSC:** `async function Component() { const data = await db.query(...); return <.../> }`. `await` прямо в теле, данные из БД напрямую, без API-слоя, в том же процессе что и рендер.
#flashcards/frontend/rendering-strategies/rsc/data-fetching

## Streaming SSR + Suspense

Какую роль играет `loading.tsx` в Next.js App Router?
?
`loading.tsx` — это **«`<Suspense>` fallback для первоначального рендера `page.tsx`»**. Фреймворк автоматически оборачивает медленные или асинхронные участки дерева в Suspense, отправляет каркас страницы сразу, а данные для остальных частей — по мере готовности, формируя единый потоковый ответ («single streaming response»).
#flashcards/frontend/rendering-strategies/rsc/streaming

Как устроен потоковый ответ в Next.js App Router с RSC?
?
Каркас (`layout.tsx`) готов → отправляется **немедленно**. Медленные/асинхронные участки автоматически оборачиваются в `<Suspense>`. Фреймворк отправляет fallback'и сразу, а данные для остальных частей — **по мере готовности**. Формируется «single streaming response» — единый потоковый ответ, без перезагрузки страницы.
#flashcards/frontend/rendering-strategies/rsc/streaming

## Главный паттерн

Обязан ли серверный компонент быть обёрткой над клиентским?
?
**Нет, не обязан.** Это самый частый паттерн (серверный = данные + структура, клиентский = интерактивность внутри), но серверный компонент может существовать **и сам по себе**. Правильный вопрос: **«нужна ли этому компоненту интерактивность?»** Если нет — клиентский компонент не нужен вовсе.
#flashcards/frontend/rendering-strategies/rsc/main-pattern

Блог со статьями одинаковый для всех, в кодовых блоках нужна подсветка синтаксиса (highlight.js ~100 КБ). Как распределить код между серверным и клиентским компонентами, чтобы highlight.js не попал в клиентский bundle?
?
**Сделать Article полностью серверным компонентом — без клиентского вообще.** `import hljs from 'highlight.js'` в серверном, `await db.articles.findUnique(...)`, рендер готового HTML. `highlight.js` останется на сервере, данные из БД напрямую, HTML готов к отображению. Клиентский компонент **не нужен** — интерактивности нет.
#flashcards/frontend/rendering-strategies/rsc/main-pattern

Чем Server Island (Astro) отличается от RSC по формату вывода и масштабу?
?
**Формат:** Server Island отдаёт **HTML-фрагмент**; RSC отдаёт **RSC-payload** (сериализованное дерево, из которого опционально генерируется HTML).
**Масштаб:** Server Island — конкретный помеченный блок (`server:defer`); RSC — целая архитектура: серверные компоненты переплетены с клиентскими в **едином дереве**, передаются через `children`, работают с БД напрямую. Аналогия работает на уровне «приходит результат, а не код», но RSC — более широкая концепция.
#flashcards/frontend/rendering-strategies/rsc/main-pattern
