# 🎴 CSR (Client-Side Rendering) — Flashcards

Source: [[CSR-Client-Side-Rendering]]. Глава 1.1 курса, подглава 4. Якорь [Pat] patterns.dev.

## Базовая концепция

Что именно сервер отдаёт браузеру в модели CSR? Что находится внутри главного `<div>`?
?
**Практически пустой HTML-документ.** Внутри `<div id="root"></div>` **ничего нет** — нет контента, нет статей, нет карточек. Есть только тег-крючок и ссылка на JS-бандл. Весь интерфейс, данные и логика приезжают «в виде JavaScript-кода» ([Pat]). Если выключить JS — увидишь пустую страницу.
#flashcards/frontend/rendering-strategies/csr/foundations

Чем CSR является по отношению к SSR (одной фразой)?
?
**Зеркальным антиподом.** При SSR сервер отдаёт «готовую газету» (контент уже в HTML). При CSR сервер отдаёт «печатный станок и инструкцию» (пустой shell + JS) — браузер сам строит DOM, делает запросы, рисует UI.
#flashcards/frontend/rendering-strategies/csr/foundations

В чём разница между `ReactDOM.render` и `createRoot`, и зачем в CSR используется именно `createRoot`?
?
`ReactDOM.render` (React ≤17) — синхронный, устарел. `createRoot` (React 18+) включает **Concurrent Rendering**: React может приостанавливать рендер, переключаться между задачами, отбрасывать устаревший результат. Это фундамент для `Suspense`, `useTransition`, потокового рендера.
#flashcards/frontend/rendering-strategies/csr/foundations

Сформулируй главную фразу-маркер CSR из источника [Pat].
?
«Весь интерфейс, данные и логика передаются по сети **в виде JavaScript-кода**». Это отличает CSR от SSR/SSG, где контент уже лежит в HTML.
#flashcards/frontend/rendering-strategies/csr/foundations

## Когда использовать / избегать

Назови 4 сценария «когда стоит использовать CSR» (по [Pat]).
?
**1.** Страница скрыта за авторизацией (SEO не требуется). **2.** Долгая сессия — пользователь открыл один раз и проводит много времени (затраты на бандл окупаются). **3.** Высокая плотная интерактивность с сохранением состояния (редакторы, таблицы, Figma). **4.** Нужна автономная работа через service worker (PWA).
#flashcards/frontend/rendering-strategies/csr/when-to-use

Назови 4 сценария «когда следует избегать CSR» (по [Pat]).
?
**1.** Страница индексируется поисковиками или нужен предпросмотр по ссылке. **2.** Пользователь быстро уходит (новости, лендинги). **3.** Критически важны LCP и TTFB. **4.** Аудитория на слабых устройствах или медленном интернете.
#flashcards/frontend/rendering-strategies/csr/when-to-use

Почему за авторизацией CSR — нормальный выбор, а для публичной статьи — нет?
?
**За авторизацией:** Googlebot не залогинится, краулер страницу не увидит → SEO-аргумент против CSR отпадает. **Публичная статья:** нужна индексация + предпросмотр (og:image, og:title) → должен быть серверный HTML. CSR здесь проигрывает по SEO и LCP.
#flashcards/frontend/rendering-strategies/csr/when-to-use

Почему «долгая сессия» аргумент за CSR, а «быстрый отскок» — против?
?
**Долгая сессия:** дорогая первая загрузка бандла размазывается на часы использования → окупается. **Быстрый отскок:** пользователь зашёл на 30 секунд и ушёл — дорогая загрузка никак не окупится, плюс LCP критичен для конверсии.
#flashcards/frontend/rendering-strategies/csr/when-to-use

## Метрики

Сформулируй главный минус CSR одной фразой (из источника).
?
«Скорость отрисовки полностью зависит от того, как быстро клиентское устройство сможет загрузить и выполнить JS-бандл». Производительность **делегируется устройству пользователя** — ты теряешь контроль.
#flashcards/frontend/rendering-strategies/csr/metrics

Почему в CSR TTFB обычно хороший, а LCP — плохой?
?
**TTFB быстрый:** сервер отдаёт статический shell, ничего не рендерит — только сетевая задержка до CDN. **LCP плохой:** должен дождаться скачать → парсить → выполнить JS → первый рендер → (возможно) fetch данных → React перерисует. Всё это «позже», чем при SSR.
#flashcards/frontend/rendering-strategies/csr/metrics

Почему INP в CSR со временем становится **лучше**, а не хуже? (INP-парадокс)
?
При загрузке main thread занят парсингом JS → INP плох. **Но после загрузки** — наоборот: больше нет сетевых запросов при каждом взаимодействии, навигация мгновенная, состояние уже в памяти. Это «нативное ощущение», ради которого CSR и выбирают. CSR — единственный паттерн, где INP со временем **улучшается**.
#flashcards/frontend/rendering-strategies/csr/metrics

Почему CLS в CSR — высокий риск?
?
React «взрывается» из пустого `<div>` в заполненный интерфейс → вёрстка сдвигается. Без skeleton-плейсхолдеров элементы прыгают, метрика CLS портится.
#flashcards/frontend/rendering-strategies/csr/metrics

## Дополнительные проблемы

Что значит «краулеры выполняют JS с ограниченным бюджетом»? Как это влияет на SEO?
?
Googlebot умеет выполнять JS (через Web Rendering Service), но на сайт выделяется ограниченное число запросов и процессорного времени. Если CSR-страница требует 2 МБ JS + 3 fetch-запроса — бот может не дождаться и положить в индекс **частичный** контент или пустой shell. Не «не индексируется», а «индексируется хуже и медленнее».
#flashcards/frontend/rendering-strategies/csr/problems

Какое ключевое число иллюстрирует «диспаритет устройств» в CSR?
?
**Парсинг 1 МБ JS на бюджетном смартфоне — больше секунды** (на десктопе — миллисекунды). Разработчик на MacBook Pro видит «всё быстро», пользователь на Moto G4 — «висит 4 секунды». Классическая ловушка перформанса CSR.
#flashcards/frontend/rendering-strategies/csr/problems

Что такое «водопад запросов» (waterfall) в CSR и почему он медленный?
?
Шаблон `useEffect → fetch → setState` создаёт последовательные запросы: второй стартует только после первого, третий — после второго. **Общее время = сумма, а не максимум.** Каждый `useEffect + fetch + setState` — новый «тур» в водопаде.
#flashcards/frontend/rendering-strategies/csr/problems

Почему skeleton UI лучше спиннера для CLS?
?
Skeleton резервирует место под контент → CLS не растёт. Спиннер = пустое место, которое потом «взрывается» контентом и двигает вёрстку. По времени может быть одинаково, но CLS у skeleton лучше.
#flashcards/frontend/rendering-strategies/csr/problems

## Как выжать максимум

Какой бюджет критичного JS рекомендует [Pat] (число)? Откуда оно?
?
**~170 КБ в сжатом (gzip) виде.** Число из HTTP Archive / Addy Osmani — порог, при котором средний мобильный девайс ещё укладывается в разумное TTI. Дальше начинаются проблемы. Инструменты: `webpack-bundle-analyzer`, `source-map-explorer`, `bundlephobia`.
#flashcards/frontend/rendering-strategies/csr/optimization

Как `React.lazy` + динамические импорты помогают CSR? Приведи минимальный пример.
?
**Code splitting по маршрутам:** чанк маршрута грузится только когда на него перешли. Пользователь на `/dashboard` не скачивает код админки.
```jsx
const AdminPanel = lazy(() => import('./routes/AdminPanel'));
```
Каждый `lazy(() => import(...))` создаёт отдельный чанк.
#flashcards/frontend/rendering-strategies/csr/optimization

Зачем `<link rel="modulepreload">`?
?
Это «hint» браузеру: **начни скачивать и парсить** чанк заранее, даже если ещё не выполнил. Полезно, когда знаешь, что пользователь сейчас перейдёт (например, навёл на ссылку) — чанк подгружается до клика.
#flashcards/frontend/rendering-strategies/csr/optimization

Зачем `IntersectionObserver` в CSR?
?
Для **отложенной загрузки** некритичного UI (чат, виджеты, рекомендации): компонент грузится только когда приближается к видимой области. Экономит бандл при первом рендере.
#flashcards/frontend/rendering-strategies/csr/optimization

В чём разница между app shell и streaming shell?
?
**App shell** — стабильная SPA/PWA-оболочка (хедер/футер/навигация), грузится один раз, живёт всю сессию, кэшируется service worker. **Streaming shell** — часть SSR-страницы **вне** Suspense-границ, отправляется первым при стриминге. Это разные концепции из разных паттернов.
#flashcards/frontend/rendering-strategies/csr/optimization

Почему TanStack Query / SWR / Apollo «обязательны» для серьёзного CSR?
?
Решают 5 проблем сразу: **дедупликация** (10 компонентов → 1 запрос), **кэширование**, **ретраи**, **фоновое обновление**, **race-condition handling**. Без них наивный `useEffect + fetch` снова и снова рождает водопады и баги.
#flashcards/frontend/rendering-strategies/csr/optimization

## Outgrowing CSR

Что рекомендует [Pat], когда прототип на CSR начинает обслуживать реальных пользователей? (3 шага)
?
**1.** Переход на фреймворк (Next.js / Remix / TanStack Start) → SSR/SSG «из коробки» + привычная SPA-навигация. **2.** Публичные маршруты → React Server Components (контент без клиентского JS), интерактивные экраны остаются на клиенте. **3.** Streaming SSR — показывать значимый контент до загрузки всех данных.
#flashcards/frontend/rendering-strategies/csr/outgrowing

Как распределить стратегии между блогом продукта (нужен SEO) и авторизованным дашбордом (плотная интерактивность)?
?
**Блог** → SSG / RSC / Streaming SSR (SEO важен, LCP критичен, JS почти не нужен). **Дашборд** → CSR / Islands (за авторизацией, плотная интерактивность, состояние в памяти). Это **гибрид**: нельзя «всё на одном паттерне» — у зон разные требования. Архитектурный паттерн «Outgrowing CSR».
#flashcards/frontend/rendering-strategies/csr/outgrowing
