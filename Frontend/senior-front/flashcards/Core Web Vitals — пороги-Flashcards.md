# Core Web Vitals — пороги-Flashcards

---

Назови три метрики Core Web Vitals и их пороги «good» (полевые данные, 75-й перцентиль за 28 дней).
?
**LCP ≤ 2.5 s** (Largest Contentful Paint — главный контент виден), **INP ≤ 200 ms** (Interaction to Next Paint — отклик на действие), **CLS ≤ 0.1** (Cumulative Layout Shift — сдвиг контента). Мнемоника: «2.5 / 200 / 0.1» — секунды / миллисекунды / безразмерно; разные единицы помогают запомнить, что метрики разные по природе.

---

Что заменил INP и когда? Почему замена строже?
?
INP заменил **FID (First Input Delay)** в **марте 2024**. FID мерял задержку только **первого** взаимодействия; INP меряет **все** взаимодействия за сессию и берёт худшее (или близкое к нему). INP строже, потому что FID не ловил медленные интеракции после первой — например, тормоза после загрузки длинного списка или дорогой гидратации.

---

Какое пороговое значение TTFB «good» и почему TTFB не входит в тройку Core Web Vitals, хотя важен?
?
TTFB «good» — **≤ 800 ms** (🟡 ≤ 1800 ms, 🔴 > 1800 ms). TTFB не CWV, потому что это **корневая** метрика, а не UX-метрика: LCP не может быть быстрее TTFB (первый байт приходит раньше любого контента). То есть TTFB — причина, LCP — следствие, измеримое пользователем. Им нельзя управлять как самостоятельной UX-целью, но его нужно держать низким, чтобы LCP вообще уложился.

---

Как выбор рендеринг-стратегии (глава 1.1) влияет на каждую из трёх CWV? Соедини стратегию → метрику → механизм.
?
- **SSG / PPR → LCP и TTFB**: HTML в первом ответе, контент виден без ожидания JS; статический shell отдаётся с CDN мгновенно.
- **Selective Hydration / RSC / Islands → INP**: меньше JS гидратируется → главный поток свободнее → отклик на действие быстрее; RSC убирает гидратацию серверных частей совсем.
- **Skeleton UI + резервирование места под Server Islands → CLS**: динамические блоки не «сдвигают» контент, потому что место зарезервировано fallback'ом.
То есть выбор главы 1.1 — это фундамент всех трёх CWV, а не только LCP.
