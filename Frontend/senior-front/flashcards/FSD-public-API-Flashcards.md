## Контракт слайса

Что такое public API слайса и три цели хорошего API?
?
**Контракт + ворота** между слайсом и потребителями (index-файл с реэкспортами). Цели: (1) защита приложения от структурных изменений слайса; (2) значимые изменения поведения отражаются изменениями API; (3) экспорт только необходимого. Аналогия: публичный API npm-пакета.

## Wildcard-реэкспорты

Почему `export * from "./ui/Comment"` — антипаттерн?
?
(1) Рушит **discoverability** — интерфейс слайса не виден, для интеграции лезешь в код. (2) **Случайный экспорт внутренностей** — на них полагаются, рефакторинг блокируется. Бьёт по целям №3 и №1.

## @x-нотация: порядок решения (карточка на зафиксированный пробел)

Корзине нужен минимум данных товара. Полный порядок действий по источнику?
?
1. **Сначала рассмотреть слияние сущностей** (кросс-импорты в entities часто = слишком мелкая нарезка).
2. Не подходит — заводим `@x`: `entities/product/@x/cart.ts` — отдельный публичный API **только для** `entities/cart`.
3. Импорт абсолютным путём (другой слайс): `import type { Product } from "entities/product/@x/cart"`.
Рамки: минимум кросс-импортов; @x — **только на слое Entities**. Читается «product crossed with cart».
⚠️ Внутри @x-файла — **простой реэкспорт типа из model** (карточка на рецидив экзамена 2026-09-06: «наследник с усечёнными полями» — дизайн сверх канона; допустим как личное решение, но на экзамене/собесе называют канон источника). Владелец решает, что показать соседу, — витрина, не ключи от квартиры.

## Два принципа анти-циклов (карточка на зафиксированный пробел)

Как не создавать циклические импорты через index-файлы?
?
- Файлы **в одном слайсе** — всегда **относительные** импорты с полным путём (`./api/loadUserStatistics`).
- Файлы **в разных слайсах** — всегда **абсолютные** через alias (`@/features/auth`).
Классический цикл: `index.js → ui/HomePage.jsx → index.js` (HomePage импортирует из собственного index).

## Поштучные index в shared/ui

Почему в `shared/ui` index-файл на каждый компонент, а не один общий?
?
`shared/ui` — коллекция **несвязанных** вещей: общий barrel ломает tree-shaking — тяжёлая зависимость одного компонента (подсветчик кода, drag'n'drop) тянулась бы в каждый бандл из-за кнопки. Плюс много barrel files замедляет dev-сервер. Решение: `@/shared/ui/button`, `@/shared/ui/text-field`. Классика 🟡: moment со всеми локалями.

## Сегменты без index

Почему есть `features/comments/index.ts`, но не нужен `features/comments/ui/index.ts`?
?
Сегмент — деталь реализации, скрытая контрактом слайса; одного index на слайс достаточно. Лишние index в сегментах — лишние barrel files: циклы, tree-shaking, медленный dev-сервер.

## Steiger

Зачем FSD-проекту линтер Steiger?
?
Index-файл **не запрещает** импорт мимо публичного API (особенно авто-импорты IDE выбирают прямой путь). Steiger — архитектурный линтер с правилами FSD: ловит обходы public API и нарушения правила импортов автоматически.

## Правило public API на слайсах (§4.2)

Сформулируй само правило §4.2. Что оно регулирует по сравнению с правилом импортов §3.1?
?
**Каждый слайс (и сегмент на слоях без слайсов — Shared, App) обязан иметь определение public API. Модули вне слайса могут ссылаться только на него — не на внутреннюю файловую структуру.** §3.1 регулирует вертикаль («откуда по слоям»), §4.2 — как именно можно зайти в чужой слайс. Граница рефакторинга останавливается на index.ts.

## Где сколько index-файлов (§8.1, шаг 4)

Свод: сколько public API у слоёв со слайсами, у Shared и у сегментов?
?
- Слои со слайсами (entities, features, pages): **один index на слайс** — снаружи не видно, какие у слайса сегменты.
- Shared: **отдельный public API на каждый сегмент** (`shared/api`, `shared/config`) — импорты из Shared естественно организованы по назначению.
- Внутри `shared/ui` и `shared/lib`: **поштучно на каждый компонент/библиотеку** (tree-shaking, тяжёлые зависимости).
- Сегменты слоёв со слайсами (`features/comments/ui/`): **index не заводят** — лишние barrel files.

## Оформление контракта: именованные реэкспорты ролей

Как выглядит содержимое хорошего index.ts слайса? Три правила оформления.
?
```ts
// entities/product/index.ts
export { default as ProductCard } from './ui/ProductCard.astro';
export type { Product } from './model/product';
export { getProducts } from './api/getProducts';
```
(1) Только **именованные** реэкспорты — никаких `export *` (§6.1). (2) Контракт показывает **роли, а не файлы**: снаружи не видно сегментов ui/model/api. (3) Типы — через `export type`, чтобы вычищались на компиляции. Astro-компонент — дефолтный экспорт, поэтому `export { default as X } from './ui/X.astro'`.
