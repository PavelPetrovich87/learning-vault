# FSD — кросс-импорты — Flashcards

Тема: кросс-импорты как code smell, четыре причины, стратегии A–D, тревожные сигналы, строгость.
Источник: глава 1.2 курса «Фронтенд senior+ в агентную эру», подглава 7. Якорь [FSD] — feature-sliced.design, Guides → Issues → Cross-imports.

#flashcards/frontend/code-organization/fsd-cross-imports

## Определение

Что такое кросс-импорт? Что НЕ является кросс-импортом?
?
Импорт **между слайсами одного слоя** (`features/cart → features/product`, `widgets/sidebar → widgets/header`). Импорты *внутри* `shared` и `app` — **не** кросс-импорты: там нет слайсов. Это code smell — предупреждающий знак сцепления; иногда неизбежен, но должен быть осознанным и документированным.

## Четыре причины code smell

Почему кросс-импорт — code smell? Четыре причины.
?
1. **Неясное владение/ответственность** — кто владеет общей логикой; `product` меняет внутренности → ломает `cart`.
2. **Падение изоляции и тестируемости** — тест `cart` требует поднимать `product`.
3. **Рост когнитивной нагрузки** — правка требует контекста через границу.
4. **Путь к циклам** — однонаправленные зависимости → двунаправленные (A↔B), рефакторинг дорожает.

## Порядок для entities

Кросс-импорт между сущностями: порядок действий?
?
(1) **Сначала слияние** — кросс-импорты в entities часто следствие слишком гранулярной нарезки. (2) Не подошло — `@x`-нотация: отдельный public API «A для B»; последнее средство, «необходимый компромисс», **только на слое Entities**.

## Стратегия A — slice merge

Когда применяется стратегия A (слияние)? Пример.
?
Когда слайсы **не по-настоящему независимы и всегда меняются вместе** — на практике один слайс. Пример источника: `features/profile` + `features/profileSettings` → `features/profile`. Курсовой кейс: checkout + promo-code (промокод только внутри чекаута) → merge.

## Стратегия B — домен в entities

Суть стратегии B и её принципы?
?
Общий **доменный поток** нескольких фич опускается в `entities` (валидация сессии у auth и profile → `entities/session`). Принципы: в entities — только доменные типы и логика; UI остаётся в features; фичи импортируют из entities — вниз, легально.

## Стратегия C — композиция сверху (IoC)

Как стратегия C устраняет кросс-импорт? Приёмы и канонический пример.
?
**Compose из верхнего слоя** (`pages`/`app`): слайсы не знают друг о друге, страницу связывает — паттерны **IoC**: render props (React), слоты (Vue), DI через пропсы/контекст. Канон: `CommentList` принимает `renderUserAvatar?: (userId) => ReactNode`, страница вставляет `<UserAvatar>` — dependency инвертирована. 🟡 Airbnb: кнопка «в избранное» вставляется пропсом в карточку listing'а на уровне страницы.

## Стратегия D — только public API

Чем стратегия D отличается от A–C? Границы применения?
?
A–C **устраняют** кросс-импорт; D его **принимает**, когда переиспользование неизбежно: только через явный публичный API (экспортированные хуки/UI-компоненты), никогда `store`/`model`/internal (`features/auth` экспортирует `useAuth`, `AuthButton`; `features/profile` импортирует только их). Минимизация рисков строгими границами. Рецидив упр.2 (2026-09-21): D названа «оверкилл» — перепутан полюс: D — единственная *принимающая* стратегия и **минимальное зло** (даже дешевле C по трудозатратам), просто оставляет сцепление.

## Тревожные сигналы

Назови тревожные сигналы, что кросс-импорт стал проблемой (минимум 3 из 5).
?
(1) зависимость от store/model/бизнес-логики чужого слайса; (2) глубокие импорты во внутренние файлы; (3) **двунаправленные** зависимости A↔B; (4) изменения одного слайса регулярно ломают другой; (5) потоки, которые должны собираться в `pages`/`app`, впихнуты в кросс-импорты.

## Обязанности при вводе кросс-импорта (карточка на зафиксированный пробел)

Команда всё-таки вводит кросс-импорт. Какие три обязанности накладывает источник? От чего зависит строгость правил?
?
(1) Считать **осознанным архитектурным решением**; (2) **документировать обоснование**; (3) **периодически пересматривать**. Строгость — решение команды: ранний продукт с экспериментами → прагматичный размен; долгоживущие/регулируемые системы (fintech) → строгие границы окупаются.
