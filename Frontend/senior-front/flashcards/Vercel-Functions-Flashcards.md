## Основы: функция / экземпляр / инвокация

Что такое «инвокация» (invocation) в модели Vercel Functions?
?
Один запуск функции от получения HTTP-запроса до отдачи HTTP-ответа. Это цельная единица работы: запрос → функция запустилась → дела (парсинг, БД, рендеринг) → ответ → инвокация закончилась.

Является ли рендеринг React-дерева отдельной инвокацией?
?
Нет. Рендеринг — **шаг внутри** инвокации. Одна инвокация может внутри себя: распарсить cookies, сделать запрос к БД, отрендерить дерево в HTML + RSC Payload, вернуть ответ.

Является ли запрос к БД отдельной инвокацией?
?
Нет. `await db.query(...)` — это шаг внутри инвокации. В этот момент инвокация «ждёт» (idle), и в это idle-время fluid compute подсаживает работу от других инвокаций в тот же экземпляр.

N входящих запросов → сколько функций/экземпляров/инвокаций?
?
N запросов → **N инвокаций** (концептуально: одна на запрос), но **M экземпляров (M ≤ N)** — потому что Vercel переиспользует тёплые экземпляры для нескольких последовательных инвокаций.

## Тёплый vs холодный экземпляр

Что такое «тёплый» (warm) экземпляр функции?
?
Экземпляр функции, который Vercel переиспользует между инвокациями. В нём сохраняется module-level состояние (например, `let cache = {}` на уровне модуля) и инициализированные соединения.

Что такое cold start?
?
Когда Vercel поднимает новый экземпляр функции (после простоя или при росте трафика). Модуль переинициализируется: кэш на уровне модуля пуст, соединения к БД устанавливаются заново. Занимает сотни миллисекунд.

Можно ли положиться на in-memory кэш (`let cache = {}` на уровне модуля) в serverless?
?
**Нет.** Кэш разделяется только если запрос попадает на тёплый экземпляр. При cold start кэш пересоздаётся пустым. Правильный кэш — внешний (Redis, Vercel KV) или фреймворковый (`'use cache'` в Next.js 16, который кладёт значения в постоянное хранилище).

## Fluid compute

Что такое fluid compute и зачем он нужен?
?
Механика Vercel: несколько инвокаций исполняются **параллельно в одном экземпляре** функции, используя idle-время (когда инвокация ждёт ответа БД/внешнего API). Результат — меньше экземпляров нужно держать тёплыми → меньше cold starts, ниже задержка, дешевле.

Почему именно fluid compute снижает cold starts?
?
Серверный код почти всё время ждёт (БД, внешние API). Без fluid compute один экземпляр = один запрос за раз, и в idle-паузы он простаивает. С fluid compute в эти паузы запускается чужая работа → меньше экземпляров нужно → меньше cold starts.

## Data locality — главное правило

Сформулируй главное правило data locality одним предложением.
?
Функция должна физически исполняться в том же регионе, что и источник данных (БД), иначе межконтинентальный лаг между функцией и БД съест любой выигрыш от стратегии рендеринга.

В каком регионе по умолчанию исполняются Node-функции на Vercel? Почему именно там?
?
`iad1` (Вашингтон, округ Колумбия, США). Потому что большинство управляемых БД (Supabase, PlanetScale, Neon) по умолчанию живут в `aws-east-1` AWS — физически тот же регион.

БД во Франкфурте (`fra1`), функции Vercel в `iad1`, пользователь в Берлине жалуется на медленный SSR. Что делать?
?
Перенести **функции** в `fra1` (через настройки проекта Vercel). Не БД — её тяжело двигать, и она обычно уже стоит в оптимальном регионе провайдера. Двигать надо функцию к БД.

Почему именно так: «двигать функцию к БД», а не наоборот?
?
БД обычно «привязана» к своему региону (так устроены управляемые Postgres/MySQL), и переезд БД = миграция данных. Функция — это код, регион меняется настройкой в Vercel. Перенос функции = минуты, перенос БД = дни/недели.

Какой порядок межконтинентального лага функция↔БД (например, Токио↔Сан-Франциско)?
?
~150–200 мс RTT (Round Trip Time). Этого достаточно, чтобы полностью убить выигрыш от SSR/PPR — даже самая умная стратегия рендеринга не поможет, если каждый запрос ждёт 150–200 мс только на сети до БД.

## Сводная таблица: где что исполняется

Где исполняется **SSG (Static Site Generation)**?
?
При сборке (build) → статическое хранилище → CDN / Edge-кэш. Один раз при сборке. ISR (Incremental Static Regeneration) — фоновая регенерация по таймеру/вебхуку без полного ребилда.

Где исполняется **CSR (Client-Side Rendering)**?
?
В браузере клиента. Сервер отдаёт только shell + JS-бандл. Каждый визит = браузер делает всю работу.

Где исполняется **SSR (Node)**? Когда?
?
Serverless-функция на Node-рантайме, один регион. Каждый запрос. Node даёт полный доступ к npm и fs, но стоят cold starts.

Где исполняется **SSR (Edge)**? Какие ограничения?
?
Edge-функция (Web-рантайм, близко к пользователю). Каждый запрос. TTFB (Time to First Byte) ~30–80 мс. Лимиты CPU/памяти. Ограниченный набор API (нет fs, не все npm-пакеты).

Где исполняется **RSC (React Server Components)**?
?
На сервере (Node или Edge). Результат → HTML (для первого визита) + RSC Payload (для последующих навигаций). Код серверных компонентов не отправляется клиенту.

Где исполняется **PPR (Partial Prerendering, Cache Components)**?
?
Гибрид: статический shell считается при сборке, динамические чанки в `<Suspense>` стримятся при запросе.

Где исполняется **Islands**?
?
Сервер (статический HTML, как SSG) + отдельные JS-острова гидрируются точечно на клиенте. Astro, Marko, Fresh.

## 🔴 Edge vs Node: соединения к БД (СИНТЕЗ)

> Эти карточки — инженерный синтез. В якорях [DEP] Vercel Functions этого материала нет.

🔴 В чём принципиальная разница между Node и Edge по работе с БД?
?
**Node**: можно держать долгоживущий **пул соединений** (connection pool) к БД — TCP-коннект устанавливается редко, переиспользуется между инвокациями. **Edge**: нет пулов, каждое обращение к БД = новый коннект (TCP handshake + TLS + auth), что может добавить сотни мс на каждый запрос.

🔴 Что такое «пул соединений» (connection pool) к БД и почему он эффективен?
?
Набор заранее установленных TCP/TLS-коннектов к БД, разделённых между инвокациями. Когда инвокация делает `await db.query(...)`, она берёт свободный коннект из пула (микросекунды), делает запрос, возвращает коннект. Дорогое TCP/TLS-рукопожатие (30–100 мс) происходит только при инициализации пула и его расширении — не на каждый запрос.

🔴 Почему классический драйвер `pg` (Postgres) или `mysql2` плохо работает на Edge?
?
Edge-функции — это Web-стандарт в изоляции V8, они не поддерживают долгоживущие TCP-пулы. Каждый запрос к БД через классический драйвер = полное рукопожатие TCP (1 RTT) + TLS (1–2 RTT) + auth (1 RTT) + сам запрос + закрытие. Если БД в другом регионе — это десятки мс × несколько RTT = сотни мс на каждый запрос.

🔴 Какой правильный способ ходить в БД с Edge-функции?
?
Использовать **HTTP-based драйверы**: каждый запрос = один HTTP-fetch к БД, без установки долгого TCP-соединения. Примеры: `@neondatabase/serverless` (Neon Postgres, ходит по HTTP/WebSocket), драйвер PlanetScale на основе `fetch()`. Жертвуешь эффективностью одного соединения, но избегаешь рукопожатий — на Edge это часто быстрее классического пула.

🔴 Как выбор Node vs Edge (по БД-коннектам) влияет на PPR (Partial Prerendering)?
?
- **Статический shell** PPR строится при сборке → не зависит от выбора рантайма.
- **Динамические чанки в `<Suspense>`** стримятся при запросе → вот тут работает ограничение: если чанк ходит в БД через пул → это Node; если хочешь Edge (близость к пользователю) → нужен HTTP-драйвер БД (Neon, PlanetScale).

🔴 Дай решающее правило: когда Node, когда Edge (по БД-коннектам)?
?
- **Edge**: лёгкая работа (auth-чек, чтение cookie), близость к пользователю критична, драйвер БД — HTTP-based.
- **Node**: тяжёлые npm-библиотеки (Markdown, syntax highlight), пул соединений к БД, полный доступ к fs/npm.

## 🟢 Где хранится кэш `'use cache'` (по Next.js 16.3.0)

> Источник: [Next.js 16 — Caching, «Where cached content is stored»](https://nextjs.org/docs/app/getting-started#caching). Это первичный якорь [NEXT], не синтез.

Где по умолчанию хранится кэш от `'use cache'` (без модификаторов)?
?
**In-memory per-instance.** Это **ephemeral на serverless**: каждый экземпляр функции (warm/cold) держит свой кэш, и при cold start / scale-to-zero кэш теряется. Цитата: «By default the result stays in a per-instance, in-memory store that is ephemeral on serverless.»

Зависит ли дефолтное поведение `'use cache'` от рантайма (Node vs Edge)?
?
**Нет.** И на Node, и на Edge дефолт — in-memory per-instance ephemeral. Дихотомия «Node = диск, Edge = внешний сервис» — **неправильная**. Это была фактическая ошибка в первоначальном разборе.

Какая директива делает кэш `'use cache'` durable (сохраняется между инстансами)?
?
**`'use cache: remote'`** — перемещает кэш в durable cache handler, shared между инстансами. Это network roundtrip, окупается только при высоком hit rate. Цитата: «`use cache: remote` moves it to a durable cache handler shared across instances.»

Где хранится кэш от `'use cache: private'`?
?
**В браузере пользователя.** Payload включается в RSC для клиентской навигации/prefetch, и браузер держит его свежим на протяжении `stale`-окна. Session-specific. Цитата: «`use cache: private` results live only here.»

Сколько уровней хранения кэша от `'use cache'` в Next.js 16? Перечисли.
?
**Четыре:**
1. **Prerendered HTML** (static shell) — durable storage платформы за CDN.
2. **`'use cache'` (дефолт)** — in-memory per-instance, ephemeral.
3. **`'use cache: remote'`** — внешний cacheHandler (Vercel KV, Redis).
4. **`'use cache: private'`** — браузер пользователя.

Что такое `cacheHandlers` (множественное число) в Next.js 16?
?
Конфиг в `next.config.ts` для подключения **кастомных хранилищ кэша** под `'use cache'` и `'use cache: remote'`. Например, Redis/Valkey-handler. Заменяет старый единственный `cacheHandler` (singular), который был для ISR-инкрементального кэша.

Может ли `'use cache'` (дефолт) пере-вычисляться на каждом запросе на serverless?
?
**Да.** Цитата из Next.js 16: «At runtime it's cached in-memory by default, which doesn't persist across serverless requests, so it may re-evaluate on each request.» Если инстансы часто умирают (холодный трафик), `'use cache'` не даёт настоящей долговременной пользы — нужен `'use cache: remote'`.

Что нужно сделать, чтобы `'use cache'` давал настоящую долговременную кэш-пользу на serverless?
?
1. Использовать `'use cache: remote'` вместо `'use cache'`.
2. Настроить `cacheHandlers` в `next.config.ts` (Redis, Vercel KV и т.д.).
3. Учитывать, что это network roundtrip — окупается только при высоком hit rate.

## Чек-лист: выбор региона и рантайма

Что проверить при выборе региона деплоя на Vercel?
?
1. Где физически стоит БД (регион у провайдера БД).
2. В каком регионе Vercel-функции по умолчанию (`iad1` — двигать, если БД не в США).
3. Перенести функции в регион БД.
4. Для Edge: HTTP-драйвер БД, не классический пул.
5. In-memory кэш не используется (только внешний или `'use cache'`).
6. Для дашборда/чекаута: рассмотрен PPR, а не чистый SSR/CSR.
