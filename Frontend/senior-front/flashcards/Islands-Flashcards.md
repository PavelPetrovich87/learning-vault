# 🎴 Islands Architecture — Flashcards

Source: [[Islands-Architecture]]. Глава 1.1 курса, подглава 5. Якорь [Pat] patterns.dev.

## Базовая концепция

Сформулируй главную идею Islands Architecture (одной фразой).
?
**«Что, если платить только за интерактивные части?»** Статический контент — чистый HTML (0 байт JS), интерактивные зоны — отдельные острова со своим JS, гидрируются независимо.
#flashcards/frontend/rendering-strategies/islands/foundations

Чем Islands фундаментально отличается от SPA по структуре дерева? Сколько деревьев у Islands-страницы?
?
У SPA — **одно** дерево (всё связано). У Islands — **много** (по одному на каждый остров). Статья на 4 острова = 4 независимых корня, ни один не знает о других. Ошибка в одном острове не ломает другие.
#flashcards/frontend/rendering-strategies/islands/foundations

Назови 3 ключевых свойства Islands.
?
**1.** Каждый остров — собственный корень (нет общего дерева, виртуального DOM, хранилища). **2.** Гидратация параллельна и независима (по расписанию: `load`/`idle`/`visible`). **3.** Статический контент — источник истины = чистый HTML, 0 байт JS.
#flashcards/frontend/rendering-strategies/islands/foundations

## Частичная гидратация

В чём разница между прогрессивной гидратацией (Selective Hydration) и частичной гидратацией (Islands)?
?
**Прогрессивная (Selective Hydration):** страница — **единое дерево**, просто определяется порядок активации ветвей. **Частичная (Islands):** единого дерева **нет вообще**, клиентское дерево компонента никогда не собирается целиком. Это не «порядок одного дерева», а «несколько независимых деревьев».
#flashcards/frontend/rendering-strategies/islands/partial-hydration

Назови 3 Astro-директивы гидратации и когда использовать каждую.
?
**`client:load`** — сразу при загрузке (компонент над первым экраном, кликабелен сразу: кнопка лайка, меню). **`client:idle`** — когда main thread свободен (важен, но не срочен: видеоплеер). **`client:visible`** — при прокрутке в зону видимости (компонент ниже первого экрана: комментарии).
#flashcards/frontend/rendering-strategies/islands/partial-hydration

Что происходит, если у компонента в Astro НЕТ директивы гидратации?
?
Он рендерится на сервере, отдаётся как статический HTML и добавляет **ровно ноль байт JavaScript** на страницу. Это реализация принципа «платить только за интерактивные части».
#flashcards/frontend/rendering-strategies/islands/partial-hydration

Как Fresh (Deno) помечает острова, в отличие от Astro?
?
**Расположением файла.** Astro использует директиву в JSX (`client:load`). Fresh: любой компонент в `routes/` — только сервер, а интерактивны только те, что в папке `islands/`.
#flashcards/frontend/rendering-strategies/islands/partial-hydration

## Server Islands

Какую проблему решают Server Islands (появились в Astro в конце 2024)?
?
**Персональные данные ломают edge-кэш.** Если в классическом острове есть персональные данные (аватар, корзина), они попадают в основной рендер страницы → весь HTML становится персональным → нельзя кэшировать на edge. Server Islands выносят рендер персонального фрагмента в отдельный запрос → основной HTML остаётся кэшируемым.
#flashcards/frontend/rendering-strategies/islands/server-islands

Чем Server Island отличается от классического острова по двум осям оптимизации?
?
**Классический остров разделяет JavaScript** (какой JS грузить): меньше бандл. **Server Island разделяет рендер** (какую часть рендерить при запросе, а какую — закэшировать на edge): персональные данные не ломают кэш страницы.
#flashcards/frontend/rendering-strategies/islands/server-islands

Что приезжает на клиент в Server Island: HTML, JS или и то, и другое?
?
Только **HTML-фрагмент** с персональными данными. **Никакого JS-бандла.** Фрагмент приезжает из отдельного запроса и подменяет плейсхолдер. Если нужна интерактивность — внутри серверного острова вкладывается классический (с `client:load`).
#flashcards/frontend/rendering-strategies/islands/server-islands

Делает ли Server Island компонент кликабельным? Если нет — зачем он нужен?
?
**Нет.** Server Island решает смысл «показать правильные персональные данные» (аватар, корзина как HTML), а не «реагировать на клики». Для кликов нужен классический остров (JS + гидратация). Аватар без кликов → Server Island (0 JS). Карусель → классический остров.
#flashcards/frontend/rendering-strategies/islands/server-islands

Как комбинировать персональные данные + интерактивность (корзина с кликами)?
?
**Вложить классический остров внутрь серверного.** `server:defer` и `client:load` не смешиваются на одном компоненте. Серверный остров (`server:defer`) рендерит персональный HTML, а внутри него стоит `<CartInteractive client:load initialCart={cart} />` — он гидрируется и даёт клики.
#flashcards/frontend/rendering-strategies/islands/server-islands

Откуда берётся бандл для классического острова внутри Server Island?
?
В серверном фрагменте, кроме контента, лежит **МЕТКА** (например, `data-component="/assets/CartInteractive-a1b2.js"`). Astro-runtime (маленький JS на странице с самого начала) видит метку и **по ней** скачивает бандл — ровно как браузер качает `<script src="...">` по ссылке в HTML.
#flashcards/frontend/rendering-strategies/islands/server-islands

## Сравнение с RSC и Qwik

Чем Islands отличается от RSC (React Server Components)?
?
**Структура дерева:** Islands — много независимых деревьев; RSC — **единое** дерево React. RSC: серверные компоненты не отправляют клиентский JS и читают данные из БД, но модель требует «один большой React runtime». Islands: каждый остров — отдельный корень, нет общего runtime.
#flashcards/frontend/rendering-strategies/islands/comparison

Что такое Qwik и что у него вместо гидратации?
?
**Qwik (Resumability / возобновляемость).** Вообще отвергает гидратацию. Слушатели встроены прямо в HTML, один глобальный слушатель подгружает код по требованию при взаимодействии. Страница «resumable» — состояние сериализовано в HTML, повторное выполнение компонента не нужно. «Каждое событие — свой остров», но без явных границ.
#flashcards/frontend/rendering-strategies/islands/comparison

Что общего у Islands, RSC и Qwik, и в чём различие?
?
**Общее:** все три отправляют меньше JavaScript на клиент (реакция на «слишком много JS» в CSR/SSR). **Различие по дереву:** Islands — много деревьев; RSC — единое дерево; Qwik — единое (но resumable, без гидратации).
#flashcards/frontend/rendering-strategies/islands/comparison

## Преимущества и недостатки

Назови 4 преимущества Islands.
?
**1.** Экстремальная производительность (Astro: **80%+ меньше JS** для контентных сайтов). **2.** SEO и доступность (HTML-first). **3.** Изоляция сбоев (баг в одном острове не роняет страницу). **4.** Стратегия загрузки (`load`/`idle`/`visible`).
#flashcards/frontend/rendering-strategies/islands/tradeoffs

Почему синхронизация состояния между островами — главный архитектурный минус?
?
Острова **не имеют общего стора** (нет Redux/Zustand/Context). Чтобы синхронизировать, нужны: URL-параметры, куки, кастомные DOM-события (`window.dispatchEvent(new CustomEvent(...))`), микро-стор (Nano Stores). Это сложнее, чем `useState` в общем родителе SPA. **Сигнал:** если постоянно нужно делиться состоянием — ты вышел из зоны «в основном статичный контент».
#flashcards/frontend/rendering-strategies/islands/tradeoffs

Почему классические острова не умеют стримить HTML на клиент?
?
Потому что классический остров рендерится **внутри общего прохода рендера страницы** — это часть того же HTML, отдаётся одним цельным документом. Стриминг требует возможности «отложить» блок, вынести его рендер. У классического острова такой инструкции нет. Только `server:defer` умеет выносить рендер в отдельный запрос. Исторически Islands выросли из SSG (статика при сборке), где стриминг не нужен.
#flashcards/frontend/rendering-strategies/islands/tradeoffs

Назови 4 недостатка Islands.
?
**1.** Разделение ментальной модели (нет простоты «одно дерево, один стор»). **2.** Сложность коммуникации (нет общего состояния между островами). **3.** Ограничения экосистемы (фреймворки моложе React/Vue, библиотеки пишутся под SPA). **4.** Сложность миграции (перенос SPA → Islands = переписывание архитектуры).
#flashcards/frontend/rendering-strategies/islands/tradeoffs

## Когда использовать

Назови 3 сценария, когда Islands — «практически идеальный выбор».
?
Страница преимущественно статична, интерактивные части локализованы: **1.** Документация, новости, блоги, лендинги. **2.** Страницы товара в e-commerce (JS — галерея + «в корзину»). **3.** Дашборды с преимущественно читаемыми данными.
#flashcards/frontend/rendering-strategies/islands/when-to-use

Назови 3 сценария, когда Islands — «плохой вариант».
?
Интерактив глобален — общее состояние пронизывает множество виджетов, смена маршрута обновляет половину экрана, «фундаментально одна большая интерактивная поверхность»: **1.** Совместный редактор кода. **2.** Canvas-приложение типа Figma. **3.** Интерфейс видеоконференций. → Лучше единое дерево (SPA, SSR с гидратацией или RSC).
#flashcards/frontend/rendering-strategies/islands/when-to-use
