## Что такое holotypes

Что такое «holotypes» в контексте выбора стратегии рендеринга?
?
Спектр типов приложений (Portfolio, Content, Storefront, Social, Immersive), каждый из которых ценит своё. Подставляешь продукт в таблицу → получаешь отправную точку для выбора стратегии. Цитата [Pat]: «Depending on the type of the application or the page type, some of the patterns may be more suitable.»

## Таблица holotypes (5 типов)

Назови 5 holotypes и для каждого — что ценит.
?
1. **Портфолио / Блог** — простота, минимальная интерактивность.
2. **Контент (CNN)** — обнаруживаемость (discoverability).
3. **Магазин (Amazon)** — производительность загрузки.
4. **Соцсети (Facebook)** — глубокие сессии, динамичность.
5. **Иммерсивные (Figma)** — полная интерактивность, погружение.

## Holotype → стратегия (по источнику [Pat])

Какой паттерн подходит для **Портфолио / Блога**? Почему?
?
**Статика (SSG = Static Site Generation).** Контент обновляется редко, одинаков для всех, интерактивность минимальна. HTML считается один раз при сборке, лежит на CDN, отдаётся за ~10–30 мс глобально.

Какой паттерн подходит для **Контента (CNN)**? Почему Static ИЛИ SSR?
?
**Static или SSR (Server-Side Rendering).** Ключевое слово источника: **discoverability** — скорость и глубина индексации (статья в Google за минуты). Static — для опубликованных статей; SSR — для breaking news, счётчиков, live-блогов; ISR с коротким `revalidate` — для главного. В отличие от блога, **критична свежесть**.

Какой паттерн подходит для **Магазина (Amazon)**? Почему гибрид?
?
**Гибридные подходы** (Astro, Marko, Hydrogen). Магазин напряжён по двум осям одновременно: производительность загрузки + персонализация + SEO. Ни один чистый паттерн не покрывает всё: SSG не даёт персонализации цен/наличия, SSR медленно на высоком трафике, CSR плох для SEO.

Какой паттерн подходит для **Соцсетей (Facebook)** по источнику [Pat]?
?
**SSR (Next, Remix).** Контент 100% персональный (лента у каждого своя), обновляется в реальном времени, за авторизацией (SEO не нужен), пользователи проводят часами. Почему НЕ CSR: классический CSR-SPA даёт пустой экран → загрузка → данные; для ленты, куда заходят часто, это проигрывает SSR со streaming.

🔴 Какой паттерн подходит для **Соцсетей** по современному Next.js 16 (синтез курса)?
?
**RSC (React Server Components) + PPR (Partial Prerendering) + Client Components.** Именно Facebook (Meta) придумал RSC для этого holotype — максимальная персонализация + быстрая загрузка + минимум JS. В якоре [Pat] PPR не упоминается; это более свежая рекомендация.

Какой паттерн подходит для **Иммерсивных (Figma)**? Почему CSR?
?
**CSR (Client-Side Rendering).** Почти весь экран интерактивен, состояние сложное и локальное (canvas, документы), SEO не нужен (за логином), первый показ не критичен. Серверный рендеринг бесполезен или вреден: HTML сразу заменяется canvas, SSR добавляет нагрузку без пользы.

## Спектр интерактивности

Расположи 5 holotypes по спектру «меньше интерактивности → больше интерактивности». Какие стратегии на концах?
?
Портфолио/Блог → Контент → Магазин → Соцсети → Иммерсивные.
- Левый конец (мин. интерактивности): **SSG** (один HTML).
- Правый конец (макс. интерактивности): **CSR** (полное SPA).

## Routing-level strategy

Может ли одно приложение сочетать разные стратегии? Где проходит граница?
?
**Да** — граница проходит по **маршруту**, не по всему продукту. Пример Figma: `figma.com/` (лендинг) → SSG (SEO нужен, обновляется редко); `figma.com/file/[id]` (приложение) → CSR (полная интерактивность, за логином). В Next.js: `app/(marketing)/page.tsx` = SSG с `'use cache'`; `app/(app)/file/[id]/page.tsx` = CSR/RSC-heavy.

## 🔴 Главный критерий выбора

🔴 Назови эвристику выбора по двум вопросам: «нужна персонализация?» и «нужен SEO?».
?
- **Нужна персонализация / данные пользователя?** → SSR / RSC + Client Components. Если нет → SSG.
- **Нужен SEO?** → SSG / SSR (HTML в первом ответе). Если нет → CSR допустим.
- **Полная интерактивность (canvas, IDE)?** → CSR.

Это синтез курса, не прямая цитата [Pat].

## Магазин — самый напряжённый holotype

Почему магазин — самый сложный holotype для выбора стратегии?
?
Он напряжён **по двум осям одновременно**:
1. Производительность загрузки (медленный магазин = потерянная продажа; «100 мс задержки = 1% потерь» по Amazon).
2. Персонализация (рекомендации, цены, наличие — зависят от пользователя).
3. SEO (страницы товаров должны индексироваться).

Ни один чистый паттерн не покрывает всё → нужен гибрид.

🔴 Как современный Next.js 16 + Cache Components решает магазин?
?
**PPR (Partial Prerendering):** статический shell (каталог, навигация) при сборке + динамические чанки в `<Suspense>` (рекомендации, корзина, цена) стримятся при запросе. Это современная реализация holotype «магазин». В [Pat] упоминаются Astro/Marko/Hydrogen — это baseline; Next.js 16 = актуальная рекомендация курса.

## Карточка товара как два holotype в одном

Как одна страница (карточка товара) может принадлежать двум holotypes одновременно?
?
- Для **анонимного** пользователя = «Контент» (SEO, discoverability) → статическая часть, индексируется.
- Для **залогиненного** = «Магазин» (персонализация, корзина) → динамические чанки.

PPR именно это и решает: статический shell общий, динамические чанки персональные (через `cookies()`/`searchParams` в `<Suspense>`).

## Checklist выбора стратегии

Назови 7 шагов выбора стратегии для нового продукта.
?
1. Определить holotype продукта (таблица).
2. Разбить продукт на маршруты (routing-level strategy).
3. Для каждого маршрута: что ценит? (SEO / персонализация / интерактивность / производительность).
4. Подобрать стратегию по таблице holotypes + таблице 9.4.
5. 🔴 Проверить регион деплоя: функция в том же регионе, что и БД (data locality).
6. 🔴 Для durable кэша на serverless: `'use cache: remote'` + `cacheHandlers`, не дефолтный in-memory ephemeral.
7. Для смешанных страниц: рассмотреть PPR (статический shell + `<Suspense>` для динамических чанков).

## 🔴 Атрибуция: источник vs Next.js 16

🔴 В чём разница между ответом «по источнику [Pat]» и «по современному Next.js 16» для магазина и соцсетей?
