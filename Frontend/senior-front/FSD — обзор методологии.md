# FSD — обзор методологии

> Подглава 2 главы 1.2 курса «Фронтенд senior+ в агентную эру». Якорь [FSD] — feature-sliced.design, Get Started → Overview. Продолжение: [[FSD — зачем архитектура (проблемы и требования)]].

## Executive Summary (ELI5)

> **Feature-Sliced Design** (FSD) — архитектурная методология для каркаса фронтенд-приложений: **компиляция правил и соглашений об организации кода**. Главная цель — сделать проект более понятным и стабильным перед лицом постоянно меняющихся бизнес-требований.

FSD — не только доки, но и инструментарий: линтер **Steiger** (проверяет архитектуру) + генераторы папок (CLI/IDE).

## Кому подходит: два критерия

1. Делаете **фронтенд** (UI: web, mobile, desktop).
2. Строите **приложение**, а не библиотеку.

Нет ограничений на язык, фреймворк, стейт-менеджер. Можно внедрять инкрементально, в монорепо, масштабировать пакетами (каждый пакет — свой FSD-корень).

⚠️ **Нюанс (зафиксированный пробел):** библиотека не подходит НЕ потому, что «у неё нет архитектуры» (архитектура у библиотеки бывает — модули, экспорты), а потому что FSD делит проект по **бизнес-доменам приложения** — слайсам, которых у переиспользуемой библиотеки нет.

## Оговорка о миграции

Переходить с существующей архитектуры — только если она **причиняет неудобства**: проект стал слишком большим/взаимосвязанным для новых фич, ожидается рост команды. «If the current architecture works, maybe it's not worth changing» — если работает, возможно, менять не стоит.

## Базовый пример: три уровня иерархии

```
- app/                    ← СЛОЙ
  - routes/               ← СЕГМЕНТ
  - analytics/
- pages/                  ← СЛОЙ
  - home/                 ← СЛАЙС
  - article-reader/       ← СЛАЙС
    - ui/                 ← СЕГМЕНТЫ
    - api/
- shared/                 ← СЛОЙ
  - ui/                   ← СЕГМЕНТ
  - api/
```

- **Слои (layers)** — стандартизированные папки верхнего уровня;
- **слайсы (slices)** — делят слой **по доменам** (в `pages` — по страницам);
- **сегменты (segments)** — делят слайс/слой **по технической цели**.

Мнемоника «город»: слои — районы, слайсы — кварталы по смыслу, сегменты — коммуникации по назначению.

## Четыре преимущества ↔ три боли

| Преимущество | Механика | Закрывает боль |
|---|---|---|
| **Uniformity** (однородность) | структура стандартизирована → проекты однородны | bus-factor/онбординг |
| **Stability** (стабильность при изменениях) | модуль слоя не импортирует свой слой и выше → изолированные изменения | «всё зависит от всего» |
| **Controlled reuse** | по слою: очень переиспользуемый или очень локальный код → баланс DRY/практичность | две крайности переиспользования |
| **Orientation to business** | разбиение по бизнес-доменам, бизнес-язык в именах | продукту можно работать, не понимая несвязанные части |

Каждое преимущество — зеркальный ответ на боль из [[FSD — зачем архитектура (проблемы и требования)]].

## Связи

- Слой/слайс/сегмент детально — следующие подглавы (Reference → Layers / Slices-segments).
- Монорепо-совет (пакеты = отдельные FSD-корни) — разовьётся в главу 1.9 курса.
- StyleNest (сквозной проект) — приложение → FSD применим; `@stylenest/ui-kit` как npm-пакет — уже нет.

## Self-check

1. Два критерия применимости? → фронтенд + приложение (не библиотека).
2. Когда мигрировать? → только когда текущая архитектура причиняет боль.
3. Три уровня иерархии на дереве? → layers (`app`) / slices (`pages/article-reader`) / segments (`ui`, `api`).
4. Какое преимущество отвечает на «updated the store of one page — fell off on the other»? → **Stability** (запрет импортов в пределах слоя и вверх).
