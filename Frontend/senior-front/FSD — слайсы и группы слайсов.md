# FSD — слайсы и группы слайсов

> Подглава 4 главы 1.2 курса «Фронтенд senior+ в агентную эру». Якорь [FSD] — Reference → Slices and segments (раздел Slices) + Slice groups. Продолжает: [[FSD — слои и правило импортов]].

## Executive Summary (ELI5)

Слайс — папка, группирующая код **по смыслу для продукта**. Слой отвечает «какая ответственность», слайс — «какой домен». Имена не стандартизированы — приходят из языка конкретного бизнеса.

## Слайс: правила

- Имена слайсов определяются бизнес-доменом: фотогалерея — `photo`, `effects`, `gallery-page`; соцсеть — `post`, `comments`, `news-feed` (🟡 на реальных продуктах: Avito — `listing`, `chat`, `profile`; Airbnb — `listing`, `booking`, `host`).
- **Shared и App не содержат слайсов** (нет доменов / все домены сразу — см. [[FSD — слои и правило импортов]]).

### Zero coupling, high cohesion

Идеальный слайс:
- **zero coupling** — независим от других слайсов своего слоя;
- **high cohesion** — содержит **большую часть кода, относящегося к его основной цели** (не «узкий доменный код», а именно полнота: всё про заказ — в слайсе заказа).

Независимость обеспечивает правило импортов: только слои строго ниже.

### Правило public API на слайсах

> *Every slice (and segment on layers that don't have slices) must contain a public API definition. Modules outside of this slice/segment can only reference the public API, not the internal file structure.*

Внутри слайса код организуется как угодно — пока публичный API скрывает внутренности. Это даёт свободу рефакторинга без поломки соседей (механика index-файлов — §6).

## Группы слайсов (slice groups)

Необязательная часть FSD: папка, собирающая связанные слайсы рядом для **навигации**. Вводится, когда плоский список просматривать тяжело.

**Три «НЕ» группы:**
1. **Не слайс** — нет своих сегментов (`model`, `ui`, `api`);
2. **Нет public API** — никакого `index.ts` у папки;
3. **Нет общего кода** — общий код нескольких слайсов уходит **на слой ниже**.

Каждый слайс внутри группы остаётся полноценным слайсом.

**Когда вводить:** критерий очевиден с первого взгляда; слайсы одного контекста разбросаны; слайсов слишком много для обзора.
**Когда не надо:** имён достаточно; нет естественного критерия; в группе было бы 2–3 слайса.

Пример источника (entities):

```
entities/
  payment/          # группа: invoice, receipt, transaction
  user/             # слайс вне группы — имя самодостаточно
```

**Pages на реальных продуктах:** KakaoPay (кейс справочника) — `order/{create, detail, list}`; GitHub 🟡 — URL `github.com/<owner>/<repo>/issues` подсказывает группу `repo/` во вложенном роутинге.

**Features — осторожно:** фича охватывает несколько сущностей, критерий найти труднее. `features/cart/` без ясного критерия сползает в «дом всего cart-домена» (DTO, мапперы) — источник предупреждает прямо.

## Кейс, решённый на сессии (Booking.com-клон)

30 слайсов в `pages`, из них 12 — про хозяина объекта (dashboard, calendar, listings, bookings, payouts, reviews, photos, pricing, inbox, settings, promotions, verification). Решение пользователя: **группа `host/`** — соответствует критериям: критерий очевиден (хозяин — реальный домен Booking, отдельный продукт for Partners), слайсов много, разбросаны. Проверки: слайсы внутри остаются слайсами, у `host/` нет index/сегментов/общего кода; гостевые страницы остаются вне группы.

## Self-check

1. Откуда берутся имена слайсов? → из бизнес-домена продукта; не стандартизированы.
2. High cohesion — это? → слайс содержит большую часть кода своей основной цели.
3. Три «НЕ» группы слайсов? → не слайс (без сегментов), без public API, без общего кода; общий код — слоем ниже.
