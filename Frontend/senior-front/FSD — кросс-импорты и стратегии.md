# FSD — кросс-импорты и стратегии A–D

> Подглава 7 главы 1.2 курса «Фронтенд senior+ в агентную эру». Якорь [FSD] — Guides → Issues → Cross-imports. Продолжает: [[FSD — public API и barrel files]].

## Executive Summary (ELI5)

Кросс-импорт — импорт **между слайсами одного слоя** (`features/cart → features/product`). Не путать: внутри `shared`/`app` слайсов нет — там импорты свободны. Это **code smell**, но не грех: у источника четыре стратегии лечения и честная оговорка про строгость.

## Четыре причины code smell

1. **Неясное владение** — кто отвечает за общую логику? Команда `product` рефакторит внутренности → незаметно ломает `cart`.
2. **Падение изоляции/тестируемости** — тест `cart` требует поднимать `product`.
3. **Рост когнитивной нагрузки** — даже мелкая правка требует контекста через границу.
4. **Путь к циклам** — однонаправленные зависимости эволюционируют в двунаправленные (A↔B), рефакторинг дорожает.

## Порядок для entities

Кросс-импорты в entities часто = **слишком гранулярная нарезка**. Порядок: (1) рассмотреть **слияние**; (2) не подошло — `@x` (последнее средство, «необходимый компромисс», только entities — см. [[FSD — public API и barrel files]]).

## Стратегии для features/widgets

**A — Slice merge.** Слайсы не по-настоящему независимы и **всегда меняются вместе** → один слайс (`features/profile` + `features/profileSettings` → `features/profile`).

**B — Опустить доменный поток в `entities` (domain-only).** Общий домен нескольких фич → `entities` (валидация сессии у `features/auth` и `features/profile` → `entities/session`). В entities — только доменные типы и логика; UI остаётся в фичах; фичи импортируют вниз — легально.

**C — Композиция с верхнего слоя (pages/app), IoC.** Слайсы не знают друг о друге, страница связывает. Приёмы: **render props** (React), **слоты** (Vue), DI через пропсы/контекст. Канонический пример: `CommentList` принимает `renderUserAvatar?: (userId) => ReactNode`, страница вставляет `<UserAvatar>`. Реальный пример 🟡: карточка объявления Airbnb (`entities/listing/ui`) не знает про избранное — `features/favorites` вставляется в неё пропсом на уровне страницы.

**D — Только через публичный API.** A–C не подошли, кросс-переиспользование неизбежно → только именованные экспорты (хуки, UI-компоненты), никогда `store`/`model`/internal. Единственная стратегия, **принимающая** кросс-импорт. «Общаться можно, лезть в душу — нет».

## Тревожные сигналы (кросс-импорт — уже проблема)

- зависимость от store/model/бизнес-логики чужого слайса;
- глубокие импорты во внутренние файлы;
- двунаправленные зависимости (A↔B);
- изменения одного слайса регулярно ломают другой;
- потоки, которые должны собираться в `pages`/`app`, впихнуты в кросс-импорты.

## Строгость — решение команды; обязанности при вводе

Ранний продукт с экспериментами → часть кросс-импортов = прагматичный размен скорости. Долгоживущие/регулируемые (fintech) → строгие границы окупаются. **Если вводишь кросс-импорт — три обязанности:** (1) осознанное архитектурное решение, (2) документируй обоснование, (3) периодически пересматривай.

## Кейс, решённый на сессии (клон Ozon)

`features/checkout` импортирует `features/promo-code`, промокод используется только внутри чекаута. Решение пользователя: **стратегия A (merge)** — не независимы, меняются вместе; запасной план при появлении второго потребителя — **стратегия B** (вынести промокоды в собственный домен).

## Self-check

1. Четыре причины code smell? → владение, изоляция/тесты, когнитивная нагрузка, циклы.
2. A–D одной фразой каждая? → merge / домен в entities / композиция сверху (IoC) / только public API.
3. Три обязанности при вводе кросс-импорта? → осознанное решение, документировать, пересматривать.
