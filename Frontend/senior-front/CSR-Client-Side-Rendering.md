# 🧠 Topic: Client-Side Rendering (CSR)

> [!abstract] Executive Summary (ELI5)
> CSR — это когда сервер отдаёт браузеру **пустую страницу** (`<div id="root"></div>`) и **JS-бандл**. Весь интерфейс, данные и логика приезжают в виде JavaScript, который в браузере сам строит DOM, делает запросы и рисует UI. Это зеркальный антипод [[SSR-Server-Side-Rendering|SSR]]: при SSR сервер отдаёт «готовую газету», при CSR — «печатный станок и инструкцию».

> Источник: глава 1.1 курса, подглава 4. Якорь: [Pat] patterns.dev, «Client-Side Rendering».

---

## 🎯 The "Why"

- **Problem Solved:** CSR оптимален, когда (1) страница скрыта за авторизацией (SEO не нужен), (2) пользователь открывает приложение один раз и проводит в нём много времени (долгая сессия окупает загрузку бандла), (3) нужна плотная интерактивность с сохранением состояния (редакторы, таблицы), (4) нужна автономная работа через service worker (PWA).
- **Alternatives:**
    - [[SSR-Server-Side-Rendering|SSR]] — когда контент зависит от запроса и важен LCP/SEO;
    - [[Static-Rendering|Static / SSG]] — когда контент одинаков для всех;
    - [[ISR-Incremental-Static-Regeneration|ISR]] — когда данные терпят устаревание.
- **Trade-offs:** CSR даёт мгновенную навигацию после загрузки и минимум сетевых запросов при взаимодействии, но платит: LCP запаздывает (ждёт бандл), SEO с ограниченным краулер-бюджетом, диспаритет устройств (1 МБ JS = секунды на бюджетном Android).

## 💡 Mental Model & Analogy

- **Аналогия:** SSR — ресторан, где повар готовит блюдо под твой заказ и подаёт готовым. CSR — ресторан самообслуживания: тебе выдают пустую тарелку и поварённого-робота в коробке; ты сам распаковываешь робота, он готовит, ты ешь. Первая загрузка долгая (распаковка), зато потом робот быстро готовит снова и снова.
- **Ключевая фраза-маркер:** «весь интерфейс, данные и логика передаются по сети **в виде JavaScript-кода**» ([Pat]).

```
SSR:  [запрос] → [сервер строит HTML с данными] → [отдать] → [браузер рисует] → [гидратация]
                                                                       ↑ LCP тут

CSR:  [запрос] → [сервер отдаёт пустой shell] → [скачать JS] → [парсить] → [выполнить] → [fetch] → [RENDER]
                                                                                              ↑ LCP тут
```

## 🛠️ Core Principles & Mechanics

### Что отдаёт сервер

Практически пустой HTML-документ. Контента страницы внутри нет — есть только тег-крючок и ссылки на JS-чанки:

```html
<!DOCTYPE html>
<html>
  <head><title>My App</title></head>
  <body>
    <div id="root"></div>  <!-- пусто, React всё построит -->
    <script type="module" src="/assets/index-a1b2c3d4.js"></script>
  </body>
</html>
```

> Если в этот момент выключить JS в браузере — пользователь увидит буквально пустую страницу.

### Точка входа: `createRoot` (React 18+)

В React 18+ классический `ReactDOM.render` устарел. Современная CSR-точка входа использует `createRoot`, который включает **Concurrent Rendering**:

```jsx
import { createRoot } from 'react-dom/client';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(<App />);
```

**Зачем `createRoot`:** включает Concurrent-режим — React может приостанавливать рендер, переключаться между задачами, отбрасывать устаревший результат. Это фундамент для `Suspense`, `useTransition`, потокового рендера.

## 📋 Когда использовать / избегать

| ✅ Использовать CSR | ❌ Избегать CSR |
|---|---|
| Страница скрыта за авторизацией (админки, дашборды) | Страница индексируется поисковиками (лендинг, блог) |
| Одна долгая сессия (редакторы, Figma) | Пользователь быстро уходит (новости, маркетинг) |
| Высокая плотная интерактивность с состоянием | Критичны LCP и TTFB |
| Офлайн-PWA через service worker | Слабые устройства / медленный интернет |

**Принципы:**
- За авторизацией → Googlebot не залогинится → SEO-аргумент отпадает → CSR ок.
- Долгая сессия → первая загрузка амортизируется; быстрый отскок → дорогая загрузка не окупается.

🔗 **Якорь:** [Pat] — разделы When to use / avoid.

## 📊 Производительность и метрики

**Главный минус (одной фразой):** «скорость отрисовки полностью зависит от того, как быстро клиентское устройство сможет загрузить и выполнить JS-бандл» ([Pat]). Производительность делегируется устройству пользователя — ты теряешь контроль.

| Метрика | Поведение в CSR | Почему |
|---|---|---|
| **TTFB** | ✅ быстрый | сервер отдаёт статический shell, ничего не рендерит |
| **FCP / LCP** | ❌ запаздывают | ждут: скачать → парсить → выполнить JS → первый рендер → (возможно) fetch |
| **TTI / INP** | ⚠️ сначала плохо, потом отлично | при загрузке main thread занят; **после** — нет сетевых запросов при каждом действии |
| **CLS** | ❌ высокий риск | переход от пустого `div` к заполненному UI = layout shift |

> **INP-парадокс:** CSR — единственный паттерн, где INP со временем **улучшается**. После загрузки навигация и взаимодействие мгновенны (нет сети, состояние в памяти) — ради этого «нативного ощущения» CSR и выбирают.

## ⚠️ Дополнительные проблемы CSR

1. **SEO.** Краулеры умеют выполнять JS, но с **ограниченным бюджетом**. Серия последовательных запросов → индексация долго или частично. Не «не индексируется», а «индексируется хуже и медленнее».
2. **Ощущение производительности.** Пустой экран/спиннер всё время загрузки раздражает сильнее, чем skeleton (даже если по времени одинаково).
3. **Диспаритет устройств.** Ключевое число: **парсинг 1 МБ JS на бюджетном смартфоне — больше секунды** (на десктопе — миллисекунды). Разработчик на MacBook Pro видит «всё быстро», пользователь на Moto G4 — «висит 4 секунды».
4. **Дублирование кода.** Валидация формы: на сервере (клиенту верить нельзя) и на клиенте (для UX). Удваивает работу.
5. **Водопады запросов (waterfalls).** Шаблон `useEffect → fetch → setState` создаёт последовательные запросы — общее время = **сумма**, а не максимум.

### Водопад запросов — главный архитектурный грех

```jsx
// ❌ Антипаттерн: 3 последовательных тура
useEffect(() => {
  fetch('/api/user').then(u => {
    fetch(`/api/orders?userId=${u.id}`).then(o => {  // ждём первого
      o.forEach(order => fetch(`/api/items?orderId=${order.id}`));  // ждём второго
    });
  });
}, []);
```

## 🚀 Как выжать максимум из CSR

Если остановились на CSR — строго управляйте размером JS-бандла.

### 1. Бюджет: 170 КБ (gzip) критичного JS

Число из HTTP Archive / Addy Osmani (через [Pat]): порог, при котором средний мобильный девайс ещё укладывается в разумное TTI. Инструменты: `webpack-bundle-analyzer`, `source-map-explorer`, `bundlephobia`.

### 2. Code splitting через `React.lazy`

Не грузить маршрут, пока на него не перешли:

```jsx
import { lazy, Suspense } from 'react';

const AdminPanel = lazy(() => import('./routes/AdminPanel'));
const Dashboard  = lazy(() => import('./routes/Dashboard'));

function App() {
  return (
    <Suspense fallback={<PageSpinner />}>
      <Routes>
        <Route path="/admin"     element={<AdminPanel />} />
        <Route path="/dashboard" element={<Dashboard />} />
      </Routes>
    </Suspense>
  );
}
```

### 3. Прелоад через `modulepreload`

Заранее подгружать чанки, которые понадобятся (например, при наведении на ссылку):

```html
<link rel="modulepreload" href="/assets/admin-panel-a1b2.js" />
```

### 4. Отложенная загрузка через `IntersectionObserver`

Виджеты вне первого экрана (чат, рекомендации) — грузить только при приближении к видимой области.

### 5. App Shell + Service Worker

Кэшировать shell + критичные ассеты через service worker → повторный визит мгновенно из кэша:

```js
// service-worker.js (упрощённо, shell-first стратегия)
const SHELL_CACHE = 'app-shell-v1';
self.addEventListener('install', (e) => {
  e.waitUntil(caches.open(SHELL_CACHE).then((c) => c.addAll([
    '/', '/index.html', '/assets/index-a1b2.js', '/styles.css'
  ])));
});
self.addEventListener('fetch', (e) => {
  e.respondWith(caches.match(e.request).then((c) => c || fetch(e.request)));
});
```

> **App shell ≠ streaming shell.** App shell — стабильная SPA/PWA-оболочка, грузится один раз, живёт всю сессию. Streaming shell — часть SSR-страницы вне Suspense, отправляется первым при стриминге. См. [[SSR-Server-Side-Rendering|SSR]] §3.7.

### 6. Skeleton UI вместо спиннера

Skeleton резервирует место под контент → CLS не растёт. Спиннер = пустое место, которое потом «взрывается» контентом и двигает вёрстку.

```jsx
function ArticleSkeleton() {
  return (
    <div className="skeleton">
      <div className="skeleton-line title" />
      <div className="skeleton-line" />
      <div className="skeleton-line" />
    </div>
  );
}
```

### 7. TanStack Query / SWR / Apollo — обязательно

Почему «обязательно»: решают 5 проблем сразу — дедупликация, кэширование, ретраи, фоновое обновление, race-condition handling. Наивный `useEffect + fetch` снова и снова рождает водопады.

```jsx
// ✅ С TanStack Query — параллельно, без водопадов
function UserDashboard({ userId }) {
  const { data: user } = useQuery({ queryKey: ['user'], queryFn: fetchUser });
  const { data: orders } = useQuery({
    queryKey: ['orders', user?.id],
    queryFn: () => fetchOrders(user.id),
    enabled: !!user,  // стартует только когда user готов
  });
}
```

## 📈 Outgrowing CSR (культура обновления)

Когда прототип на CSR начинает обслуживать реальных пользователей, [Pat] рекомендует переходить на фреймворки (Next.js / Remix / TanStack Start). Эволюционный путь:

1. **Переход на фреймворк** → SSR/SSG «из коробки», сохраняя SPA-навигацию на клиенте.
2. **Публичные маршруты → [[React-Server-Components]]** → контент рендерится сервером без клиентского JS; интерактивные экраны остаются на клиенте.
3. **Streaming SSR** → показывать значимый контент до того, как загрузятся все данные.

### Архитектурный паттерн гибридного приложения

```
┌─────────────────────────────────────────────┐
│  Публичные страницы (лендинг, блог, цены)   │  → RSC / SSG / Streaming SSR
│  JS почти не нужен                          │
├─────────────────────────────────────────────┤
│  Авторизованная зона (дашборд, редактор)    │  → CSR / Islands
│  Плотная интерактивность                    │
└─────────────────────────────────────────────┘
```

> Это мостик к [[Islands-Architecture]] и [[React-Server-Components]]: оба паттерна пытаются **сохранить интерактивность CSR**, но **избавиться от его главной цены** — обязательной загрузки JS для любого контента.
