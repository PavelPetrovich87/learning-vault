# Holotypes (типы приложений)

> Подглава 10 (финальная теоретическая) главы 1.1 курса «Фронтенд senior+ в агентную эру». Якорь [Pat] — patterns.dev, введение «Rendering Patterns». Это сводная таблица всей главы — отвечает на вопрос «какой паттерн выбрать для какого продукта?».

## Executive Summary (ELI5)

Не существует «лучшего» паттерна рендеринга вообще. Существует **спектр типов приложений** (holotypes), и каждый ценит своё:

> «Depending on the type of the application or the page type, some of the patterns may be more suitable.» — [Pat]

Подставляешь свой продукт в таблицу → получаешь отправную точку для выбора стратегии. Holotypes расположены по спектру «минимальная интерактивность → полная интерактивность».

## The Why

Все 9 предыдущих подглав были про «как работают стратегии». Эта — про «когда какую выбрать». Без неё глава остаётся теорией без практического выхода.

## Mental Model: спектр интерактивности

```
Меньше интерактивности                                      Больше интерактивности
   ┌──────────┬──────────┬──────────┬──────────┬──────────┐
   │ Портфолио │  Контент  │  Магазин  │  Соцсети  │ Иммерсивн.│
   │  / Блог   │  (CNN)    │ (Amazon)  │ (Facebook)│  (Figma)  │
   └──────────┴──────────┴──────────┴──────────┴──────────┘
       SSG      Static/SSR    Гибрид      SSR       CSR
   (один HTML)  (с ISR/SSR)  (Islands,    (RSC+     (полное
                              PPR)         PPR)     SPA)
```

Чем правее — тем больше интерактивности и тем меньше смысла в статике.

## Таблица holotypes (по [Pat])

| Holotype                | Что ценит                             | Подходящий паттерн (по источнику)          |
| ----------------------- | ------------------------------------- | ------------------------------------------ |
| **Портфолио / Блог**    | Простота, минимальная интерактивность | Статика (SSG = Static Site Generation)     |
| **Контент (CNN)**       | Обнаруживаемость (discoverability)    | Static или SSR (Server-Side Rendering)     |
| **Магазин (Amazon)**    | Производительность загрузки           | Гибридные подходы (Astro, Marko, Hydrogen) |
| **Соцсети (Facebook)**  | Глубокие сессии, динамичность         | SSR (Next, Remix)                          |
| **Иммерсивные (Figma)** | Полная интерактивность, погружение    | CSR (Client-Side Rendering)                |

## Разбор по holotypes

### 1. Портфолио / Блог → SSG

**Что ценит:** простота, минимальная интерактивность.

Контент:
- обновляется редко (статья раз в неделю, портфолио раз в год);
- одинаков для всех;
- интерактивность минимальна (разве что кнопка «тёмная тема»).

**Почему SSG:** HTML считается один раз при сборке, лежит на CDN (Content Delivery Network), отдаётся за ~10–30 мс глобально. JS-фреймворк в браузере не нужен (или минимум — пара островов).

### 2. Контент (CNN) → Static ИЛИ SSR

**Что ценит:** обнаруживаемость (discoverability).

«Discoverability» = SEO + быстрая индексация + превью при шеринге. Не «видимость в поиске» вообще, а **скорость и глубина индексации**: статья должна попасть в Google за минуты, не часы.

**Почему Static ИЛИ SSR:**
- **Static (SSG)** — для опубликованных статей, которые не меняются.
- **SSR** — для breaking news, счётчиков, live-блогов.
- **ISR (Incremental Static Regeneration)** — пере-валидация по короткому `revalidate` для главного.

Ключевое отличие от блога: **частота обновления** и **критичность свежести**. Блог может ISR раз в сутки, новостям нужны минуты.

### 3. Магазин (Amazon) → Гибридные подходы

**Что ценит:** производительность загрузки.

Самый напряжённый holotype — **две оси одновременно**:
- производительность загрузки (медленный магазин = потерянная продажа);
- персонализация (рекомендации, цены, наличие);
- SEO (страницы товаров должны индексироваться).

Ни один чистый паттерн не покрывает всё. Поэтому гибрид:
- **Astro** (Islands) — статический HTML + островки интерактивности.
- **Marko** (eBay) — стриминговый рендеринг с тонкой гидратацией.
- **Hydrogen** (Shopify, на React) — магазин как RSC-приложение.
- 🔴 **Next.js 16 + Cache Components / PPR (Partial Prerendering)** — современная реализация этого holotype: статический shell (каталог, навигация) + динамические чанки в `<Suspense>` (рекомендации, корзина).

### 4. Соцсети (Facebook) → SSR (🔴 по Next.js 16 — RSC + PPR)

**Что ценит:** глубокие сессии, динамичность.

Особенности:
- контент 100% персональный (лента у каждого своя);
- обновляется в реальном времени;
- за авторизацией (SEO не нужен);
- пользователи проводят часами, глубоко интерактивны.

**По источнику [Pat]:** SSR (Next, Remix).

🔴 **По современному Next.js 16 (синтез курса):** RSC (React Server Components) + PPR + Client Components. Именно Facebook (Meta) и придумал RSC для этого holotype — максимальная персонализация + быстрая загрузка + минимум JS. В якоре [Pat] PPR не упоминается; это более свежая рекомендация.

**Почему НЕ CSR:** классический CSR-SPA даёт пустой экран → загрузка → данные. Для ленты, куда заходят часто и хотят мгновенный контент, это проигрывает SSR со streaming.

### 5. Иммерсивные (Figma) → CSR

**Что ценит:** полная интерактивность, погружение.

Противоположный конец спектра от блогов. Figma, Google Docs, онлайн-IDE, браузерные игры:
- почти весь экран интерактивен;
- состояние сложное и локальное (canvas, документы);
- SEO не нужен (за авторизацией);
- первый показ не критичен — пользователь залогинился и работает часами.

**Почему CSR:** серверный рендеринг здесь **бесполезен или вреден**:
- HTML сразу заменяется интерактивным canvas/приложением;
- SSR добавляет серверную нагрузку без пользы;
- приложение управляет собственным состоянием, браузерные API повсеместно.

## Три правила использования таблицы

### Правило 1: holotype — отправная точка, не приговор

Таблица даёт дефолт. Реальный продукт почти всегда смешанный. Магазин: лендинг = SSG, каталог = SSG/ISR, карточка товара = PPR, личный кабинет = RSC + Client Components.

### Правило 2: одна страница может принадлежать разным holotypes

В магазине карточка товара = «Контент» (SEO, discoverability) для анонима, но та же карточка = «Магазин» (персонализация, корзина) для залогиненного. PPR именно это и решает — статический shell общий, динамические чанки персональные.

### Правило 3: две оси — «что ценит» × «запрос/визит»

Таблица holotypes + сводная таблица 9.4 (где исполняется + когда) = полный набор для выбора. Никогда не выбирай паттерн по «модности» — выбирай по сочетанию **ценностей продукта × характеристик стратегии**.

## Routing-level strategy (одно приложение, несколько стратегий)

Граница между «статикой» и «динамикой» в одном приложении проходит по **маршруту**, не по всему продукту.

**Пример — Figma:**
- `figma.com/` (лендинг) → SSG (один для всех, SEO нужен, обновляется редко).
- `figma.com/file/[id]` (приложение) → CSR (полная интерактивность, за логином).

В Next.js это реализуется через структуру папок + route-specific config:
- `app/(marketing)/page.tsx` → может быть SSG с `'use cache'`.
- `app/(app)/file/[id]/page.tsx` → CSR/RSC-heavy, без кэширования.

## 🔴 Главный критерий выбора: есть ли персонализация?

Эвристика курса (синтез, не источник):

| Вопрос | Если «да» | Если «нет» |
|---|---|---|
| Нужна ли персонализация / данные пользователя? | SSR / RSC + Client Components | SSG |
| Нужен ли SEO? | SSG / SSR (HTML в первом ответе) | CSR допустим |
| Полная интерактивность (canvas, IDE)? | CSR | ничего из этого |

## Checklist: как выбрать стратегию для нового продукта

1. [ ] Определить holotype продукта (см. таблицу выше).
2. [ ] Разбить продукт на маршруты (routing-level strategy).
3. [ ] Для каждого маршрута: что ценит? (SEO / персонализация / интерактивность / производительность).
4. [ ] Подобрать стратегию по таблице holotypes + таблице 9.4.
5. [ ] 🔴 Проверить регион деплоя: функция в том же регионе, что и БД (подглава 9.3 — data locality).
6. [ ] 🔴 Для durable кэша на serverless: `'use cache: remote'` + `cacheHandlers`, не дефолтный in-memory ephemeral.
7. [ ] Для смешанных страниц: рассмотреть PPR (статический shell + `<Suspense>` для динамических чанков).

## 🔴 Атрибуция: источник vs современный Next.js 16

Важно различать:
- **По источнику [Pat]** — соцсети → SSR; магазин → Astro/Marko/Hydrogen. Это baseline.
- **По современному Next.js 16** — соцсети → RSC + PPR; магазин → Next.js + Cache Components. Это актуальная рекомендация курса.

Оба ответа «правильные», но mixing без пометки — нарушение правила инвариантов («синтез всегда помечен»). В квизах различать по контексту вопроса.
