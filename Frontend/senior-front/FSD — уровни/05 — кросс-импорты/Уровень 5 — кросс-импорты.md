# Уровень 5 — кросс-импорты и границы

> Правило импортов встречает реальность: двум слайсам одного слоя «нужен» общий код, форма тянет из index собственного слайса. Уровень про то, что делать с пограничными зависимостями: сначала убрать, потом — задокументированные исключения.

## Правило и почему нарушение — code smell (по главе)

> «Модуль (файл) в слайсе может импортировать другие слайсы, только если они находятся на слоях **строго ниже**.» — глава 1.2, §3.1 [FSD]

Кросс-импорт — импорт между разными слайсами **одного слоя** (`features/apply-coupon` из `features/add-to-cart`). У shared и app нет слайсов — импорты внутри них не кросс-импорты. Четыре проблемы (§7.1 [FSD], совпадают со скиллом дословно по смыслу): неясное владение, падение изоляции и тестируемости, рост когнитивной нагрузки, дорога к круговым зависимостям.

## В официальном скилле

Правило 4-3 + раздел §7, развёрнутые в `references/cross-import-patterns.md`:

> «The first move is always to remove the dependency by changing a boundary or a composition. Strategies A to C do that. **Strategy D and `@x` are the documented exceptions for a dependency that cannot reasonably be removed, not a second way of working.**» (Первый ход — всегда убрать зависимость, меняя границу или композицию… Strategy D и @x — задокументированные исключения, а не второй способ работы.) — references/cross-import-patterns.md

**Entities: сначала слияние, @x — последнее средство.** И точное правило направления:

> «**Direction rule:** in the path `entities/A/@x/B`, **A is the producer and B is the consumer**. Read it as "A crossed with B": the file `A/@x/B.ts` is the public API that A exposes specifically for B.» (В пути entities/A/@x/B A — производитель, B — потребитель: файл A/@x/B.ts — публичный API, который A открывает специально для B.) — references/cross-import-patterns.md

Правила при использовании @x: (1) документировать, почему слияние не подходит; (2) периодически пересматривать; (3) минимальная поверхность экспорта; (4) только между entities.

**Features/widgets: стратегии A–D** (в порядке предпочтения):

> «**Strategy A: slice merge.** Two slices always change together → merge. **Strategy B: push to entities.** A shared domain responsibility → move it to the entity that owns it, keep UI in the feature. **Strategy C: compose from upper layer (IoC).** The parent (pages or app) imports both slices and connects them via render props, slots, or DI. **Strategy D: Public API access.** When reuse is genuinely unavoidable, allow it only through the slice's `index.ts`. Never reach into `model/`, `store/`, or internal files.» — SKILL.md §7

**Строгость — контекстная** (§7.3 главы ⇔ «Strictness depends on project context» скилла): ранний продукт с экспериментами может позволить немного кросс-импортов как speed trade-off; долгоживущие и регулируемые системы (fintech) строже. Если кросс-импорт введён — это осознанное решение: задокументировать в коде причину и периодически пересматривать.

### Глава ↔ скилл

- **Согласованы:** четыре причины code smell; @x только на entities; минимум поверхности; документирование и пересмотр (= «обязанности команды» из §7.3 главы).
- **Скилл добавляет:** direction rule @x явно (A — producer, B — consumer); стратегии названы и пронумерованы A–D (в главе §7.2 они описаны, но без букв); порядок предпочтения A→D зафиксирован.
- **Круговые зависимости** (глава §6.4): внутри слайса — относительные импорты с **полным путём**, между слайсами — абсолютные; импорт из index собственного слайса (`../`) замыкает круг. Скилл добавляет: двунаправленные зависимости — сигнал пересмотреть границы/композицию.

## Итог уровня

- Первый ход — убрать зависимость (A/B/C), исключения (D, @x) — явные и редкие.
- @x: только entities, producer/@x/consumer, минимальная поверхность, задокументирован.
- Анти-циклы: внутри слайса — относительные полные пути, между слайсами — абсолютные.
