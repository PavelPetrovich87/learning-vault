# Уровень 6 — группы слайсов, public API для сред, инкрементальное внедрение

> Масштаб: слайсов десятки, один код нужен по-разному серверу и клиенту, а рядом — легаси-проект без FSD. Уровень про навигацию без новых границ, точки входа для сред и миграцию без «большого взрыва».

## Группы слайсов (по главе)

> «Группа слайсов — это папка, которая содержит связанные слайсы одного слоя и служит **только для навигации**… Группа — **не слайс**: у неё нет сегментов и нет публичного API. Правила изоляции слайсов внутри группы не меняются: соседние слайсы не импортируют друг друга.» — глава 1.2, §4.3 [FSD] (справочник: пример — группа payment с invoice/receipt/transaction)

Три «НЕ» из главы: не создавать превентивно; имена слайсов должны сами подсказывать общую тему; группа не повод ослаблять изоляцию.

## В официальном скилле

`references/layer-structure.md` («when grouping closely related slices»):

> «A **slice group** is a folder that contains related slices on the same layer, used purely to make the structure easier to navigate as the number of slices grows. A slice group is **not a slice itself**: it has no segments (`model/`, `ui/`, `api/`), no public API (`index.ts`), and no shared code.» (Группа слайсов — папка связанных слайсов одного слоя, чисто для навигации… Группа — не слайс: без сегментов, без публичного API, без общего кода.) — references/layer-structure.md

Анти-паттерны группы: index.ts на папке группы (превращает её в слайс); `utils.ts`/`constants.ts` внутри группы (общему коду место в `shared/`, а доменному — возможно, это сигнал слить сущности); `_common/` между соседями (изоляция не ослабляется). Про features — «use with caution»: группа `features/cart/` притягивает весь корзинный домен и слабит принцип «фичи режутся по юз-кейсам».

## Public API для разных сред (по главе и скиллу)

> Глава 1.2, §6.3 [FSD]: слайс может открывать точки входа под среду исполнения — `index.server.ts` / `index.client.ts` — когда один index не может сохранить рантайм-границу.

> «Keep `index.ts` free of server-only exports, such as Server Components or data-access functions that import `server-only`. When a Client Component imports the slice, those exports can enter the client module graph and cause build errors. **Split only when this boundary is required.** Put server-only exports in `index.server.ts`.» (Держи index.ts свободным от server-only экспортов… Разделяй, только когда граница действительно нужна.) — references/framework-integration.md

Плюс SKILL.md §4-2: «a slice normally exposes one `index.ts`, and ad-hoc variations are not recommended».

## Инкрементальное внедрение (по главе)

> 1. «Медленно формировать слои **App и Shared** модуль за модулем, создав фундамент. 2. Раскидать весь существующий UI по **Widgets и Pages** широкими мазками, даже с зависимостями, нарушающими правила FSD. 3. Постепенно разрешать нарушения импортов и извлекать **Entities** и, возможно, **Features». — глава 1.2, §8.3 [FSD] (Overview → Incremental adoption)

> Совет: «воздержаться от добавления новых больших сущностей во время рефакторинга или рефакторить только определённые части проекта». — глава 1.2, §8.3 [FSD]

## В официальном скилле: миграция custom-архитектуры

`references/migration-guide.md`, Part 2 («converting a non-FSD codebase to FSD»), ядро — «**pages first**»:

> «The core philosophy is **pages first**: start by dividing the code by pages, then work outward. … The most important question to ask the team is: *do you really need it?*» (Начни с деления кода по страницам… Самый важный вопрос команде: точно ли вам это нужно?) — references/migration-guide.md

Порядок: **Шаг 1** — делить код по страницам (роуты становятся тонкими реэкспортами; «Pages may reference each other for now»); **Шаг 2** — отделить остальное: не импортирует pages → `shared/`, импортирует → `app/`; **Шаг 3** — кросс-импорты между страницами: copy-paste («not architecturally wrong») или в сегмент shared; **Шаг 4** — распаковать Shared (бизнес-код вернётся на свои слои); **Шаг 5** — сегменты по техническому назначению. Опционально: сущности/фичи из Redux-слайсов, чистый UI-фундамент.

### Глава ↔ скилл

- **Согласованы:** группа — навигация, не граница; сред-специфичные точки входа — исключение, не норма; миграция инкрементальна, дублирование в переходный период допустимо.
- **Акценты различаются**: глава (Overview) даёт стратегию в три шага; скилл (official from-custom guide) разворачивает её в конкретный порядок с staging-приёмом («бизнес-код временно в shared, шаг 4 вытягивает обратно»).
- **Скилл добавляет:** «avoid switching to FSD against the will of teammates»; проверку мотивации (три сигнала: новичкам тяжело, правки ломают чужое, контекст не влезает в голову).

## Итог уровня

- Группы — только навигация: без index, без общего кода, изоляция прежняя; features — с осторожностью.
- Среды: один index по умолчанию; `index.server.ts` — только когда рантайм-граница реальна.
- Миграция: pages first, инкрементально, дублирование временно допустимо, новые большие сущности — не заводить.
