# Динамические воркфлоу для веб-разработчика: практический гайд

## Для кого эта статья

Вы — веб-разработчик (frontend, backend или fullstack). Вы используете Open Code, Kilo Code или аналогичный инструмент с мультиагентной архитектурой. Вы читали о динамических воркфлоу и думаете: "Круто, но как это применить в моей ежедневной работе с React/Vue/Node/Django?"

Этот гайд — 12 конкретных сценариев из жизни веб-разработчика с готовыми подходами, паттернами и примерами промптов.

---

## Сценарий 1. Рефакторинг легаси-компонента

**Контекст.** У вас есть React-компонент на 800 строк, написанный 3 года назад. В нем смешаны логика, UI, запросы к API, сайд-эффекты и 5 уровней вложенности. Нужно разделить на переиспользуемые части.

**Паттерн:** Fan-out-and-Synthesize + Adversarial Verification

**Как строится воркфлоу:**
1. Агент-анализатор читает компонент и выделяет: чистая логика, UI-разметка, сайд-эффекты, запросы к API, вспомогательные функции
2. На основе анализа создаётся план рефакторинга с 5-7 шагами
3. Каждый шаг — отдельный субагент в своём контексте:
   - Агент-логика: выносит бизнес-логику в custom hooks
   - Агент-API: создаёт слой API-клиента
   - Агент-UI: разбивает UI на подкомпоненты
   - Агент-типы: выносит TypeScript-типы
   - Агент-тесты: пишет тесты на каждый новый модуль
4. Агент-верификатор проверяет: не потерялась ли функциональность, корректны ли типы, проходят ли тесты
5. Агент-синтезатор собирает всё воедино, обновляет импорты

**Пример промпта:**
```
Вот компонент UserDashboard.tsx (800 строк). Он смешивает логику фильтрации, 
запросы к API, рендеринг таблицы и модальных окон. 

Создай воркфлоу с Fan-out-and-Synthesize:
1. Агент-анализатор: выдели зоны ответственности
2. Параллельно запусти агентов:
   - useUserFilters hook (логика фильтрации)
   - useUserData hook (запросы к API + кэширование)
   - UserTable компонент (таблица)
   - UserModal компонент (модальное окно)
   - user.types.ts (все TypeScript типы)
3. Агент-верификатор: убедись, что публичный API компонента не изменился
4. Агент-тестов: напиши unit-тесты на каждый новый модуль
5. Собери финальный результат

Бюджет: 30 000 токенов. Запрещено менять поведение — только структура.
```

**Реальный кейс.**
> *Разработчик в e-commerce проекте столкнулся с компонентом ProductCard на 650 строк. В нём были: логика выбора вариантов товара, расчёт скидок, отображение галереи, добавление в корзину, отзывы. После рефакторинга через воркфлоу получилось 7 файлов, средний размер — 90 строк. Время на добавление новой фичи (видео-обзор товара) сократилось с 2 дней до 2 часов, потому что новый компонент VideoReview встраивался в чистый ProductCard за 20 минут.*

## Сценарий 2. Самостоятельное код-ревью

**Контекст.** Вы работаете в команде из 2-3 человек (или одни), PR висят по 2-3 дня без ревью. Или вы фрилансер и у вас нет коллеги для ревью. Нужно качественно проверить свой код перед merge.

**Паттерн:** Adversarial Verification + Classify-and-Act

**Как строится воркфлоу:**
1. Агент-классификатор определяет тип изменений (новая фича / багфикс / рефакторинг / депенденси)
2. В зависимости от типа — разные верификаторы:
   - Агент-безопасности: SQL-инъекции, XSS, утечки токенов, небезопасные зависимости
   - Агент-производительности: лишние ререндеры, N+1 запросы, тяжёлые вычисления в главном потоке
   - Агент-архитектуры: нарушение слоёв, циклические зависимости, дублирование
   - Агент-UX: обработка ошибок, состояния загрузки, edge cases
3. Каждый верификатор работает изолированно и выдаёт findings
4. Агент-рецензент синтезирует findings в структурированный отчёт PR

**Пример промпта:**
```
Вот мой PR: добавление функции экспорта отчётов в PDF (15 файлов, +420 -89 строк).
Мне нужно качественное ревью, но коллега в отпуске.

Создай воркфлоу код-ревью с Adversarial Verification:
1. Агент-классификатор: определи тип изменений
2. Запусти 4 верификатора параллельно:
   - Безопасность: проверь обработку пользовательского ввода, 
     защиту от XSS в сгенерированном PDF, доступ к файлам
   - Производительность: проверь, не блокируется ли UI при генерации PDF,
     используется ли Web Worker, размер генерируемых файлов
   - Архитектура: проверь, не нарушает ли новый код слоистую структуру,
     нет ли дублирования с существующим экспортом в CSV
   - Надёжность: проверь обработку ошибок (генерация падает? память переполняется?),
     что при больших данных (>10 000 строк)
3. Каждый верификатор должен найти минимум 1 проблему 
   (даже если это false positive — лучше перестраховаться)
4. Собери findings в markdown-отчёт с severity (Critical / Warning / Info)
```

**Реальный кейс.**
> *Фрилансер разработал форму загрузки документов для юридической платформы. Перед сдачей клиенту запустил воркфлоу ревью. Агент-безопасности нашёл: имя загружаемого файла использовалось напрямую в пути сохранения без sanitize — потенциальная Path Traversal уязвимость. Агент-производительности нашёл: загрузка 50+ файлов одновременно создавала 50 параллельных запросов без очереди. Оба findings исправлены до продакшена. Клиент провёл аудит через 2 месяца — уязвимостей не обнаружено.*

## Сценарий 3. Выбор технологии или архитектурного решения

**Контекст.** Нужно выбрать: Zustand или Redux Toolkit? REST или GraphQL? SSR или CSR? Tailwind или CSS Modules? Один человек не может глубоко знать все варианты.

**Паттерн:** Tournament

**Как строится воркфлоу:**
1. N агентов-адвокатов, каждый защищает один вариант
2. Попарные дебаты: агенты критикуют соперника, защищают свой вариант
3. Агент-судья с рубрикой (критерии проекта) определяет победителя
4. Финальный агент пишет ADR (Architecture Decision Record)

**Пример промпта:**
```
Мы выбираем state-менеджер для нового React-проекта (маркетплейс, 50+ экранов,
реальное время обновления корзины, сложные фильтры). Варианты: Zustand, Redux Toolkit, 
Jotai, React Context + useReducer.

Создай воркфлоу Tournament:
1. 4 агента-адвоката, каждый готовит аргументацию для своего варианта
2. Попарные матчи (6 матчей). В каждом матче агенты критикуют друг друга
3. Агент-судья оценивает по рубрике:
   - Производительность при частых обновлениях
   - Время разработки (boilerplate)
   - Отладка (DevTools)
   - Масштабируемость
   - Опыт команды
   - Размер бандла
4. Определи победителя. Если это не Redux Toolkit — объясни, почему.
5. Напиши ADR с обоснованием.
```

**Реальный кейс.**
> *Команда из 4 разработчиков спорила 3 недели о подходе к стилизации нового проекта. Воркфлоу Tournament провёл "битву" Tailwind vs CSS Modules vs Styled Components vs Emotion за 20 минут. Победил Tailwind по совокупности критериев, но судья отметил критическое замечание: при использовании Tailwind нужен strict design token system, иначе будет хаос. Это замечание вошло в Definition of Done. Проект прошёл 8 месяцев без единого спора о стилях.*

## Сценарий 4. Дебаг сложного бага

**Контекст.** Баг воспроизводится только в production, локально не ловится. Или баг плавающий (race condition). Или баг в чужой библиотеке. Нужно систематически проверить гипотезы.

**Паттерн:** Loop until Done + Adversarial Verification

**Как строится воркфлоу:**
1. Агент-логгер анализирует логи ошибок, выделяет ключевые паттерны
2. N агентов-гипотез генерируют независимые объяснения из разных источников (код, логи, конфиг, данные)
3. Каждая гипотеза проверяется агентом-верификатором
4. Неподтверждённые гипотезы отбрасываются, новые генерируются
5. Цикл до подтверждения или исчерпания бюджета

**Пример промпта:**
```
Баг: в production-приложении на Next.js пользователи периодически (раз в 20-30 
перезагрузок) видят пустую страницу вместо каталога товаров. В консоли ошибок нет.
Локально не воспроизводится. Логи показывают, что API-запрос возвращает данные 
корректно, но HTML приходит без контента.

Создай воркфлоу с Loop until Done:
1. Агент-анализатор: проанализируй логи, код страницы, конфиг Next.js, 
   middleware, ISR-настройки
2. Сгенерируй 5 независимых гипотез (каждая из разной области: 
   гонка данных, SSR/hydration, кэширование, middleware, race condition в useEffect)
3. Для каждой гипотезы — агент-верификатор, который ищет доказательства 
   за и против в кодовой базе
4. Если гипотеза не подтверждается — отбрось, сгенерируй новую
5. Условие остановки: найдена гипотеза с confidence > 80% И предложено исправление

Бюджет: 25 000 токенов.
```

**Реальный кейс.**
> *В приложении на Vue 3 иногда (в 5% случаев) пропадала реактивность у поля "количество" в корзине — пользователь менял число, но итоговая сумма не пересчитывалась. Разработчик 2 дня копался в computed properties. Воркфлоу за 40 минут выдало 4 гипотезы, проверило каждую. Победила: при быстром клике "+" несколько раз подряд, события обрабатывались в неправильном порядке из-за отсутствия throttle, и reactivity system Vue терял intermediate state. Исправление: добавление throttle + defensive programming в handler. Баг не воспроизводился с тех пор.*

## Сценарий 5. Написание тестов для легаси-кода

**Контекст.** У вас есть модуль без тестов (или с 15% покрытием). Нужно поднять покрытие до приемлемого уровня, но рукописное создание 100+ тестов — убийство.

**Паттерн:** Fan-out-and-Synthesize

**Как строится воркфлоу:**
1. Агент-анализатор читает код, выделяет публичные функции/методы и edge cases
2. Каждая функция получает своего агента-тестировщика
3. Агенты работают параллельно, каждый пишет тесты на свою функцию
4. Агент-верификатор проверяет: тесты действительно проверяют логику, а не просто вызывают функцию
5. Агент-синтезатор собирает всё в тестовые файлы

**Пример промпта:**
```
Вот модуль cartService.ts (12 функций, 0 тестов). Он отвечает за логику корзины: 
добавление, удаление, изменение количества, применение промокодов, расчёт доставки.

Создай воркфлоу для покрытия тестами:
1. Агент-анализатор: выдели все публичные функции и их edge cases 
   (пустая корзина, отрицательное количество, истёкший промокод, 
   максимальное количество товаров)
2. Для каждой функции — отдельный агент-тестировщик:
   - addToCart: проверка добавления, дублирования, максимума
   - removeFromCart: удаление существующего, несуществующего
   - updateQuantity: валидные/невалидные значения
   - applyPromo: валидный/невалидный/истёкший/применённый повторно
   - calculateShipping: разные зоны, вес, бесплатная доставка
3. Агент-верификатор: убедись, что тесты проверяют поведение, 
   а не просто вызов функции (нет "ожидаю undefined, получаю undefined")
4. Собери в файлы cartService.test.ts

Цель: 80%+ покрытие строк, 100% покрытие ветвлений для критичных функций.
```

**Реальный кейс.**
> *Разработчик унаследовал модуль валидации форм с 23 функциями и 0 тестов. Баги в валидации приводили к некорректным данным в БД. Воркфлоу сгенерировал 147 тестов за 25 минут. Агент-верификатор отклонил 23 теста как "smoke-тесты без проверки" — они были переписаны. Итог: 124 качественных теста, 87% покрытие. При последующем рефакторинге 2 бага пойманы тестами до попадания в staging.*

## Сценарий 6. Интеграция с внешним API

**Контекст.** Нужно интегрироваться с новым API (платёжка, доставка, CRM). Документация неполная, есть песочница. Нужно построить надёжный клиент с обработкой ошибок.

**Паттерн:** Generate-and-Filter + Adversarial Verification

**Как строится воркфлоу:**
1. Агент-исследователь изучает документацию API, выделяет endpoints, форматы, ошибки
2. N агентов-генераторов создают разные подходы к клиенту (fetch-обёртка, generated client, adapter pattern)
3. Агент-верификатор проверяет каждый подход: обработка ошибок, типизация, тестируемость
4. Агент-судья выбирает лучший
5. Агент-реализации пишет финальный код + тесты

**Пример промпта:**
```
Нужно интегрировать платёжный шлюз Stripe для подписок (создание, обновление, 
отмена, обработка вебхуков). Документация: https://stripe.com/docs/api.

Создай воркфлоу:
1. Агент-исследователь: проанализируй документацию, выдели:
   - Необходимые endpoints
   - Обязательные/опциональные поля
   - Возможные ошибки и коды
   - Требования к вебхукам (подпись, идемпотентность)
2. 3 агента-генератора, каждый предлагает архитектуру клиента:
   - Вариант A: прямой REST-клиент
   - Вариант B: обёртка над stripe-node SDK
   - Вариант C: адаптер с абстракцией PaymentProvider 
     (для возможности смены провайдера)
3. Агент-верификатор проверяет каждый вариант на:
   - Обработку сетевых ошибок и retry
   - Безопасность (не логируем API-ключи, не возвращаем клиенту)
   - Тестируемость (можно замокать)
   - Graceful degradation
4. Выбери лучший вариант, реализуй с типизацией и тестами
5. Напиши документацию для команды по использованию клиента
```

**Реальный кейс.**
> *Стартап интегрировал 3 провайдера доставки (СДЭК, Boxberry, Почта России). Для каждого — разный API, формат адресов, коды ошибок. Воркфлоу создало абстракцию DeliveryProvider с единым интерфейсом. Каждый провайдер — отдельный агент. Агент-верификатор проверил: что при отказе одного провайдера система переключается на другой (fallback). Результат: добавление 4-го провайдера (DPD) заняло 2 часа вместо 2 недель — достаточно было реализовать интерфейс DeliveryProvider.*

## Сценарий 7. Миграция между фреймворками или версиями

**Контекст.** Нужно мигрировать: React 17 → 18, Vue 2 → 3, Next.js 12 → 14, Webpack → Vite. Вручную — недели работы.

**Паттерн:** Fan-out-and-Synthesize + Loop until done

**Как строится воркфлоу:**
1. Агент-аудитор анализирует кодовую базу, выявляет breaking changes
2. Создаётся план миграции с приоритетами
3. Каждый breaking change — отдельный агент-мигратор
4. Агент-тестировщик проверяет каждое изменение
5. Цикл: тесты проходят? → да, следующий. Нет → агент-фиксер исправляет.

**Пример промпта:**
```
Мигрируем проект с React 17 на React 18. Кодовая база: 120 компонентов, 
15 custom hooks, используется React Router v5, формы на Formik.

Создай воркфлоу миграции:
1. Агент-аудитор: проанализируй кодовую базу, найди:
   - Использование ReactDOM.render (deprecated)
   - React.PropTypes (если есть)
   - Прямое манипулирование DOM
   - Компоненты, которые могут сломаться из-за Strict Mode
   - Зависимости, несовместимые с React 18
2. Составь приоритизированный план миграции
3. Каждый пункт плана — отдельный агент-мигратор в worktree
4. После каждого изменения — запуск тестов
5. Если тесты падают — агент-фиксер анализирует и исправляет
6. Условие остановки: все breaking changes устранены И тесты проходят
```

**Реальный кейс.**
> *Команда мигрировала проект с CRA (Create React App) на Vite. 340 файлов, куча импортов с абсолютными путями, SVG-импорты как ReactComponent, env-переменные. Воркфлоу разбил миграцию на 8 шагов. Каждый шаг — отдельный агент. При миграции SVG выяснилось, что 12 компонентов использовали deprecated синтаксис — агент-фиксер адаптировал их. Полная миграция заняла 3 часа вместо оцененных 3 дней. Результат: время сборки сократилось с 45 секунд до 2.3 секунды.*

## Сценарий 8. Оптимизация производительности

**Контекст.** Lighthouse показывает 45/100. Страница грузится 4.5 секунды. Нужно систематически найти и устранить bottleneck'ы.

**Паттерн:** Classify-and-Act + Fan-out

**Как строится воркфлоу:**
1. Агент-аудитор анализирует метрики (Lighthouse, Web Vitals, профайлер)
2. Классифицирует проблемы по категориям (загрузка, рендеринг, JS, сеть)
3. Каждая категория — свой агент-оптимизатор
4. Агент-верификатор проверяет: оптимизация не сломала функциональность

**Пример промпта:**
```
Вот отчёт Lighthouse для нашего лендинга: FCP 3.2s, LCP 4.8s, TTI 6.1s, 
CLS 0.25. Исходный код проекта во вложении.

Создай воркфлоу оптимизации:
1. Агент-анализатор: изучи отчёт и код, определи основные bottleneck'ы:
   - Блокирующие ресурсы
   - Неоптимальные изображения
   - Лишний JavaScript
   - Проблемы рендеринга
   - Медленные API-запросы
2. Для каждой категории — агент-оптимизатор с конкретными шагами:
   - Оптимизация изображений (WebP, lazy loading, responsive)
   - Разбиение бандла (code splitting, dynamic imports)
   - Оптимизация шрифтов (preload, font-display)
   - Ускорение API (кэширование, параллелизация)
3. Агент-верификатор: после каждой оптимизации проверь, 
   что функциональность не сломана
4. Целевые метрики: FCP < 1.8s, LCP < 2.5s, CLS < 0.1
```

**Реальный кейс.**
> *E-commerce лендинг грузился 5.2 секунды. Воркфлоу выявило 7 проблем: неоптимизированные PNG (2.1 MB), render-blocking CSS, синхронная загрузка 3 шрифтов, тяжёлый JS-бандл (1.8 MB), 4 последовательных API-запроса. 4 агента-оптимизатора работали параллельно. Результат: страница стала грузиться за 1.4 секунды. Конверсия выросла на 12% (по данным A/B теста за 2 недели).*

## Сценарий 9. Создание документации

**Контекст.** Проект живёт 2 года, документации нет. Новый разработчик приходит и теряется на 2 недели. Нужно создать: README, API-документацию, гайд по архитектуре.

**Паттерн:** Fan-out-and-Synthesize

**Как строится воркфлоу:**
1. Агент-исследователь изучает кодовую базу, выделяет модули, зависимости, архитектуру
2. N параллельных агентов-писателей:
   - README (установка, запуск, структура)
   - Архитектурный гайд (диаграммы, потоки данных)
   - API-документация (endpoints, типы, примеры)
   - Гайд для новичка (первые шаги, где что лежит)
3. Агент-верификатор проверяет: актуальность, полноту, корректность примеров
4. Агент-синтезатор собирает единую документацию

**Пример промпта:**
```
Нужно создать документацию для проекта (React + Node.js, 8 месяцев разработки, 
12 разработчиков, 200+ компонентов, 40 API endpoints). Сейчас документации почти нет.

Создай воркфлоу:
1. Агент-исследователь: проанализируй структуру проекта:
   - Архитектура (monorepo? layers?)
   - Ключевые модули и их ответственность
   - Технический стек и версии
   - Переменные окружения
   - CI/CD pipeline
2. Параллельно запусти 4 агента-писателя:
   - README.md: установка, запуск, переменные окружения, скрипты
   - ARCHITECTURE.md: слои, потоки данных, ключевые решения
   - API.md: все endpoints с примерами запросов/ответов
   - ONBOARDING.md: первый день разработчика, где что лежит, 
     как добавить фичу от идеи до деплоя
3. Агент-верификатор: проверь, что примеры кода актуальны 
   (можно скопировать и запустить), что нет устаревших путей
4. Собери финальную документацию
```

**Реальный кейс.**
> *Команда из 6 разработчиков 1.5 года работала над проектом без документации. При уходе ключевого разработчика часть knowledge утратилась. Воркфлоу за 3 часа создало полную документацию: README, ARCHITECTURE с диаграммами, API docs с curl-примерами, ONBOARDING гайд. Агент-верификатор нашёл 7 неточностей (переименованные endpoints, устаревшие env-переменные). Новый разработчик вышел на полную продуктивность за 3 дня вместо 2 недель.*

## Сценарий 10. Разработка новой фичи от ТЗ до PR

**Контекст.** Product manager прислал ТЗ на новую фичу. Нужно: понять ТЗ, спроектировать решение, написать код, тесты, документацию.

**Паттерн:** Полная оркестрация — Classify + Fan-out + Adversarial

**Как строится воркфлоу:**
1. Агент-аналитик читает ТЗ, задаёт уточняющие вопросы (AskUserQuestion), выделяет требования
2. Агент-архитектор проектирует решение (схема данных, API, компоненты)
3. N агентов-разработчиков пишут код параллельно (backend, frontend, types, API)
4. Агент-тестировщик пишет тесты
5. Агент-верификатор проверяет соответствие ТЗ
6. Агент-ревьюер проводит код-ревью

**Пример промпта:**
```
ТЗ: "Добавить систему уведомлений в личном кабинете. Пользователь может 
видеть уведомления о заказах, акциях, системные. Уведомления должны быть 
помечены как прочитанные. Должна быть бейдж с количеством непрочитанных 
на иконке колокольчика. Push-уведомления не нужны — только внутри приложения."

Создай полное воркфлоу разработки фичи:
1. Агент-аналитик: проанализируй ТЗ, задай мне 3-5 уточняющих вопросов 
   через AskUserQuestion (например: сколько уведомлений хранить? 
   есть ли приоритеты? нужна ли фильтрация?)
2. Агент-архитектор: спроектируй решение:
   - API endpoints (GET /notifications, PATCH /notifications/:id/read, 
     DELETE /notifications/:id)
   - Модель данных (Notification: id, type, title, message, read, createdAt)
   - React-компоненты (NotificationBell, NotificationList, NotificationItem)
   - State management
3. Параллельная разработка:
   - Агент-backend: реализуй API + миграции БД
   - Агент-frontend: реализуй компоненты UI
   - Агент-types: определи все TypeScript интерфейсы
4. Агент-тестировщик: unit + integration тесты
5. Агент-верификатор: проверь соответствие ТЗ (все ли требования реализованы?)
6. Собери финальный PR с описанием
```

**Реальный кейс.**
> *Разработчик получил ТЗ на "систему купонов и скидок" для маркетплейса. Вместо последовательной разработки запустил воркфлоу. Агент-аналитик задал 4 уточняющих вопроса (stackable coupons? expiration? minimum order?), которые сам разработчик не подумал задать PM — ответы изменили архитектуру. 3 агента разработчика работали параллельно. Верификатор нашёл, что ТЗ требовало "историю применённых купонов" — пункт, который разработчик пропустил бы. Фича была реализована за 1.5 дня вместо оцененных 4, с полным покрытием тестами и документацией.*

## Сценарий 11. Разбор технического долга

**Контекст.** В проекте накопился технический долг: deprecated зависимости, warning'и в консоли, TODO-комментарии, неконсистентные паттерны. Нужно систематически всё это разобрать.

**Паттерн:** Classify-and-Act + Loop until done

**Как строится воркфлоу:**
1. Агент-аудитор сканирует кодовую базу, классифицирует долг по категориям
2. Каждая категория — свой агент-фиксер
3. Цикл: фикс → проверка → следующий

**Пример промпта:**
```
Проанализируй нашу кодовую базу на технический долг. Вот что я вижу: 
warning'и в консоли, 47 TODO-комментариев, deprecated зависимости, 
console.log в production-коде.

Создай воркфлоу:
1. Агент-аудитор: просканируй код, классифицируй долг:
   - Security (hardcoded secrets, устаревшие пакеты с уязвимостями)
   - Производительность (ненужные ререндеры, тяжёлые импорты)
   - Качество кода (дублирование, мёртвый код, console.log)
   - Зависимости (deprecated, outdated, unused)
   - Техдолг в комментариях (TODO, FIXME, HACK)
2. Для каждой категории — приоритизированный список
3. Агент-фиксер: начни с Critical (security), затем High, затем Medium
4. После каждого фикса — проверка, что ничего не сломалось
5. Условие остановки: все Critical и High исправлены
```

**Реальный кейс.**
> *Разработчик запустил воркфлоу аудита на проекте, который 2 года не обновлял зависимости. Аудит выявил: 3 критические уязвимости (в lodash, axios, webpack-dev-server), 12 deprecated пакетов, 34 console.log, 156 неиспользуемых импортов. Воркфлоу за 2 часа исправило всё критичное и высокоприоритетное. Проект обновлён, warning'и исчезли, security audit проходит чисто.*

## Сценарий 12. Создание дизайн-системы

**Контекст.** Проект разрастается, компоненты копируются с изменениями, нет единообразия. Нужно создать базовую дизайн-систему: типографика, цвета, кнопки, инпуты, карточки.

**Паттерн:** Generate-and-Filter + Fan-out

**Как строится воркфлоу:**
1. Агент-исследователь анализирует существующие компоненты, выделяет паттерны
2. Агент-дизайнер создаёт дизайн-токены (цвета, шрифты, отступы, скругления)
3. N агентов-разработчиков создают базовые компоненты параллельно
4. Агент-верификатор проверяет: accessibility, responsive, consistency
5. Агент-писатель создаёт Storybook/документацию

**Пример промпта:**
```
Нужно создать базовую дизайн-систему для нашего React-проекта. 
Сейчас у нас 15 разных вариантов кнопок, 8 вариантов инпутов, 
нет единой типографики.

Создай воркфлоу:
1. Агент-исследователь: проанализируй существующие компоненты, 
   выдели паттерны (какие цвета чаще всего? какие размеры? 
   какие состояния: hover, disabled, loading?)
2. Агент-дизайнер: создай дизайн-токены:
   - Цвета (primary, secondary, success, warning, error + оттенки)
   - Типографика (заголовки, body, caption, font sizes, weights)
   - Отступы (scale: 4, 8, 12, 16, 24, 32, 48)
   - Скругления, тени
3. Параллельно создай компоненты:
   - Button (variants: primary, secondary, ghost, sizes: sm/md/lg, states)
   - Input (variants, sizes, states, icon support)
   - Card (variants, padding options)
   - Typography (Text, Heading компоненты)
   - Stack (Flexbox-обёртка для отступов)
4. Агент-верификатор: проверь:
   - Accessibility (contrast ratio, focus states, aria-labels)
   - Responsive behavior
   - Консистентность с существующим UI
5. Создай Storybook stories для каждого компонента
6. Напиши гайд: "Как добавить новый компонент в дизайн-систему"
```

**Реальный кейс.**
> *Команда из 4 разработчиков тратила 30% времени на согласование UI — каждый делал компоненты по-своему. Воркфлоу создало дизайн-систему с 12 базовыми компонентами за 1 день. Агент-верификатор отметил, что primary color не проходил WCAG contrast для текста на кнопке — цвет был скорректирован. Через 3 месяца: время на UI-разработку сократилось на 40%, количество багов "не так выглядит" снизилось на 80%.*

## Краткая шпаргалка: какой паттерн когда использовать

| Твоя задача | Паттерн | Пример промпта-ключа |
|-------------|---------|---------------------|
| Рефакторинг большого компонента | Fan-out + Adversarial | "Разбей на части, параллельно обработай, верифицируй" |
| Код-ревью без коллеги | Adversarial Verification | "Запусти 3-4 верификатора с разными фокусами" |
| Выбор технологии | Tournament | "Сделай Tournament между вариантами A, B, C" |
| Плавающий баг | Loop until Done | "Генерируй гипотезы, проверяй, цикл до подтверждения" |
| Написание тестов | Fan-out | "Каждая функция — свой агент-тестировщик" |
| Интеграция с API | Generate-and-Filter | "Сгенерируй 3 подхода, отфильтруй лучший" |
| Миграция версий | Fan-out + Loop | "По шагам, каждый в worktree, цикл до прохождения тестов" |
| Оптимизация | Classify + Fan-out | "Классифицируй проблемы, оптимизируй параллельно" |
| Документация | Fan-out + Synthesize | "Параллельно пиши разделы, собери в единый документ" |
| Новая фича от ТЗ | Полная оркестрация | "От анализа ТЗ до PR с тестами" |
| Техдолг | Classify + Loop | "Аудит, классификация, фикс по приоритетам" |
| Дизайн-система | Generate-and-Filter + Fan-out | "Токены + компоненты параллельно + верификация" |

## Как начать прямо сегодня

### Шаг 1. Выбери одну задачу
Возьми ту задачу, которую ты сейчас откладываешь, потому что она "большая и сложная". Рефакторинг легаси-компонента? Написание тестов? Миграция? Это идеальный кандидат.

### Шаг 2. Определи паттерн
Используй шпаргалку выше. Не усложняй — начни с одного паттерна.

### Шаг 3. Напиши промпт
Будь конкретен: укажи бюджет токенов, ограничения ("не меняй поведение"), ожидаемый результат.

### Шаг 4. Запусти и наблюдай
Первые 2-3 запуска будут обучением — ты поймёшь, как твой инструмент (Open Code / Kilo Code) интерпретирует воркфлоу. Корректируй промпты.

### Шаг 5. Сохраняй шаблоны
Удачные воркфлоу сохраняй в `~/.claude/workflows` или эквивалент. Со временем у тебя будет библиотека из 10-15 шаблонов под типовые задачи.
