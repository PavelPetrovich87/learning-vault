## 0. Зачем эта глава (мостик фронтенд → бэкенд)

Браузерный event loop и серверный — две разные инженерные истории. В браузере «тяжёлая» задача — это, в худшем случае, синхронный пересчёт вьюхи на пару сотен миллисекунд: подтормаживает UI, пользователь замечает. На сервере синхронная задача на 500 мс блокирует **одновременно тысячи соединений** — и не «подтормаживает», а роняет сервис под нагрузкой.

Три вопроса главы:

1. **Почему** Node спроектирован именно так — single thread + non-blocking I/O + reactor pattern ([НД] гл.1).
2. **Как** устроен event loop изнутри — фазы, микрозадачи, `nextTick` (Node docs).
3. **Где** Node «душится» под нагрузкой — CPU-bound, исчерпание thread pool, callback-queue — и что с этим делать ([НД] гл.11).

## 1. 🟢 Философия платформы — «the Node way»

> Источник: [НД] Chapter 1, «The Node.js philosophy» (стр. 2–6).

Четыре столпа.

### 1.1. Small core
Ядро Node (рантайм + встроенные модули) держат минимальным, оставляя большую часть функциональности userland'у. Малое ядро легче поддерживать и стимулирует инновации вне ядра. В последние годы принцип стал **менее строгим** [НД, стр. 3]: в ядро добавили WebSockets, unit-test фреймворк, Web Fetch API и др.

### 1.2. Small modules
Принцип проектирования **маленьких модулей** — речь не только о размере, но об **узости scope**. Восходит к Unix-философии: «Small is beautiful», «Make each program do one thing well». Совместно с npm это решает «dependency hell»: если `depA` и `depB` зависят от разных версий `depC`, каждый получает свою копию в `node_modules/depA/node_modules/depC@1.0.0` и `node_modules/depB/node_modules/depC@2.0.0` — конфликта нет.

> ⚠️ **Supply-chain привязка.** Рост атак на цепочку поставок ПО заставил индустрию осторожнее относиться к сторонним зависимостям [НД, стр. 5]. Важно оценивать, поддерживается ли модуль и действительно ли он нужен. Подробнее — модуль 3 (security) и модуль 5 (agentic SDLC).

### 1.3. Small surface area
Желательное свойство модуля — **минимальная открытая поверхность API**. Распространённый паттерн — экспортировать одну сущность (функцию или класс). Многие Node-модули проектируются **для использования, а не для расширения**.

### 1.4. Simplicity and pragmatism
Опирается на KISS и «worse is better» (Richard P. Gabriel):

> «The design must be simple, both in implementation and interface. It is more important for the implementation to be simple than the interface. Simplicity is the most important consideration in a design.» [в [НД], стр. 5–6]

В Node это поддерживается прагматичной природой JavaScript: вместо сложных классовых иерархий — простые классы, функции, замыкания.

## 2. 🟢 I/O — главное «бутылочное горло»

> Источник: [НД] Chapter 1, «I/O is often the bottleneck» (стр. 7).

**I/O — самая медленная из фундаментальных операций компьютера** [НД, стр. 7].

| Операция | Порядок времени |
|---|---|
| Доступ к RAM | наносекунды (10⁻⁹ с) |
| Доступ к диску / сети | миллисекунды (10⁻³ с) |

Разница — **шесть порядков**. I/O обычно не дорог по CPU, но добавляет **задержку** между запросом к устройству и завершением операции.

Веб-сервер — почти целиком I/O: принять соединение, прочитать запрос, сходить в БД, дёрнуть сторонний API, отдать ответ. Если на каждый запрос выделять поток и блокировать его на каждом I/O — ресурсы расходуются впустую (потоки дорогие по памяти и context switch'ам). Это и мотивирует всю архитектуру Node.

## 3. 🟢 Blocking → non-blocking → busy-waiting

> Источник: [НД] Chapter 1, «Blocking I/O» / «Non-blocking I/O» (стр. 7–9).

### 3.1. Blocking I/O
Вызов, соответствующий I/O-запросу, **блокирует выполнение потока до завершения операции** [НД, стр. 7]:

```text
// blocks the thread until the data is available
data = socket.read()
// data is available
print(data)
```

Веб-сервер на blocking I/O **не способен обрабатывать несколько соединений в одном потоке**. Традиционное решение — отдельный поток/процесс на каждое соединение. Проблема: **поток дорог** [НД, стр. 8] — память и context switch'и.

### 3.2. Non-blocking I/O + busy-waiting
Современные ОС поддерживают **non-blocking I/O**: системный вызов всегда возвращается немедленно; если данных нет — код ошибки `EAGAIN`. Простое (и плохое) решение — **busy-waiting** [НД, стр. 9]:

```text
resources = [socketA, socketB, fileA]
while (!resources.isEmpty()) {
    for (resource of resources) {
        data = resource.read()
        if (data === NO_DATA_AVAILABLE) continue
        if (data === RESOURCE_CLOSED) resources.remove(i)
        else consumeData(data)
    }
}
```

Цикл сжигает CPU-циклы, итерируясь по ресурсам, которые большую часть времени недоступны.

## 4. 🟢 Event demultiplexer → Reactor pattern

> Источник: [НД] Chapter 1, «Event demultiplexing» / «The reactor pattern» (стр. 9–13).

### 4.1. Event demultiplexing
Современные ОС дают **нативный механизм** — **синхронный event demultiplexer** (он же «event notification interface»). Он наблюдает за несколькими ресурсами и генерирует событие, когда операция завершается. Преимущество: **demultiplexer блокируется, пока не появятся новые события** [НД, стр. 10].

Псевдокод из книги:

```text
watchList.add(socketA, FOR_READ)        // 1
watchList.add(fileB, FOR_READ)
while (events = demultiplexer.watch(watchList)) {  // 2 — event loop
    for (event of events) {              // 3
        data = event.resource.read()
        if (data === RESOURCE_CLOSED) demultiplexer.unwatch(event.resource)
        else consumeData(data)
    }
}
```

`demultiplexer.watch()` **синхронен и блокирует**, пока любой ресурс не станет готов. Когда это происходит — возвращает набор событий. Каждый возвращенный event обработается; ресурс гарантированно готов и не блокируется. Когда все события обработаны — поток снова блокируется. Это и есть **event loop**.

Несколько I/O-операций обрабатываются **в одном потоке**, без busy-waiting. Бонус: отсутствие in-process race conditions и синхронизации потоков.

### 4.2. Reactor pattern
**Reactor pattern** — вариация вышеописанного, и именно его использует Node.js [НД, стр. 11]. Главная идея: с каждой I/O-операцией связан **handler**. В Node.js handler — это callback-функция (cb).

![[1-1-reactor-pattern.drawio]]

Что происходит в приложении по reactor pattern [НД, стр. 12–13]:

1. Приложение инициирует I/O-операцию, отправляя запрос в Event Demultiplexer, и указывает handler. Отправка — **non-blocking call**.
2. Когда I/O-операции завершаются, Demultiplexer помещает события в **Event Queue**.
3. Event Loop итерирует по Event Queue.
4. Для каждого события вызывается связанный handler.
5. Handler возвращает управление Loop по завершении (5a); во время выполнения может запросить новые асинхронные операции (5b) → новые элементы в Demultiplexer.
6. Когда все элементы Event Queue обработаны, Loop снова блокируется на Demultiplexer.

> **Когда Node-процесс завершается?** Event loop видит, что не осталось незавершённых операций или событий, и процесс выходит [НД, стр. 13]. Активные handles/requests (таймеры, открытые сокеты, fs-операции) держат loop живым.

Книжное определение: reactor pattern **обрабатывает I/O, блокируясь до появления новых событий от наблюдаемых ресурсов, и реагирует, диспетчеризуя каждое событие связанному handler'у** [НД, стр. 14].

## 5. 🟢 libuv и полный рецепт Node

> Источник: [НД] Chapter 1, «libuv, the I/O engine of Node.js» / «The complete recipe for Node.js» (стр. 13–15).

### 5.1. libuv
У каждой ОС свой интерфейс event demultiplexer: **epoll на Linux, kqueue на macOS, IOCP на Windows** [НД, стр. 13]. Поверх — разные типы ресурсов ведут себя по-разному даже в одной ОС: в Unix обычные файлы файловой системы **не поддерживают** non-blocking-операции — чтобы симулировать non-blocking, нужен отдельный поток вне event loop.

Все эти несоответствия потребовали **более высокую абстракцию**. Core-команда Node создала нативную (C) библиотеку **libuv**:

1. сделать Node совместимым со всеми основными ОС;
2. нормализовать non-blocking-поведение разных типов ресурсов.

libuv — низкоуровневый I/O-движок Node, **вероятно, важнейший компонент, на котором Node построен** [НД, стр. 14]. Две его роли:

1. **Абстрагирует системные вызовы** (epoll/kqueue/IOCP) → единый API.
2. **Реализует reactor pattern** + содержит **thread pool** 🟡 (для операций, которые нельзя сделать через event demultiplexer — см. §6.3).

### 5.2. Полный рецепт Node
К reactor pattern и libuv нужны ещё **три ингредиента** [НД, стр. 14]:

- **Bindings (C++)** — обвязка, оборачивающая libuv и другие низкоуровневые возможности и экспортирующая их в JavaScript.
- **V8** — JavaScript-движок от Google (изначально для Chrome). Один из источников скорости Node.
- **Core JavaScript library** — высокоуровневый Node.js API (`fs`, `http`, `crypto`, `net`, `stream`...).

![[1-1-node-stack.drawio]]

**Путь запроса через стек:** JS-код (`fs.readFile(...)`) → Core JS library → Bindings (C++) → libuv → epoll/kqueue/IOCP или thread pool → событие в event queue → loop диспетчеризует → bindings → core → callback в V8 на main thread.

## 6. 🟡 Event loop под нагрузкой: фазы и микрозадачи

> Источник: 🟡 Node.js official docs — «Event loop, timers, and process.nextTick».

### 6.1. Фазы event loop
Event loop — цикл из **шести фаз**. Каждая фаза имеет FIFO-очередь колбэков; Node выполняет все колбэки текущей фазы (или до лимита) и переходит к следующей:

| # | Фаза | Что выполняется |
|---|---|---|
| 1 | **timers** | Колбэки `setTimeout()` / `setInterval()` |
| 2 | **pending callbacks** | I/O-колбэки, отложенные на следующую итерацию (некоторые TCP-ошибки типа `ECONNREFUSED`) |
| 3 | **idle, prepare** | Только внутренне |
| 4 | **poll** | Получение новых I/O-событий и выполнение I/O-колбэков. Здесь Node блокируется, ожидая соединений/данных, когда уместно |
| 5 | **check** | Колбэки `setImmediate()`, сразу после poll |
| 6 | **close callbacks** | close-колбэки (`socket.on('close', ...)` и др.) |

![[1-1-event-loop-phases.drawio]]

Между запусками event loop Node проверяет, есть ли ожидающие асинхронные I/O или таймеры; если нет — процесс завершается чисто.

### 6.2. `process.nextTick` и микрозадачи (Promise)

**`process.nextTick()`** — «технически не часть event loop» (Node docs). Использует **nextTickQueue**, которая обрабатывается **после завершения текущей операции, независимо от текущей фазы**. Все переданные колбэки выполняются **прежде, чем event loop перейдёт к следующей фазе**.

**Опасность I/O starvation.** Поскольку nextTick прерывает естественный ход event loop, рекурсивные `process.nextTick()` позволяют **«голодать» I/O**: loop никогда не дойдёт до фазы poll, потому что nextTick-очередь не пустеет.

```javascript
let bar = null
function someAsyncApiCall(callback) { process.nextTick(callback) }
someAsyncApiCall(() => { console.log('bar', bar) })  // bar 1
bar = 1
```

**Микрозадачи (Promise)** выполняются после завершения синхронных операций текущей фазы, до перехода к следующей. Но **nextTickQueue имеет приоритет над очередью промисов** — сначала drain'ятся все nextTick, потом все микрозадачи промисов, потом фаза меняется.

> **`process.nextTick()` vs `setImmediate()` — самая злополучная путаница в именах Node** (Node docs):
> - `process.nextTick()` — срабатывает немедленно в той же фазе (до продолжения loop);
> - `setImmediate()` — срабатывает в следующей итерации event loop, в фазе check.
>
> Node docs рекомендует в большинстве случаев `setImmediate()`, потому что его проще рассуждать и он не несёт риска starvation I/O.

**Порядок выполнения (вне I/O-колбэка):**

```javascript
console.log('1')
setTimeout(()   => console.log('2'), 0)
process.nextTick(() => console.log('3'))
console.log('4')
Promise.resolve().then(() => console.log('5'))
// Вывод: 1, 4, 3, 5, 2
```

`setTimeout(cb, 0)` и `setImmediate()` — порядок **не детерминирован** в простом скрипте (зависит от производительности процесса при старте), но **гарантирован** внутри I/O-колбэка: `setImmediate` всегда первым (фаза check идёт сразу после poll).

### 6.3. 🟡 libuv thread pool — где появляются «фоновые» потоки

> Источник: 🟡 libuv design doc → «Thread pool work scheduling» + Node docs.

Пока что может показаться, что Node «однопоточный» целиком. Это верно для **JavaScript-кода** — он всегда исполняется в одном потоке event loop. Но libuv, помимо event loop, содержит **thread pool** — пул рабочих потоков для операций, которые нельзя сделать через неблокирующий I/O-мультиплексор (epoll/kqueue/IOCP).

**Что по умолчанию идёт в thread pool libuv:**

| API / операция | Идёт в thread pool? | Комментарий |
|---|---|---|
| Большинство `fs.*` (readFile, writeFile, stat...) | ✅ да | В Unix обычные файлы не поддерживают non-blocking |
| `crypto.pbkdf2`, `crypto.scrypt`, CPU-bound crypto | ✅ да | CPU-тяжёлые операции |
| `dns.lookup()` (через `getaddrinfo`) | ✅ да | Синхронный системный резолвер |
| `zlib` (некоторые операции) | ✅ да | CPU-bound компрессия |
| `dns.resolve*` | ❌ нет | Использует c-ares (async), не thread pool |
| Сетевой I/O (TCP/UDP сокеты, HTTP) | ❌ нет | epoll/kqueue/IOCP напрямую |
| Ваш JS-код (любой) | ❌ нет | Только в потоке event loop |

**Параметры пула:**

- Размер по умолчанию — **4 потока**, максимум — **1024**.
- Задаётся `UV_THREADPOOL_SIZE` **до старта Node** (читается один раз при инициализации libuv): `UV_THREADPOOL_SIZE=8 node server.js`. При опечатке в имени Node молча берёт дефолт.

> **Почему это важно под нагрузкой.** 8 параллельных запросов, каждый читает файл: на пуле из 4 потоков четыре чтения идут параллельно, ещё четыре **встанут в очередь** — даже при свободном event loop. Симптом: CPU не загружен, I/O не утилизирован, но latency растёт. Это не «Node тормозит» — это thread pool исчерпан.

## 7. 🟢 JS в Node vs в браузере (мостик)

> Источник: [НД] Chapter 1, «JavaScript in Node.js» (стр. 15–20).

Главное отличие — **среда выполнения** [НД, стр. 15]. В браузере JS запускается в безопасном окружении, ограничивающем доступ к системе. На сервере бэкенд требует доступа к БД, файловой системе, сети — поэтому **Node имеет доступ ко всем сервисам ОС**. Самое заметное отличие: **в Node нет DOM**, нет `window` и `document`.

### 7.1. Run the latest JavaScript with confidence

В браузере код должен работать на разных устройствах и браузерах — отсюда транспилеры и полифиллы. **В Node эти проблемы не стоят** [НД, стр. 15–16]: приложение запускается на известной версии Node; свежие версии несут свежий V8 — можно использовать новейшие ECMAScript-фичи без транспиляции.

> **Оговорка.** Для библиотеки на стороне потребителя — таргетировать **самую старую активную LTS** и указывать `engines` в `package.json`; пакетный менеджер предупредит о несовместимости.

### 7.2. Модульная система

Node с самого начала включал модульную систему. Оригинальная — **CommonJS** (`require`); сегодня есть **ES modules** (`import`), который Node принимает синтаксически, но реализация под капотом отличается от браузерной. Подробнее — глава 1.2.

### 7.3. Полный доступ к ОС

Биндинги к большинству сервисов ОС [НД, стр. 16–17]: `fs`, `net`/`dgram` (TCP/UDP), `http`/`https`, `crypto` (OpenSSL), `v8`, `vm`, `child_process` (другие процессы), глобальный `process` (`process.env`, `process.argv`).

### 7.4. Native code и WebAssembly

Userland-модули с нативным кодом (C/C++/Rust) через Node-API: переиспользование библиотек, низкоуровневый доступ (IoT/роботика), ускорение CPU-тяжёлых участков. Альтернатива — **WebAssembly**.

### 7.5. Node и TypeScript

TS не запускается напрямую — транспилируется. Опции [НД, стр. 18–19]: `tsc`; раннеры `ts-node`/`tsx` (`node --import=tsx example.ts`); **с Node 22.6+** — type stripping: запуск TS-файлов напрямую `node` (только «стираемый» синтаксис, `tsconfig.json` игнорируется). Для TS-разработки под Node — `@types/node`.

## 8. 🟢 CPU-bound под нагрузкой: где Node душится

> Источник: [НД] Chapter 11, «Running CPU-bound tasks» (стр. 516–534). Центральная практическая часть главы.

Асинхронная «дорогая» операция (async `totalSales()`) **не мешает** параллельным запросам — каждый вызов разворачивает стек обратно в event loop [НД, стр. 516]. Но **дорогая синхронная задача** не отдаёт управление до завершения — это **CPU-bound**.

### 8.1. Демо-задача: subset sum

Полный перебор — **O(2ⁿ)**: вход из 20 целых → свыше миллиона комбинаций (1 048 576). Этого хватает, чтобы «удушить» event loop [НД, стр. 516–517].

> ⚠️ **DoS-предупреждение** [НД, стр. 519]: эндпоинт, способный надолго блокировать event loop, — **не только производственная проблема, но и поверхность атаки**. Атакующий дёшево триггерит тяжёлые вычисления → loop блокирован → сервер не отвечает **никому**. Без злого умысла то же происходит под высокой нормальной нагрузкой, если долгие операции не изолированы. Избегать блокировки loop'а — критично для надёжности и безопасности.

### 8.2. Три приёма (по [НД] гл.11)

1. **Interleaving с `setImmediate`** — отдавать управление loop'у после каждого шага (или нескольких). Цена: overhead × шаги; плохо для длинных шагов. ⚠️ `process.nextTick()` **нельзя** — I/O starvation (§6.2).
2. **External processes (`child_process.fork`)** — задача целиком в отдельном процессе: полная скорость без interleaving, несколько CPU, возможен C/Go/Rust. Паттерн **process pool** (держать прогретыми + лимит против DoS). Цена: память и старт.
3. **Worker threads** — потоки внутри главного процесса, каждый со своим V8 и event loop; **меньший memory footprint и быстрый старт**; связь через postMessage/ArrayBuffer/SharedArrayBuffer. Дефолтный выбор для CPU-bound в Node.

### 8.3. 🟢 Для production: готовые библиотеки

Учебные пулы не умеют таймауты/ошибки/отказы. Боевые: **`piscina`** (пул worker threads) и **`workerpool`** (процессы и потоки) [НД, стр. 534]. Если CPU-bound превышает capacity узла — масштабирование на несколько узлов (тема глав 12–13 книги и стретча курса).

> Лестница изоляции CPU-bound целиком — [[1.1 CPU-Bound Ladder]]; диагностика по симптомам — [[1.1 Diagnostics Cheat Sheet]].

## 9. 🟡 Связь со сквозным проектом (`shop-api`)

> Синтез-связка с проектом курса (🟡 — за пределами якоря).

Первая реальная поверхность «Node душится» в проекте:

- **CPU-bound в пути запроса** — синхронный ресайз картинок «на лету»: один тяжёлый запрос замораживает все эндпоинты. Решение §8: пул worker threads (`piscina`).
- **Тяжёлый `JSON.parse`** — большие пейлоады (`POST /orders/bulk`) блокируют loop на всё время парсинга. Mitigation: лимиты тела, потоковый парсинг, вынос.
- **Исчерпание thread pool** — fs + crypto в одном запросе × 8 параллельных → очередь к пулу из 4. Симптом: низкий CPU, низкий I/O, растущая latency.

Карта рисков по всем трём подпроектам — `project/risks-1-1.md`; рабочий стенд блокировки — `project/shop-api/` (сценарий B в `scenario-B.log`). Метрики «как заметить, что loop душится» — глава 4.7.
