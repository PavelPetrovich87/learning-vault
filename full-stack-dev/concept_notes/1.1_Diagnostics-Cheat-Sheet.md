# 1.1 Справочник: диагностика Node под нагрузкой (симптом → диагноз)

> Оперативный справочник по материалу [[1.1 Event loop]]. Использовать при инцидентах и ревью: по симптому из мониторинга найти диагноз и рецепт.

## Главная таблица

| Что видно (мониторинг) | Диагноз | Уровень* | Быстрая проверка | Рецепт |
|---|---|---|---|---|
| Один «тяжёлый» запрос → виснут **все** (health-check молчит) | Синхронный CPU-bound на main thread | 0 | code review: `*Sync`, чистый JS-перебор/парсинг в хендлере | Вынести (см. [[1.1 CPU-Bound Ladder]]) |
| Event loop lag растёт, CPU высокий | Долгие синхронные колбэки на main (CPU-bound, `JSON.parse` больших тел) | 0 | profile: что занимает loop; поиск `parse`/`while`/`for` по большим данным | Лимит тела, потоковый парсинг, worker |
| **Loop lag в норме** (единицы мс), CPU низкий, диск низкий, но latency ×5 | **Исчерпание libuv thread pool** (fs + crypto.pbkdf2 + dns.lookup съели 4 слота) | 2 | посмотреть, что в коде идёт в пул; попробовать `UV_THREADPOOL_SIZE` | Кеш/прекеш, argon2 (свой пул), keep-alive, разумный пул-сайз |
| CPU низкий, диск **утилизирован полностью** | Само I/O — узкое место (диск), пул не виноват | — | метрики диска | Больше пул не поможет; кеш, меньше чтений, другой носитель |
| Сервер «лагает рывками» (периодические микрофризы) | Interleaving с **большими кусками** (уровень 1) | 1 | размер шага в `setImmediate`-цикле | Мельчить шаги или уйти на уровень 2–3 |
| Loop lag в норме, CPU в норме, но ответы **конкретного** эндпоинта медленные | Клиент сам ждёт externals (БД, сторонний API) — честное I/O-ожидание | — | трейсинг внешних вызовов | Это не болезнь Node; оптимизировать запросы/кеш |
| Память растёт со временем | Утечка: listener'ы на многоразовых ресурсах (worker.on без removeListener), процессы пула не умирают | — | heap snapshot; счётчик listeners `getMaxListeners` | Гигиена адаптеров; idle-termination пула |

\* Уровни — по лестнице изоляции: [[1.1 CPU-Bound Ladder]].

## Три железных правила

1. **Health-check — нулевой работы.** `GET /health` не ходит в БД, не читает файлы. Тяжёлый health-check → при любой нагрузке оркестратор считает под мёртвым и рестартует его в худший момент. (Как «I'm alive!» в [НД] ch.11.)
2. **`async` ≠ «в другом потоке».** Синхронный код внутри async-функции блокирует loop ровно так же. `async` — это про Promise и `await`, не про потоки.
3. **CPU-bound эндпоинт = DoS-поверхность.** Один запрос может стоить копенту атакующему и весь сервис — тебе. Щиты: лимит размера тела, лимит пула (`poolMax`, `cpus().length - 1`), прекеш результатов.

## Где смотреть (метрики)

- **Event loop lag** — главный индикатор здоровья main thread (lag растёт → level 0; lag в норме при растущей latency → ищи пул/external). Реализация — `perf_hooks.monitorEventLoopDelay` / `eventLoopUtilization`.
- CPU, disk utilisation, сеть — вместе с lag дают строку таблицы выше.
- Глубже — flamegraph и нагрузочное тестирование (глава 4.7 курса).
