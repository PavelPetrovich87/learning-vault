# 1.1 Справочник: лестница изоляции CPU-bound

> Оперативный справочник по [[1.1 Event loop]] §8: как выбирать способ выполнения тяжёлой синхронной работы в Node. От «ниже некуда» до «не в этой машине».

## Лестница уровней

| Уровень | Приём | Где работает | Цена | Когда брать |
|---|---|---|---|---|
| **0** | ничего | main thread, непрерывно | сервер мёртв; DoS-поверхность | никогда (референс «как нельзя») |
| **1** | `setImmediate` interleaving | main thread, кусками между поколениями | overhead на каждый шаг; лаги при больших кусках | задача **редкая** и куски **мелкие**; менять код лень/нельзя |
| **2** | `child_process.fork` + пул | отдельный **процесс** | память (десятки МБ), старт (десятки мс), обмен только копиями | нативный риск segfault; другой язык (Go/Rust/C); нужен жёсткий memory-limit; другие флаги запуска; кластер |
| **3** | worker threads + пул | отдельный **поток** в том же процессе | дешевле процесса; данные копируются (или transfer/shared) | **по умолчанию** для чистого JS CPU-bound |
| **prod** | `piscina` / `workerpool` | уровень 2–3 со всеми отказоустойчивостями (таймауты, рестарты) | зависимость | **в production почти всегда** вместо своего пула |
| **∞** | масштабирование на узлы | несколько машин | вся стоимость распределёнки | нагрузка превышает capacity одного узла |

Правило перехода: сначала спроси «нужна ли задача вообще» (прекеш, кеш, лимит входа), потом поднимайся по лестнице ровно настолько, насколько требует нагрузка. Не масштабируйся раньше времени.

## Процесс vs worker thread (критерии)

**Worker thread** = дешёвое тело потока + дисциплинированная душа процесса: адресное пространство и FD **общие** с main (поэтому возможен transfer/shared), но JS-куча **своя** (свой V8, свой loop). Краш-изоляция слабее процесса.

**Процесс** = железная изоляция (MMU): крах ребёнка не валит сервер; память/FD/рантайм полностью свои. Дороже во всём.

| Критерий | Выбор |
|---|---|
| Чистый JS, частые задачи | worker (piscina) |
| Нативный модуль с риском краха | процесс |
| Другой язык/рантайм | процесс |
| Жёсткий memory-limit на задачу | процесс (cgroup/OOM точечно) |
| Нужны transferable/SharedArrayBuffer | worker (процессу недоступны) |

## Обмен данными worker ↔ main

| Механизм | Данные | Когда |
|---|---|---|
| `postMessage` | сериализация → **копия** | по умолчанию, 99% |
| transferable ArrayBuffer | владение **переезжает** (у отправителя `byteLength → 0`) | большие бинарные «либо там, либо там»: ресайз, аудио |
| SharedArrayBuffer + Atomics | байты **одни на двоих**, синхронизация вручную | одновременный доступ обоих: прогресс, lock-free |

У fork-процессов доступен только первый (копия): указатель через границу адресных пространств передать нельзя.

## Пул (скелет, общий для процессов и потоков)

Три списка: `pool` (свободные) / `active` (занятые) / `waiting` (очередь продолжений — `{resolve, reject}` промисов). `acquire()`: свободный → дать; лимит → в waiting; иначе родить и ждать `ready`/`online`. `release()`: если есть ждущие — сразу передать первому (`resolve(worker)`), иначе на стеллаж. Процессы/воркеры не убиваются между задачами — амортизация старта. Лимит `poolMax` = DoS-щит; ориентир — `cpus().length` (`- 1` оставить main). Гигиена адаптера: `removeListener` на многоразовом воркере после `end`.
