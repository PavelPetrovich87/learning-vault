## 0. Зачем эта глава (мостик фронтенд → бэкенд)

Ты — сеньор-фронтендер, и `import`/`export` ты пишешь каждый день. Но в браузере модули приезжают через bundler и HTTP, а в Node они **читаются с локального диска и выполняются в процессе сервера, до первого оборота event loop**. Это меняет всё:

- **Когда** выполняется твой код модуля (порядок evaluation зависит от графа зависимостей, а не от порядка строк в entry-файле);
- **Что именно** приезжает в `import` (live binding на исходную переменную, а не копия значения);
- **Как** спецификация `fastify` превращается в конкретный файл на диске (алгоритм разрешения через `node_modules` — то, чего в браузере нет вовсе);
- **Почему** половина npm-экосистемы до сих пор на CommonJS и как с ней жить (интероп).

Плюс — прямой стык с главой 1.1: ты уже знаешь из эксперимента `04-server-startup-probe`, что `bind` и события `listening`/`error` живут в списке задач **до** старта колеса фаз. Эта глава достраивает картину: **весь граф модулей строится и выполняется тоже до первого оборота event loop** — загрузка модулей это фаза инициализации процесса, а не «работа внутри фаз».

И наконец: грамотная модульная структура — это и есть «DI на модулях» до всяких фреймворков. В NestJS (главы 1.5–1.6) контейнер DI будет строиться поверх тех же механизмов, поэтому понимание загрузки модулей — фундамент для всего модуля 1.

## 1. 🟢 Зачем нужны модули

> Источник: [НД] гл.2, «The need for modules» (стр. 21–22).

Сначала разграничим термины. **Модуль** — это сам кусок ПО (файл/юнит функциональности). **Модульная система** — это синтаксис и инструменты, которые позволяют определять модули и использовать их в проекте.

Модули — «кирпичи» для структурирования нетривиальных приложений: они позволяют делить кодовую базу на маленькие юниты, которые разрабатываются и тестируются независимо. Хорошая модульная система, неважно в каком языке, закрывает три фундаментальные потребности:

1. **Организация кода.** Кодовая база делится на несколько файлов — это держит код организованнее и проще для понимания и позволяет разрабатывать и тестировать части независимо.
2. **Реиспользование кода и управление зависимостями.** Легко делиться функциональностью между проектами; разработчик строит поверх существующих модулей (включая сторонние), и пользователь импортирует модуль вместе со всем, что тому требуется, без трения.
3. **Инкапсуляция и сокрытие информации.** Детали реализации прячутся, наружу торчит только ясный простой интерфейс: большая часть кода остаётся приватной, а публичными делаются только нужные функции/классы/объекты.

### История вопроса ([НД] стр. 22–23)

JavaScript долго жил вообще без модульной системы. В браузере код просто резали на файлы и подключали разными `<script>`-тегами — для простых интерактивных сайтов этого хватало. Когда приложения выросли (jQuery, Backbone, AngularJS), сообщество придумало свои стандарты де-факто: **AMD** (asynchronous module definition, популяризован RequireJS) и позже **UMD** (universal module definition).

Node.js при создании получил уникальную возможность: серверный рантайм с прямым доступом к файловой системе — без HTML-тегов и URL. Для модульной системы Node выбрал реализацию спецификации **CommonJS** — независимой (не входившей в ECMAScript) инициативы стандартизовать JavaScript вне браузера. CommonJS доминировал в Node годами и даже попал в браузер через бандлеры (Browserify, Webpack).

В **2015 году ES2015** дал официальную стандартную модульную систему — **ES-модули (ESM)**. Спецификация тогда определила только синтаксис и семантику; реализации пришлось ждать годами — Node.js дал стабильную поддержку ESM только с **версии 13.2 (2019)**. Переход затянулся, в переходные годы библиотеки публиковали «dual-mode» (работает и с ESM, и с CJS). Сегодня ESM — общепринятый стандарт: новые проекты пишутся на нём, CommonJS остаётся в легаси и старых библиотеках, и его использование ожидаемо снижается. Эта книга (и наш курс) использует ESM во всех примерах, но понимать CommonJS необходимо — ты неизбежно встретишь его в чужих кодовых базах.

## 2. 🟢 Revealing module pattern — модули до модульных систем

> Источник: [НД] гл.2, «The revealing module pattern» (стр. 23–25).

Прежде чем разбирать ESM, книга показывает, как сделать «модуль» голыми средствами языка. Это не археология: этот паттерн — фундамент, на котором построен сам CommonJS, и он объясняет, **откуда** берётся инкапсуляция в модульных системах.

Проблема, которую он решает: в браузере каждый скрипт исполняется в глобальном скоупе. Нет namespace'ов — и внутренний код приложения и сторонние библиотеки засоряют глобальный скоуп своими переменными. Если одна библиотека создала глобальную `utils`, а другая (или твой код) её перезапишет — код, зависящий от `utils`, упадёт непредсказуемым образом. Равно как опасно вызывать чужую «внутреннюю» функцию, не предназначенную для внешнего использования. Глобальный скоуп — риск, растущий вместе с приложением.

Решение — **revealing module pattern**:

```javascript
const myModule = (() => {
  const privateFoo = () => {}
  const privateBar = []
  console.log('Inside:', privateFoo, privateBar)
  const exported = {
    publicFoo: () => {},
    publicBar: () => {},
  }
  return exported
})() // скобки распарсились — функция вызвана,
     // возвращённое значение присвоено в myModule

console.log('Outside:', myModule.privateFoo, myModule.privateBar)
console.log('Module:', myModule)
```

Паттерн использует **самовызывающуюся функцию** (IIFE — immediately invoked function expression) для создания приватного скоупа. Работает это на двух свойствах языка: переменные, созданные внутри функции, недоступны снаружи; а `return` выборочно продаёт информацию наружу. Вывод:

```
Inside: [Function: privateFoo] []
Outside: undefined undefined
Module: { publicFoo: [Function: publicFoo], publicBar: [Function: publicBar] }
```

Три наблюдения: (а) приватные `privateFoo`/`privateBar` доступны внутри IIFE; (б) снаружи их нет даже при печати объекта — `myModule.privateFoo` это `undefined`; (в) доступны только экспортированные свойства.

Именно эта схема — обёртка модуля функцией с приватным скоупом и возвращаемым «экспортом» — и есть то, во что Node оборачивает каждый CommonJS-файл (увидишь в §12). На практике строить свою модульной системы не нужно — но теперь ты знаешь, из чего она сделана.

## 3. 🟢 Включение ESM в Node.js

> Источник: [НД] гл.2, «Using ES modules in Node.js» (стр. 25–27).

Поскольку CommonJS существовал в Node задолго до ESM, поддержку ESM пришлось добавлять, сохраняя обратную совместимость: **ESM в Node — не дефолт, а opt-in**. Каждый `.js`-файл по умолчанию считается CommonJS. Попробуй выполнить файл с `import` без настройки — получишь:

```
(node:69441) Warning: To load an ES module, set "type": "module" in the
package.json or use the .mjs extension.
SyntaxError: Cannot use import statement outside a module
```

Способы сказать Node, что файл — ESM:

1. **Расширение `.mjs`** (а `.cjs`, наоборот, форсирует CommonJS);
2. **`"type": "module"` в ближайшем родительском `package.json`** — рекомендация книги и наш выбор;
3. Флаг `--experimental-default-type="module"` — эквивалент `"type": "module"`, но указывается при каждом запуске;
4. Флаг `--experimental-detect-module` — Node сканирует «неоднозначные» `.js`-файлы на ключевые слова `import`/`export`.

> 🔬 **Freshness-check (живые доки, вне книги):** книга писалась, когда detect-module был флагом с прицелом на будущее («Node 23 принял module detection по умолчанию — вероятно, это станет дефолтом»). Так и произошло: с Node 23 авто-детект включён по умолчанию. Тем не менее рекомендация `"type": "module"` остаётся самым явным и надёжным сигналом — не полагайся на эвристику. Наш `shop-api` уже живёт с `"type": "module"` (задел из главы 1.1).

## 4. 🟢 Синтаксис ESM: экспорты и импорты

> Источник: [НД] гл.2, «The ES module syntax» (стр. 27–33).

### 4.1. Именованные экспорты и импорты

Ключевое правило: **в ESM всё приватно по умолчанию**, публично — только экспортированное. Ключевое слово `export` ставится перед сущностями:

```javascript
// logger.js
export function log(message) {
  console.log(message)
}
export const DEFAULT_LEVEL = 'info'
export const LEVELS = {
  error: 0, debug: 1, warn: 2, data: 3, info: 4, verbose: 5,
}
export class Logger {
  constructor(name) {
    this.name = name
  }
  log(message) {
    console.log(`[${this.name}] ${message}`)
  }
}
```

Импортировать можно по-разному:

```javascript
// namespace import — все члены модуля одним объектом
import * as loggerModule from './logger.js'
console.log(loggerModule)
// [Module] {
//   DEFAULT_LEVEL: 'info',
//   LEVELS: { error: 0, debug: 1, warn: 2, data: 3, info: 4, verbose: 5 },
//   Logger: [Function: Logger],
//   log: [Function: log]
// }
```

Книга рекомендует быть явным и импортировать только нужное: `import { log } from './logger.js'`. Несколько сущностей — в одних скобках: `import { Logger, log } from './logger.js'`. Сущности приезжают в текущий скоуп — возможен **конфликт имён**:

```javascript
import { log } from './logger.js'
const log = console.log
// SyntaxError: Identifier 'log' has already been declared
```

Решение — переименование через `as`: `import { log as log2 } from './logger.js'`. Это спасает и когда два модуля экспортируют одно имя, и когда хочется локально более короткое имя.

Импорт **несуществующего** имени — это ошибка на этапе загрузки (runtime-анализ, но до выполнения твоего кода):

```javascript
import { something } from './logger.js'
// SyntaxError: The requested module './logger.js' does not provide
// an export named 'something'
```

### 4.2. Экспорт по умолчанию (default export)

```javascript
// logger.js
export default class Logger {
  /* ... */
}

// main.js
import MyLogger from './logger.js'   // имя выбирает потребитель
const logger = new MyLogger('info')
```

Имя `Logger` в исходнике игнорируется — сущность регистрируется под именем **`default`**. Поэтому потребитель называет её как хочет, без скобок и `as`. Внутри это просто именованный экспорт с именем `default`:

```javascript
import * as loggerModule from './logger.js'
console.log(loggerModule.default)   // [class Logger]
```

Но явно импортировать `{ default }` нельзя — `default` зарезервированное слово, имя переменной из него не сделать (`SyntaxError: Unexpected reserved word`); как свойство объекта (`loggerModule.default`) — можно.

### 4.3. Смешанные экспорты

```javascript
// logger.js
export default function log(message) {
  console.log(message)
}
export function info(message) {
  log(`info: ${message}`)   // внутри ссылается на log(), НЕ на default()
}

// main.js — default всегда первым, до фигурных скобок
import mylog, { info } from './logger.js'
// import { info }, mylog from './logger.js'  // SyntaxError
```

### 4.4. Default vs named: практические следствия

Книга разбирает трейдоффы — это прямая инструкция к действию для кода проекта:

- **Default** удобен, чтобы подчеркнуть «главную» функциональность модуля, и позволяет импортировать без знания точного имени.
- **Named** — явные: предопределённые имена дают IDE автодополнение, automatic imports и рефакторинг. Напечатал `writeFileSync` — редактор сам добавил `import { writeFileSync } from 'node:fs'`. С default-экспортами так не выходит: одна функциональность в разных файлах живёт под разными именами, выводы о происхождении кода по имени сделать нельзя.
- **Default может мешать tree shaking** (dead code elimination): если весь функционал модуля — свойства одного default-объекта, бандлер при импорте объекта считает «используемым» весь объект и ничего не выкинет.

Вывод книги: **минусы default-экспортов перевешивают плюсы, сообщество в целом за то, чтобы их избегать**; некоторые линтеры включают правило против них по умолчанию (Biome — `nodejsdp.link/no-default-export`). Это не железное правило: **все core-модули Node.js имеют и default, и набор named-экспортов**; React использует смешанные экспорты. Думай о developer experience пользователей твоего модуля.

### 4.5. Идентификаторы модулей (module specifiers)

Что можно написать в кавычках `import ... from '...'`:

| Тип | Примеры | Смысл |
|---|---|---|
| **Относительные** | `./logger.js`, `../logger.js` | путь относительно файла-импортёра |
| **Абсолютные** | `file:///opt/nodejs/config.js`, `/opt/nodejs/config.js` | полный путь явно |
| **Bare** | `fastify`, `http` | модуль из `node_modules` (установлен пакетным менеджером) либо core-модуль Node |
| **Deep imports** | `fastify/lib/logger.js` | путь **внутри** пакета из `node_modules` |

Нюансы: чтобы не путать core-модули Node со сторонними, поддержан необязательный префикс **`node:`** (`node:http`) — **рекомендованный способ импорта core-модулей** (ты уже видел его в `shop-api` и в ревью T1/R3 главы 1.1). URL-импорты (`https://unpkg.com/lodash`), возможные в браузере, Node не поддерживает.

## 5. 🟢 Статические и динамические импорты

> Источник: [НД] гл.2, «Static and dynamic imports» (стр. 33–35).

ES-модули **статичны**: импорты описываются на верхнем уровне модуля, вне условных конструкций, и имя модуля нельзя собрать выражением в рантайме — только константные строки:

```javascript
if (condition) {
  import module1 from 'module1'   // нельзя
} else {
  import module2 from 'module2'
}
```

Ограничение — не слабость, а источник возможностей: статичность даёт **статический анализ дерева зависимостей**, а он — оптимизации вроде tree shaking.

Для случаев «загрузить тяжёлый модуль только при обращении к фиче» или «выбрать модуль по окружению/языку» есть **динамический импорт** — оператор `import()`:

```javascript
// strings-el.js / strings-en.js / strings-es.js
export const HELLO = 'Γεια σου κόσμε'   // 'Hello World' / 'Hola mundo'

// main.js
const SUPPORTED_LANGUAGES = ['el', 'en', 'es', 'it', 'pl']      // 1
const selectedLanguage = process.argv[2]                        // 2
if (!selectedLanguage) { /* usage + exit 1 */ }                 // 3
if (!SUPPORTED_LANGUAGES.includes(selectedLanguage)) { /* 4 */ }
const translationModule = `./strings-${selectedLanguage}.js`    // 5
const strings = await import(translationModule)                 // 6
console.log(strings.HELLO)                                      // 7
```

`import()` синтаксически выглядит как функция с идентификатором модуля аргументом и **возвращает промис, который резолвится в объект модуля**. Идентификатор собирается в рантайме (`./strings-${lang}.js`) — заметь: с префиксом `./`, потому что для динамического импорта относительный путь считается от текущего модуля, как у статического. Запуск `node main.js it` печатает `Ciao mondo`.

Для серверного Node это не экзотика: тяжёлые зависимости (производственные библиотеки, редкие роуты) можно не грузить при старте — прямая экономия времени cold start и памяти. Стык с главой 1.1: статические импорты грузятся **до** запуска сервера; динамический `import()` — это уже асинхронная операция **внутри** работающего event loop.

## 6. 🟢 Алгоритм разрешения модулей (module resolution algorithm)

> Источник: [НД] гл.2, «The module resolution algorithm» (стр. 35–37).

**Dependency hell** — сценарий, когда две зависимости программы требуют общую библиотеку, но несовместимые её версии. Node решает это элегантно: **версия модуля определяется тем, откуда он загружается**. Это возможно благодаря тому, как пакетные менеджеры (npm/pnpm) раскладывают зависимости и как алгоритм разрешения отображает спецификатор в файл на диске (`'fastify/lib/logger.js'` → `file:///Users/.../node_modules/fastify/lib/logger.js`).

Заглянуть внутрь можно функцией `import.meta.resolve()` — она показывает, во что спецификатор разрешится в текущем контексте. Три главные ветки алгоритма:

1. **Файловые модули.** Спецификатор начинается с `/` — абсолютный путь (нормализуется, превращается в `file://`-URL). С `./` или `../` — относительный путь от директории импортирующего модуля.
2. **Core-модули Node.** Если спецификатор без `/`, `./`, `../` — сначала ищется среди core-модулей; найденный возвращается с префиксом `node:` (уже с `node:` — как есть).
3. **Пакеты.** Иначе — поиск в первой же директории `node_modules`, найденной **при подъёме вверх** по дереву каталогов от импортирующего модуля; не нашли — выше, до корня файловой системы.

```javascript
console.log(import.meta.resolve('./utils/example.js'))
// -> file://<project_path>/utils/example.js
console.log(import.meta.resolve('assert'))
// -> node:assert
console.log(import.meta.resolve('fastify/lib/logger.js'))
// -> file://<project_path>/node_modules/fastify/lib/logger.js
```

Почему это убивает dependency hell: `node_modules` — то место, куда пакетный менеджер кладёт зависимости **каждого пакета отдельно**. Смотри на структуру:

```
myApp
├── foo.js
└── node_modules
    ├── depA/index.js
    ├── depB
    │   ├── bar.js
    │   └── node_modules/depA/index.js
    └── depC
        ├── foobar.js
        └── node_modules/depA/index.js
```

`myApp`, `depB` и `depC` зависят от depA — но у каждого **своя приватная копия**:

- `import 'depA'` из `/myApp/foo.js` → `/myApp/node_modules/depA/index.js`;
- из `/myApp/node_modules/depB/bar.js` → `/myApp/node_modules/depB/node_modules/depA/index.js`;
- из `/myApp/node_modules/depC/foobar.js` → `/myApp/node_modules/depC/node_modules/depA/index.js`.

Отсюда и побочный эффект, который обязан знать бэкендер: **`instanceof` и сравнение по ссылке между «одинаковыми» пакетами может ломаться**, если в дерево попали две версии. Алгоритм разрешения — ядро устойчивости управления зависимостями Node: сотни и тысячи пакетов в приложении без коллизий версий.

## 7. 🟢 Загрузка модулей вглубь: граф зависимостей и три фазы

> Источник: [НД] гл.2, «Module loading in depth → Loading phases» (стр. 37–39).

Node использует **графы зависимостей**, чтобы загрузить модули в правильном порядке: интерпретатор строит граф из всех нужных модулей; respecting dependencies гарантирует, что каждый модуль доступен, когда понадобится. Узел графа — модуль, стрелка — «зависит от». Отправная точка — файл, переданный интерпретатору, — называется **entry point**. От него интерпретатор рекурсивно, **в глубину (depth-first)**, обходит все `import`-утверждения, пока всё необходимое не будет исследовано и выполнено.

Процесс разделён на **три фазы**:

1. **Phase 1 — construction (парсинг).** Интерпретатор находит все импорты и рекурсивно загружает содержимое каждого модуля из его файла.
2. **Phase 2 — instantiation (инстанциация).** Для каждой экспортированной сущности каждого модуля создаётся **именованная ссылка в памяти — пока без значения**. Затем ссылки импортов и экспортов связываются между модулями (**linking**). Никакой JavaScript-код в этой фазе не выполняется.
3. **Phase 3 — evaluation (выполнение).** Интерпретатор выполняет код, чтобы созданные ссылки получили фактические значения. Только теперь возможно выполнение кода от entry point — «все пробелы заполнены».

Метафора книги: **фаза 1 находит все точки, фаза 2 соединяет точки в пути, фаза 3 проходит пути в правильном порядке.**

Ключевое следствие: фазы разделены, поэтому **никакой код не выполняется, пока весь граф зависимостей не построен целиком** — именно поэтому импорты обязаны быть статическими.

И контраст с CommonJS (важно для §12–13): CJS **динамичен** — при `require` содержимое модуля немедленно загружается **и сразу выполняется**. Гибко (`require` внутри `if` и циклов, идентификаторы из переменных) — но именно поэтому CJS плохо справляется с циклическими зависимостями, а ESM справляется (§9).

![[1-2-esm-loading-phases.drawio]]

> 🟡 **Стык с главой 1.1 (синтез, вне книги):** три фазы загрузки происходят **до старта колеса event loop** — это часть инициализации процесса. В эксперименте `04-server-startup-probe` мы видели, что `bind` и события `listening`/`error` живут «в списке задач до фаз». Теперь цепочка полная: (1) парсинг и линковка графа модулей → (2) evaluation модулей (снизу вверх по графу — твой код в `server.js` выполняется последним) → (3) заявка `listen` кладётся в nextTick-очередь → (4) только потом стартует колесо фаз. Всё, что ты пишешь на верхнем уровне модулей, — это «до event loop».

## 8. 🟢 Read-only live bindings

> Источник: [НД] гл.2, «Read-only live bindings» (стр. 39–40).

Ещё одна фундаментальная характеристика ESM: импортированные сущности — это **read-only live bindings** (живые привязки только для чтения) к экспортированным значениям. Пример из книги:

```javascript
// counter.js
export let count = 0
export function increment() {
  count++
}

// main.js
import { count, increment } from './counter.js'
console.log(count)    // 0
increment()
console.log(count)    // 1
count++               // TypeError: Assignment to constant variable!
```

Читать `count` можно в любой момент; менять — через функцию родного модуля (`increment()`). Прямое присваивание импортированной переменной — ошибка, как будто это `const`. То есть: биндинг нельзя перезаписать из потребителя (**read-only**), но он отражает текущее значение в модуле-источнике (**live**) — изменения в источнике потребитель видит.

Контраст с CommonJS: там при `require` **весь объект `exports` копируется (shallow copy)** — если примитив (число/строка) в источнике потом изменился, импортёр этого **не увидит**. Живые биндинги же — основа того, как ESM переживает циклические зависимости: следующий раздел.

## 9. 🟢 Циклические зависимости — по фазам

> Источник: [НД] гл.2, «Circular dependencies» (стр. 40–46).

Циклическая зависимость: два и более модулей зависят друг от друга по кругу (A импортирует B, B импортирует A). Многие считают это внутренней проблемой дизайна, но в реальном проекте это случается — нужно понимать, как система себя ведёт.

Сценарий из книги: `main.js` импортирует `a.js` и `b.js`; `a.js` импортирует `b.js`; `b.js` импортирует `a.js`:

```javascript
// a.js
import * as bModule from './b.js'
export let loaded = false
export const b = bModule
loaded = true

// b.js
import * as aModule from './a.js'
export let loaded = false
export const a = aModule
loaded = true

// main.js
import * as a from './a.js'
import * as b from './b.js'
console.log('a ->', a)
console.log('b ->', b)
```

Запуск `main.js` выводит (сокращённо):

```
a -> [Module: null prototype] {
  b: [Module: null prototype] { a: [Circular *1], loaded: true },
  loaded: true
}
b -> [Module: null prototype] {
  a: [Module: null prototype] { b: [Circular *1], loaded: true },
  loaded: true
}
```

`a.js` и `b.js` видят друг друга **полностью**: `loaded = true` во всех ссылках; `b` внутри `a` и `a` внутри `b` — настоящие **ссылки** на модули, не копии, дублирования данных нет. Если поменять порядок импортов в `main.js` — вывод не изменится. А в CommonJS тот же пример дал бы `loaded: false` внутри, и вывод **зависел бы от порядка импортов** (следствие динамичности и поверхностного копирования).

Разберём, как ESM этого добивается — по трём фазам:

**Фаза 1 — парсинг.** Обход от entry point в глубину, каждый модуль посещается один раз: (1) из `main.js` первый импорт ведёт в `a.js`; (2) в `a.js` находим импорт `b.js`; (3) в `b.js` — импорт обратно в `a.js`, но тот уже посещён → путь не исследуем повторно (цикл «срезан»); (4) сворачиваемся: в `b.js` других импортов нет — возврат в `a.js`, там тоже — возврат в `main.js`; импорт `b.js` в `main.js` уже посещён — игнорируется. Итог — линейное/древовидное представление графа без циклов.

**Фаза 2 — инстанциация.** Дерево обходится **снизу вверх**: (1) `b.js` — карта экспортов `loaded`, `a`; (2) `a.js` — `loaded`, `b`; (3) `main.js` — ничего не экспортирует. Значения пока неинициализированы. Вторым проходом — **линковка**: (1) `b.js` линкует экспорты `a.js` под локальным именем `aModule`; (2) `a.js` линкует экспорты `b.js` как `bModule`; (3) `main.js` линкует всё из `b.js` как `b` и всё из `a.js` как `a`. Всё ещё только ссылки на будущие значения.

**Фаза 3 — выполнение.** Код выполняется **снизу вверх** (post-order DFS): первым — `b.js`: (1) `loaded = false`; (2) экспорт `a` получает значение — ссылку на объект модуля `a.js`; (3) `loaded = true`. Затем `a.js`: (4) `loaded = false`; (5) `b` = ссылка на модуль `b.js`; (6) `loaded = true`. И только потом — `main.js`, к этому моменту все экспорты полностью вычислены. Поскольку импорты отслеживаются как ссылки, каждый модуль имеет актуальное представление о другом — даже при цикле.

## 10. 🟢 Модули, изменяющие другие модули (monkey patching)

> Источник: [НД] гл.2, «Modules that modify other modules» (стр. 46–52).

Модуль может не экспортировать ничего — и всё же быть полезным, **модифицируя глобальный скоуп или другие модули**. Практика называется **monkey patching**: изменение существующих объектов в рантайме для расширения поведения или временных фиксов. Обычно это обескураживается, но в отдельных сценариях (тестирование) — полезно и безопасно.

Классический пример — необязательный колоризатор логгера:

```javascript
// logger.js
export const logger = {
  info(message)   { console.log(`[INFO]\t${message}`) },
  error(message)  { console.log(`[ERROR]\t${message}`) },
  warn(message)   { console.log(`[WARN]\t${message}`) },
  debug(message)  { console.log(`[DEBUG]\t${message}`) },
}

// colorizeLogger.js — экспортов нет, только side effect
import { logger } from './logger.js'
const RED = '\x1b[31m', YELLOW = '\x1b[33m', GREEN = '\x1b[32m',
      WHITE = '\x1b[37m', RESET = '\x1b[0m'
const originalInfo  = logger.info
const originalWarn  = logger.warn
const originalError = logger.error
const originalDebug = logger.debug
logger.info  = message => originalInfo(`${GREEN}${message}${RESET}`)
logger.warn  = message => originalWarn(`${YELLOW}${message}${RESET}`)
logger.error = message => originalError(`${RED}${message}${RESET}`)
logger.debug = message => originalDebug(`${WHITE}${message}${RESET}`)

// main.js
import { logger } from './logger.js'
import './colorizeLogger.js'   // side-effect import, без from
logger.info('Hello, World!')
```

Колоризатор сохраняет оригинальные методы, оборачивает их (цвет вокруг сообщения) и подменяет на объекте. Импорт без `from` — упрощённый синтаксис для «модулей ради побочного эффекта»: закомментируй строку — цвета исчезнут, функциональность не пострадает.

**Как это сочетается с read-only bindings?** Биндинг переприсвоить нельзя, но если его значение — **объект, мутировать сам объект можно**: `logger` (объект) экспортирован именованным биндингом → его свойства доступны для записи. Это и делает колоризатор. А вот дальше книга методично показывает три «неправильных» способа и почему они падают:

```javascript
// replaceLogger.js — переприсвоить импортированный биндинг
logger = { /* ... */ }
// TypeError: Assignment to constant variable.

// replaceLogger2.js — переприсвоить член namespace-объекта
import * as loggerModule from './logger.js'
loggerModule.logger = { /* ... */ }
// TypeError: Cannot assign to read only property 'logger' of object '[object Module]'
```

Третий способ **работает** — если заранее изменить сам `logger.js`, добавив default-экспорт-обёртку:

```javascript
// logger.js — добавлен default, оборачивающий все члены
export const logger = { /* ... */ }
export default { logger }

// replaceLogger3.js
import loggerModule from './logger.js'   // default = обычный объект, НЕ module namespace
loggerModule.logger = { /* своя реализация */ }
```

Namespace-импорт даёт объект модуля с read-only членами, а **default-импорт — просто обычный объект**, члены которого менять можно. Но у трюка есть гвоздь:

```javascript
// main2Broken.js — патч НЕ виден!
import { logger } from './logger.js'     // именованный импорт — ДРУГАЯ ссылка
import './replaceLogger3.js'             // патчит default-обёртку
logger.info('Hello, World!')             // без цвета
```

`replaceLogger3.js` патчит `logger` **внутри default-обёртки**; именованный биндинг `logger` указывает на исходный объект мимо обёртки. Работает только вариант, где потребитель импортирует **default**:

```javascript
// main2.js
import loggerModule from './logger.js'
import './replaceLogger3.js'
loggerModule.logger.info('Hello, World!')   // цвет есть
```

Подход хрупок — требуется одновременное выполнение **трёх условий**: (1) субъект (`logger.js`) экспортирует объект со всеми членами как default; (2) патчер импортирует default и модифицирует его члены; (3) потребитель использует default-экспорт, а не именованные. Если субъект или патчер сторонние — условия вне твоего контроля. Но техника выстрелит в главе курса про тестирование ([НД] гл.10 — мок `node:fs` в юнит-тестах).

**Безопасность:** monkey patching — вектор атаки: вредоносный код в зависимостях может патчить модули для эксфильтрации данных, повышения привилегий, изменения поведения. Команда Node.js ассоциировала практику с записью **CWE-349** в Common Weakness Enumeration и публикует рекомендации по защите: `nodejsdp.link/cwe-349`. Для сеньора-бэкендера это ещё один аргумент следить за supply chain зависимостей.

> 🟡 **Стык с проектом:** в `shop-api` из главы 1.1 `loop-lag.js` экспортирует `startLagMonitor` и **не мутирует никого извне** — именно поэтому его можно подключать/отключать без сюрпризов. Держись этого стиля: модуль без скрытых side effects на чужие модули.

### Monkey patching и TypeScript ([НД] стр. 52–53)

TypeScript проверяет типы и компилирует код **до** исполнения, а патчинг происходит **в рантайме** — после того, как TS свою работу сделал. Отсюда три класса проблем: (1) **type safety** — изменив тип члена (скажем, `number` → `string`), получаешь runtime-ошибки там, где ждёшь метод старого типа (`toFixed()` у строки); TS поймает это только если патч в том же TS-проекте; (2) **сложность `.d.ts`** — расширение чужих типов хрупко; (3) **потеря IntelliSense** — IDE не знает о патче: новые методы не появятся в автодополнении. Вывод книги: для TypeScript-проектов monkey patching — last resort; и проверяй сторонние модули на скрытые патчи.

## 11. 🟢 CommonJS

> Источник: [НД] гл.2, «CommonJS modules» (стр. 53–54).

CommonJS постепенно заменяется ESM (для новых проектов рекомендован ESM), но официально не депрекирован — понимать его нужно для работы со старыми кодовыми базами и библиотеками. Две главные концепции: **`require`** — функция импорта модуля из локальной файловой системы; **`exports`/`module.exports`** — специальные переменные для экспорта публичной функциональности.

```javascript
// math.cjs
'use strict'
function add(a, b) {
  return a + b
}
module.exports = { add }   // или `exports.add = add`

// main.cjs
'use strict'
const { add } = require('./math.cjs')
console.log(add(2, 3))   // 5
```

Три вещи, которые обязан помнить бэкендер:

1. **`'use strict'` пишется явно** — CJS не строгий по умолчанию (в ESM — всегда строгий, см. §12).
2. **`require()` синхронный и динамический**: резолвит модуль, грузит файл и **немедленно выполняет** его содержимое, без колбэка. Синхронность диктует стиль: инициализация модулей ограничена синхронным кодом — поэтому многие core-библиотеки Node держат синхронные API рядом с асинхронными (`readFile`/`readFileSync` в `node:fs`). Нужна асинхронная инициализация — экспортируй «неинициализированный» модуль с отложенной инициализацией (и accompanying-проблемы; элегантные решения — [НД] гл.11, Advanced Recipes).
3. Помнишь revealing module pattern (§2)? Каждый CJS-файл Node фактически оборачивает в такую функцию — `require`, `exports`, `module` это **параметры обёртки**, а не глобалы.

Историческая заметка книги: асинхронная версия `require()` существовала в раннем Node и была удалена — усложняла механизм, предназначенный для инициализации, где асинхронный I/O приносит больше проблем, чем пользы.

## 12. 🟢 ESM и CommonJS: различия и интероперабельность

> Источник: [НД] гл.2, «ES modules and CommonJS—differences and interoperability» (стр. 54–62).

### 12.1. Различия среды выполнения

| Аспект | ESM | CommonJS |
|---|---|---|
| **Strict mode** | всегда включён, не отключается | выключен по умолчанию, включается `'use strict'` |
| **Top-level await** | да — `await` прямо на верхнем уровне | нет — только внутри `async function main() { }` с вызовом |
| **this на верхнем уровне** | `undefined` | ссылка на `exports` (`this === exports` → true) |

`globalThis` в обоих системах ведёт себя одинаково — ссылка на объект глобальных утилит платформы (`setInterval`, `structuredClone`).

### 12.2. Отсутствующие ссылки: `__filename`, `__dirname`, `require`, `exports`

В ESM привычных CJS-переменных нет — обращение даёт `ReferenceError`. `__filename`/`__dirname` (абсолютный путь к текущему модулю и его папке) полезны для путей относительно файла. Эквиваленты ESM:

```javascript
// Node ≥ 20.11 (введены в январе 2024)
const __filename = import.meta.filename   // /path/to/project/main.js
const __dirname = import.meta.dirname     // /path/to/project

// Универсально (любая версия с ESM)
import { fileURLToPath } from 'node:url'
import { dirname } from 'node:path'
const __filename2 = fileURLToPath(import.meta.url)  // file:///… → путь
const __dirname2 = dirname(__filename2)
```

`import.meta.url` — URL текущего файла вида `file:///path/to/current_module.js`; `fileURLToPath()` конвертирует его в путь, `dirname()` отрезает имя файла.

### 12.3. Импорт CJS из ESM

Работает — через default:

```javascript
// someModule.cjs
'use strict'
module.exports = { someFeature: 'someFeature' }

// main.js (ESM)
import someModule from './someModule.cjs'   // ок: default = module.exports
console.log(someModule)                     // { someFeature: 'someFeature' }
```

А именованный импорт — падает, если свойство не было экспортировано напрямую через `exports.someFeature`:

```javascript
// main2.mjs
import { someFeature } from './someModule.cjs'
// SyntaxError: Named export 'someFeature' not found. The requested module
// './someModule.cjs' is a CommonJS module, which may not support all
// module.exports as named exports.
// CommonJS modules can always be imported via the default export, for example using:
// import pkg from './someModule.cjs'; const { someFeature } = pkg;
```

(Причина: named-экспорты для CJS Node определяет статическим анализом `module.exports` — явное `exports.someFeature = …` анализатор видит надёжно, а «`module.exports = { someFeature }`» — не всегда.) Два обхода, если исходный модуль менять нельзя (сторонний пакет):

```javascript
// Решение 1 — рекомендация из самой ошибки: default + деструктуризация
import someModule from './someModule.cjs'
const { someFeature } = someModule

// Решение 2 — воссоздать require() в ESM
import { createRequire } from 'node:module'
const require = createRequire(import.meta.url)
const { someFeature } = require('./someModule.cjs')
```

`createRequire()` даёт функцию, ведущую себя в точности как CJS-`require`.

### 12.4. Импорт ESM из CJS

По книге: `require()` ES-модуля → `ERR_REQUIRE_ESM`, сообщение предлагало динамический `import()`:

```javascript
// main.cjs
'use strict'
async function main() {
  const { someFeature } = await import('./someModule.mjs')   // работает
  console.log(someFeature)
}
main()
```

Нюансы: `import()` асинхронен, а top-level await в CJS нет — нужна обёртка `async main()`. Книга упоминала флаг `--experimental-require-module` для прямого `require(esm)`.

> 🔬 **Freshness-check (живые доки, 2026-08-24):** с момента книги всё стабилизировалось. `require(esm)` расфлажен во всех поддерживаемых LTS-линейках (v20.19.0+, v22.12.0+) и получил статус stable (v25.4.0); **в нашей Node 24 `require()` синхронно грузит ESM без всяких флагов** — ошибка `ERR_REQUIRE_ESM` для обычных модулей ушла в прошлое. Единственное оставшееся ограничение: модуль с **top-level await** через `require()` не загрузится — `ERR_REQUIRE_ASYNC_MODULE` (синхронный require не может ждать асинхронной инициализации). Источник: [Joyee Cheung, «require(esm) in Node.js: from experiment to stability»](https://joyeecheung.github.io/blog/2025/12/30/require-esm-in-node-js-from-experiment-to-stability/), [Node.js ESM docs](https://nodejs.org/api/esm.html).

### 12.5. Импорт JSON

В CJS — одной строкой: `require('./sample.json')` читает, парсит и возвращает (эквивалент `readFileSync` + `JSON.parse` без бойлерплейта). В ESM наивная попытка падает:

```javascript
import data from './sample.json'
// TypeError [ERR_IMPORT_ATTRIBUTE_MISSING]: Module "[…]/sample.json" needs
// an import attribute of "type: json"
```

Нужен **import attribute**:

```javascript
import data from './sample.json' with { type: 'json' }
console.log(data)

// динамический вариант — данные в default, атрибут вторым аргументом
const { default: data2 } = await import('./sample.json', {
  with: { type: 'json' },
})
```

Зачем атрибут: **безопасность**. Явное объявление типа говорит загрузчику ESM, что перед нами JSON, и он не попытается исполнить файл как код — даже если под `.json`-расширением прячется JavaScript (потенциальный вектор атаки).

> 🔬 **Freshness-check (живые доки, 2026-08-24):** книга предупреждала про экспериментальный статус и warning «Importing JSON modules is an experimental feature». В Node 24 JSON-модули и import attributes (`with`) стабильны — warning больше не появится. Атрибут `type: 'json'` остаётся обязательным. Источник: [Node.js ESM docs](https://nodejs.org/api/esm.html).

Если экспериментальные фичи не для тебя (или старый Node) — те же альтернативы:

```javascript
// Альтернатива 1 — руками
import { readFile } from 'node:fs/promises'
import { join } from 'node:path'
const jsonPath = join(import.meta.dirname, 'sample.json')
const data = JSON.parse(await readFile(jsonPath, 'utf-8'))

// Альтернатива 2 — createRequire
import { createRequire } from 'node:module'
const require = createRequire(import.meta.url)
const data3 = require('./sample.json')
```

## 13. 🟢 Модули в TypeScript

> Источник: [НД] гл.2, «Using modules in TypeScript» (стр. 62–65).

TypeScript — надмножество JavaScript, интегрирующееся с разными средами. Про модули TS думает в двух контекстах: **входные** модули (как ты пишешь) и **выходные** (что эмитится компилятором) — и умеет конвертировать между системами: можно писать ESM и компилировать в CommonJS. Поведение задаётся `tsconfig.json`.

Что должен решить компилятор на примере `import sayHello from 'greetings'`:

1. **Module loading** — загрузится ли `greetings.ts` или скомпилированный `greetings.js` из того же пакета?
2. **Module type & resolution** — какой формат у файла по конвенциям имени/расположения; specifier `greetings` без пути — вероятно, пакет из `node_modules`, но какой именно файл? Плюс path aliases (кастомные префиксы путей) — ещё один фактор резолва.
3. **Output transformation** — преобразовать ли импорты (например, ESM → CJS) при эмите?
4. **Compatibility** — корректно ли провзаимодействуют обнаруженные типы модулей после трансформаций?
5. **Binding** — какой именно экспорт `greetings` привязывается к `sayHello`?

Ответы зависят от хоста (Node.js, Webpack, …): спецификация ECMAScript определяет линковку импортов/экспортов, но **не** определяет резолв модулей и ничего не знает о CommonJS — рантаймы и бандлеры волны устраивать свои правила. Обязанности TS по модулям: адаптироваться к хосту (скомпилировать в валидный формат), обеспечить совместимость (импорты в выходных файлах резолвятся), корректно типизировать импортируемое.

Ключевые опции (рекомендации книги для Node.js):

- **`module: "NodeNext"`** — формат выходных модулей по последней модульной системе Node; влияет и на detection типов, и на поддержку `import.meta`/top-level await. Важно даже при `noEmit` — для type-checking и IntelliSense.
- **`verbatimModuleSyntax`** (TS 5.0) — импорты/экспорты должны быть написаны в форме с минимальной трансформацией при эмите (эмитится как ESM — пиши синтаксисом ESM). Держит результаты предсказуемыми; для Node.js рекомендовано включать. Следствие для практики: `import type { … }` для типов, иначе эмит сломает рантайм-импорт несуществующих имён.
- **`moduleResolution: "NodeNext"`** — чтобы TS интерпретировал спецификаторы по правилам Node; дублирует `module` по умолчанию, поддерживает будущие фичи резолва.

Готовые конфигурации под разные контексты: `nodejsdp.link/total-typescript-tsconfig`.

> 🟡 **Стык с курсом:** в сквозном проекте TypeScript появится в главах 1.5+ (NestJS генерирует tsconfig сам). Сейчас достаточно запомнить связку: `module: NodeNext` + `moduleResolution: NodeNext` + `verbatimModuleSyntax` — и почему «входной синтаксис ≠ выходной».
