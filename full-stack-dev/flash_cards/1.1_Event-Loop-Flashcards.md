# 1.1 Event loop — Flashcards

> Карты по главе 1.1 «Event loop под нагрузкой, libuv, где Node душится». Глава в `[[1.1 Event loop]]`.

## Философия и I/O

В чём разница между «small core» и «small modules» в Node-философии?
?
Small core — про **сам рантайм** (минимум встроенного в ядро Node, максимум в userland). Small modules — про **дизайн пакетов** (узкий scope, одна ответственность). Small modules решает dependency hell через вложенные `node_modules` (каждый потребитель тащит свою версию dep).
Source: [[1.1 Event loop]]

Почему I/O называют «главным бутылочным горлом» в серверном коде?
?
I/O (диск/сеть) — порядка **миллисекунд**, RAM — порядка **наносекунд**. Разница в 6 порядков. Веб-сервер почти целиком состоит из I/O (accept, read request, БД, кеш, сторонние API). Blocking-поток на каждом I/O = расход памяти и context switch'ов впустую.
Source: [[1.1 Event loop]]

## Reactor pattern

Какую конкретно проблему решает event demultiplexer (по сравнению с busy-waiting)?
?
В busy-waiting поток сжигает CPU, опрашивая ресурсы, которые большую часть времени недоступны. Demultiplexer **блокируется**, пока любой из наблюдаемых ресурсов не станет готов, и возвращает только реальные события. Так несколько I/O-операций обрабатываются **в одном потоке** без waste.
Source: [[1.1 Event loop]]

Опиши 6 шагов reactor pattern.
?
1. Приложение шлёт запрос + handler в Event Demultiplexer (non-blocking). 2. Завершённые операции → Event Queue. 3. Event Loop итерирует по очереди. 4. Для каждого события вызывается handler. 5a. Handler возвращает управление Loop (5b: может инициировать новые async ops). 6. Когда очередь пуста — Loop блокируется на Demultiplexer до новых событий.
Source: [[1.1 Event loop]]

## libuv и стек Node

Зачем Node нужен libuv? (минимум 3 причины)
?
1. **Портабельность**: единый API над epoll (Linux), kqueue (macOS), IOCP (Windows). 2. **Нормализация разных типов ресурсов** в одной ОС (обычный файл не поддерживает non-blocking в Unix). 3. **Реализация reactor pattern** (event loop + event queue). 4. **Thread pool** для операций, которые нельзя сделать через event demultiplexer.
Source: [[1.1 Event loop]]

Назови 4 ингредиента «полного рецепта Node» и кто из них C/C++, кто JS.
?
1. **libuv** (C) — event loop + thread pool. 2. **Bindings** (C++) — мост C ↔ JS, экспортирует libuv в JS. 3. **V8** (C++) — JS-движок (JIT). 4. **Core JavaScript library** (JS) — высокоуровневый API (`fs`, `http`, `crypto`...). Поверх всего — твой прикладной JS-код.
Source: [[1.1 Event loop]]

## Два пути через libuv (главный концепт)

Почему `fs.readFile` идёт в thread pool, а `fetch` (Web Fetch API) — через epoll, без thread pool?
?
Обычный файл в Unix **нельзя наблюдать через epoll** — ядро всегда говорит «готов», но сам `read()` блокирует поток на диске. Поэтому libuv отдаёт чтение файла рабочему потоку из пула. Сокет же — ровно то, что epoll умеет: ядро будит epoll, когда в сокет пришли данные, никакой поток не простаивает.
Source: [[1.1 Event loop]]

Какой поток исполняет твой callback после `fs.readFile` завершился? А после `fetch`?
?
**Всегда main thread.** Thread pool / epoll только **делают операцию** (блокирующий read / ожидание данных сокета) и кладут событие в queue. Main thread в фазе poll забирает событие и вызывает твой callback. Разница — только в том, *кто ждёт*, не в том, *кто бежит*.
Source: [[1.1 Event loop]]

Что идёт в libuv thread pool (минимум 3 пункта), а что НЕ идёт?
?
**Идёт в pool:** `fs.readFile`, `crypto.pbkdf2`/`scrypt`, `dns.lookup` (getaddrinfo), `zlib` (часть операций). **НЕ идёт:** сетевой I/O (TCP/HTTP/UDP) — epoll/kqueue/IOCP напрямую; `dns.resolve*` — c-ares (async); весь твой JS-код — только main thread.
Source: [[1.1 Event loop]]

## Event loop: фазы и микрозадачи

Назови 6 фаз event loop по порядку.
?
1. **timers** (setTimeout/setInterval). 2. **pending callbacks** (отложенные I/O-ошибки типа ECONNREFUSED). 3. **idle, prepare** (internal). 4. **poll** (новые I/O-события, блок в epoll). 5. **check** (setImmediate). 6. **close callbacks** (socket.on('close')). Между фазами — drain nextTickQueue + microtaskQueue.
Source: [[1.1 Event loop]]

Какой порядок вывода и почему?
```js
console.log('1')
setTimeout(()   => console.log('2'), 0)
process.nextTick(() => console.log('3'))
console.log('4')
Promise.resolve().then(() => console.log('5'))
```
?
**1, 4, 3, 5, 2.** Сначала sync (`1`, `4`). Затем между фазами drain'ятся очереди: nextTick (`3`) → Promise (`5`). Только после этого loop входит в фазу timers и выполняет `setTimeout` (`2`). nextTick/Promise — «вне фаз», приоритет выше любой фазы.
Source: [[1.1 Event loop]]

Почему рекурсивный `process.nextTick(recurse)` намертво вешает сервер, хотя в нём нет `while(true)` и нет CPU-bound?
?
nextTickQueue обрабатывается **до перехода к следующей фазе**. Рекурсия постоянно пополняет очередь, поэтому loop **никогда не доходит до фазы poll** → новые I/O-события не принимаются. Это I/O starvation. Для «после текущей операции» безопаснее `setImmediate` — срабатывает в фазе check, не морит голодом poll.
Source: [[1.1 Event loop]]

Почему порядок `setTimeout(cb, 0)` vs `setImmediate(cb)` не детерминирован в простом скрипте, но **гарантирован** внутри I/O-колбэка?
?
В простом скрипте: после sync loop входит в任意 фазу — зависит от текущего времени (≥1 мс с момента `setTimeout` → сработает timers; <1 мс → poll → check). Внутри I/O-колбэка: код выполняется в фазе **poll**, а сразу после poll идёт фаза **check** → `setImmediate` всегда первый.
Source: [[1.1 Event loop]]

## Когда process выходит

Почему `node -e 'setTimeout(()=>{}, 1000)'` ждёт секунду, а `node -e 'console.log(1)'` выходит сразу?
?
Между оборотами loop Node проверяет, есть ли активные handles/requests (таймеры, открытые сокеты, fs-операции). Активный handle держит loop живым. `setTimeout` — активный таймер на 1 с. Во втором случае — нет активных handles → процесс завершается чисто после sync-кода.
Source: [[1.1 Event loop]]

## Thread pool: параметры и ловушки

Как задаётся размер libuv thread pool? Почему `process.env.UV_THREADPOOL_SIZE = 8` внутри кода не работает?
?
Переменная окружения **`UV_THREADPOOL_SIZE`** (дефолт **4**, максимум **1024**), до старта Node: `UV_THREADPOOL_SIZE=8 node server.js`. Внутри кода — поздно: libuv читает переменную **один раз при инициализации**, до выполнения пользовательского кода. При опечатке в имени Node молча берёт дефолт.
Source: [[1.1 Event loop]]

Почему `dns.lookup` идёт в thread pool, а `dns.resolve` — через epoll?
?
`dns.lookup` — обёртка над **синхронным системным** `getaddrinfo()` (libc, читает /etc/hosts, nsswitch) → блокирует поток → пул. `dns.resolve` — библиотека **c-ares**: сама открывает UDP/TCP-сокеты и шлёт DNS-запросы → сокеты → epoll, пул не нужен. Нюанс: `http.request`/`fetch` по имени хоста резолвят через `dns.lookup` → **едят слот пула**.
Source: [[1.1 Event loop]]

Симптом: под нагрузкой CPU 10%, диск утилизирован на 30%, но latency x5. В коде — `fs.readFile` + `crypto.pbkdf2` на каждый запрос. Диагноз?
?
**Исчерпание libuv thread pool** (дефолт 4). Обе операции идут в пул: fs — потому что файл нельзя наблюдать через epoll, pbkdf2 — CPU-bound. 5-й и дальше запросы стоят в очереди пула, main thread свободен (loop lag нормальный). Лечение: кешировать файл при старте; для crypto — worker_threads / argon2 (свой пул) / разумный `UV_THREADPOOL_SIZE`.
Source: [[1.1 Event loop]]

Почему `UV_THREADPOOL_SIZE=128` может ухудшить ситуацию (3 контраргумента)?
?
1. **Oversubscription**: 128 CPU-bound потоков на N ядрах → планировщик ОС жжёт время на context switch'и. 2. **Память**: каждый поток — стек ~до 1 МБ; в контейнере с лимитом — риск OOM-kill. 3. **I/O-bound не ускоряется**: если потоки ждут диск, узкое место — сам диск, больше потоков не даёт прироста. Пул имеет смысл растить только для CPU-bound или разноустройственного I/O.
Source: [[1.1 Event loop]]

Почему рекурсивный `setImmediate` НЕ вызывает starvation, а рекурсивный `process.nextTick` — вызывает?
?
setImmediate обрабатывается **поколениями**: фаза check берёт один снимок очереди за оборот; immediates, добавленные во время выполнения, ждут **следующего оборота** (loop между поколениями обязан пройти timers и poll → I/O обслуживается). nextTickQueue drain'ится **до дна в одном такте**, включая добавленное во время drain'а → при рекурсии очередь не пустеет никогда → фаза poll недостижима. Проверено экспериментом: nextTick-рекурсия 3 с — 0 срабатываний таймера; setImmediate-рекурсия — таймер ровно каждые 100 мс при ~500K шагов/100 мс.
Source: [[1.1 Event loop]]

Рекурсия через setImmediate — полностью ли безопасна? Какие две деградации возможны?
?
Это **лаги, а не смерть**: (1) если один immediate-колбэк сам долгий (500 мс синхронной работы) — loop стоит эти 500 мс; (2) если одна партия immediates гигантская (100 000 сразу) — поколение обрабатывается долго, оборот затягивается, latency растёт. Но I/O между поколениями обслуживается → starvation невозможен. Шкала: nextTick-рекурсия = смерть; тяжёлый/массовый immediate = лаги; нормальный interleaving = здоровье.
Source: [[1.1 Event loop]]

Процесс vs worker thread: что у кого «своё», что общее, и почему?
?
**Процесс (fork)**: своё адресное пространство (изоляция на уровне MMU-железа), своя таблица FD, свой V8 + libuv + thread pool. Крах изолирован железно. **Worker thread**: поток внутри процесса → адресное пространство и FD **общие** с main (поэтому transferable/shared возможны — можно передать указатель на байты), но JS-куча **своя** (свой V8, свой loop) — потому что куча V8 не потокобезопасна. Формула: worker = «дешёвое тело потока + дисциплинированная душа процесса». Крах воркера изолирован слабее (может утянуть весь процесс).
Source: [[1.1 Event loop]]

postMessage / transferable ArrayBuffer / SharedArrayBuffer — для кого доступны и когда какой?
?
Только для **worker threads** (у fork-процессов — только сериализация-копия через `process.send`, т.к. адресные пространства разные и передать указатель нельзя). **postMessage** — копия, по умолчанию для 99% случаев. **transferable** — владение буфером переезжает (у отправителя обнуляется), ноль копирования — для больших бинарных данных «либо там, либо там» (картинка на ресайз). **SharedArrayBuffer** — байты одни на двоих, синхронизация вручную через Atomics (риск гонок данных) — для одновременного доступа обоих (прогресс-бар, lock-free очереди).
Source: [[1.1 Event loop]]

Критерии выбора: fork-процесс vs worker threads?
?
**По умолчанию — worker threads** (дешевле, быстрее, transfer/shared, piscina). **Процесс — если**: (1) нативный код с риском segfault (изоляция краха: умирает ребёнок, не сервер); (2) другой язык/рантайм (Go/Rust/Python); (3) нужен жёсткий memory-limit (cgroup/OOM-kill точечно); (4) другие флаги запуска/версия Node; (5) кластеризация (cluster-модуль = форки). Для чистого JS CPU-bound — воркеры через piscina, лимит `cpus().length - 1`.
Source: [[1.1 Event loop]]

## Диагностика и лестница (справочники)

Симптом: event loop lag в норме (~5 мс), CPU 10–15%, диск 20–30%, но latency ×5. Диагноз? Как проверить?
?
**Исчерпание libuv thread pool.** Loop не виноват (lag норма), CPU/диск недогружены — значит узкое место в очереди к 4 потокам пула (fs + crypto.pbkdf2 + dns.lookup в одном запросе). Проверка: посмотреть, какие операции кода идут в пул; эксперимент с `UV_THREADPOOL_SIZE=8` (стало лучше → пул). Рецепты: кеш/прекеш, argon2 (свой пул), keep-alive, разумный размер пула. См. [[1.1 Diagnostics Cheat Sheet]]
Source: [[1.1 Event loop]]

Симптом: один «тяжёлый» запрос (ресайз, большой JSON.parse) — и ВСЕ запросы виснут, health-check молчит. Диагноз? Почему async-функция не спасает?
?
**Синхронный CPU-bound на main thread** (уровень 0): весь JS — один поток; loop стоит на время задачи → ни poll, ни timers, ни ответы. `async` не спасает: async — про Promise/await, а не про потоки; синхронный код внутри async-функции блокирует loop так же. Рецепт: вынести по лестнице (worker/piscina). См. [[1.1 CPU-Bound Ladder]]
Source: [[1.1 Event loop]]

Перечисли лестницу изоляции CPU-bound (6 уровней) с ценой каждого.
?
**0** ничего — main thread непрерывно, сервер мёртв. **1** `setImmediate`-interleaving — кусками между поколениями; цена: overhead × шаги, лаги при больших кусках. **2** fork-процесс + пул — изоляция железная; цена: память, старт, обмен копиями. **3** worker threads + пул — дешевле; данные копируются (или transfer/shared). **prod** piscina/workerpool — готовые отказоустойчивые пулы. **∞** масштабирование на узлы — когда один сервер не справляется. Правило: сначала «нужна ли задача вообще» (прекеш/лимит), потом минимально достаточный уровень. См. [[1.1 CPU-Bound Ladder]]
Source: [[1.1 Event loop]]

Почему health-check должен быть «нулевых затрат»? Что случится с тяжёлым `GET /health` (SELECT 1 + readFileSync) при падении БД?
?
Оркестратор (K8s) решает «жив ли под» по health-check. Тяжёлый health-check при любой нагрузке/проблеме с БД начинает таймаутиться → оркестратор считает под мёртвым → убивает/рестартует **здоровый** под — в худший момент. Health-check = мгновенный ответ без БД и файлов (как «I'm alive!» в [НД] ch.11). Деградацию БД проверяет отдельный readiness/liveness-зонд с другой семантикой. См. [[1.1 Diagnostics Cheat Sheet]]
Source: [[1.1 Event loop]]

CPU-bound эндпоинт как DoS-поверхность: почему дёшев атакующему и как закрыть (3 щита)?
?
Один запрос (20–30 чисел в subset-sum-подобный перебор, гигантский пейлоад) стоит атакящему копейки, а держит event loop мёртвым — сервер не отвечает **никому**. Щиты: (1) лимит размера тела/входных данных (413); (2) лимит пула воркеров (`poolMax`/`cpus().length - 1`) — лишние запросы в очередь, а не в процессы; (3) прекеш/кеш результатов, чтобы тяжёлой работы не было вообще. См. [[1.1 CPU-Bound Ladder]]
Source: [[1.1 Event loop]]

8 параллельных запросов, каждый пишет одну строчку в лог (fs.appendFile). CPU 15%, диск 20%, latency растёт. Что именно стоит в очереди?
?
**Async fs-операции стоят в очереди к libuv thread pool** (путь B): 8 операций → 4 потока, остальные ждут свободного потока. Работа копеечная — потому CPU и диск недогружены, а latency = ожидание в очереди к пулу, не к железу. Рецепты: `UV_THREADPOOL_SIZE` (если операций легитимно много), буферизация логов + один writer пачками, вынос логирования из горячего пути (syslog/сеть). См. [[1.1 Diagnostics Cheat Sheet]]
Source: [[1.1 Event loop]]

Симптом: lag в норме, CPU низкий, диск низкий, latency ×3. Кроме исчерпания libuv thread pool — какая вторая гипотеза? Как поймать одной метрикой?
?
**Ожидание внешней зависимости:** пул соединений БД исчерпан (запросы ждут свободное соединение) или внешний API отвечает медленно. Время тратится ВНЕ процесса — loop свободен, CPU/диск не грузятся. Поймать: метрика ожидания соединения из пула БД (acquire wait) или трейсинг длительности внешних вызовов (было 5 мс → стало 150 мс = вот и ×3). См. [[1.1 Diagnostics Cheat Sheet]]
Source: [[1.1 Event loop]]

Диагностическая пара по метрикам: (а) lag растёт + CPU высокий; (б) lag в норме + CPU низкий + latency растёт. Что означает каждая?
?
**(а) Синхронный код на main thread** — JSON.parse, ресайз, крипта: loop стоит, процессор пашет. Lag-метрика измеряет именно «сколько подряд цикл не мог обойти фазы» — JSON.parse не «тормозит» цикл, он его блокирует целиком. **(б) Main свободен** — ищи очередь (libuv thread pool) или ожидание вне процесса (пул соединений БД, внешний API). См. [[1.1 Diagnostics Cheat Sheet]]
Source: [[1.1 Event loop]]

## Ошибки сервера (EventEmitter)

Почему слушатель `server.on('error')` вешают ДО `listen()`, и что произойдёт при `emit('error')` без слушателя?
?
`listen()` асинхронен: ошибка привязки порта (EADDRINUSE) приходит **событием** в одном из следующих тиков, а не исключением в месте вызова. Конвенция EventEmitter: `emit('error')` без слушателя = throw необработанного исключения → **процесс падает** со стектрейсом. Слушатель ставят до `listen()`, чтобы он гарантированно существовал к моменту ошибки; `try/catch` вокруг `listen()` бесполезен — исключение вылетает в другом кадре стека.
Source: [[1.1 Event loop]]

## Валидация входа (из проекта shop-api)

`Number()` при разборе query-параметра: какие неожиданные значения дают `''`, `' '`, `'12abc'`, `'0x10'`? Почему это ловушка для валидации?
?
`Number('')` → **0** и `Number(' ')` → **0** — пустое значение молча превращается в валидный ноль; `Number('12abc')` → NaN; `Number('0x10')` → **16** (hex-строка парсится). Поэтому `?ms=` (пустой параметр) проходит `Number.isInteger` как 0. Ревью-урок: у числового диапазона проверять ОБА конца (0, отрицательные, пустая строка, дробные), и код должен соответствовать собственному тексту ошибки (`1..10000` обещано — проверяй и `ms < 1`).
Source: [[1.1 Event loop]]

## Метрика loop-lag (из проекта T4)

Что означают idle, active и utilization в строке `[lag] util=0.002 idle=499.0ms active=1.0ms`?
?
**active** — время, когда loop исполнял JS (колбэки, хендлеры запросов, микрозадачи). **idle** — loop «спит» в epoll: спросил у ОС «есть события?», ответа нет — это НОРМА здорового сервера (90%+ времени), НЕ блокировка и не «заморозка». **utilization** — не время, а ДОЛЯ: active/(active+idle). Блокировка видна как рост active (loop пашет busy-wait или синхронный код), а не idle.
Source: [[1.1 Event loop]]

Почему во время блокировки loop'а (`/block?ms=2000`) монитор [lag] замолкает — и что печатает после разблокировки?
?
Метрика — пассажир того же колеса: колбэк `setInterval` не может выполниться, пока loop занят. Строки пропадают на весь блок (проверено: 2 с тишины), а после освобождения печатается ОДНА строка за всё время молчания: `active≈2006ms`, `idle≈44ms` (хвост покоя до блока), `util≈0.979`. «Замолчавшая метрика» — сама по себе диагностический признак: если строки [lag] перестали приходить — loop встал.
Source: [[1.1 Event loop]]

Что делает `timer.unref()` и зачем его вызывать у мониторингового `setInterval`?
?
Активный таймер «держит процесс живым»: Node не выходит, пока есть активные хендлы (как `setTimeout` на секунду в `node -e`). `unref()` исключает таймер из этого счёта: если монитор — последнее, что осталось (сервер закрыт, `stop()` забыли), процесс всё равно завершится. Принцип: наблюдательный модуль не должен менять время жизни процесса.
Source: [[1.1 Event loop]]

Обработчик SIGINT: почему `server.close(() => process.exit(0))` лучше, чем сразу `process.exit(0)`?
?
`server.close()` снимает слушателя с порта и ДОЖИДАЕТСЯ in-flight запросов: уже принятые клиенты успевают получить свои ответы, а не обрыв (ECONNRESET, обрезанный ответ). Колбэк `close` срабатывает, когда активные соединения завершились, — только тогда выходим. Немедленный `exit` обрывает всех на середине. (Порт — вторичный фактор: TIME_WAIT достаётся ядру в обоих случаях.)
Source: [[1.1 Event loop]]

`eventLoopUtilization(a, b)` для дельты: в каком порядке передавать сэмплы и в чём ловушка?
?
Дельта считается как **a − b**, поэтому НОВЫЙ сэмпл передаётся ПЕРВЫМ: `eventLoopUtilization(now, prev)`. Если перепутать — idle/active придут отрицательными (бессмыслица), но utilization будет выглядеть нормальным: знак сокращается в отношении active/(active+idle). Урок ревью: сверять смысл каждого поля вывода, а не только итоговую цифру.
Source: [[1.1 Event loop]]

Метрика utilization vs lag-пробник (`monitorEventLoopDelay`): что видит каждый?
?
**Utilization** — среднюю занятость за интервал: «какую долю времени loop работал». Много мелких заторов (10 × 50 мс) заметно именно здесь. **Пробник** (шедулим колбэк и меряем опоздание / гистограмма `monitorEventLoopDelay`) — худший приступ: один затор на 800 мс даст пик лага, хотя средняя занятость почти не выросла. В бою ставят парой: utilization — «сколько пахал», probe — «какой самый длинный приступ».
Source: [[1.1 Event loop]]
