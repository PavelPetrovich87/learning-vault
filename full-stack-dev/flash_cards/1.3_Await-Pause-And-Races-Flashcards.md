# 1.3 (доп.) await: пауза и меняющийся мир — Flashcards

> Доп-колода по теме «что видит async-функция после паузы» (запрос из сессии по блоку D главы 1.3). Цель — мгновенно различать: общая переменная / локальный снапшот / мутация объекта / параметр, и видеть окно гонки между проверкой и записью. Все эталонные выводы проверены на Node 24.18.0. Глава — `[[1.3_Async-Control-Flow]]` (в работе).

## Правило-якорь

Одной фразой: что `await` замораживает, а что — нет?
?
`await` замораживает **позицию** («где я остановился») и собственные локальные переменные функции + **ссылки** на внешние окружения (замыкание). Он НЕ замораживает мир: всё общее — переменные внешних скоупов, содержимое объектов — при пробуждении будет таким, каким его оставили другие. Правило: хочешь «старое» — **скопируй** до паузы; хочешь защититься от других — **зарезервируй** до паузы.
Source: [[1.3_Async-Control-Flow]]

## Что видит функция после паузы

Что выведет и почему?

```js
let a = 0
async function f() {
  await delay(100)
  console.log(a)
}
f()
a = 1
```
?
`1`. `a` — общая переменная области модуля; при паузе сохраняется ссылка на окружение, а не копия значения. Функция просыпается и читает **текущее** содержимое `a`, которое к тому моменту поменял вызывающий код.
Source: [[1.3_Async-Control-Flow]]

Что выведет?

```js
let a = 0
async function f() {
  const snap = a
  await delay(100)
  console.log(snap)
}
f()
a = 1
```
?
`0`. Единственный способ увидеть «старое на момент упаковки» — самому скопировать значение в собственную локалку **до** паузы. `snap` — личный карман функции, кроме неё ссылок на это значение нет, поэтому изменение общей `a` на него не влияет.
Source: [[1.3_Async-Control-Flow]]

Что выведет?

```js
const cfg = { retries: 0 }
async function f() {
  await delay(100)
  console.log(cfg.retries)
}
f()
cfg.retries = 3
```
?
`3`. Обе стороны держат ссылку на **один и тот же объект**; пауза не клонирует содержимое. Мутация общего объекта видна с любой стороны — даже мимо переменных, напрямую через поля. `await` защищает только личные локалки, и то лишь потому, что до них никто не может дотянуться.
Source: [[1.3_Async-Control-Flow]]

Что выведет?

```js
let msg = 'старое'
async function f(text) {
  await delay(100)
  console.log(text)
}
f(msg)
msg = 'новое'
```
?
`старое`. Параметр — собственная переменная кадра функции: при вызове в неё копируется **значение**. Дальнейшее переприсваивание переменной вызывающего (`msg = ...`) на параметр не влияет. Тот же силуэт, что и карта про общую `a`, — но значение скопировано в момент вызова, а не читается заново после паузы.
Source: [[1.3_Async-Control-Flow]]

Что выведет?

```js
async function f(obj) {
  await delay(100)
  console.log(obj.n)
}
const o = { n: 0 }
f(o)
o.n = 5
```
?
`5`. Параметр копирует **ссылку** на объект, а не объект. Контраст с соседними картами: переприсваивать чужую переменную бесполезно (параметр-примитив останется старым), мутировать общий объект — видно сразу. Главный маркер таких задач: **reassign ≠ mutate**.
Source: [[1.3_Async-Control-Flow]]

## Порядок выполнения

Какой порядок вывода и почему?

```js
async function f() {
  console.log('A')
  await delay(10)
  console.log('C')
}
f()
console.log('B')
```
?
`A, B, C`. До первого `await` тело async-функции выполняется синхронно (отсюда `A` первым). На `await` функция сохраняет состояние и **возвращает управление** вызывающему — тот печатает `B` и заканчивается. Остаток тела (`C`) выполнится после resolve. `await` — точка выхода, а не ожидание: «ожидание» существует только для читателя кода.
Source: [[1.3_Async-Control-Flow]]

## Гонки на await-точках (прод)

Сколько раз выполнится `readConfig()`? Что получат вызовы?

```js
let cache = null
async function handler() {
  if (!cache) {
    cache = await readConfig()   // 50мс
  }
  return cache
}
handler()   // запрос 1
handler()   // запрос 2, сразу следом
```
?
**2 раза.** Классический TOCTOU: первый вызов проверил `cache` (пусто), уснул на `await`, **не записав ничего**; второй за время его сна видит всё ещё пустой `cache` и тоже запускает чтение. Окно гонки — между проверкой и присваиванием; его открыл `await`, разорвавший check и write на разные тики.
Source: [[1.3_Async-Control-Flow]]

Почини одним движением. Сколько раз теперь выполнится `readConfig()`?

```js
let p = null
function handler() {
  p ??= readConfig()   // readConfig() возвращает промис
  return p
}
handler()   // запрос 1
handler()   // запрос 2
```
?
**1 раз.** Проверка и присваивание — один синхронный шаг, без паузы между ними: второй вызов физически не может влезть внутрь. Кэшируем **промис**, а не значение — запись в кэш случается до паузы, а результат дожидается каждый у своего (того же) промиса. Это паттерн `/version` из shop-api: `pkgPromise ??= readFile(...)`.
Source: [[1.3_Async-Control-Flow]]

Что напечатается?

```js
let balance = 100
async function withdraw(amount) {
  if (balance >= amount) {
    await delay(10)
    balance -= amount
    return 'ok'
  }
  return 'нет средств'
}
withdraw(80).then(console.log)
withdraw(80).then(console.log)
setTimeout(() => console.log(balance), 50)
```
?
`ok`, `ok`, `−60`. Обе проверки `balance >= 80` прошли по старому `balance = 100`: проверки случились в первом тике, а записи — после пробуждений. Lost update (потерянная запись) **в однопоточном рантайме**: `await` разорвал check и write на разные тики. Лечение: проверка+резервирование синхронно одной операцией, либо очередь/транзакция, которая не даёт двум списаниям пересечься.
Source: [[1.3_Async-Control-Flow]]

Почему проверка и резерв обязаны стоять в одном синхронном куске — до `await`?

```js
const inFlight = new Set()
async function get(key) {
  if (inFlight.has(key)) return 'уже делается'
  inFlight.add(key)        // резерв
  await delay(10)          // ...и только теперь пауза
  inFlight.delete(key)
  return 'готово'
}
```
?
`has` + `add` выполняются в одном тике — между ними **не может** влезть конкурентный вызов, окно гонки закрыто. Если бы между проверкой и резервом стоял `await`, два вызова увидели бы пустой Set и оба пошли делать одну работу (та же TOCTOU-карта, но про дедупликацию). Это паттерн паука из главы: «зарезервируй до паузы» — в бой он же придёт как дедупликация задач и идемпотентность.
Source: [[1.3_Async-Control-Flow]]
