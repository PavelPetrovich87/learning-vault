# 1.2 Модульная система — Flashcards

> Карты по главе 1.2 «Модульная система: ESM/CJS, загрузка, DI на модулях». Глава в `[[1.2_Module-System]]`.

## Зачем модули

Какие три фундаментальные потребности закрывает любая модульная система?
?
(1) **Организация кода** — деление кодовой базы на файлы, независимая разработка и тестирование частей. (2) **Реиспользование и управление зависимостями** — шаринг функциональности между проектами, импорт модуля вместе со всеми его зависимостями. (3) **Инкапсуляция/сокрытие информации** — приватность по умолчанию, наружу только явный интерфейс.
Source: [[1.2_Module-System]]

Что такое revealing module pattern и при чём тут CommonJS?
?
IIFE создаёт приватный скоуп (переменные функции недоступны снаружи), а `return` выборочно экспортирует публичный API. Node фактически оборачивает каждый CJS-файл в такую функцию: `require`, `exports`, `module` — параметры обёртки, а не глобалы.
Source: [[1.2_Module-System]]

## Три фазы загрузки

Назови три фазы загрузки ES-модулей. Что происходит в каждой и чего НЕ происходит?
?
(1) **Construction/парсинг**: DFS от entry, находятся все импорты, загружается содержимое файлов; каждый модуль посещается один раз, циклы срезаются. (2) **Instantiation**: для каждого экспорта — именованная ссылка в памяти **без значения**; вторым проходом импорты линкуются с экспортами; **код НЕ выполняется**. (3) **Evaluation**: код выполняется post-order (снизу вверх), entry — последним; ссылки получают значения. Метафора книги: фаза 1 находит точки, фаза 2 соединяет их в пути, фаза 3 проходит пути.
Source: [[1.2_Module-System]]

Почему из трёх фаз следует, что импорты обязаны быть статическими?
?
Фазы разделены: никакой код не выполняется, пока весь граф не построен и не слинкован. Значит, загрузчику нужно знать все импорты заранее — верхний уровень, константные строки. Это даёт статический анализ дерева зависимостей → tree shaking. Идентификатор из выражения (`./strings-${lang}.js`) — только через динамический `import()`.
Source: [[1.2_Module-System]]

В каком порядке выполняются модули ESM-программы и кто выполняется последним?
?
Post-order DFS от entry point: сначала самые глубокие листья графа, затем вверх по дереву; **entry point выполняется последним** — к этому моменту все экспорты зависимостей вычислены. Поэтому в shop-api порядок: config → lib → хендлеры → реестр → loop-lag → server.js.
Source: [[1.2_Module-System]]

## Порядок старта процесса (стойкая тема)

Полная цепочка старта Node-процесса от команды `node server.js` до первого оборота event loop.
?
(1) Construction+instantiation графа модулей (парсинг, биндинги, линковка — код не выполняется). (2) Evaluation: модули post-order, server.js (entry) последним. (3) Во время evaluation выполняется строка `server.listen(...)` — она кладёт **заявку** (bind + события listening/error) в nextTick-очередь. (4) Синхронный код закончился → drain микрозадач/nextTick (bind, события listening/error) → стартует колесо фаз. Заявку listen кладёт сам вызов `listen()` — она не существует до выполнения кода entry.
Source: [[1.2_Module-System]]

Как три фазы загрузки соотносятся с фазами event loop из главы 1.1?
?
Весь граф модулей (construction → instantiation → evaluation) строится и выполняется **до первого оборота колеса** — это инициализация процесса, а не «работа внутри фаз». Исключение-нюанс: top-level await ставит модуль на паузу, и колесо **крутится, пока модуль ждёт** (поэтому require такого модуля → ERR_REQUIRE_ASYNC_MODULE). Динамический `import()` — уже асинхронная операция внутри работающего loop.
Source: [[1.2_Module-System]]

## Live bindings vs снимок CJS

Что можно и что нельзя делать с импортированным в ESM биндингом?
?
**Read-only**: переприсвоить из потребителя нельзя — `count++` → TypeError (как с const); нельзя и переприсвоить член namespace-объекта (`mod.logger = …` → TypeError). **Live**: читать актуальное значение можно всегда — изменение в источнике (через его `increment()`) видно импортёру. Мутация объекта-значения разрешена — сам биндинг не меняется (канал monkey patching).
Source: [[1.2_Module-System]]

«Снимок vs ссылка»: что получает импортёр в CJS и в ESM, и как это видно на примитиве?
?
**CJS**: shallow copy объекта exports — примитив, изменённый в источнике позже, потребителю **не виден** (снимок на момент require). **ESM**: live binding на переменную источника — потребитель всегда видит текущее значение. Это причина, почему в CJS-цикле потребитель видит `loaded: false`, а в ESM — `loaded: true`.
Source: [[1.2_Module-System]]

Циклическая зависимость a↔b: чем отличается поведение ESM от CJS?
?
**ESM**: не фатальна — фаза 1 срезает цикл (уже посещённый модуль не исследуется повторно), instantiation линкует ссылки, evaluation post-order даёт каждому актуальные ссылки; порядок импортов в entry не влияет. **CJS**: require немедленно выполняет модуль — один из двух окажется **полувыполненным** (частичный exports: свойства, навешанные до require, есть, остальных нет); кто полувыполнен — решает порядок входа из entry.
Source: [[1.2_Module-System]]

## Резолвинг

Три ветки алгоритма разрешения модулей Node — какие спецификаторы куда идут?
?
(1) **Файловые**: `/` — абсолютный путь → file:// URL; `./`, `../` — относительный от импортирующего файла. (2) **Core**: спецификатор без `/`/`./`/`../` сначала ищется среди core-модулей → возвращается с `node:` (bare ≠ автоматически npm-пакет!). (3) **Пакеты**: поиск в первой директории node_modules от импортирующего модуля **вверх** по дереву каталогов до корня ФС. Посмотреть резолв: `import.meta.resolve(specifier)`.
Source: [[1.2_Module-System]]

Как приватные node_modules каждого пакета решают dependency hell — и какой побочный эффект это создаёт?
?
Пакетный менеджер кладёт зависимости каждого пакета отдельно: у depB и depC — свои node_modules/depA. Запрос depA из разных файлов резолвится в **разные файлы (URL)** → несовместимые версии не конфликтуют. Побочный эффект: две версии одного пакета в дереве = два синглтона (модуль — синглтон per resolved URL) → `instanceof` и сравнение по ссылке ломаются.
Source: [[1.2_Module-System]]

## Экспорты

Аргументы сообщества против default-экспортов (и законные исключения)?
?
Default теряет: IDE-автодополнение и automatic imports (имя выбирает потребитель — по имени не найти происхождение), рефакторинг, tree shaking (default-объект «используется» целиком). Линтеры включают правило против (Biome). Исключения: core-модули Node (имеют и default, и named), React. Правило курса: named-экспорты везде; default — только модуль-одну-функцию (главную сущность).
Source: [[1.2_Module-System]]

## Интероп CJS/ESM

Именованный импорт из CJS-пакета падает — почему и два обхода?
?
Named-экспорты из CJS Node определяет **статическим анализом** исходника: явное `exports.foo = …` видно надёжно, а `module.exports = { foo }` — значение вычисляется в рантайме, анализатору невидимо → SyntaxError «Named export not found». Обходы: (1) `import pkg from '…'; const { foo } = pkg` — рекомендация из самой ошибки; (2) `createRequire(import.meta.url)` из `node:module` → настоящий require().
Source: [[1.2_Module-System]]

Импорт JSON в ESM: что требует синтаксис и зачем обязателен атрибут?
?
`import data from './x.json' with { type: 'json' }` — без атрибута ERR_IMPORT_ATTRIBUTE_MISSING. В динамическом `import()` атрибут вторым аргументом: `await import('./x.json', { with: { type: 'json' } })`, данные — в `default`. Причина — **безопасность**: явное объявление типа запрещает загрузчику исполнять содержимое как код (JS под маской .json — вектор атаки). Альтернативы: `readFile` + `JSON.parse` или `createRequire` + `require('./x.json')`.
Source: [[1.2_Module-System]]

## 🔬 Node 24 (freshness)

Что изменилось с require(esm) к Node 24 по сравнению с книгой?
?
Ошибка `ERR_REQUIRE_ESM` ушла в прошлое: `require(esm)` расфлажен (v20.19+/v22.12+) и стабилен (v25.4) — `require()` синхронно грузит ESM без флагов. Единственное ограничение: модуль с **top-level await** → `ERR_REQUIRE_ASYNC_MODULE` (синхронный require не может ждать асинхронной инициализации).
Source: [[1.2_Module-System]]

Ещё два 🔬-факта Node 24 по модулям?
?
(1) JSON-модули и import attributes (`with { type: 'json' }`) стабильны — экспериментальный warning не появится; атрибут остаётся обязательным. (2) `import.meta.filename`/`import.meta.dirname` — эквиваленты `__filename`/`__dirname` в ESM, Node ≥ 20.11 (январь 2024); универсально — `fileURLToPath(import.meta.url)`.
Source: [[1.2_Module-System]]

## Monkey patching

Как monkey patching сочетается с read-only bindings и чем это опасно?
?
Биндинг переприсвоить нельзя, но если значение — **объект, мутировать его свойства можно** (защита именованного экспорта — половинная). Патч через default-обёртку хрупок: нужны одновременно (1) default-экспорт объекта у субъекта, (2) патчер импортирует default, (3) потребитель тоже default — именованный импорт обходит патч. Опасность: supply chain — вредоносная зависимость патчит модули (CWE-349); чистый diff и зелёные тесты патч не ловят.
Source: [[1.2_Module-System]]
