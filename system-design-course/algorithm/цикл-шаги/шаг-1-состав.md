# Шаг 1 «Состав»

> Карта цикла: [[модуль-цикл]] · термины: [[словарь]] · карта алгоритма: [[Алгоритм выбора решений]]
> **Статус:** ✅ прогрилован (раунд 3, переоформлен раундами 8–8.1) · первый из шести шагов цикла. Исполняет проектировщик.

**Идея шага.** Ответить на вопрос «из каких частей состоит система?» — без единого названия технологии. Часть = **роль**: именованная обязанность («хранит сессии», «принимает сообщения от клиента»). Технологию в роль сажают позднейшие шаги — это **лестница конкретизации**: роль (шаг 1) → класс решений (шаг 3) → продукт (шаг 5). На каждой ступени решение обязано назвать то, что оно несёт: роль называет боль, класс — свою применимость, продукт — роль.

Шаг — функция над состоянием модели: читает готовые данные, работает, записывает результат. Сам ничего не хранит: рождённое внутри исполнения (кластер, цепочка ролей) либо записывается в состав, либо выбрасывается.

## Вход

| Что | Откуда | Зачем |
|---|---|---|
| Очередь болей — реестр, отсортированный по серьёзности | модель (реестр болей; сортирует оценщик — [[модуль-модель]]) | что болит и в каком порядке лечить |

**Формат входа (контракт):**

```yaml
# очередь болей = реестр в отсортированном виде; значения — из примера ниже («доска объявлений»)
- формулировка: сбой записи теряет опубликованное объявление   # свойство системы с числом, без технологий
  требование: НФТ «объявления не теряются»                     # откуда боль: запись рамки (ФТ или НФТ-число)
  сценарий: отказ элемента                                      # один из шести сценариев рамки
  класс: теряет данные                                          # оценщик выбрал из шкалы рамки
  доля: 2%                                                      # % работы системы, кому хуже; из параметров нагрузки
  # кратности нет — поле опционально
- формулировка: отказ единственного элемента роняет сервис
  требование: НФТ «отказ одного элемента не роняет сервис»
  сценарий: отказ элемента
  класс: роняет всё
  доля: 100%
  кратность: ×2                # пережить отказ одной копии может только пул из двух и больше
```

Порядок записей — уже итоговый: очередь приходит отсортированной. Шкала последствий и параметры нагрузки — **не вход шага**: их потратил оценщик при вычислении реестра (класс — из шкалы, доля — из параметров нагрузки).

Если цикл запускается впервые и реестра нет — сначала **baseline**: наивный монолит «всё в одном элементе» (в редизайне существующего проекта — текущая система). Оценщик считает боли baseline'а, это первая очередь.

## Тело шага

**1. Взять кластер** — верхнюю группу очереди: боли с общей причиной или общими пострадавшими. Не одну боль (боли связаны между собой) и не весь реестр (лечим порциями). Серьёзность кластера: класс — самый страшный из классов его болей, доля — объединение пострадавших, без двойного счёта общих.
**2. Придумать цепочку ролей, закрывающую кластер.**
- Порядок — по зависимостям: если роль Б не работает без роли А, роль А рождается раньше.
- Размер — минимальный: роль закрывает свою группу болей и ничего сверх; маленький шаг дешевле проверить и дешевле откатить.
- Соответствие болей и ролей — многие-к-многим: одна боль часто закрывается цепочкой из нескольких ролей, одна роль может закрывать несколько болей.
**3. Записать в состав** — одной из четырёх модификаций (таблица ниже). Шаг 1 — единственный шаг, которому разрешено менять состав; шаги 2–6 его только читают и, если он мешает, возвращаются сюда. У каждой модификации названа боль, которую она закрывает.
**4. Проверки** — все зелёные, иначе не выходим:
- **покрытие:** у каждого требования (ФТ и НФТ-числа) есть роль-носитель; требование без носителя — дыра;
- **kill-test:** смерть любой роли обязана ронять или деградировать именованное число; роль, чья смерть ничего не меняет, — лишняя;
- **связь оправдана обменом:** роли соединены, только если обмениваются работой хотя бы в одном сценарии.

### Четыре модификации состава (примеры)

| Вид | Боль → модификация |
|---|---|
| **Добавление роли** | данные в единственном элементе, его отказ — невосполнимая потеря → добавлена роль «вторичная копия хранилища» |
| **Разрез** | тяжёлые отчёты и лёгкие интерактивные запросы в одном элементе, отчёты блокируют интерактив → разрезан на «роль интерактива» и «роль отчётов» |
| **Слияние** | две роли всегда вызываются вместе и по отдельности не нужны, каждый запрос платит лишний сетевой переход → слиты в одну |
| **Смена связи** | при всплеске клиенты топят роль напрямую → между ними поставлен буфер-очередь, связь перестроена через него |

## Выход

**Новая версия состава** (роли + связи) — записана в модель. Каждый возврат на шаг 1 из шагов 2/3/6 — ещё одна версия; их последовательность — готовый рассказ о ходе проектирования.

**Формат выхода (контракт):**

```yaml
состав:
  версия: v2                                  # каждый возврат на шаг 1 порождает следующую версию
  роли:
    - имя: приёмник запросов                  # обязанность, без технологий
      закрывает:                              # боли; соответствие многие-к-многим
        - отказ единственного элемента роняет сервис
      кратность: ×2 → 2 копии                 # пережить отказ одной копии; уточнит шаг 2
      зависит от:                             # роли, без которых не работает; задаёт порядок рождения
        - хранилище объявлений
  связи:
    - от: приёмник запросов
      к: хранилище объявлений
      обмен: запись и чтение объявлений       # какая работа идёт по связи; без обмена связи нет
      работает в: каждом сценарии             # сценарий, в котором связь живая

протокол проверок:                            # прикладывается к версии состава
  покрытие:
    - требование: объявления не теряются
      носитель: вторичная копия хранилища
  kill-test:
    - роль: приёмник запросов
      смерть роняет: 1/N ёмкости, сервис жив
  обмен:
    - связь: приёмник → хранилище
      работает в: каждом сценарии
```

Побочный эффект: состав изменился → реестр болей пересчитался сам (он производная состава) → следующая итерация цикла читает уже новую очередь.

## Пример одного захода

Домен: доска объявлений. Показан **один заход** шага 1 — не весь шаг до стопа.

**Что пришло (вход).** Рамка (фрагмент): НФТ «объявления не теряются»; НФТ «отказ одного элемента не роняет сервис»; НФТ «поиск p95 ≤ 500 мс при пике»; ФТ «пользователь публикует объявление с фото». Параметры нагрузки: 50 000 DAU, 10 действий/день; нагрузка по действиям: поиск = 40% действий, публикация = 2% действий; пик ×3. Baseline: монолит «всё в одном элементе». Очередь болей (посчитана и отсортирована оценщиком по дефолтной шкале):

| # | Боль | Класс | Доля |
|---|---|---|---|
| 1 | сбой записи теряет опубликованное объявление | теряет данные | 2% публикаций |
| 2 | отказ единственного элемента роняет сервис | роняет всё | 100% запросов |
| 3 | поиск по всем объявлениям 4 с на пике | деградирует | 40% запросов |
| 4 | нет черновиков (ФТ) | деградирует | 5% действий |

**Как шло (тело).**
1. Кластер = боли 1–2: общая причина — «всё в одном элементе», данные и сервис живут вместе и вместе умирают. Класс кластера — «теряет данные» (худший из двух), доля — 100% (объединение пострадавших).
2. Цепочка ролей в порядке зависимостей:
   - «хранилище объявлений» — данные переезжают из монолита (разрез);
   - «вторичная копия хранилища» — закрывает боль 1 (добавление);
   - «приёмник запросов» (пул из 2 копий — кратность ×2 из боли) — закрывает боль 2: отказ одного обработчика больше не роняет сервис (разрез); зависит от хранилища.
3. Модификации состава: два разреза + одно добавление; у каждой названа закрываемая боль.
4. Проверки: kill-test — смерть копии возвращает боль 1 (риск потери объявлений), смерть одного обработчика отнимает половину ёмкости, но сервис жив; связь «приёмник → хранилище» обменивается работой (запись и чтение) в каждом сценарии; у болей кластера есть роли-носители.

Боль 3 (поиск) в кластер не вошла — минимальность: заход лечит одну группу болей, поиск — следующий заход.

**Что получилось (выход).** Состав v2: три роли (хранилище, копия, приёмник с кратностью 2) + связь «приёмник → хранилище» с обменом «запись и чтение объявлений, каждый запрос». Протокол проверок зелёный. Побочный эффект: реестр пересчитался — боли 1–2 погасли, очередь теперь возглавляет поиск (боль 3). Шаг не закончен: реестр не пуст.

## Когда шаг закончен

Очередь пуста по оценщику: при текущем составе и текущей рамке лечить больше нечего. Это не финал: слабость оценщика (примерные расчёты не увидят, что одного хранилища на два вида работы не хватит) вскроется на шаге 2. Окончательная готовность — **подпись**: первый полный проход 1→6 без возвратов.

## Типичные провалы

- **Бренд вместо роли:** «поставим Redis» в составе — скрытое решение: продукт (третья ступень лестницы) назначен без проверок шагов 2–5. Правильно: «роль быстрого хранилища сессий».
- **Роль без боли:** не проходит kill-test — «архитектура-прыжок», здание без несущей причины.
- **Связь без обмена:** роли соединены «на всякий случай».
