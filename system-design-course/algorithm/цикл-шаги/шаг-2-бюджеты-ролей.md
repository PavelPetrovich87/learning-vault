# Шаг 2 «Декомпозиция бюджетов ролей»

> Карта цикла: [[модуль-цикл]] · термины: [[словарь]] · карта алгоритма: [[Алгоритм выбора решений]]
> **Статус:** ✅ прогрилован (2026-09-07, раунды 9–10) · второй из шести шагов цикла. Исполняет проектировщик.

**Идея шага.** SLO — это НФТ с числом, и живёт оно в **рамке**: например, «поиск p95 ≤ 500 мс при пиковой нагрузке». Это обещание про систему целиком — от клиента до ответа; меняет его только владелец, через торг.

Почему общее число нельзя отдать части: время ответа **складывается из участков ролей**, которые запрос проходит по очереди. Клиентские 500 мс — это не чьё-то личное время, а сумма: доставка 100 + приёмник 10 + хранилище 390. Ни одна роль не владеет этими 500 мс целиком. Поэтому «какое хранилище укладывается в 500 мс?» — пустой вопрос: пока хранилищу не назначена его доля, проверять нечего, любое «укладывается». Шаг 2 назначает доли: приёмнику — «≤ 10 мс», хранилищу — «≤ 390 мс». Это и есть **бюджеты ролей** — собственные требования ролей, по которым шаг 3 отбирает кандидатов: класс хранилищ, отвечающий за 390 мс, проходит; отвечающий за 600 — отсеивается.

Главный сигнал шага — те же суммы, когда они не сходятся: минимальные цены ролей плюс доставка дают 560 > 500 → состав обещание не исполнит, и это выясняется здесь, а не после постройки системы.

Шаг — функция над состоянием модели: читает SLO рамки и состав, записывает бюджеты в модель, сам ничего не хранит. Наполняет заглушку модели «нагрузка на роли, бюджеты и ёмкость».

## Вход

| Что | Откуда | Зачем |
|---|---|---|
| SLO — все НФТ-числа | рамка (требуемые значения) | числа, которые раскладываем |
| Состав — роли и связи | модель (записан шагом 1; формат — контракт выхода [[шаг-1-состав]]) | из связей читаются пути запросов |
| Протокол проверок состава | модель (приложен шагом 1; покрытие: требование → носитель) | носители неделимых требований |
| Параметры нагрузки | рамка | частоты для нагрузки на роли и ёмкости |
| Нагрузка по действиям | рамка (подраздел поля 4: действие · доля · объект) | действия для проводки по путям и доли для λ |
| Сценарии | рамка | условия проверки раскладки (день · пик · рост) |
| Порядки величин | справочник | доставка и цены фаз без брендов |

**Формат входа (контракт):**

```yaml
# SLO = НФТ-числа рамки; значения — из примера ниже («доска объявлений»)
- качество: latency
  требуемое: p95 ≤ 500 мс            # число + перцентиль
  условие: пик и горизонт роста       # при каких сценариях обязано держаться
- качество: доступность
  требуемое: ≥ 99%
  условие: за месяц
- качество: сохранность
  требуемое: объявления не теряются   # числа нет — обязанность; неделимое
# нагрузка по действиям — подраздел поля 4: «поиск 40% действий; публикация 2%, объект ~200 КБ»
# состав и протокол проверок — в формате выхода шага 1 (версия, роли, связи, покрытие, kill-test, обмен)
```

## Тело шага

**1. Разобрать качества.** Выписать все SLO и прогнать каждый через тест делимости (правило ниже): делимые — режем на доли, неделимые — оставляем носителю (роль, которой шаг 1 уже назначил это требование проверкой покрытия — [[шаг-1-состав]]); стоимость не трогаем.

**2. Посчитать снизу.** Вычесть доставку (среда до входа системы и обратно, порядок из справочника) — остаток и есть сумма, доступная ролям. Затем оценщик проводит каждое действие (из нагрузки по действиям; имена действий — глаголы ФТ «делаем») от входа по цепочке ролей и суммирует цены фаз — порядки из справочника, не бренды. Нет входа для цены фазы → строка в реестр вопросов.

**3. Сверить сверху.** Доставка + сумма фаз против SLO — в каждом сценарии рамки, при котором SLO обещан, а не только в среднем «дне»: в пик запросов больше — очереди длиннее, фазы дороже; на горизонте роста данных больше — чтение дольше. Если сумма влезает, а доля какой-то фазы несправедлива — перераспределить: излишек дешёвой фазы дорогой. Единственная правка чисел без смены состава.

**4. Раздать бюджеты, подтвердить неделимые.** Доля роли по каждому делимому качеству; сборка обратно обязана сойтись: доставка + доли latency ≤ SLO, девятки доступности в произведении ≥ SLO (на примерных расчётах — правило «+1 девятка», см. арифметику). Неделимые требования остаются у носителей из протокола покрытия шага 1 — шаг 2 подтверждает, нового носителя не ищет (не у кого — возврат на шаг 1).

**5. Посчитать ёмкость.** Два числа на роль: нагрузка — сколько запросов/с к ней приходит (арифметика ниже) — и слоты — сколько запросов она обязана держать одновременно: λ × W, где W — время слота, своя фаза + ожидания подчинённых ролей (Закон Литтла); план при загрузке ≤ 70–80 %. Здесь кратность шага 1 («не 1 элемент, а 6») проверяется числом: слоты раскладываются по копиям — видно, сколько копий реально нужно.

**6. Решить «не влезает».** Если даже минимальные цены фаз плюс доставка превышают SLO — по возрастанию цены: перераспределить (п. 3, уже попробовано) → сменить состав или связи (возврат на шаг 1) → торг (SLO меняет только владелец, проектировщик идёт переговорщиком).

### Тест делимости (правило)

К каждому SLO один вопрос: **можно ли назначить каждой роли её долю так, чтобы доли собрались обратно в общее число?**

| Качество | Сборка из ролей | Вердикт | Действие шага |
|---|---|---|---|
| latency | сумма времён ролей пути | делимое | резать на доли |
| доступность (availability) | произведение доступностей ролей пути | делимое | раздать девятки |
| сохранность | нет сборки | неделимое | подтвердить носителя из протокола покрытия |
| стоимость | сумма | делимое, но не режем | валюта кандидатов — шаги 4–5 |

По одному качеству за раз: мс, девятки и рубли не смешиваются; обмен между качествами — только через цену кандидатов (шаги 4–5) или торг с владельцем.

### Арифметика долей (техника оценщика)

- **Доставка и фазы.** SLO обещано end-to-end — часы на клиенте: `SLO = доставка + Σ фаз ролей`. **Доставка** — среда до входа системы и обратно: не роль, в составе её нет; цена — порядок из справочника (регион ~десятки мс, межрегион ~сотня); вычитается из SLO до дележа. **Фаза** — участок пути внутри одной роли; фазы бывают только у ролей. (Канон: 1.2, упр. 2 — бюджет латентности; словарь, Latency — response time = обслуживание + сеть + ожидание.)
- **Девятки доступности.** Доступности ролей пути перемножаются и съедают надёжность системы: три роли по 99% дают системе 97% — простои ролей складываются в простой системы, поэтому ролям нужно больше девяток, чем системе. Примерные расчёты — правило **«+1 девятка»**: каждой роли пути на одну девятку больше системной, одна для всех (позиция в цепочке не важна — множители равноправны, умножение идёт один раз по всему пути, а не по уровням); запаса хватает до ~10 ролей (0.9999¹⁰ ≈ 99.9%). Роль на нескольких путях берёт самое строгое из требований. Точная развеска — произведением ровно по SLO (99.95% × 99.95% ≈ 99.9%) — исполнениям «расчёт» и «прогон».
- **Путь запроса.** Вход системы — роль, в которую не входит ни одной связи от других ролей (клиент — не роль). Действие пользователя (из нагрузки по действиям — подраздел поля 4) проводится от входа по цепочке ролей состава; механика взаимодействия (поллинг против push, ходок за сессией) — наше решение, множит запросы. Путь — рабочий материал исполнения: рождается и выбрасывается; в модель пишется только свёртка — нагрузка на роли.
- **Нагрузка на роли** = параметры нагрузки × механика взаимодействия. Формат записи: `роль · сценарий · λ запр/с`.
- **Слот** — единица параллельности роли: один слот = один запрос одновременно. Воркер держит слот и пока синхронно ждёт подчинённую роль (обработчик ждёт хранилище) — время слота = своя фаза + ожидания. Слоты = λ·W (Закон Литтла), план при загрузке ≤ 70–80 % — у порога взрывается хвост.

### Конвейер чисел (откуда → как → куда)

## Выход

**Бюджеты ролей** — записаны в модель (наполняют заглушку производных). Весь пакет привязан к версии состава (`версия_состава`); у каждого числа — происхождение (`выведено_из`): из какого SLO какого сценария оно выведено. Секции верхнего уровня идут по адресам записи: производные (бюджеты · доставка · неделимые · нагрузка · ёмкость), реестр вопросов (наружу), возвраты (переход цикла).

**Формат выхода (контракт):**

```yaml
версия_состава: v2                          # после возврата на шаг 1 — пересчёт
бюджеты_ролей:
  - роль: приёмник запросов
    качество: latency
    требуемое: ≤ 10 мс на запрос поиска     # число + что измеряем
    выведено_из: «поиск p95 ≤ 500 мс, пик»
  - роль: хранилище объявлений
    качество: latency
    требуемое: ≤ 390 мс на поиск
    выведено_из: «поиск p95 ≤ 500 мс, пик»
  - роль: приёмник запросов
    качество: доступность
    требуемое: ≥ 99.9% за месяц   # правило «+1 девятка» к системным 99%
    выведено_из: «доступность ≥ 99% за месяц»
  - роль: хранилище объявлений
    качество: доступность
    требуемое: ≥ 99.9% за месяц   # та же девятка — всем ролям пути
    выведено_из: «доступность ≥ 99% за месяц»
доставка:                                   # вычет из SLO до дележа; не бюджет роли
  - условие: клиенты в соседнем регионе
    цена: ~100 мс (RTT)
    выведено_из: справочник (порядок)
неделимые:                                  # носители из протокола покрытия шага 1
  - требование: объявления не теряются
    носитель: хранилище объявлений (+ вторичная копия)
нагрузка_на_роли:
  - роль: приёмник запросов
    сценарий: пик
    λ: 18/с          # все запросы; механика: одно действие ≈ один запрос
  - роль: хранилище объявлений
    сценарий: пик
    λ: 7/с           # поиск
ёмкость:                                    # слоты = λ·W ÷ 0.75; вернулась кратность шага 1
  - роль: приёмник запросов
    слоты: 1 на копию   # кратность ×2 подтверждена
  - роль: хранилище объявлений
    слоты: 4 одновременных поиска
реестр_вопросов:                            # → наружу, к владельцам чисел (модель, М5)
  - число: время поиска при объёме ×10
    подстановка: ~3.5 с (порядок)
    развилка: 1–4 с — возврат при любом исходе
    режим: в долг
возвраты:                                   # переход цикла, не данные модели
  - на шаг 1: поиск на горизонте роста не влезает (~3.5 с > 500 мс)
```

## Пример одного исполнения

Домен: доска объявлений, продолжение примера шага 1 — тот же состав v2 (приёмник ×2 → хранилище + вторичная копия).

**Что пришло (вход).** SLO рамки: «поиск p95 ≤ 500 мс» (пик и рост); «доступность (availability) ≥ 99% за месяц»; «объявления не теряются». Параметры: 50 000 DAU, 10 действий/день; нагрузка по действиям: поиск 40% действий, публикация 2% действий (объект ~200 КБ); пик ×3. Справочник: доставка до соседнего региона ~100 мс (RTT); маршрутизация ~10 мс; поиск по диску на их объёме ~350 мс.

**Как шло (тело).**

1. **Классификация SLO (П1).** Выписали все SLO рамки и прогнали через тест делимости. «Поиск p95 ≤ 500 мс» — делимое: время ответа — сумма участков ролей, его можно резать на доли. «Доступность ≥ 99%» — делимое: доступности ролей перемножаются, девятки можно раздать ролям. «Объявления не теряются» — неделимое: «теряет по чуть-чуть» не собирается обратно в «не теряет совсем»; носитель уже назначен шагом 1 (хранилище с вторичной копией) — подтверждаем, нового не ищем.
2. **Нагрузка на роли (П2).** Механика взаимодействия пока простая: одно действие ≈ один запрос, каждый запрос идёт через приёмник, поиск дополнительно падает на хранилище. Считаем λ на пик: 50 000 DAU × 10 действий/день ÷ 86 400 с ≈ 5.8 действий/с в среднем; ×3 (пик) ≈ 18 запросов/с на приёмник; поиск — 40% действий ≈ 7 запросов/с на хранилище. Записали в `нагрузка_на_роли`.
3. **Снизу: доставка и фазы (П3).** Вычли доставку: клиенты в соседнем регионе, справочник даёт ~100 мс (RTT), — ролям остаётся 500 − 100 = 400 мс. Цены фаз — порядки из справочника: приёмник (маршрутизация) ~10 мс, поиск по диску на текущем объёме ~350 мс. Сумма пути: 100 + 10 + 350 = 460 мс.
4. **Сверка сверху по сценариям (П3).** Пик: 460 ≤ 500 — влезает. Горизонт роста (объём ×10): поиск по диску масштабируется с объёмом — порядок ~3.5 с, сумма ~3.6 с > 500 мс — не влезает. Это не ошибка расчёта, а сигнал: текущий состав не исполнит обещание на росте.
5. **Бюджеты (П3, П4).** Резерв 500 − 460 = 40 мс отдали самой дорогой фазе — поиску в хранилище: бюджет 350 + 40 = 390 мс; приёмнику — 10 мс. Сборка обратно: 100 + 10 + 390 = 500 — сходится. Девятки: системные 99% — это две; по правилу «+1 девятка» каждой роли пути — по три (99.9%); проверка произведением: 99.9% × 99.9% ≈ 99.8% ≥ 99% — с запасом.
6. **Ёмкость (П5).** Слоты = λ × W ÷ 0.75. Приёмник: 18 × 0.01 ÷ 0.75 ≈ 0.24 — меньше одного слота на копию, значит двух копий (кратность шага 1) хватает: кратность подтверждена числом. Хранилище: 7 × 0.35 ÷ 0.75 ≈ 3.3 — округляем вверх до целого: 4 слота одновременного поиска.
7. **«Не влезает» (П3 → возврат).** На горизонте роста даже минимальная цена фазы поиска (~3.5 с) больше всего SLO — перераспределение долей не поможет, состав надо менять: записан возврат на шаг 1 — родить роль поиска. Очередь болей это предсказывала: после пересчёта на составе v2 боли «теряет данные» и «роняет всё» закрыты, и «поиск 4 с на пике» возглавила очередь ещё до шага 2. Время поиска при объёме ×10 — число с развилкой (порядок 1–4 с), но при любом исходе решение то же, поэтому строка ушла в реестр вопросов в режиме «в долг», работа продолжена на консервативной подстановке ~3.5 с.

**Что получилось (выход).** Бюджеты пика записаны на составе v2 (контракт выше), возврат на шаг 1 зафиксирован. Шаг не закончен целиком: на пике всё сошлось, на горизонте роста — нет; закончится, когда шаг 1 родит роль поиска и распределение сойдётся во всех сценариях рамки.

## Когда шаг закончен

- каждый SLO рамки разложен: делимые — до всех ролей своих путей, неделимые — у носителей;
- каждая роль, через которую идут запросы, несёт числа по каждому качеству, которое на неё ложится;
- сборка обратно сходится по каждому SLO в каждом сценарии рамки;
- «не влезает» не спрятано: каждое — возврат на шаг 1 или торг, зафиксировано явно.

## Типичные провалы

- **Бюджет из воздуха:** число роли не выводится из SLO → `выведено_из` обязательно: из какого SLO какого сценария.
- **Делить неделимое:** «хранилище теряет не больше 40% объявлений» — абсурд; тест делимости обязателен для каждого SLO. И обратное — резать стоимость раньше шагов 4–5.
- **Впритык:** план ёмкости при загрузке → 100 % — хвост взрывается ещё до отказа → слоты с запасом 70–80 %.
- **Один сценарий:** распределение посчитали только для «дня», пик и рост не смотрели → все сценарии рамки.
- **Идеальный путь:** чистое обслуживание без очередей и доставки → цена фазы = обслуживание + ожидание; доставка вычитается из SLO до дележа.
- **Стерильность потеряна:** «Redis быстрый» при дележе → цены — порядки из справочника; бренд назначает шаг 5.
- **Молчаливая правка SLO:** не влезает — и число рамки тихо поправили под расчёт → SLO меняет только владелец, через торг.
- **Дорогое раньше дешёвого:** сразу ломать состав → лестница: перераспределение → шаг 1 → торг.
