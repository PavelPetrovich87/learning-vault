# Словарь терминов

> Живой словарь алгоритма [[Алгоритм выбора решений]]: термины добавляются по мере прогрила модулей, по куску за раз. **Дисциплина языка:** в заметках модулей используются термины из этого словаря; новый термин вводится здесь, а не по ходу текста. **Английская пара (правило, 2026-09-07):** специфический для системного дизайна термин сопровождается в скобках общеупотребительным английским эквивалентом — latency, availability, SLO; русский термин основной, английский — мост к книгам и интервью.
>
> ⚠️ **Двойное существование.** Канон — `algorithm/словарь.md` в репозитории курса; эта — зеркало. При любой правке обновляются **обе** копии.

## Общее

| Термин | Определение |
|---|---|
| **Проектировщик** | Человек, исполняющий алгоритм: проходит шаги цикла, выступает переговорщиком с владельцами чисел и временно владеет предположениями. Роль цикла, не модуль. |
| **Прогриловано** | Содержимое пункта обсуждено на гриллинге и записано: определения, правила, границы согласованы. |
| **Структура зафиксирована** | Каркас модуля собран (состояния, права, инварианты), но отдельные части ещё не наполнены определениями — они-заглушки и ждут своего шага цикла. Не путать с «прогриловано»: структура не означает содержимое. |
| **Заглушка** | Часть модуля, у которой есть ячейка в состоянии и известно, каким шагом она наполнится, но определения ещё нет. Не дыра: место и срок определены. |
| **Наполнение** | Доля частей модуля, прогрилованных сверх зафиксированной структуры; записывается как «наполнение X/Y» (у модели — 4/5). |
| **Типичный провал** | Повторяющийся сценарий ошибки, против которого написано правило модуля; рубрика «как это обычно ломается». |
| **Latency** (языковое решение, 2026-09-01) | Задержка. Пишем английским словом, не «латентность»: русский гибрид тянет ассоциацию «скрытое» (латентный период, латентная переменная), а инженерный смысл термина — «задержка». Строго (1.4, Клеппманн): latency — только ожидание; полное время запроса — response time (обслуживание + сеть + ожидание). |
| **Роль** (2026-09-01) | То, что элемент состава обязан выполнять: именованная обязанность без технологии («сессионный стор», «канал доставки»). Конкретного исполнителя в роль сажает шаг 5 (продукт). Голая «роль» — всегда роль состава; роли людей — «роль пользователя». Предложение переименовать в «элемент» отозвано: элемент читается как вещь, роль — функция. |

## РАМКА (куски 1–3: контракт · различие с моделью · типичный провал — прогрилованы)

| Термин | Определение |
|---|---|
| **Рамка** | Внешние вводные данные проекта: факты и чужие решения, влияющие на проектирование; наши проектные решения менять их не могут. Меняет только владелец — извне. |
| **Владелец числа** | Тот, кто имеет право установить значение: заказчик, интервьюер, маркетинг, справочник; крайний случай — сам проектировщик с пометкой «предположение». |
| **Чтение / запись рамки** | Чтение — шаг берёт значение для работы; запись — изменение значения. Запись — монополия владельца. |
| **Стерильность** | Запрет называть в записях рамки технологии, продукты и компоненты: рамка хранит условия, не решения. Тест: прочитай запись вслух — названия частей системы не должны прозвучать. |
| **Уточнение** | Вопрос → ответ владельца: узнать существующее значение (заполнить пустое, снять предположение). Принятого не меняет. |
| **Торг** | Предложение обмена → решение владельца: изменить уже принятое значение за названную выгоду (ослабить SLO ↔ дешевле). |
| **Число без владельца** | Значение, выглядящее фактом без источника: нельзя проверить, обменять, обновить. Красный флаг процесса, а не данность. |
| **Правило двух источников** | У любого числа ровно одно из двух происхождений: из рамки (установил владелец · мы временно предположили · арифметика над числами рамки) или наш расчёт в модели (в формулу входят проектные решения). |
| **Тест «рамка или модель» (тест проектной зависимости)** | Куда положить число: мысленно поменяй любое проектное решение. Число изменилось — модель; не изменилось — рамка. |
| **Предположение** | Число, которое мы сами временно выдаём за владельца, пока он не ответил. Живёт в рамке с пометкой; меняется уточнением, но не решением. |
| **Требуемое / фактическое значение** | Требуемое — сколько должно быть (рамка, меняется только торгом). Фактическое — сколько даёт наше решение (модель до запуска, мониторинг после). |

## НАГРУЗКА (раунд 7)

| Термин | Определение |
|---|---|
| **Параметры нагрузки** | Поведение пользователей и его вычислимые следствия: действий/день, размеры, λ средняя/пиковая, объём/год. Не требование, а условие, при котором НФТ обязаны выполняться. Рамка, поле 4. Термин Клеппманна (гл. 1); в курсе 1.2 то же называлось «воронкой». |
| **Нагрузка по действиям** (формат утверждён пользователем, 2026-09-07; рабочее имя «раскладка действий» отозвано) | Подраздел поля 4 «Параметры нагрузки»: общий счётчик действий/день, разложенный по конкретным действиям. Имя действия — глагол из ФТ «делаем»; глубина разбиения = глубина ФТ, дальше не режем. Запись: `действие · доля в % действий · объект (если есть)`; доли в сумме ~100%; единица «% запросов» запрещена — запросов на действие считает механика взаимодействия (модель). Потребители: доля затронутого (реестр болей), шаг 2 — путь запроса и λ на роли. |
| **Нагрузка на роли** | Сколько работы прилетает каждой роли после механики (поллинг, фан-аут, обращения за сессией). Модель; распределение по ролям — работа шага 2. = параметры нагрузки × механика. |
| **Нагрузка на роли = параметры нагрузки × механика взаимодействия ролей** | Параметры от решений не зависят (рамка), механика взаимодействия — наша (модель). Разводит тест «рамка или модель». «Спрос» выведен из оборота — рыночный термин (раунд 7.1). |
| **Механика взаимодействия ролей** | Наши решения о том, как роли взаимодействуют между собой и с клиентами, обслуживая работу пользователей: поллинг против push, фан-аут, обращение за сессией. Входит множителем в нагрузку на роли. |
| **Поллинг** (языковое решение, 2026-09-01) | Механизм свежести: клиент сам периодически спрашивает сервер, «есть ли новое»; противоположность — push (сервер сообщает сам). Пишем «поллинг», не «опрос»: «опрос» — слишком широкое понятие. Частота поллинга — модель; свежесть — рамка. |

Отклонено (зафиксировано, чтобы не возвращаться): «нагрузочные требования» как третий сорт требований рядом с ФТ/НФТ — нагрузка не требование, а условие; требованием она становится только внутри НФТ производительности: «p95 ≤ X при нагрузке Y» (канон: Клепманн разводит параметры нагрузки и показатели производительности; скелет RFC — разделы 2 «Требования» и 3 «Оценка нагрузки»).

## МОДЕЛЬ (структура зафиксирована · наполнение 4/5)

| Термин | Определение |
|---|---|
| **Реестр болей** | Полный список болей текущего состава: боль = f(требование × сценарий × состав). Производная («тень» состава и рамки): руками не правится, пересчитывается при каждой модификации состава. Отдаётся шагу 1 очередью — отсортированной по мере серьёзности (сортирует оценщик). |
| **Реестр вопросов** (прежде — «реестр запросов», переименован 2026-09-07) | Производная часть модели — список «что добыть вовне»: `{какое число · у кого · какой вопрос · какая развилка · что подставлено на время}`. Пишут оценщик (нет входа · чувствительное предположение) и шаги цикла; читает проектировщик-переговорщик — носит вопросы владельцам чисел. Переименование освободило слово «запрос» для единицы работы (один запрос = одна порция работы роли в пути). |
| **Мера серьёзности** | Правило сортировки реестра болей в очередь: сначала класс последствий, при равенстве — доля затронутого; без арифметики. Живёт в модели, исполняет оценщик; дефолтный порядок и правило — в заметке модели. |
| **Класс последствий** | «Что будет, если боль не лечить»: теряет данные / роняет всё / деградирует. Упорядочены по необратимости; порядок для проекта подтверждает владелец (рамка: «что для нас необратимо?»). Оценщик выбирает класс каждой боли из шкалы рамки. |
| **Доля затронутого** | Скольким станет хуже, в % от всей работы системы: у ФТ — доля действий, которым нужна функция; у НФТ — доля запросов/пользователей, которым хуже. Считает оценщик из параметров нагрузки. |

## ЦИКЛ · шаг 1 «Состав» (прогрилован, раунд 3)

| Термин | Определение |
|---|---|
| **Кластер болей** | Порция реестра болей на один заход в цикл: самый серьёзный срез очереди (сортировка: класс последствий → доля затронутого). Не хранится — существует только внутри исполнения шага 1; не вторая сущность рядом с реестром, а выборка из него. Серьёзность кластера = max по классу, объединение по доле. |
| **Цепочка минимальных ролей** | Результат развёртки кластера: новые роли в порядке зависимостей, каждая минимального размера и закрывает названную боль. Через цепочку шаг 1 модифицирует состав. |
| **Заход** | Одно исполнение шага 1: взят один кластер болей, развёрнут в цепочку ролей, состав изменён. Не путать с проходом — полным циклом 1→6. |
| **Baseline** | Отправная точка цикла: наивный монолит «всё в одном элементе»; в редизайне существующего проекта — текущая система. Его реестр болей — первая очередь. |
| **Модификация состава** | Разрешённое изменение состава, один из четырёх видов: добавление роли, разрез, слияние, смена связи. Исполнитель — только шаг 1; каждая модификация называет закрываемую боль. Слово «мутация» выведено из оборота (2026-09-01). |
| **Кратность** (слово «доза» выведено из оборота, 2026-09-02) | Во сколько раз одного минимального элемента не хватит (×N): у боли — поле очереди, у роли — сколько родить экземпляров. Экземпляр — не обязательно копия: копия (реплика) закрывает отказоустойчивость, доля (шард) — объём, слоты — мощность (посчитает шаг 2). Примеры: пик 240 запросов/с при 40 на элемент → ×6; пережить отказ одной копии → ×2. В сортировке не участвует (серьёзность — про порядок, кратность — про размер); уточняется бюджетами шага 2. |
| **Kill-test** | Проверка роли: её смерть обязана ронять или деградировать именованное число; иначе роль лишняя. |
| **Носитель** | Роль, которой шаг 1 назначил требование (ФТ или НФТ-число) проверкой «покрытие»: у каждого требования обязан быть носитель, требование без носителя — дыра в составе. Шаг 2 для неделимых качеств нового носителя не ищет — подтверждает носителя шага 1 (нет носителя — возврат на шаг 1). Пример: «объявления не теряются» → носитель — хранилище объявлений + вторичная копия. |
| **Подпись состава** | Критерий готовности состава: первый полный проход 1→6 без возвратов. |

## ЦИКЛ · шаг 2 «Декомпозиция бюджетов ролей» (прогрилован, раунды 9–10)

| Термин | Определение |
|---|---|
| **SLO** | Целевое значение НФТ-числа, при котором система считается исправной: «p95 ≤ 300 мс при пиковой нагрузке», «доступность ≥ 99,9 % за месяц». НФТ без числа не существует (1.3) — SLO и есть это число вместе с условием: перцентиль, период, сценарий. В рамке хранится как требуемое значение (меняется только торгом); фактическое даёт наше решение — модель до запуска, мониторинг после. Канон: 1.4 (Клеппманн, стр. 40 — перцентили как контракт). |
| **Доступность (availability)** (языковые решения, 2026-09-02; английская пара — 2026-09-07) | Доля времени (или запросов), за которую система выполняет свою функцию; записывается «девятками»: 99,9 % ≈ не больше 43 минут простоя в месяц. Английская пара — availability, термин книг и интервью; uptime — бытовой синоним («время работы»); accessibility — другое понятие (доступность интерфейса для людей с ограничениями, a11y), не про девятки. Канон: 1.2 (девятки), 1.4 (девятки приложены к перцентилям). Сборка из частей — произведением: запрос проходит роли подряд, система ответила, только когда живы все роли его пути, поэтому две роли по 99 % дают системе 99 % × 99 % ≈ 98 %. Отсюда работа шага 2 с этим качеством: назначить каждой роли её девятку, чтобы система удержала свою. |
| **Бюджет роли** | Собственное требование роли — её доля качества, выведенная из SLO (поле контракта `выведено_из`). По бюджетам шаг 3 отбирает кандидатов: класс, не умеющий в 390 мс, отсеивается. Сборка бюджетов пути обязана сходиться обратно в SLO. |
| **Качество** | Вид, по которому система оценивается числом: latency · доступность (availability) · сохранность · стоимость. По одному качеству за раз: мс, девятки и рубли не смешиваются; обмен между качествами — только через цену кандидатов (шаги 4–5) или торг с владельцем. |
| **Делимое / неделимое** (тест делимости) | Можно ли назначить ролям доли, собирающиеся обратно в общее число: latency — делимое (сумма времён ролей пути), доступность — делимое (произведение доступностей), сохранность — неделимое (нет сборки; назначается носителю), стоимость — делимое, но не режем (валюта кандидатов шагов 4–5). Тест обязателен для каждого SLO; исполняет П1 шага 2. |
| **Путь запроса** | Цепочка ролей от входа системы (роль без входящих связей; клиент — не роль) по действию пользователя. Рабочий материал исполнения шага 2: рождается при проводке действий (П2) и выбрасывается; в модель пишется только свёртка — нагрузка на роли. |
| **Фаза** | Участок пути внутри одной роли; фазы бывают только у ролей. Цена фазы — порядок из справочника (не бренд); внутри цены — обслуживание + ожидание. |
| **Доставка** | Среда до входа системы и обратно: не роль, в составе её нет. Цена — порядок из справочника (регион ~десятки мс, межрегион ~сотня); вычитается из SLO до дележа: `SLO = доставка + Σ фаз ролей`. |
| **Слот** | Единица параллельности роли: один слот = один запрос одновременно; воркер держит слот и пока синхронно ждёт подчинённую роль. Слоты = λ × W (Закон Литтла), где W = своя фаза + ожидания; план при загрузке ≤ 70–80 % — у порога взрывается хвост. Считает П5 шага 2. |
| **Запрос** | Единица работы: одна порция работы роли в пути (запрос поиска, запрос записи). Порождается действием через механику взаимодействия («одно действие ≈ один запрос» — механика, а не закон). С 2026-09-07 слово однозначно: реестр недостающих чисел называется реестром вопросов. |
| **Переговорщик** | Наружная функция проектировщика: ходит с вопросами из реестра вопросов к владельцам чисел; доступные операции — уточнение и торг. Единственный канал, которым цикл влияет на рамку. |
| **Правило «+1 девятка»** | Доступность на примерных расчётах: каждой роли пути на одну девятку больше системной, одна для всех — умножение идёт один раз по всему пути, не по уровням; запаса хватает до ~10 ролей (0.9999¹⁰ ≈ 99.9 %); роль на нескольких путях берёт самое строгое. Точная развеска произведением ровно по SLO — исполнениям «расчёт» и «прогон». Считает П4 шага 2. |
| **Подалгоритм** | Часть шага цикла, выделенная в отдельный мини-алгоритм «откуда → как → куда»: описание + диаграмма в папке шага (`шаг-2-подалгоритмы/`). Шаг 2 = П1 классификация SLO · П2 нагрузка на роли · П3 бюджет latency · П4 бюджет доступности · П5 ёмкость; порядок: П1 → П2 → П3 ∥ П4 → П5. |

## Аналогия инстанса (инсайт пользователя, 2026-08-28)

Рамка — аргументы конструктора инстанса; модель — переменные инстанса (реестры — computed-свойства: только пересчитываются; состав — поле с единственным сеттером «шаг 1, через боль»); цикл — код методов; уточнение/торг — config hot-reload аргумента с пересчётом вычисляемых переменных.
