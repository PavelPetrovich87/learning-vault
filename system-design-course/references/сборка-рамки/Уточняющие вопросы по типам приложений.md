# Уточняющие вопросы по типам приложений — interview cheat sheet

> **Назначение.** Справочник для «набивки руки»: на интервью при дизайне типового приложения знать, какие вопросы задавать интервьюеру при сборке рамки. Основа — твоя рамка (поля 1–7) и процедура «анкета → детекторы → щупы» ([[заполнение-рамки]]); внешние источники (§8) — сверка и дополнение, не замена канона.
>
> **Как читать.** Вопросы — на английском, как они прозвучат на интервью. Пример ответа — на русском: это **предположение-кандидат**, которое ты озвучиваешь вслух сразу после вопроса («Let's assume…»), а не ждёшь ответа. Числа в примерах — типовые предположения сильных кандидатов из источников; в скобках — откуда. У каждого блока строка «зачем спрашиваем» — какой развилке ответ руководит.

## 0. Быстрая выжимка — «тип → 5 главных вопросов»

Повторить перед интервью; полные разделы в §3.

| Тип | Пять вопросов, без которых нельзя начинать |
|---|---|
| Мессенджер/чат | 1:1 or group chat (member limit)? · Max message size / media support? · Offline delivery window & history retention? · Online status — needed? how fresh? · Delivery/read receipts? |
| Лента/соцсеть | Chronological or ranked feed? · How many friends/follows (celebrities?) · Media in feed? · Feed page size & pagination? · Staleness/latency target? |
| Короткие ссылки | Read-to-write ratio? · Custom aliases? · Link expiration? · Click analytics (301 vs 302)? · Latency/availability target? |
| Видеостриминг | Upload + watch only, or search/recommendations too? · Max video size, formats, quality levels? · Resumable upload needed? · Startup latency vs smoothness? · Daily upload/watch volume? |
| Файловое хранилище | Max file size? · Multi-device sync — conflicts? · Sharing & permissions? · Versioning / deleted-file retention? · Dedup expected? |
| Поиск/автокомплит | Top-K results? · Latency (before the next keystroke)? · Freshness of suggestions? · Typo tolerance / personalization? · Query volume & dictionary size? |
| Матчинг (ride-hailing/маркетплейс) | Match latency window? · Location update rate (ping interval)? · Double-assignment prevention (consistency)? · Search radius / geo granularity? · Payments, ratings — in scope? |
| Платежи | In-house processing or PSP? · Idempotency / duplicate handling? · Consistency vs availability? · Reconciliation in scope? · Currencies, regions, throughput? |

Универсальные блоки (§2) спрашиваются **всегда**, до типовых.

## 1. Как пользоваться

**Связь с твоим алгоритмом.**

- **Универсальные блоки §2 = анкета по полям рамки** — порядок вопросов повторяет порядок полей: продукт и границы → масштаб → рост → профиль нагрузки → данные → НФТ → ограничения.
- **Типовые блоки §3 = готовые цели для щупов** — доменный слой: сущности этого типа × «сколько? / как часто? / что произойдёт, если…».
- **Детекторы** работают по ответам интервьюера: ярлык без числа → «how much?»; число без владельца → «who set it?».

**Мини-скрипт первых 5 минут** (режим интервью из [[заполнение-рамки]]):

1. Сузь имя продукта: «Uber — rides, Eats or freight? MVP or mature?»
2. Пройди универсальные блоки §2 (У1 → У10), на «assume whatever» — предположение с числом вслух и дальше.
3. Перейди к типу из §3: 5 главных вопросов (§0) + что успеешь.
4. Пересказ-чекпоинт: «So we build X for Y at scale Z, without W — correct?»
5. Только потом — маркерная доска. Джимми из 1.1 не тянет руку.

**Тайминг из источников:** Alex Xu — 3–10 минут на шаг 1 из 45; hellointerview — ~5 минут на requirements; interviewing.io таймингов намеренно не даёт. Ориентир: 5–10 минут.

**Куда падают ответы** (раскладка из твоего же канона): число → NFR / параметры нагрузки; поведение («what happens if…») → FR; граница («in v1?») → вне рамок.

## 2. Универсальные блоки — спрашиваются у любого приложения

Каждый блок привязан к полю рамки ([[модуль-рамка]]). Формат: EN вопрос → пример ответа-предположения.

### У1. Продукт и границы — поле 2, знак «делаем/не делаем»

Зачем спрашиваем: «Answering without a thorough understanding of the requirements is a huge red flag» (Alex Xu). Список без границ — половина работы.

- **What specific features are we going to build?** → «Let's scope to the top 3: …» (hellointerview: цель — top-3 фичи)
- **What is explicitly out of scope for v1?** → «payments, ratings and scheduled rides — below the line» (hellointerview, Uber)
- **Mobile app, web, or both? Anything else — smart TV, embedded?** → «mobile + web, mobile is primary»
- **Can tweets/posts/messages be edited or deleted after publishing?** → «edits — no, deletes — yes» (interviewing.io: mutability — обязательный вопрос)
- **Do any of the business objects hold media — images, video, attachments?** → «text only in v1, media — v2» (interviewing.io: «Always ask whether any business object can hold media»)
- **Is it MVP or a mature system? Single region or global product?** → «MVP, one region, but designed to grow ×10»

### У2. Пользователи и масштаб — поля 1, 4

- **How many users does the product have? DAU?** → «10M DAU» (ByteByteGo, news feed) / «50M DAU» (ByteByteGo, chat) — бери порядок из интервьюера, дефолт 10M
- **What does a typical user do in the app — what's the core action and how often?** → «sends ~20 messages/day» (hellointerview) / «~40» (interviewing.io) — бери 20–40
- **What's the expected read-to-write ratio?** → «10:1» — НО всегда подтверди у интервьюера (см. §5: источники расходятся от 10:1 до 1000:1)
- **How many concurrent users at peak?** → «из DAU: ~20% одновременно онлайн» (200M из 1B — hellointerview)

### У3. Рост и горизонт — поле 1

- **How fast does the company anticipate to scale up — in 3 months, 6 months, a year?** (Alex Xu, дословно) → «×2 за год; скачок ×10 после запуска»
- **Is there a launch/marketing event that will spike traffic?** → «эфир блогера: вечер ×5, первые полчаса ещё ×2» (наш живой пример — ХомяЧат 2.1)
- **What's the anticipated scale on the horizon we're designing for?** → «проектируем под верх вилки ×2 от цели»

### У4. Профиль чтение/запись и пик — поля 4, 6

- **What's the daily action volume — writes per day, reads per day?** → «500M tweets/day → ~6K writes/s, 100K reads/s» (primer, Twitter)
- **Is traffic uniform across the day? What's the peak multiplier?** → «пик ×2–3 к среднему; событийный скачок ×10+» (рамка, сценарии 2 и 4)
- **What does the distribution of requests look like?** (interviewing.io) → «80/20 — горячие записи тянут хвост»
- **Do you want me to do the estimation math now or skip it?** (interviewing.io, дословно) → сам вопрос про математику — часть этикета

### У5. Данные: размер записи, объём, срок — поле 4

- **How big is a typical record — message, post, file?** → «~100 bytes сообщение; ~10 KB пост с медиа-ссылкой» (interviewing.io / primer)
- **How much data do we expect to handle? Total after a year?** → «действий/день × байты × 365; например 150 TB/мес» (primer, Twitter)
- **How long do we store the data?** → «chat history — forever» (ByteByteGo) / «5 лет» (живой пример кандидата) — спроси и зафиксируй
- **Does anyone actually read old data? What share of reads hits records older than a week?** → «~5%» (наш ХомяЧат) — горячие vs холодные данные
- **What are the inputs and outputs of the system?** (primer) → «на входе URL, на выходе redirect» — грубая, но полезная рамка

### У6. Латентность ключевых операций — поле 3

- **What's the latency target for the core user-facing operation — p95 or p99?** → «feed rendering < 200 ms» (hellointerview: квантифицировать, не «low latency»)
- **Which workflows are synchronous/user-facing (latency-critical) and which are background?** (interviewing.io) → «отправка и отдача — синхронные; доставка офлайн — фон»
- **Is the target p50, p95 or average?** → «p95 ≤ 500 ms» — среднее не принимается (наш канон 1.4)

### У7. Доступность и цена простоя — поле 3

- **What's the cost of downtime? Which window is the most expensive?** (interviewing.io) → «окно пиковой выручки недопустимо к простою» (наш «Столик»: пятница 18–21)
- **What availability target — how many nines?** → «99.9% (≈9 ч/год)» — и не говори «6 nines»: «звучит как самозванство» (interviewing.io, дословно «behaving like an imposter»)
- **What happens on failure — degrade or drop?** → «деградация: без онлайн-статусов, но чат работает»

### У8. Консистентность vs доступность — поле 3

- **If there's a network partition, do we prioritize consistency or availability?** (hellointerview, CAP deep dive) → эвристика источника: «Would it be catastrophic if users briefly saw inconsistent data?»
- **Can two users end up buying/booking the same item?** → «нет — double booking non-negotiable» (Airbnb: strong consistency для брони)
- **How stale can the data be when read?** → «feed — до 1 минуты eventual consistency» (hellointerview)

### У9. География, клиенты и среда — поля 4, 5

- **Where are the users — one region or worldwide? Where's the data allowed to live?** → «мир; данные личные — GDPR-регион» (наш ХомяЧат: «мир» как консервативная сторона для латентности)
- **What's the company's technology stack? What existing services might we leverage?** (Alex Xu, дословно) → «облако, помесячная оплата; готового ничего»
- **Client platforms — what are they capable of?** → «мобильные пуш-уведомления доступны; embedded-клиенты пишут, но не читают» (наш ХомяЧат: поилка)

### У10. Ограничения — поле 5

- **What's the budget and the team?** → «команда из одного + фрилансер на выходные» (наш ХомяЧат: «команда из одного» режет кандидатов вроде K8s-кластера)
- **What's the deadline?** → «10 недель до эфира» (наш ХомяЧат)
- **Any compliance, legal or security constraints?** → «карты не храним — PSP сторонний» (Alex Xu vol.2, payments)

### У11. Безопасность и приватность — поле 3/5

- **Is there any workflow that requires special security considerations?** (interviewing.io, дословно) → «переписка приватна: никто кроме участников не читает»
- **End-to-end encryption required?** → «в v1 — нет, transport-only» (ByteByteGo, chat: «not yet»)
- **Do we trust the client — or validate fares, IDs, timestamps server-side?** → «всё серверное; fare от клиента — red flag» (hellointerview, Uber)

## 3. Восемь типов приложений — уникальные блоки

Каждый тип: что делает его особенным → мини-профиль типовых чисел → блоки вопросов. Универсальные блоки §2 предполагаются уже пройденными.

### Т1. Мессенджер / чат (WhatsApp, Messenger, Telegram)

**Что особенного.** Главный вопрос типа — **доставка**: как получатель узнаёт о сообщении. Всё остальное (presence, история, статусы) — надстройки над этим. Read/write почти симметричны (у 1:1 чата ~1:1 — ByteByteGo), в отличие от контентных систем. Живые долгоживущие соединения — количество одновременных клиентов важнее RPS.

**Мини-профиль чисел** (типовые предположения кандидатов):

- 20–40 сообщений/день на пользователя (hellointerview 20 / interviewing.io 40 — расходятся, бери порядок)
- среднее сообщение ~100 байт текст; медиа-вложение 0,5–1 МБ (interviewing.io, интервьюер поправил 0,5 → 1)
- latency доставки < 500 мс (hellointerview)
- одно мощное соединение-сервер держит ~50 000 concurrent connections; ~10 KB памяти на соединение → 1M соединений ≈ 10 GB (interviewing.io / ByteByteGo)
- история: «forever» (ByteByteGo) или 5 лет (живой пример) — спроси
- 200M одновременно онлайн из 1B пользователей (hellointerview)

**Блоки и вопросы:**

*Доставка и офлайн-поведение* — зачем спрашиваем: это архитектурное решение №1 (упр. 2 / глава 2.5).
- **1 on 1 or group based?** → «оба» (ByteByteGo)
- **If the recipient is offline, what happens to the message — for how long do we keep trying?** → «не теряется; доставляется при возвращении, окно ≥ 30 дней» (hellointerview)
- **Does the user learn about a message without opening the app?** → «уведомление телефона + бейдж непрочитанных» (наш ХомяЧат: стерильная форма без механизма)

*Группы*
- **What's the maximum group size?** → «100» (ByteByteGo; hellointerview) — interviewing.io: интервьюер ждал именно этого вопроса в моке WhatsApp
- **Group features — mentions, replies, admin?** → «нет, v1 — просто мультикаст»

*Presence («кто онлайн»)*
- **Do we need an online indicator at all?** → «да, для друзей» (ByteByteGo)
- **How fresh must the status be — seconds? minutes?** → «свежесть ~30 с; heartbeat каждые 5–10 с» (ByteByteGo)
- **How many friends' statuses does a user watch?** → «десятки активно смотримых, единицы одновременно на экране» (наш ХомяЧат: 5 активных)

*Статусы сообщения*
- **Delivery receipts? Read receipts? Typing indicators?** → «delivered + read — да; typing — нет» — ByteByteGo отмечает: кандидат в каноне их НЕ спросил; interviewing.io-интервьюер ждал. Спроси — это дешёвые баллы.

*Размер и ограничения*
- **What's the message size limit?** → «текст < 100 000 символов» (ByteByteGo) / «~100 байт среднее» (interviewing.io)
- **Attachment support — images? video? audio?** → «только текст» (ByteByteGo) / «изображения» (мок WhatsApp)

*Шифрование и приватность*
- **End-to-end encryption required?** → «not yet» (ByteByteGo)
- **Who can read a conversation besides participants?** → «никто» (наш ХомяЧат)

*История и мультидевайс*
- **How long do we store chat history? Can users browse it? Search it?** → «forever, чтение — да, поиск — вне рамок v1» (наш ХомяЧат №30–31)
- **Multiple devices per user — same history everywhere?** → «да, устройство тянет сообщения новее своего курсора» (ByteByteGo)

### Т2. Лента / соцсеть (news feed, Twitter, Instagram)

**Что особенного.** **Фан-аут (fan-out)**: один пост должен оказаться в лентах тысяч подписчиков — чтение и запись несимметричны (сотни чтений на запись). Граф подписок и «звёзды» (миллионы подписчиков) ломают наивные схемы. Медиа в постах — почти всегда.

**Мини-профиль чисел:**

- 10M DAU (ByteByteGo) / 100M active (primer, Twitter)
- 500M твитов/день → ~6 000 writes/s; 250B reads/мес → ~100 000 reads/s (primer)
- пост ~10 KB с медиа; 150 TB нового контента/мес (primer)
- до 5 000 друзей (ByteByteGo: Facebook-лимит) / < 1 000 (мок Google)
- precomputed feed: 200 постов × 10 байт ≈ 2 KB на пользователя (hellointerview)
- staleness ленты ≤ 1 минуты; latency отдачи < 500 мс (hellointerview)

**Блоки и вопросы:**

*Порядок ленты* — зачем: определяет, простая ли это система (хронология) или ML-продукт (ранжирование).
- **Is the feed reverse chronological or ranked by relevance/score?** → «reverse chronological» (ByteByteGo; их же канон упрощает)
- **If ranked — what's the business goal: engagement, time spent?** → «engagement» (мок Google: кандидат сам спросил — интервьюер отметил как сильный ход)
- **Personalized with private data or public signals only?** → «только публичные» (мок Google)

*Граф подписок*
- **How many friends/follows can a user have? Are follows mutual or one-way?** → «односторонние, до 5 000» (ByteByteGo) / «взаимные, единицы активных» (наш ХомяЧат — другой продукт, другой ответ)
- **Are there celebrities with millions of followers?** → «да — 90M+ подписчиков» (hellointerview, «Justin Bieber») — вопрос, который включает гибридную механику

*Контент ленты*
- **Can the feed contain images, videos, or just text?** → «images and videos» (ByteByteGo)
- **Post size limit? Edits after publishing? Deletion?** → «10 KB, без редактирования, удаление — да»

*Страница и пагинация*
- **How many posts per feed page? Infinite scroll or pagination?** → «~20 на страницу, infinite scroll» (мок Google: пагинация вне скоупа — уточни)
- **How far back does a user scroll — a day, a week?** → «неделя-месяц» (мок Google: «By recent, how far is that?»)

*Свежесть*
- **How stale may the feed be — does a new post appear instantly?** → «до 1 минуты eventual consistency» (hellointerview)

*Соцфичи*
- **Likes, comments, shares, DMs — in scope?** → «лайки/комментарии — ниже линии» (hellointerview, FB News Feed)

### Т3. Короткие ссылки (URL shortener, TinyURL, bit.ly)

**Что особенного.** Экстремально read-heavy: на одну созданную ссылку — десятки-тысячи кликов. Сама система маленькая (запись ~100–500 байт), но redirect-путь обязан быть миллисекундным и переживать пики. Излюбленная «разминка»-интервью.

**Мини-профиль чисел:**

- read:write — главная развилка типа: 10:1 (ByteByteGo, primer) / 100:1 (AlgoMaster) / 1000:1 (hellointerview) → **спроси интервьюера**, дефолт 100:1
- 100M новых URL/день → ~1 160 write QPS, ~11 600 read QPS при 10:1 (ByteByteGo); 500M redirects/день ≈ 5 800 RPS (hellointerview)
- запись ~100–500 байт/URL; 1B URL × 500 B = 500 GB — влезает в один Postgres (hellointerview)
- redirect < 100 мс; availability 99.9% (hellointerview / AlgoMaster)
- длина кода: 62^7 ≈ 3,5 трлн комбинаций (арифметика; примечание: AlgoMaster в тексте ошибся на три порядка — 62^7 это ~3,5×10¹², не 10⁹)

**Блоки и вопросы:**

*Redirect-профиль*
- **What's the read-to-write ratio — clicks per created link?** → «100:1, поправьте» (см. §5)
- **Redirect latency target? Is it cached by the browser?** → «< 100 мс; кеш браузера зависит от 301/302»

*301 vs 302 — аналитика* — зачем: выбор определяет, видит ли сервер клики.
- **301 or 302 redirect? Do we need click analytics?** → «302: каждый клик через сервер — считаем клики; 301 закеширует браузер и спрячет их» (ByteByteGo)
- **What analytics — how many clicked, when, from where?** → «кол-во и время; батчами в warehouse, не в пути redirect» (AlgoMaster)

*Жизненный цикл ссылки*
- **Do links expire? Default TTL?** → «бессрочно по умолчанию, TTL опционально» (AlgoMaster: год/бессрочно)
- **Can short URLs be updated or deleted?** → «нет — создал и всё» (ByteByteGo)

*Алиасы*
- **Custom aliases — allowed? Uniqueness rules? Reserved words?** → «да; проверка уникальности, whitelist символов, служебные слова занять» (AlgoMaster)

*Уникальность*
- **Collision behavior — regenerate or fail?** → «перегенерация с солью, 3–5 попыток» (hellointerview)
- **How short must the code be — fixed length?** → «7 символов base62 хватает на годы» (ByteByteGo)

### Т4. Видеостроминг (YouTube, Netflix)

**Что особенное.** Два гигантских потока: **загрузка** (большие файлы вверх, медленный транс-кодинг) и **отдача** (массовый параллельный стрим вниз через CDN). Функционально ядро крошечное («upload + watch» — Alex Xu), поэтому весь вес переносят НФТ. hellointerview прямо предупреждает: готового списка вопросов про битрейт нет — «have some brief back and forth to figure out what part of the system they care about».

**Мини-профиль чисел:**

- 5M DAU; средний ролик 300 МБ; max upload 1 ГБ; хранилище ~150 ТБ/день (конспект Alex Xu гл.14)
- 1M загрузок/день, 100M просмотров/день, ~365M записей метаданных за год (hellointerview)
- 10 ГБ на 100 Мбит/с ≈ 13+ минут — почему upload обязан быть resumable (hellointerview)
- чанк загрузки 5–10 МБ (hellointerview)

**Блоки и вопросы:**

*Границы продукта*
- **Core features — just upload and watch, or also search, recommendations, comments?** → «upload + watch; остальное — ниже линии» (hellointerview)
- **Platforms: mobile, web, smart TV?** → «все три» (Alex Xu)

*Загрузка*
- **Max video size? Duration limits?** → «десятки ГБ» (hellointerview)
- **Resumable upload — required? What happens on network drop at 95%?** → «да, чанки по 5–10 МБ» (hellointerview)
- **Who uploads — anyone, or verified creators? Moderation?** → «любой; модерация — фон»

*Отдача и качество*
- **Adaptive bitrate — must quality change with network conditions? How many quality levels?** → «да, несколько уровней» (Alex Xu: «ability to change video quality» в НФТ)
- **Startup latency vs smoothness — what matters more?** → «плавность важнее старта» (НФТ «smooth video streaming»)
- **DRM needed?** → «в v1 — нет» (Alex Xu упоминает FairPlay/Widevine как опцию)

*Каталог и метаданные*
- **What metadata do we keep per video — title, size, views?** → «title, description, size, счётчики» (Alex Xu)
- **Video views count — real-time or eventually consistent?** → «eventual — счётчик не блокирует просмотр»

*Стоимость*
- **Infrastructure cost constraints?** → «CDN — только для популярных; редкие — по требованию» (Alex Xu: «low infrastructure cost»)

### Т5. Файловое хранилище / cloud drive (Dropbox, Google Drive)

**Что особенное.** **Синхронизация**: одни и те же данные с нескольких устройств, правки в офлайне → конфликты. Большие файлы → чанковка и дедупликация. Data loss недопустима, а консистентность между устройствами — может подождать секунды.

**Мини-профиль чисел:**

- 10–50M DAU (книга / systemdesigninterview.com)
- макс. файл 10–50 ГБ (источники расходятся — спроси); средний файл/дельта 0,5–2 МБ (книга / sdi.com)
- 2 файла/день на пользователя (книга); 3:1 read-to-write (sdi.com); 400 ТБ/день нового (sdi.com, при 2 МБ и 200M writes/day)
- чанк 4 МБ (книга, sdi.com) / 5–10 МБ (hellointerview)
- версии и удалённые — 30 дней (sdi.com)

**Блоки и вопросы:**

*Синхронизация*
- **Sync across devices — automatic? What if the same file is edited on two devices offline?** → «auto-sync; конфликт разрешается…» — источники расходятся: last write wins (hellointerview) / first wins + конфликтные копии (книга) / 409 + conflicted copy (sdi.com) — **спроси интервьюера, что важнее: простота или недопущение потери правок**
- **How quickly must an edit appear on the other device?** → «секунды — это ок» (hellointerview: availability over consistency)
- **Offline edits — queued and synced later?** → «да, offline backup queue» (книга)

*Файлы*
- **Max file size?** → «10 ГБ» (книга) / «50 ГБ» (hellointerview) — спроси
- **What file types — any?** → «любые бинарники»

*Дедупликация*
- **Do we deduplicate identical content — across users?** → «да, по хешу чанка, в т.ч. между пользователями» (sdi.com)
- **Delta sync — upload only changed parts?** → «да, сравнение хешей чанков» (книга)

*Шаринг и права*
- **Sharing — links, permissions (read/write), folders?** → «ссылки + права; enterprise-модели вне рамок» (sdi.com)
- **Link expiry / revocation?** → «pre-signed URLs с TTL ~5 минут» (hellointerview)

*Версии и удаление*
- **Version history — how many versions, how long?** → «30 дней» (sdi.com; hellointerview: versioning вне скоупа их базовой постановки — спроси)
- **Deleted files — purge when?** → «30 дней корзина»

### Т6. Поиск / автокомплит (typeahead)

**Что особенное.** **Индекс вместо БД**: запросы идут по префиксу в словаре, а не по ключу. Латентность — на порядок жёстче обычного (ответ должен успеть до следующего нажатия клавиши), свежесть — наоборот, слабая (минуты-часы). K всегда маленькое.

**Мини-профиль чисел:**

- 10M DAU × 20 запросов/день → ~20 000 QPS данных, пик ×2 = 40 000 (Alex Xu гл.13)
- словарь: ~100M популярных запросов × ~20 символов; trie ~12 GB RAM (System Design School)
- K = 5–10 (по умолчанию 10 — School; 5 — Alex Xu)
- латентность < 100 мс (Alex Xu)
- свежесть: обновление топов раз в час (Alex Xu: «hourly»); minutes-to-hours acceptable (School)

**Блоки и вопросы:**

*Результаты*
- **Top-K — how many suggestions?** → «5–10» (Alex Xu / School)
- **Ranked by what — raw popularity, recency, personalization?** → «популярность с затуханием по свежести» (School: recency decay)
- **Typo tolerance — must we correct misspellings?** → «в v1 — нет» (School: вне базовой постановки)

*Латентность и поведение клиента*
- **What latency — must suggestions arrive before the next keystroke?** → «< 100 мс» (Alex Xu)
- **Debounce/cancellation client-side — agreed?** → «да, клиент не палит каждый символ» (School)

*Свежесть*
- **How fresh must suggestions be — can a trending query appear in minutes?** → «час — норм; тренды отдельной структурой» (School)

*Словарь и объём*
- **What's the query dictionary — all queries ever, or top-N popular?** → «top-100M популярных» (School)
- **New/zero-frequency queries — suggest anything?** → «20% запросов новые — они копятся как кандидаты» (Alex Xu)
- **Multiple languages?** → «один язык в v1»

*Границы*
- **Is this just autocomplete, or full search results too?** → «только подсказки; сам поиск — отдельная система» (School: search engine out of scope)

### Т7. Матчинг: ride-hailing / маркетплейс (Uber, Airbnb, Yelp)

**Что особенное.** Двусторонний рынок: **гео-запросы + матчинг в реальном времени**. Волна обновлений локаций (водители пингуют каждые секунды) на порядки превышает деловые операции. Ключевой НФТ — не допустить двойного назначения (double booking / две поездки одному водителю).

**Мини-профиль чисел:**

- 10M водителей × пинг каждые 5 с ≈ **2M location updates/sec** (hellointerview, Uber)
- матчинг < 1 минуты (hellointerview)
- радиус 5 → 10 км = площадь ×4 — латентность растёт нелинейно (ByteByteGo, Uber Eats)
- geohash: 5 символов ≈ 5 км, 9 ≈ 5 м (hellointerview)
- Airbnb: 1,5M броней/день ≈ 17 write TPS — «маленькая» запись, но strong consistency (systemdesign.one)

**Блоки и вопросы:**

*Гео-запросы*
- **How do we search — radius around a point, map viewport, or address?** → «радиус вокруг точки» 
- **What radius / granularity?** → «5 км для машин; маркетплейс — зона доставки» (ByteByteGo: 5–10 км)
- **Moving objects — how often do locations update?** → «каждые 5 с» (hellointerview)

*Матчинг*
- **What's the matching window — how fast must supply meet demand?** → «секунды-минута» (hellointerview)
- **Can two passengers be matched to the same driver (double assignment)?** → «нет — strong consistency, non-negotiable» (hellointerview / Airbnb)
- **Driver declines — re-match? Penalty?** → «рематч без штрафа в v1»

*Нагрузка*
- **Peak concentration — all requests from one city center at once?** → «да, 100k из одной локации» (hellointerview)
- **Read vs write — browsing vs booking?** → «read-heavy: ~1000 read QPS против 17 write TPS» (systemdesign.one, Airbnb)

*Скоуп рынка*
- **Fare estimation — in scope? Real-time surge pricing?** → «fare estimate — да; surge — нет» (hellointerview)
- **Payments, ratings, scheduled rides — in scope?** → «всё ниже линии» (hellointerview — сам назови, это ждут)
- **Search filters — dates, guests, price, amenities?** → «да, все» (Airbnb)

*Доверие*
- **Do we trust client-reported fare/location/timestamps?** → «нет — валидация сервером» (hellointerview: red flag №1 типа)

### Т8. Платежи / транзакционные системы

**Что особенное.** **Корректность важнее всего**: потерянные и задвоенные платежи фатальны — здесь консистентность побеждает доступность, а throughput почти не важен. Двойная запись (double-entry ledger), идемпотентность и сверка (reconciliation) — словарь типа.

**Мини-профиль чисел:**

- 1M транзакций/день ≈ 10 TPS — и это нормально: фокус «on correctness, not throughput» (Alex Xu vol.2)
- суммы хранить строками/десятичными, не double (vol.2)
- идемпотентность: unique constraint в БД; конкурентный дубликат → 429 (vol.2)

**Блоки и вопросы:**

*Периметр и партнёры*
- **What kind of payment system — pay-in, pay-out, or both? Which payment methods?** → «pay-in + pay-out; карты» (vol.2)
- **Do we process cards ourselves or via a PSP (Stripe/Braintree)?** → «PSP сторонний — карты не храним» (vol.2; вопрос compliance)
- **One currency or many? One region or global?** → «одна валюта, один регион» (vol.2)

*Корректность*
- **What happens if the same payment request arrives twice — retry, user double-click?** → «идемпотентность по ключу; дубликату отдаём прежний результат» (vol.2)
- **Exactly-once delivery — required? Possible?** → «нет: at-least-once + идемпотентность = эффект exactly-once» (vol.2)
- **Consistency vs availability — what wins during a partition?** → «consistency: задвоенный платёж хуже отказа» (hellointerview, CAP: деньги/inventory/места — consistency)

*Сверка*
- **Reconciliation — in scope? Daily settlement files?** → «да: ночная сверка с PSP, расхождения — три категории разбора» (vol.2: «the last line of defense»)

*Отказы и ретраи*
- **Retry policy — backoff? What if the PSP is down mid-payment?** → «exponential backoff + dead letter queue; зависшие — мониторинг» (vol.2)
- **Partial failure — money left our ledger but PSP didn't charge?** → «сверка ловит; ручной разбор»

## 4. Red flags — как не надо

1. **Начинать решение до вопросов.** «Answering without a thorough understanding of the requirements is a huge red flag» (Alex Xu); «giving out an answer quickly does not give you bonus points» (Pragmatic Engineer о книге).
2. **Вопрос-решение.** «How do we cache the feed?» — не вопрос требования. Правильно: «How stale may the feed be?» — а кеш родится как ответ.
3. **Названный бренд там, где ждут функцию.** «Say the generic name of the component, not the brand name… Don't say Kafka. Instead, say 'a queue.'» (interviewing.io) — внешняя версия твоей же стерильности рамки.
4. **«6 nines» и прочие лозунги.** Пустые девятки без цены простоя звучат «behaving like an imposter» (interviewing.io). Правильно: «What's the cost of downtime?» → число.
5. **Список без доменных вопросов.** «Учётка, оплата, сессии» на любом домене — маркер слабого сбора (твой 1.1). Минимум: 3 вопроса из §0 типа.
6. **Одно число на всё.** «У нас 100k пользователей» — не масштаб: DAU → действий → RPS → пик (твой канон 1.2 + ловушка §6.2 content.md).
7. **Молчаливое предположение.** Ввёл 500 RPS «примем» — через десять минут ссылаешься как на данность интервьюера (твой «типичный провал» из модуля-рамка). Предположения записывай и помечай.
8. **Не спросить про медиа.** interviewing.io: «Always ask whether any of the business objects can hold media» — размер данных меняется на порядки.
9. **Пустой TBD.** Каждый вопрос — с кандидатом-ответом вслух; «Ask them!» (interviewing.io о бедных промптах).

## 6. Упражнения — как тренировать

1. **Прогон по памяти:** тебе называют тип (или ты берёшь из §0) → 5 главных вопросов + 3 универсальных блока — вслух, по памяти, за 3 минуты. Сверка с шпаргалкой; что забыл — карточка-кандидат.
2. **Обратное упражнение:** читаешь чужой разбор системы (hellointerview problem breakdowns) и выписываешь, какие вопросы автор задал до схемы. Сравниваешь со «своими» для этого типа.
3. **Чужой домен:** «спроектируй лифт/кофе-машину/аптеку» — универсальные блоки без типового; тренирует анкету.
4. **Мок по расписанию:** раз в неделю один тип из §3 полностью — с числами-предположениями вслух.
5. Карточки по типам заводим после первых прогонов — из живых ошибок, не из файла.
