# Deep Research Prompt v2: How Classic Interview Questions Mutated in the AI Era

> **Назначение:** Промпт-**расширение** к первому исследованию. Первый отчёт ([[report]] в папке `ai-era-full-stack-result/`) сконцентрировался на AI-native темах (RAG, agents, MCP, LLM gateway, AI evaluation) и недостаточно раскрыл, что произошло с **классическими** вопросами собеседований. Этот промпт закрывает пробел: он требует показать **before → after** трансформацию классического канона, а не повторять AI-паттерны.
>
> **Связанные заметки:** [[AI-Era Fullstack Interview Landscape]], первый промпт [[ai-era-fullstack-interview-research-prompt]], отчёт v1 в `ai-era-full-stack-result/report/report.md`.
> **Как использовать:** Скопировать "Часть 2" целиком в Deep Research агента. Дать ему доступ к отчёту v1 (или вставить его краткое содержание), чтобы он строил поверх, а не с нуля.

## Часть 1. Контекст (для меня, не для агента)

**Что уже сделано:** Первое исследование подтвердило структурный сдвиг собеседований (coding ↓, System Design ↑, появление AI-блоков, разрешение AI на интервью у Google/Meta/Shopify/Canva). Главный вывод: *«cheap implementation, expensive understanding»*.

**Чего не хватает:** Отчёт многократно утверждает «классические блоки не исчезли, они трансформировались», но **не показывает саму трансформацию**. Классика (DSA, классический System Design, frontend deep-dives, backend/DB, CS fundamentals) осталась в тени AI-хайпа.

**Гипотеза, которую я хочу проверить:** Классические вопросы не просто «остались» — они **переосмыслены**. Поскольку AI пишет код, классику теперь спрашивают (а) глубже (фокус на reasoning/trade-offs, а не на синтаксисе), (б) в новых форматах (review/debug AI-вывода вместо написания с нуля), (в) с AI-resistant механиками для проверки настоящего понимания. Мне нужна **карта модификаций**, чтобы готовиться к классике правильно, а не игнорировать её.

## Часть 2. Deep Research Prompt (копировать в агента)

> **Роль:** Ты — старший исследователь технического найма, специализирующийся на эволюции **классических** форматов собеседований под давлением AI. Ты уже знаком с выводами предыдущего исследования (Phase 1), которое показало рост AI-native тем. Твоя новая задача — **дополнить**, а не повторить его.
>
> **Задача:** Взять канон классических вопросов для fullstack-собеседований эпохи 2020–2023 и показать, как **каждый классический архетип** изменился к 2026 году под влиянием AI: переоценка веса, переформатирование, сдвиг критериев оценки, anti-cheating механики. Главный выход — **before → after карта модификаций** и план подготовки по классике.

### 2.1. Контекст и явные ограничения

**Что уже известно из Phase 1 (НЕ повторяй это, опирайся как на基):**
- Coding-раунды снизились в весе (~20%); System Design вырос (~25%); появились отдельные AI-блоки (RAG, agents, evals, MCP).
- Google/Meta/Shopify/Canva разрешают или требуют AI на интервью; Anthropic запрещает и строит «AI-resistant evaluations».
- Сдвиг от creation к evaluation; «cheap implementation, expensive understanding».

**Чего Phase 1 НЕ раскрыл (твой фокус сейчас):**
- КАК именно классические вопросы модифицировались — конкретные before/after примеры.
- Что осталось инвариантным (фундамент), а что стало переменным (формат/оценка).

> [!warning] Анти-задача
> НЕ уходи снова в RAG / agents / MCP / vector DB / LLM gateway. Это покрыто. Если упоминаешь AI — только в контексте того, как он **изменил классический вопрос** (например, «классическую задачу на debounce теперь дают как ревью AI-кода»).

### 2.2. Классические блоки для анализа (разбери КАЖДЫЙ)

Для каждого блока обязательно дай: **Pre-AI форма (2020–2023)** → **AI-era форма (2026)** → **Что осталось инвариантным** → **Сдвиг критериев оценки** → **Anti-cheating механика** → **Конкретные примеры вопросов до/после**.

#### CB-1. Algorithms & Data Structures (LeetCode-канон)
- Всё ещё спрашивают arrays/strings/trees/graphs/DP/two-pointers? Какие исчезли, какие остались?
- Как проводят live-coding, когда AI решает LeetCode мгновенно: запрет AI + прокторинг? «объясни/оптимизируй AI-решение»? устные dry-run?
- Сместился ли акцент с «реши» на «объясни сложность / докажи корректность / найди edge cases»?
- Как компании детектируют читинг на remote-coding (Anthropic multi-level, прокторинг, on-site возврат)?

#### CB-2. Классический System Design (не-GenAI)
- Всё ещё дают «design Twitter / Uber / WhatsApp / URL shortener / rate limiter / distributed cache / notification system / news feed»?
- Как модифицировались: добавляют ли AI-компонент в классический дизайн? Стало ли больше веса на trade-offs/observability/cost, раз код пишется быстро?
- Изменилась ли глубина: ждут ли теперь capacity estimation, CAP, consistency models, sharding — глубже, чем раньше?
- Что для fullstack/frontend-уклона: frontend system design (design Figma/Google Docs frontend, image carousel, infinite scroll, design system)?

#### CB-3. Frontend Deep-Dives
- Классика: event loop, rendering pipeline, reflow/repaint, critical rendering path, browser internals.
- React internals: reconciliation, fiber, hooks rules, re-render optimization, memoization, Suspense.
- CSS: specificity, flexbox/grid, responsive, containment; Accessibility (a11y, ARIA, WCAG); Web performance (Core Web Vitals, bundle, lazy load).
- Как это спрашивают в 2026: всё ещё устно? через debug AI-сгенерированного компонента? Стало ли важнее, т.к. «архитектура фронта остаётся человеческой задачей»?

#### CB-4. Backend, API & Database
- API design (REST vs GraphQL vs gRPC), idempotency, pagination, versioning, auth (JWT/OAuth/sessions).
- Базы данных: schema design, нормализация, индексы, query optimization, N+1, транзакции/ACID, isolation levels, оптимистичные/пессимистичные блокировки.
- Конкурентность, кэширование (Redis), очереди, rate limiting на уровне бэка.
- Как модифицировались: дают ли «отревьюй этот AI-сгенерированный SQL/endpoint и найди проблемы»?

#### CB-5. CS Fundamentals
- OOP/SOLID, паттерны проектирования, сложность, concurrency primitives, networking (HTTP/TLS/DNS/TCP), security basics (XSS/CSRF/SQLi/OWASP).
- Canva убрала «CS Fundamentals round» — кто оставил и как? На какие фундаментальные основы опираются «AI-resistant evaluations» (Anthropic)?
- Стали ли fundamentals важнее как раз потому, что отличают «AI as Amplifier» от «AI as Replacement»?

#### CB-6. Behavioral & Take-home
- Что в behavioral осталось классическим (ownership, conflict, leadership) и что добавилось (AI-этика, AI-decision-making) — но фокус на инвариантах.
- Take-home: классический формат (build a feature) — стал ли он сложнее/реалистичнее, т.к. AI ускоряет? Как оценивают, когда AI ожидается? Как делают take-home «AI-resistant» (Anthropic multi-level)?

### 2.3. Сквозные вопросы (ответь после поблочного разбора)

- Q1. **Инварианты vs переменные.** Составь явный список: что в классике осталось НЕИЗМЕННЫМ (вечный фундамент) и что стало ПЕРЕМЕННЫМ (формат доставки, способ оценки, anti-cheating).
- Q2. **Сдвиг глубины.** Подтверди или опровергни: классику теперь спрашивают на бóльшей глубине reasoning, т.к. имплементация подешевела. Приведи before/after примеры одного и того же вопроса на разной глубине.
- Q3. **Read > Write.** Насколько широко классический «напиши X» заменён на «отревьюй/отладь AI-сгенерированный X»? Это уже мейнстрим или нишевый формат?
- Q4. **Anti-cheating канон.** Какие классические форматы вернулись/усилились именно ради защиты от AI (on-site, прокторинг, устные dry-runs, multi-level задачи, live-debugging)?
- Q5. **Frontend-специфика.** Для fullstack с frontend-уклоном (React/Next.js): какие классические frontend-вопросы дают наибольший сигнал в 2026 и как они изменились?

### 2.4. Гипотезы для валидации

Для каждой: **Verdict (Confirmed/Partially/Refuted)**, **Evidence (свежие источники)**, **Confidence (1-5)**.

| # | Гипотеза |
|---|----------|
| C1 | Классические DSA-задачи не убраны, но переформатированы: меньше «реши с нуля», больше «объясни/оптимизируй/найди баг», часто на AI-сгенерированном коде. |
| C2 | Классический (не-GenAI) System Design остаётся ядром loop и теперь оценивается глубже по trade-offs/observability/cost. |
| C3 | Frontend deep-dives (event loop, reconciliation, rendering, a11y, perf) выросли в значимости, т.к. «архитектура фронта — человеческая задача». |
| C4 | CS fundamentals стали важнее как фильтр «понимания vs vibe-coding», и на них опираются AI-resistant evaluations. |
| C5 | Live-coding без AI + прокторинг/on-site возвращаются у части компаний именно как анти-AI мера. |
| C6 | Один и тот же классический вопрос теперь имеет «два этажа»: базовый (что раньше = пройти) и углублённый (что теперь = выделиться). |

### 2.6. Инструкции по выполнению

1. **Строй поверх Phase 1, не повторяй.** Если тема уже раскрыта в первом отчёте (RAG, agents, MCP) — не трогай, кроме как для связи с классикой.
2. **Before → After обязателен.** Любое утверждение о модификации классики подкрепляй парой «как было / как стало» с конкретными примерами вопросов.
3. **Свежие источники (2025–2026).** Указывай дату. Приоритет — реальные отчёты о собеседованиях, инженерные блоги, hiring-аналитика.
4. **Конкретика вместо абстракций.** Не «System Design стал глубже», а «раньше хватало нарисовать боксы; теперь просят capacity estimation для 100M DAU и обоснование consistency model».
5. **Контекст кандидата:** senior fullstack, React/Next.js/TypeScript/Node.js, активно использует AI. Frontend-уклон классики разбирай подробнее.
6. **Главный выход — разделы 2, 4 и 7.** Карта мутаций, список инвариантов и classic-track focus points. Всё должно сходиться к плану подготовки по классике.
7. **Честность о неопределённости.** Где данных мало (например, точные веса блоков), помечай как оценку и указывай уровень уверенности.

## Приложение: Глоссарий

| Термин | Определение |
|--------|-------------|
| **Классический канон** | Вопросы эпохи 2020–2023: DSA/LeetCode, классический System Design, frontend/backend deep-dives, CS fundamentals, behavioral, take-home. |
| **Инвариант** | Элемент собеседования, не меняющийся от внедрения AI (вечный фундамент). |
| **Переменная** | Элемент, изменившийся в формате доставки или способе оценки под влиянием AI. |
| **Two Floors** | Идея, что один классический вопрос имеет базовый уровень (раньше = пройти) и углублённый (теперь = выделиться). |
| **AI-resistant evaluation** | Формат задания, устойчивый к решению через AI (multi-level, on-site, прокторинг, live-debug). |
| **Read > Write сдвиг** | Замена «напиши код с нуля» на «прочитай/отревьюй/отладь существующий (часто AI-сгенерированный) код». |
| **Classic Track / AI Track** | Два направления подготовки: классика (этот отчёт) и AI-native темы (Phase 1). |
