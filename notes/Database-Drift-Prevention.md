# 🧠 Topic: Предотвращение дрифта схемы БД (Database Drift Prevention)

> [!abstract] Executive Summary (ELI5)
> Дрейф базы — это когда живая база потихоньку перестаёт соответствовать тому, что описано в репозитории (миграциям). Как здание, которое перестроили без обновления чертежей: по документации строить больше нельзя, все новые бригады ошибаются. Профилактика — одна идея, разложенная на много техник: **репозиторий — единственный источник истины, база — производная**, а любые расхождения ловятся инструментами, а не памятью людей.

---

## 🎯 The "Why"

**Проблема:** схема БД меняется постоянно, и у каждого изменения есть два пути — через код (миграция в git) или руками (консоль, GUI-редактор, хотфикс). Второй путь всегда быстрее «прямо сейчас» и всегда дороже потом:

- свежая база из миграций ≠ реальная база → «работает у меня», мистические баги;
- история схемы неполна → «зачем эта колонка?» — никто не помнит;
- восстановление «пересоздать из миграций» больше не работает — это уже другая база;
- **для агентной разработки критично вдвойне:** агенты понимают мир по репозиторию; если реальная база знает что-то, чего нет в git, агенты пишут код под вымышленный мир.

**Анти-пример (личный опыт):** легаси eloomi5.32 — 402 инкрементальные миграции поверх прод-схемы, которой в гите никогда не было. Схему пришлось восстанавливать археологией: SQL-сид руками, генерация таблиц по `$fillable` моделей, auto-heal по текстам ошибок. Истиной была живая база — худший из вариантов. (Полная история — в сессии запуска легаси локально.)

---

## 💡 Mental Model & Analogy

**Архив чертежей.** Проектная документация здания лежит в архиве (git). Любая перепланировка — хоть стену снести, хоть розетку — начинается с чертежа, положенного в архив (файл-миграция), и только потом исполняется. Подрядчик, тихоdemoтировавший стену без чертежа, ломает систему: новые бригады строят по устаревшим планам, а «отстроить по проекту» невозможно. База при этом — **скот, а не питомец** (cattle, not pet): любую можно убить и вырастить заново по документации.

## 📚 Каталог техник

### A. Источник истины

**A1. Миграции — единственный источник схемы.**
Истина о схеме живёт в git; база — функция от истории миграций: воспроизвёл все миграции на чистой базе → получил ровно ту же схему, что у всех (локально, CI, прод). Fresh clone → `db:reset` → идентичная схема. Детально: кандидат на истину два — живая база или репо; выбираем репо, всегда.

**A2. Запрет ручных правок (no manual DDL).**
Никаких `ALTER TABLE` в консоли, таблиц-редакторов в pgAdmin/DBeaver, «быстрых» починок локальной базы, прямых хотфиксов чужой базы. Любой DDL — только через миграцию в git. Разрешено: обычная работа приложения с данными, исследовательские SELECT, локальные эксперименты с последующим reset. Дата-фиксы — тоже кодом (миграция данных/скрипт), чтобы были ревью и история.

**A3. Пересоздавай, а не чини (recreate, not repair).**
Если база разошлась — она пересоздаётся из миграций, а не выравнивается руками. Починка руками дешевле только в моменте; стратегически она легализует дрейф.

**A4. Иммутабельность применённых миграций.**
Правка уже применённой (закоммиченной) миграции — отдельный вид дрейфа: у одних сред она в старой версии, у других в новой. Правило: применённая миграция неизменяема; изменение = новая миграция сверху. Инструментально ловится checksum-валидацией (Flyway `validate`, Liquibase checksums) и Prisma journal.

**A5. Один путь изменений (single path of change).**
Все среды (dev/staging/prod) получают схему одним и тем же пайплайном (`migrate deploy` из CI). Никаких отдельных «прод-скриптов наката». `db push` (схема мимо миграций) — только одноразовые локальные эксперименты, никогда в общий путь.

### B. Детекция дрифта

**B1. Журнал миграций + drift detection.**
В базе лежит журнал применённых миграций (`_prisma_migrations`, `flyway_schema_history`). Инструмент сравнивает три вещи: желаемую схему, историю миграций, живую базу. Расхождение, не объяснимое журналом, → «drift detected», инструмент отказывается работать тихо и требует миграцию или честный reset. Prisma: `migrate dev` делает это автоматически.

**B2. Shadow database.**
Prisma для каждой операции `migrate dev` создаёт временную shadow-БД, накатывает на неё все миграции и сверяет результат с желаемой схемой. Это детект «миграции разошлись со schema.prisma» и защитa от нелинейных историй. Нюанс: роли нужен `CREATE DATABASE` (в Testcontainers/CI — строчка сетапа, без неё загадочные ошибки).

**B3. Diff-сверки по расписанию.**
`prisma migrate diff --from-migrations --to-url $PROD_URL` (аналоги: `migrate diff`, Skeema diff, Atlas `schema diff`) — периодическая задача, сравнивающая миграции с реальной базой каждой среды и кричащая при расхождении. Дешёвый страховой полис на «кто-то всё-таки полез руками».

**B4. Снапшоты схемы.**
`pg_dump --schema-only` по крону в объектное хранилище: бесплатная точка сверки + forensic («когда появилась эта колонка?»). Не защита, но детектория после факта.

### C. Процесс и дисциплина

**C1. Ревью сгенерированного SQL.**
Миграция, сгенерированная ORM (Prisma, Doctrine, Alembic), — черновик, а не истина: генераторы умеют деструктивные сюрпризы (DROP при переименовании). Правило: SQL читается глазами, правится руками при необходимости, тенантная/политическая обвязка, которой ORM не знает, дописывается в ту же миграцию.

**C2. Одна логическая правка = одна миграция = один PR.**
Мелкие атомарные миграции легко ревьюить, откатывать и бисектить; большие слияния «всё сразу» скрывают деструктивные шаги.

**C3. Разделение schema- и data-миграций.**
Долгие дата-трансформации не живут в schema-миграциях (блокируют деплой) — отдельные, повторяемые, ревьюируемые скрипты/джобы. Смешение провоцирует «быстрые» ручные доработки данных после наката.

**C4. Expand–contract (parallel change) для бездаунтайма.**
Каждое разрушительное изменение схемы — в две фазы: expand (добавили новое, пишем в оба места, читаем старое) → contract (переключили чтение, убрали старое) отдельной миграцией позже. Связь с дрифтом: двухфазность убирает повод для «временных» ручных костылей между релизами — каждая фаза завершена и закоммичена.

### D. Тестирование

**D1. Fresh-DB verification в CI.**
Каждый ран CI поднимает пустую базу (Testcontainers) и накатывает миграции с нуля. Если история миграций невоспроизводима (правка старой миграции, забытый файл, рассинхрон), падает здесь — задолго до прода.

**D2. Структурные инвариант-тесты.**
Тесты, проверяющие не поведение, а **структуру забора** — интроспекция системных каталогов БД. Канонический пример из eloomi-next: инвариант RLS — «у каждой таблицы вне белого списка есть колонка `tenant_id` + ENABLE + FORCE + политика; роль подключения — не владелец/superuser/bypassrls». Ловит класс ошибок, невидимый поведенческим тестам: тесты с одним тенантом утечку чужих данных увидеть не могут физически. Сообщение об ошибке печатает готовый SQL-фикс — самочинящийся цикл для агентов.

**D3. Поведенческие канарейки на механизмы.**
Парная пара к инварианту: маленький тест «два тенанта», доказывающий, что механизм (например, RLS + `SET LOCAL`) реально фильтрует в рантайме, а не формально присутствует. Инвариант широкий (все таблицы), канарейка глубокая (механика работает).

### E. Агентно-специфичное

**E1. «Мир агента = репозиторий».**
Агент пишет код по тому, что видит в git. Любая реальность вне репо (рукоправленная база, недокументированные данные) — источник мистических ошибок, которые агент не может диагностировать. Отсюда жёсткость A2/A5 в агентных командах выше, чем в людских.

**E2. Правила исполняются инструментом, а не дисциплиной.**
Мета-принцип: каждое архитектурное правило стараемся опустить с уровня «написано в конвенциях» до «не выражается инструментом» (линт, генератор, RLS-инвариант, checksum). Пример: деление миграций по неймспейсам контекстов делает межконтекстные связи невыразимыми в Prisma-схеме. Чем ниже уровень энфорсмента, тем меньше агент может сломать.

**E3. Сообщения об ошибках как протокол самопочинки.**
Тест падает не «RLS broken», а «course_reviews: колонка есть, ENABLE нет; фикс: ALTER TABLE ...». Агент (или человек) чинит по сообщению без археологии. Ошибка = инструкция.

**E4. Контраст с auto-heal.**
Auto-heal легаси (лечить базу по текстам ошибок) и fresh-DB-подход — противоположности: первый выводит схему из наблюдений за живой системой, второй — из декларации в git. Первый допустим как археология незнакомой системы, недопустим как процесс своей.

## ✅ Чек-лист (внедрить на новом проекте)

- [ ] Миграции в git — единственный источник схемы; ручной DDL запрещён (записать в AGENTS.md)
- [ ] `migrate deploy` из CI — единственный путь изменений для всех сред
- [ ] Fresh-DB накат миграций в каждом CI-раннере
- [ ] Drift-детект включён (`migrate dev` для людей, `migrate diff` по крону для сред)
- [ ] Применённые миграции неизменяемы (checksum-валидация, если инструмент даёт)
- [ ] Структурный инвариант-тест на критичные свойства схемы (у нас — RLS)
- [ ] Поведенческая канарейка на механизм изоляции
- [ ] Ревью сгенерированного SQL обязательно; ошибки тестов печатают готовый фикс
- [ ] Разделение schema/data-миграций; долгие трансформации — вне schema-миграций
- [ ] Правило «recreate, not repair» + db:reset одной командой
