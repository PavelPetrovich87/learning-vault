# 🧠 Topic: Skill Design from Competency Maps — из книги или бизнес-процесса в набор скиллов

> [!abstract] Executive Summary (ELI5)
> Чтобы превратить компетенцию (книгу, домен, бизнес-процесс) в скиллы, нужно две независимые карты: **карта знаний** (домены/слои — система координат, «что существует») и **карта работ** (jobs — «что заказывают»). Скилл вырезается **только по работам**: у него свой вход, свой выход, свой триггер. Знания прикладываются к работе как загружаемые справочники. Карта знаний служит валидатором покрытия — показывает, какие клетки срез скилла уже закрыл, — но никогда не является лекалом, по которому режут скиллы. Итог компетенции — не один мега-скилл, а **композиция независимых скиллов в плоском пуле с явными указателями-передачами** (координирует работу агент, а не граф вызовов между скиллами).

---

## 🎯 The "Why"

**Проблема:** источник (книга, регламент, бизнес-процесс) устроен по темам, а харнессу нужны работы. Если переносить структуру источника напрямую («глава 3 → скилл интервью-техник»), получаются **скиллы-темы**: без собственного триггера (никто не скажет «примени главу 3»), с конкурирующими описаниями (харнесс не понимает, кого звать) и с энциклопедическим раздутием. Обратная крайность — один god-skill на всю компетенцию: из него в конкретном запуске нужен один-два фрагмента, а грузится всё.

**Решение — три правила, выведенных на практике (скилл requirements-agreement):**

1. **Р1 — ядро + загружаемые части.** Ядро SKILL.md (~300 строк) — маршрутизатор: миссия, режимы старта, шаги процесса, роутер «что читать когда». Глубина живёт в `references/` (знания, читаются по мере надобности) и `templates/` (бланки, заполняются, а не читаются). Скилл самодостаточен: источник (книга, волт, курс) — откуда **копируют** при развитии, а не **зависимость**, которую скилл читает.
2. **Р2 — композиция.** Вся компетенция = набор независимых скиллов, могущих вызывать друг друга. Связанные работы — за одним маршрутизатором; менее связанные — отдельные скиллы. Связь между скиллами — явные указатели в разделах «Границы применения» («это работа скилла X — примени его»), перелинковка двусторонняя.
3. **Р3 — job-контракт.** Скилл = законченная работа, границы которой задают четыре поля: **вход** (с какого состояния начинаем), **выход** (какой результат выдан), **триггер** (когда харнесс зовёт), **не-цели** (соседние работы, которые явно не делаем).

---

## 💡 Mental Model & Analogy

**Карта знаний = карта города. Скилл = маршрут. Срез = линия маршрута на карте.**

Маршрут не «состоит из линий на карте» — он состоит из шагов; линия — его след.
Аналогия из разработки: тестовое покрытие — тесты не состоят из строк покрытия;
покрытие — проекция, по которой видно дыры.

Отсюда ключевые различения:
- **Модуль/глава/домен** = единица *обучения* или *описания* (тема).
- **Скилл** = единица *применения* (job-to-be-done).
- **Срез** = единица *анализа* (проекция скилла на карту знаний; обычно сквозная
  вертикаль через несколько доменов, но может лежать и горизонтально в одном).

## 🛠 Method / Pipeline

### Шаг 0. Определить тип источника — от этого зависит, с какой стороны входить

| Тип источника | Что дано сразу | Что надо построить | Риск |
|---|---|---|---|
| **Теория** (книга, курс, стандарт) | карта знаний (главы/темы) | карта работ: какие *jobs* живут за темами — спросить «что по этому материалу *заказывают*?» | скиллы-темы без триггеров (энциклопедия) |
| **Практика** (бизнес-процесс, регламент, домен) | карта работ (процессы = кандидат-jobs: у процесса естественные вход/выход/триггер) | карта знаний: какие знания нужны для исполнения работ | бог-skill из всего процесса целиком |

### Шаг 1. Карта доменов (ядра по доменам)

Разложить территорию на домены/слои. Это **система координат**, не контейнер
скиллов: скилл имеет право пересекать несколько доменов (вертикальный срез).
Для книги домены часто совпадают с группами глав; для бизнес-процесса —
с функциональными областями (закупки, производство, продажи…) плюс сквозные
слои (фундаментальные понятия, контекст, управление).

### Шаг 2. Выделить работы-jobs (в каждом домене и на пересечениях)

К каждой кандидатуре — тест Р3: *свой вход? свой выход? можно заказать отдельно,
без остального процесса?* Два «да» → скилл. Нет → это ступень существующего
процесса → `reference` внутри скилла (знание к ступени), не отдельный скилл.

### Шаг 3. Собрать каждый скилл по Р1

Ядро-маршрутизатор (миссия-стоп-правила, режимы старта, шаги, таблица
контрактов-указателей, ловушки, границы, роутер) + `references/` + `templates/`.
Прогрессивная загрузка: материал ступени нужен на 10 минут процесса,
не на весь запуск.

### Шаг 4. Связать скиллы в композицию (Р2)

Указатели в «Границах применения» в обе стороны. Кандидаты на отпочкование
отслеживать: скилл выделяется из части существующего, когда у части появляется
**собственный вход, выход и триггер** (пример: «управление изменениями принятого
baseline» — другой вход, чем «согласовать с нуля»).

**Поправка (исслед. пак, 2026-10-06):** это **плоский пул, координируемый моделью**,
а не граф вызовов: «вызов скилла X» — рекомендация-указатель в тексте, которую
исполняет агент-координатор. Надёжность композиции = **непересекающиеся
description-триггеры** (ревизия при добавлении каждого нового скилла). Гарантированная
межскилловая механика — слой инструментов с контрактами (паттерн MCP), не
скилл-скилл вызов.

### Шаг 5. Проецировать и вести покрытие

Срезы скиллов на карте знаний дают: (а) какие клетки заполнены и где дыры
(напр., замер «скилл не знает уровней требований» = пустая клетка фундамента);
(б) план развития — инкременты **закрашивают клетки**, не двигая границ
(job-контракт стабилен; растёт глубина и версия скилла).

Карта работает в обе стороны: **проверяет сделанное** (покрытие срезов) и
**обнаруживает будущее** (непокрытые цепочки). Но непокрытая клетка — это
*вопрос* «какая работа здесь живёт?», а не ответ «нужен скилл». После job-теста
исход один из трёх: (1) ступень существующего скилла → инкремент; (2) свой
вход/выход/триггер → новый скилл; (3) работы нет, только знание → не скилл
и не инкремент, просто справочный материал. Третий исход — самый частый
за пределами рабочих книг: не всякая территория карты — работа.

**Поправка (CHREST + Александер):** карта проверяет presence клеток, но не
**связность** — «скиллы перечислены, а композиция не работает» она не видит.
Разделение труда: **карта планирует инкременты, связность проверяет живой eval**
на реальной задаче. Порядок инкрементов — по карте, приоритеты — по боли живых
прогонов (паттерн-язык: карта растёт снизу вверх от повторяющихся проблем).

## ⚠️ Anti-patterns

1. **Скилл-тема** («глава N как скилл»): нет триггера, не срабатывает, конкурирует
   с соседями по описанию.
2. **God-skill**: вся компетенция в одном — в запуске нужен один фрагмент,
   а грузится всё; маршрутизатор разбухает.
3. **Зависимость от источника**: скилл читает книгу/волт/курс при работе —
   ломает портабельность. Источник — для копирования при инкрементах.
4. **Резка по карте**: скиллы определяют, глядя на домены/главы, а не на работы.
   Правильный вопрос не «какую главу покрыть», а «какую работу выполнить».
5. **Границы двигаются инкрементами**: добавление материала меняет не job-контракт,
   а глубину внутри него. Если тянет поменять вход/выход — это вопрос об
   отпочковании нового скилла, не о расширении старого.
6. **Граф вызовов между скиллами**: проектирование композиции как функций, вызывающих
   друг друга. Индустрия (Agent Skills + MCP) — плоский пул, координируемый моделью;
   надёжность дают неперекрывающиеся триггеры, а не рёбра.
7. **Карта как доказательство**: заполненные клетки ≠ работающая композиция; presence
   не проверяет связность — для этого живой eval на реальной задаче.

## 📦 Worked example (мини)

**Источник:** Вигерс/Битти «Разработка требований к ПО» + практика курса.
**Карта знаний:** фундамент (уровни, люди, процесс) / крыло разработки (выявление,
анализ, спецификация, валидация) / крыло управления (baseline, изменения,
трассировка) / контекст (цели, пользователи, правила, agile).
**Работа-job:** «довести проект от сырых бизнес-целей до первого согласованного
baseline» → скилл `requirements-agreement`. Триггер: «начинают проект, заказчик
прислал хотелки, просят собрать/подписать требования».
**Срез:** проходит сквозь карту вертикалью (цели → роли → контакты → ворота →
baseline), из каждого домена беря минимальную глубину; будущие главы книги
закрашивают клетки инкрементами (levels, roles, norms, gates, templates),
а «управление изменениями» с другим входом отпочкуется в отдельный скилл.
