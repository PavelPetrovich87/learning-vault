# Postgres RLS и мультитенантность — Flashcards

Related: [[Postgres-RLS-Multi-Tenancy]] · [[Dual-Write-Problem-and-Transactional-Outbox]]

<!-- Почему фильтрацию арендаторов перенесли из кода приложения в СУБД (RLS)? :: -->
<!-- Корректность app-фильтров зависит от того, что КАЖДЫЙ разработчик КАЖДЫЙ запрос написал правильно: один забытый фильтр (как scope Landlord в легаси eloomi) = утечка данных, незаметная для тестов. RLS вшивает фильтр в таблицу: СУБД применяет его к каждому запросу автоматически, чужие строки не выдаст даже рукописный SQL в psql. Забыть фильтр невозможно — он больше не пишется в коде. -->
<!-- #flashcards/backend -->

<!-- Два фильтра политики RLS и чем они различаются? :: -->
<!-- **USING** — какие СУЩЕСТВУЮЩИЕ строки видны (SELECT/UPDATE/DELETE); **WITH CHECK** — какие НОВЫЕ строки допустимы (INSERT/UPDATE). Для политики FOR ALL с заданным только USING Postgres автоматически использует то же выражение и как WITH CHECK. -->
<!-- #flashcards/backend -->

<!-- Почему SELECT без контекста возвращает 0 строк молча, а INSERT без контекста падает с ошибкой? :: -->
<!-- SELECT пропускает строки через USING: выражение дало NULL → строки «не существуют» → пустой результат без ошибки. INSERT проверяется WITH CHECK: новая строка не проходит → ERROR `new row violates row-level security policy`. Оба fail closed, но семантика разная: чтение — тихая пустота, запись — громкий отказ. -->
<!-- #flashcards/backend -->

<!-- Разбери по частям: tenant_id = current_setting('app.tenant_id', true)::uuid :: -->
<!-- current_setting читает параметр сессии (именованная ячейка соединения; точка в имени = пользовательский параметр). Второй аргумент true = missing_ok: не установлен → вернуть NULL, а не ошибку. ::uuid — приведение текста к UUID. Сравнение с NULL даёт NULL → трактуется как «строка не проходит». Цепочка: нет контекста → NULL → NULL-сравнение → не видно ни одной строки. -->
<!-- #flashcards/backend -->

<!-- Почему параметр арендатора устанавливается локально в транзакции (set_config(..., true))? :: -->
<!-- Соединения Postgres переиспользуются пулом. Параметр, переживший транзакцию, остался бы в соединении и достался бы следующему запросу — контекст ЧУЖОГО арендатора. SET LOCAL (третий аргумент true) стирает значение при COMMIT/ROLLBACK. Мост: транзакционно-скоупед «контекст-провайдер». -->
<!-- #flashcards/backend -->

<!-- Что делает FORCE ROW LEVEL SECURITY и почему без него изоляция дырява именно в eloomi-next? :: -->
<!-- Postgres по умолчанию освобождает от RLS владельца таблицы. FORCE отменяет исключение — политики действуют и на владельца. В eloomi-next владелец всех таблиц — eloomi_owner (роль миграций): без FORCE миграции и seed молча видели бы всех арендаторов. Направление: FORCE не «обходит», а ЗАКРЫВАЕТ обход. -->
<!-- #flashcards/backend -->

<!-- Зачем каноническая функция apply_tenant_rls вместо SQL политик в каждой миграции? :: -->
<!-- Ручной SQL = дрейф: в одной забыли FORCE, в другой другая формулировка. Одна функция в схеме platform порождает все политики: ADR-006 «byte-identical» = все политики проекта рождены одним текстом. Новая tenant-таблица = одна строка вызова в миграции. Пропуск ловит инвариант-тест (pg_class/pg_policies), а не ревью. -->
<!-- #flashcards/backend -->

<!-- DDL внутри plpgsql-функции: почему EXECUTE format('%I.%I', ...)? :: -->
<!-- DDL (ALTER TABLE, CREATE POLICY) нельзя выполнить статическим планом, когда имя таблицы — параметр: строка команды собирается в рантайме → динамический SQL через EXECUTE. %I — безопасное квотирование идентификатора (спецсимволы, инъекции). '' внутри литерала = экранированная одинарная кавычка. -->
<!-- #flashcards/backend -->

<!-- GRANT и политика RLS — как два слоя связаны и что регулирует каждый? :: -->
<!-- GRANT — классические привилегии: какие ТАБЛИЦЫ роль может трогать в принципе (без него permission denied ещё до RLS). Политика — какие СТРОКИ внутри таблицы видны. Уровни не смешивать: политика работает со строками (DML); создание таблиц (DDL) — территория GRANT и владения, политики её не касаются. ALTER DEFAULT PRIVILEGES распространяет гранты на будущие таблицы схемы. -->
<!-- #flashcards/backend -->

<!-- Почему tenants без политики, и что такое GLOBAL_TABLES? :: -->
<!-- Логину нужно найти арендатора по коду компании ДО того, как известен tenant_id → реестр арендаторов глобальный. ADR-005: таблицы без tenant_id обязаны быть в константе GLOBAL_TABLES (platform.tenants + public._prisma_migrations). Инвариант-тест проверяет обе стороны: tenant-таблица без политики = ошибка; таблица без tenant_id вне списка = ошибка. -->
<!-- #flashcards/backend -->

<!-- Грабля PG 15+: permission denied for schema public при первой миграции — что случилось и как вылечено? :: -->
<!-- PG 15 (2022, харденинг) отобрал право CREATE в схеме public у псевдороли PUBLIC. Prisma пишет книгу миграций в public → роль миграций упёрлась. Лечение: ALTER DATABASE eloomi OWNER TO eloomi_owner — в PG15+ схема public принадлежит pg_database_owner, владение БД дало владение схемой. -->
<!-- #flashcards/backend -->

<!-- Пул соединений и «запомнить тенант в соединении»: почему это схема-ловушка? :: -->
<!-- Соединение возвращается в пул вместе со своим состоянием. Следующий запрос получит контекст предыдущего арендатора — мгновенная межарендаторская утечка. Единственная безопасная дисциплина: параметр живёт ровно одну транзакцию (SET LOCAL / set_config(..., true)) и стирается при её завершении. -->
<!-- #flashcards/backend -->

<!-- Какая роль в стеке единственная имеет BYPASSRLS и как ограничен её инвентарь? :: -->
<!-- eloomi_system (SystemDb). Инвентарь закрыт ADR-005: seed (первичное наполнение) и event replay/rebuild, каждое использование — review-маркер. Рантайм-роль eloomi_app BYPASSRLS не имеет и под политиками — RLS видит всё. -->
<!-- #flashcards/backend -->
