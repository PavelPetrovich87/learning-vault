# 🧠 Topic: Один источник правды — схема как код, артефакты генерятся

> [!abstract] Executive Summary (ELI5)
> Сущность описывается **один раз** — декларативной машиночитаемой схемой; всё остальное (типы, валидация, клиенты, миграции, документация, моки) **генерируется** из неё. Правишь схему — все производные обновляются сами. Править производные руками — запрещено: они не «твои», они слепки. Принцип один, применений много: Prisma-схема → клиент и миграции БД; zod-схема → типы и валидация и OpenAPI; protobuf → стабы на десятке языков.

---

## 🎯 The "Why"

**Проблема:** одна и та же информация, записанная в двух местах, — это уже два разных знания, и расходятся они молча. Спека отстала от кода → фронт шлёт мусор. Типы отстали от валидатора → компилятор уверенно пропускает баг. Схема БД отстала от миграций → «работает у меня» ([[Database-Drift-Prevention]]).

**Для агентной разработки критично:** мир агента = репозиторий. Одна схема — один понятный ему источник; рассинхрон ручных копий агент не диагностирует никогда, потому что обе копии «правильные».

**Мета-принцип:** правило должно исполняться инструментом, а не дисциплиной. SoT (single source of truth) — способ опустить уровень энфорсмента с «не забудь синхронизировать» до «синхронизация происходит физически, другого кода нет».

---

## 💡 Mental Model & Analogy

**Мастер-форма в литейном цехе.** Одна форма → много отливок. Изменил форму — все следующие отливки новые. Долбить готовую отливку напильником = править сгенерированный код: деталь сделана, но она больше не соответствует ни форме, ни другим отливкам. Чинят **форму**, потом льют заново.

## 📚 Каталог: схема → артефакты

| Схема (источник правды) | Генерируемые артефакты | Замечания |
|---|---|---|
| **Prisma schema** | TS-клиент, SQL-миграции, типы моделей | наш выбор для БД (eloomi-next ADR-006); клиенты не коммитятся |
| **Zod schema** | TS-тип (`z.infer`), рантайм-валидация, OpenAPI-фрагмент | наш выбор для HTTP-границы; см. [[OpenAPI-From-Zod]] |
| **OpenAPI-спека** | документация (Swagger UI), клиенты (orval), моки (Prism), контракт-тесты | режим **spec-first** — то же знание, противоположное направление генерации |
| **GraphQL SDL** | типы резолверов (graphql-codegen), типизированные клиенты, интроспекция | схема API как контракт |
| **Protobuf `.proto`** | стабы на десятках языков, gRPC-каркас | старейший и самый строгий пример |
| **tRPC-роутер** | типы фронта напрямую из роутера бэка | без спеки вовсе; только TS↔TS монорепо — наш стек подходит, но выбираем OpenAPI ради универсальности |
| **Drizzle schema** | SQL, миграции, типы | младший брат Prisma, более SQL-first |
| **JSON Schema** | валидаторы (ajv), документация, формы | знамя, под которое конвертируются остальные |
| **Дизайн-токены (style-dictionary)** | CSS-переменные, iOS, Android | SoT работает и вне бэкенда |
| **Terraform / Helm** | инфраструктура сред | SoT на уровне «что вообще задеплоено» |

**Два направления генерации:**
- *code-first*: код-схема → спека (наш путь: zod → OpenAPI);
- *spec-first*: спека → код и клиенты (protobuf, GraphQL-стек).

Принцип один: знание о форме рождается **ровно в одном месте**.

## 🚫 Анти-паттерны

1. **Декоративное дублирование:** `@nestjs/swagger`-декораторы + отдельный валидатор — спека и валидация как две копии; расходятся молча.
2. **Напильник по отливке:** правка сгенерированного файла (клиента, миграции, спеки). Правка теряется при следующей генерации, а до той — врёт остальным.
3. **Коммит генератов «чтобы в PR было видно»:** шум в диффах + соблазн правок. Обзорность делается задачей/отчётом в CI, не коммитом. (Исключение — консюмеры без node-окружения; фиксировать исключение явно, как в ADR-006.)
4. **«Временная» ручная синхронизация:** «пока поправим оба места руками» — постоянная должность без названия.
5. **Декоративная схема:** схема есть, но рантайм валидирует чем-то другим (или ничем). Хуже отсутствия — создаёт иллюзию контракта.

---

## ✅ Когда принцип оправдан

- ≥2 производных артефакта, **или** хотя бы один производный, который обязан не отставать (валидация, миграции, контракт клиента);
- форма активно меняется (а в LMS — меняется всё);
- есть CI, который может генерировать и валидировать воспроизводимость.

**Не оправдан:** одна копия, не растёт, генерация дороже инфраструктуры, чем ручной файл. SoT — не догма, а ответ на цену дрейфа.

---

## ✅ Чек-лист внедрения

- [ ] На каждую сущность — ровно одна декларативная схема; где она живёт — зафиксировано в ADR
- [ ] Сгенерированное не коммитится (или коммитится по явному исключению)
- [ ] Генерация запускается одной командой и входит в verify до typecheck/build (turbo-зависимость)
- [ ] Ручная правка генерата = lint-ошибка/ошибка ревью (маркер «generated» в шапке файла)
- [ ] Воспроизводимость проверяется в CI: сгенерь в чистом чекауте → diff пустой
- [ ] Схемы проходят ревью как контракты (изменение схемы = ломающее или аддитивное — осознанно)
