# 🧠 Topic: Графы в AI-driven репозиториях — слои, дебат «индекс vs поиск», алгоритм выбора

> [!abstract] Executive Summary (ELI5)
> У агента нет памяти о репозитории — есть контекстное окно и способ его наполнить. Способов три: **живой поиск** (агент ходит grep'ом), **индексы** (структура построена заранее) и **гибрид** (слои + правило маршрутизации). Графы при этом — не «ещё один индекс», а три разных дара: **контекст** (агент стартует ориентированным), **планирование** (батчи, blast radius) и **инварианты** («ничего лишнего не сломалось» — это поиском не проверяется, только измерением по графу). Выбор — не «граф или нет», а алгоритм из 5 вопросов: тип работ → масштаб → потребители → владение → что уже стоит. Ниже — 7 типовых ситуаций, прогнанных через алгоритм; в двух правильный вердикт — «граф не заводить», ещё в одной — «только временный, умирёт вместе с задачей».

---

## 🎯 The "Why"

**Проблема:** fresh-context агент стартует с нулевым знанием репозитория. Каждая его ориентация — это grep-экспедиция за токены, у каждого агента своя (неповторимая и потенциально кривая) картина, и часть связей поиск не находит никогда (строки, DOM, смысловые совпадения без общих слов).

**Почему графы — не автоматический ответ:** у любого графа есть стоимость владения (генерация, инвалидация, разбор расхождений, онбординг). Ошибки симметричны и обе дороги:
- **лишний граф** — владение без выгоды + ложный авторитет, когда он протух;
- **отсутствующий граф** — сгоревшие токены, слепые пятна агентов, непроверяемые обещания («behavior-preserving», «ничего лишнего не тронул»).

**Что граф даёт поиск в принципе не может:** измеримую дельту. Вопрос «где определён X» решает поиск; обещание «после моего PR изменилось ровно то, что заявлено» — только равенство множеств рёбер. Формула на все случаи: **поиск отвечает на вопросы, граф проверяет обещания**.

## 💡 Mental Model & Analogy

**Город и навигация в нём.** Агентный поиск — разведка на местности: спрашиваешь прохожих (grep), идёшь на шум (glob), читаешь таблички (файлы). Дёшево начать, дорого на каждом шаге, невозможно объять. Repo map — туристическая карта в кармане: грубая, но сразу видно кварталы. Эмбеддинги — «где-то я уже видел что-то похожее по духу»: находит без общих слов, но иногда путает. Символьный граф (LSP/MCP) — адресная система: точный адрес каждого символа и список всех, кто на него ссылается. Build-граф — схема метро: какие станции затронет закрытие перегона. Инвариант — это не карта, а *поверка*: сравнение плана маршрута с фактическим треком.

## 📚 Каталог

### A. Пять слоёв графов (о чём вообще речь)

«Граф» — одно слово, пять разных сущностей. Первое движение при выборе — выбрать слой под *вопрос*, на который нужно отвечать.

| Слой | Что это | Типичные инструменты | На какой вопрос отвечает |
|---|---|---|---|
| **A1. Импорт-граф** | «кто кого импортирует», статика файлов | dependency-cruiser, madge, knip, lockfiles, SBOM | «Что сломается при перемещении/удалении? Где хабы и слои?» |
| **A2. Символьный граф** | определения/ссылки/вызовы на уровне функций | tree-sitter, LSP, SCIP | «Кто вызывает эту функцию? Все ли переопределения найдены?» |
| **A3. Семантический граф (CPG)** | AST + поток данных + taint | CodeQL, Joern, Semgrep | «Может ли ввод пользователя дотечь до SQL? Прекрасно для уязвимостей» |
| **A4. Знаниевый слой** | граф + эмбеддинги + LLM-суммаризации | GraphRAG, локальные code-graph MCP | «Какие части кода связаны с фичей X по смыслу?» |
| **A5. Build/task-граф** | граф сборочных единиц | nx, turbo, Bazel | «Какой минимальный набор тестов/сборок затронет PR?» (affected) |

Ключевая мысль: слои отвечают на вопросы *разной природы*. Перепутать слой — значит купить рентгеновский аппарат для проверки давления в шинах.

### B. Три способа добычи контекста (дебат изнутри)

**B1. Агентный поиск (позиция «никаких индексов»).** Модель в цикле *думать → grep/glob/read → наблюдать*: она сама — движок запросов и ранкер, каждый следующий запрос формулируется с учётом найденного. Плюсы: абсолютная свежесть, нулевое владение, точность на точных вопросах (бенчмарки: точный поиск и трассировка импортов выигрываются grep'ом). Минусы: токенная цена на масштабе, разрыв ключевых слов (вопрос «где валидация периода», а функция зовётся `tjekPeriode`), невидимые связи (строковые события), rabbit holes.

**B2. Индексы — три разных механизма:**
- **Repo map** (Aider-стиль): tree-sitter вытаскивает символы → граф «кто на кого ссылается» → PageRank (важен тот, на кого ссылаются важные) → top-N сигнатур под бюджет токенов. Транзиентная карта, пересобираемая под диалог — дешёвая ориентация, не индекс.
- **Эмбеддинг-индекс** (Cursor-стиль): Merkle-дерево хешей для инкрементального диффа → чанкинг по AST (функция не режется посередине) → векторы с кэшем по хешу чанка → ANN-поиск по запросу. Единственный механизм, который находит **смысловое совпадение без общих ключевых слов**. Плата: инфраструктура, протухание между реиндексами, чанкинг-артефакты.
- **Символьный граф как MCP-инструменты** (Serena-стиль): под капотом — настоящий язык-сервер, который сам поддерживает и сам же инвалидирует свой индекс; агент получает `find_symbol` / `find_referencing_symbols` — один детерминированный хоп вместо экспедиции. Горизонт тот же, что у компилятора: строки и DOM не видит.

**B3. Гибрид (консенсус 2026).** Не «всё вперемешку», а слои по возрастанию цены и убыванию детерминизма:

```
L0  статика в промпте   AGENTS.md, structure.md, repo map   — цена 0, всегда
L1  живой поиск         grep / glob / read                  — discovery, свежесть 100%
L2  структурные запросы graph-slice, LSP/MCP                — вопросы известной формы, 1 хоп
L3  семантика           эмбеддинги                          — смысловой разрыв, последняя инстанция
L4  инварианты          графовый дифф, архи-гейты           — обещания, не retrieval
```

Routing-правило: точный вопрос известной формы → L2; точный текст → L1; смысл без ключевых слов → L3; глобальная картина → L0; обещание → L4.

**B4. Инвалидация — вопрос, убивающий индексы.** У каждого слоя с индексом должен быть ответ «когда пересобираемся»: шаг в CI/verify (гарантия на каждый прогон), git-hook (на границах коммитов), watcher с инкрементальным реиндексом (Merkle-дифф), rebuild-on-query (круиз на месте, если он секундный). Нет ответа → персистентный индекс заводить нельзя: stale index **хуже отсутствия**, потому что выглядит авторитетно.

### C. Алгоритм выбора: пять вопросов

Порядок не случаен: 1 выбирает *слой*, 2 и 3 — *окупаемость и форму*, 4 — *выживаемость*, 5 — *точку входа*.

**C1. Какой тип доминирующих работ на ближайшие месяцы?**
Смотреть git log за 3–6 месяцев (feat vs refactor vs массовые перемещения), трекер (эпики-миграции), CI (миграционные ветки). Доминанта → слой: миграции → A1+инвариант; фичи → поиск; аудит → A3; монорепа-CI → A5.
❌ Часто отвечают «какие графы сейчас модные». ✅ Грамотно: слой выводится из типа обещаний, которые надо проверять.

**C2. Сколько модулей и как быстро меняется?**
Мера — **модули, не строки** (100k строк в 30 файлах и в 800 — разные миры). Обязательно вычесть замороженное (vendor, generated, легаси-углы, куда никто не ходит): `git log --since` по файлам покажет горячее ядро. <~200–300 активных → поиск справляется; сотни → срезы и импорт-граф как рабочий инструмент; тысячи/монорепа → символьный слой и A5.
❌ Мерить LOC. ✅ Считать горячие модули и скорость их изменения.

**C3. Кто потребители — агенты какого рода?**
Выписать роли: кто исполняет (интерактивный человек+IDE vs автономные прогоны с программной сборкой промпта), кто проверяет (есть ли аудитор/гейт с требованиями доказательств), кто планирует. Потребитель определяет **форму**: автономному исполнителю — срез в промпте, аудитору — инвариант, планировщику — отчёт, интерактивной паре — часто ничего сверх AGENTS.md.
❌ Строить отчёт, который никто не откроет («граф как театр»). ✅ Артефакт проектируется от потребителя.

**C4. Какова цена протухания? Кто и когда пересобирает?**
Три подвопроса: (1) в какой момент граф гарантированно синхронизируется (гейт/hook/watcher/on-query)? (2) что происходит при промахе — красный ли гейт (как «lockfile out of date») или молчаливое «кто-нибудь пересоберёт»? (3) не может ли артефакт сравнить себя с самим собой (классика: процесс, который пересоздаёт и отчёты, и эталон «до» — дифф становится всегда-зелёной декорацией)? Плюс взвесить ущерб: врущий зелёный инвариант — катастрофа, врущий отчёт — досадно.
❌ Считать протухание неприятностью. ✅ Считать его ядом: stale-инвариант проходит все проверки, пока не выстрелит.

**C5. Что уже стоит?**
package.json + CI-конфиг — главный список: nx/turbo/Bazel, dependency-cruiser/madge/knip, CodeQL/Semgrep, `no-restricted-imports` и baseline-файлы, lockfile/SBOM (это уже графы!), LSP-инфраструктура редактора. Графы часто уже есть — просто не называются графами.
❌ Строить второй источник истины рядом с существующим. ✅ Один движок, один резолвер — и открыть к нему доступ.

### D–J. Семь ситуаций: алгоритм в работе

> Формат каждой карты: контекст → 🧭 ход мыслей (пять вопросов с конкретными сигналами) → ✅ вердикт → ⚠️ анти-паттерн. В ходы мыслей специально включены места, где легко свернуть не туда.

### D. Ситуация 1 — Миграция / большой рефакторинг силами агентов

**Контекст.** Легаси-приложение на устаревшей архитектуре (смена структуры каталогов, выкорчёвывание старого модульного стандарта, переезд на новый фреймворк). Работы ведутся автономными агентами батчами, каждый батч обещает «поведение не изменилось».

**🧭 Ход мыслей.**
1. *Тип работ?* Git log сплошь состоит из перемещений и перелицовки импортов; трекер — эпик «переезд». Это миграция → слой **A1**, и не просто как карта, а как **инвариант**: behavior-preserving = сохранность связности с точностью до переименования путей.
2. *Масштаб?* ~400–900 активных модулей. Точечный поиск работает, но структурные вопросы («кто тянет этот модуль», «ровно ли переместилось») требуют транзитивности — grep её не даёт.
3. *Потребители?* Автономный исполнитель (fresh context) → нужен **срез файла** в промпте (кто импортирует/что импортирует). Аудитор с требованием доказательств → **графовый дифф против плана батча**. Планировщик батчей → **отчёт** с fan-in, чтобы резать работу по хабам.
4. *Владение?* Проект гейтится CI/verify — значит, отчёты пересобираются каждым прогоном (свежесть бесплатна), а эталон «до» фиксируется на границах батчей с привязкой к коммиту. Критический подпункт: генерация отчётов не имеет права трогать эталон, иначе дифф сравнивает дерево с самим собой и всегда зелёный.
5. *Что стоит?* Линтер зависимостей уже есть (правила слоёв) → граф доступен флагом экспорта, тикет = «открыть доступ», а не «построить».

**✅ Вердикт.** Импорт-граф в трёх формах: отчёт (планировщику), срез (исполнителю), дифф-инвариант (аудитору). Ядро ценности — инвариант: он превращает обещание батча в машинную проверку.
**⚠️ Анти-паттерн.** Дифф, который физически не может покраснеть (эталон пересоздаётся тем же прогоном, что и отчёты). Инструмент, не умеющий краснеть, — не инструмент, а декорация; обнаружится только на первом сломанном экране.

### E. Ситуация 2 — Фичевая разработка в небольшом проекте

**Контекст.** Продукт 150–250 активных модулей, команда делает фичи, один-два разработчика + интерактивный IDE-агент, CI обычный (тесты+линт), migrations нет и не предвидится.

**🧭 Ход мыслей.**
1. *Тип работ?* Feat/fix почти без исключений → обещание «поведение не меняется» не звучит вообще; срезаются инварианты как главный мотив.
2. *Масштаб?* Горячее ядро — полторы сотни модулей, всё обозримо агентным поиском за разумные токены.
3. *Потребители?* Один интерактивный агент, который сам ходит grep'ом и человек, который видит репо глазами. Никто не потребляет программно собранные промпты; аудитора-автомата нет.
4. *Владение?* Вот где развилка: гейт есть, но пересборка графа в нём будет стоить секунд и *нигде не понадобится* — отчёт некому читать, срез некому вставлять, инвариант нечего проверять.
5. *Что стоит?* Линтер, lockfile, может быть LSP — уже достаточно.

**✅ Вердикт.** **Граф не заводить.** Максимум — качественный AGENTS.md (слои, конвенции, грабли) как L0 и живой grep как L1. Это не «недоинвестировали», а правильный ноль: дисциплина сказать «нет» — часть компетенции.
**⚠️ Анти-паттерн.** «Поставим же граф, все ставят» → structure.md, который открывали дважды (оба раза — сам автор), и протухающий артефакт с ложным авторитетом.

### F. Ситуация 3 — Монорепа, дорогое CI, много команд

**Контекст.** 40+ пакетов, сотни инженеров, CI-минуты дорогие, PR-конвейер забит полными прогонами тестов и сборок.

**🧭 Ход мыслей.**
1. *Тип работ?* Смешанный (фичи+рефакторинг), но главная боль — **стоимость проверки**, не навигация. Это слой **A5**: вопрос «что затронуто» стоит денег каждую минуту.
2. *Масштаб?* Тысячи модулей — A1/A2 пригодились бы, но они не решают боль CI.
3. *Потребители?* CI-конвейер и ревьюеры — потребители affected-вычисления; агенты — вторичны.
4. *Владение?* Build-система сама владеет своим графом и инвалидацией — это её штатная работа; владение уже оплачено, платить второй раз не за что.
5. *Что стоит?* Обычно ничего из A5, но миграция на nx/turbo/Bazel — самостоятельный проект; оценка честная: недели, не дни.

**✅ Вердикт.** Build-граф с affected-механикой в CI — единственный слой с прямым денежным ROI. Символьный/импорт-графы — позже и только под конкретных потребителей (автономные агенты, ревью-боты).
**⚠️ Анти-паттерн.** Строить собственный affected-калькулятор на импорт-графе поверх мешанки скриптов, когда задача — кэширование и оркестрация, которую build-система решает целиком.

### G. Ситуация 4 — Security-аудит / комплаенс

**Контекст.** Fintech-приложение, требуется доказуемое отсутствие опасных потоков данных (пользовательский ввод → криптографические операции/SQL/логи), плюс регулярные аудиты.

**🧭 Ход мыслей.**
1. *Тип работ?* Аудит → обещание «опасный поток отсутствует». Импорт-граф его не проверяет принципиально: поток — это не импорт. Слой **A3 (CPG)**.
2. *Масштаб?* Не решающий, но CPG окупается и на малом, если цена пропуска высока.
3. *Потребители?* Аудитор и регулятор требуют доказательств; современная схема — статические инструменты дают кандидатов-«затравки», LLM их триажит и помогает писать правила, CPG верифицирует поток. Человек в цикле только на вердиктах.
4. *Владение?* CPG-инструменты в CI — штатная схема (пересборка на каждый прогон, находки как гейт) — вопрос закрыт выбором инструмента.
5. *Что стоит?* Semgrep часто уже стоит как линтер — это вход в экосистему; CodeQL подключается к тем же репозиториям.

**✅ Вердикт.** CPG (CodeQL/Joern/Semgrep) в CI + LLM-триаж находок. Импорт-граф не заменяет, но дополняет (архитектурные запреты «криптомодуль импортируют только двое» — это A1-правило поверх).
**⚠️ Анти-паттерн.** Пытаться вывести taint-анализ из grep-паттернов или из эмбеддингов: оба видят текст, а не поток данных; аудиту нужны доказуемые пути, а не похожие строки.

### H. Ситуация 5 — Онбординг в чужой / legacy код (анализ, не изменение)

**Контекст.** Приёмка проекта на поддержку (due diligence или вход команды). Менять ничего нельзя/не нужно — нужно быстро понять устройство: слои, хабы, циклы, мёртвые зоны, зоны риска.

**🧭 Ход мыслей.**
1. *Тип работ?* Анализ, ноль изменений → инварианты не нужны вовсе; нужна **карта**. Слой A1, роль — только отчётная.
2. *Масштаб?* Неизвестен до первого прогона — и это аргумент за отчёт: он же и есть измерение масштаба (модули, рёбра, распределение по каталогам).
3. *Потребители?* Люди и аналитические агенты; форма — человекочитаемая сводка + прицельные срезы по вопросам заказчика.
4. *Владение?* Ключевой нюанс ситуации: код **не меняется** → протухание невозможно → дешёвый одноразовый прогон легитимен даже без гейта. Единственная ситуация, где «пересоберём руками» — правильный ответ.
5. *Что стоит?* Обычно ничего; импорт-граф добавляется за день (depcruise-класс инструментов), CPG — если в скопе аудит безопасности.

**✅ Вердикт.** Лёгкий отчётный граф: structure-сводка (слои, топ fan-in/fan-out, орфаны, циклы) + срезы под вопросы. Временный артефакт: умирает вместе с задачей входа, не превращается в «постоянно обслуживаемую» инфраструктуру.
**⚠️ Анти-паттерн.** По инерции оставить отчётный граф жить в репо без потребителя и без ответа на вопрос пересборки — через полгода он заговорит враками о структуре, которой уже нет.

### I. Ситуация 6 — Автономные агентные пайплайны на большом коде

**Контекст.** Тысячи модулей; автономные агенты делают PR-ревью, мелкие фиксы и подготовку релизов без человека в цикле. Токены и latency — операционные расходы, которые считают.

**🧭 Ход мыслей.**
1. *Тип работ?* Повторяющиеся автономные операции над большим кодом → главный мотив — **токены и предсказуемость**: каждая grep-экспедиция в каждом прогоне — это деньги и вариативность.
2. *Масштаб?* Тысячи модулей → поиск физически не успевает за бюджетом; нужен предрассчитанный слой ориентации (**A2/LSP** или repo map), плюс A1 для blast radius ревью.
3. *Потребители?* Программные конструкторы промптов (им нужен структурированный ответ, не проза), ревью-боты (им нужен blast radius PR), аудиторы пайплайна (им нужны гейты).
4. *Владение?* Автономный пайплайн = готовый ритм пересборки (каждый прогон); индекс без шага синхронизации в пайплайне — мина.
5. *Что стоит?* LSP уже стоит в редакторах — обёртка в MCP-инструменты дешевле нового индекса; эмбеддинги — только если агенты жалуются на «не нахожу по словам».

**✅ Вердикт.** Слоистый гибрид: L0-отчёты в промптах, L2-инструменты (LSP/MCP, срезы) для известных форм вопросов, L1-поиск внутри агента как fallback, L3 — по показаниям. Оплачивается экономией хопов на каждом прогоне.
**⚠️ Анти-паттерн.** Персистентный эмбеддинг-индекс ради «современности» без ответа на инвалидацию: в автономном режиме никто не заметит, что индекс врёт, — агенты доверчивее людей.

### J. Ситуация 7 — Greenfield / быстрый прототип

**Контекст.** Новый проект, неделя от нуля, архитектура меняется дважды в неделю, каталоги переезжают, всё горит и летит.

**🧭 Ход мыслей.**
1. *Тип работ?* Эксперимент → обещаний нет, инварианты нечему проверять.
2. *Масштаб?* Десятки модулей — агент видит репо целиком и так.
3. *Потребители?* Один человек и один агент в интерактиве.
4. *Владение?* Вот где приговор: структура меняется ежедневно → любой персистентный граф протухает быстрее, чем окупается даже однократная генерация. Rebuild-on-query возможен, но незачем.
5. *Что стоит?* Ничего — и это правильно.

**✅ Вердикт.** **Ничего персистентного.** AGENTS.md ведётся с первого дня (он и есть L0), grep — L1. Граф появляется не «когда подрастём», а когда появится *обещание* (первая миграция) или *потребитель* (первый автономный пайплайн) — см. вопросы 1 и 3.
**⚠️ Анти-паттерн.** Ставить граф-инфраструктуру «сразу, чтобы было» в проекте, где каталоги переезжают каждую неделю: через месяц это музей экспонатов из несуществующей архитектуры.

### K. Общие анти-паттерны (сквозные)

- **K1. Граф-декорация.** Инвариант, который не может покраснеть; отчёт, который никто не открывает. Диагностика: назови последнее срабатывание графа *против* изменений. Не можешь — это декорация.
- **K2. Авторитетный вранец.** Stale-индекс без ответа «когда пересобираемся» — выглядит убедительнее своего отсутствия и потому опаснее.
- **K3. Слой не под задачу.** CPG на фичевом проекте; эмбеддинги там, где все вопросы точные; второй источник истины рядом с существующим графом.
- **K4. Мерить не то.** LOC вместо модулей; замороженный vendor, засчитанный в «горячее ядро».
- **K5. Граф без потребителя.** Каждый артефакт обязан иметь имя потребителя и место в чьём-то цикле (промпт/гейт/ревью), иначе он не актив, а пассив.

### L. Формулировки для собеседования

1. «Поиск отвечает на вопросы, граф проверяет обещания: discovery — агентный grep, а "ничего лишнего не сломалось" — только измеримая дельта по графу».
2. «Рассуждающий grep бьёт RAG на точных вопросах и не протухает; его цена — токены на масштабе и слепота к смысловому разрыву ключевых слов».
3. «Repo map — транзиентная карта (tree-sitter + PageRank), а не индекс; эмбеддинги — ровно один кейс: смысловой разрыв; символьный MCP — один детерминированный хоп для вопросов известной формы».
4. «Гибрид — слои по возрастанию цены и убыванию детерминизма, routing-таблица у агента, ответ "когда пересобираемся" у каждого индекса».
5. «Выбор графа — алгоритм из пяти вопросов: тип работ задаёт слой, масштаб и потребители — окупаемость и форму, владение — выживаемость, существующее — точку входа».
6. «Умение ответить "без графа" — та же компетенция, что умение его построить: граф без потребителя — это владение без выгоды».
