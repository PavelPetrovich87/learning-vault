# 🧠 Topic: Проблема двойной записи (Dual-Write) и Transactional Outbox

> [!abstract] Executive Summary (ELI5)
> Dual-write — это когда одно действие пользователя требует записать в **два хранилища сразу** (например: проводку в Postgres и письмо в очередь). Атомарной записи «сразу в оба» не существует — между ними всегда разрыв в миллисекунды, и краш в нём либо теряет работу, либо создаёт призрачную. Решение — бухгалтерское: в журнал (БД) в той же транзакции пишется не только факт, но и **намерение доставки**, а «курьер» (реле́й) позже дочитывает журнал по закладке и доставляет. Это и есть паттерн Transactional Outbox. Доставка становится догоняющей, а не одновременной — и потому неуязвимой к крашам.

---

## 🎯 The "Why"

**Проблема:** класс задач, где бизнес-факт живёт в транзакционной БД, а его последствие — в другой системе (очередь, кэш, поиск, файловое хранилище, чужой API). Между `COMMIT` в Postgres и `LPUSH` в Redis нет распределённой транзакции, и никогда не будет (2PC между БД и Redis не строит никто). Значит, **любой** код, пишущий в оба места, имеет окно несогласованности.

Два режима поломки — важно, что сдвиг второй записи «внутрь транзакции» меняет не безопасность, а **направление** поломки:

| Режим | Как получается | Что наблюдаем |
|---|---|---|
| **Phantom** («письмо без записи») | enqueue **внутри** tx, затем ROLLBACK | job в очереди про событие, которого нет; воркер ретраит призрак |
| **Lost** («запись без письма») | enqueue **после** COMMIT, затем краш процесса | событие в БД есть, реакции нет; в логах чисто |

**Почему «аккуратный код» не решает:** окно — миллисекунды, 99.9% кода работает годами; баг (а) не ловится тестами — недетерминизм по времени, (б) всплывает на деплоях и OOM-kill, (в) невидим — никто не сканирует «недоставленное». Классический источник «раз в месяц кто-то не получает письмо, а воспроизвести нельзя».

**Анти-пример (личный опыт):** легаси eloomi держало очередь `sync`-драйвером (всё в HTTP-процессе) — обратная крайность: нет dual-write, но нет и ретраев. Правильный вопрос не «очередь или нет», а «в каком из трёх контуров исполнять реакцию»:

```
Контур 1: in-tx          — только своя БД; атомарно команде; read-your-writes
Контур 2: after-commit   — только внешние порты; best effort; окно потери мс
Контур 3: queue/worker   — долго, ретраи, at-least-once; требует идемпотентности
```

## 💡 Mental Model & Analogy

**Бухгалтерия и почта.** Журнал проводок — Postgres: запись либо есть, либо нет, и это единственная истина. Почтовый ящик на улице — очередь. Клерк, записавший проводку и умерший по дороге к ящику, теряет письмо (lost). Клерк, опустивший письмо и отменивший проводку, отправляет призрак (phantom). Двухфазного коммита между журналом и почтой не существует. Решение бухгалтеров столетиями: **черновик письма подшивается в журнал** (транзакционно!), а курьер потом читает журнал и разносит. Запись — истина, доставка — догоняет.

## 📚 Каталог техник

### A. Распознавание (увидеть dual-write в коде)

**A1. Сигнатура проблемы.**
В одной функции (или в паре «команда + post-commit хук») две записи в разные хранилища, из которых хотя бы одна — транзакционная БД: `COMMIT` + `queue.add`, `COMMIT` + `cache.del`, `COMMIT` + `es.index`, `COMMIT` + `s3.put`, `COMMIT` + внешний POST. Любая из этих пар — dual-write.

**A2. Тест размещения (перед тем как решать).**
Пять вопросов: (T1) нужна видимость в первом чтении → контур 1; (T2) внешняя система → контур 1 запрещён; (T3) > 1–2 с или неограниченно → контур 3; (T4) потеря приемлема → контур 2, иначе — outbox; (T5) работа по расписанию → repeatable-job. Большинство «критичных» реакций — про данные, а данные пишет контур 1; очередь — про время, ретраи и объём.

### B. Наивные подходы и почему ломаются

**B1. Enqueue внутри транзакции.**
Генерирует phantom jobs при откате. Самая частая ошибка имплементации очередей; стоит запрещать явно (текстом в ADR/AGENTS.md), чтобы агенты не «оптимизировали».

**B2. Enqueue сразу после коммита (best-effort).**
Легитимен для **мягких** реакций (T4-да: письма «для информации», лог-эффекты). Окно потери — миллисекунды, стоимость — ноль. Это не решение dual-write, а осознанное принятие риска для узкого класса.

**B3. «Проверим и долечим».**
Отдельный job «найди завершённые курсы без отправленного письма и долечи». Работает, но это reconciliation по расписанию — лечение симптома; оставляется как эксплуатационная страховка, не как архитектура.

### C. Канонические решения

**C1. Transactional Outbox.**
В ту же транзакцию, что и бизнес-факт, пишется запись о намерении доставки (outbox-таблица). Атомарность по построению: проводка есть ⇒ доставка будет. (microservices.io *Transactional Outbox*; Kleppmann DDIA гл. 11.)

**C2. Polling Publisher (реле́й).**
Процесс опрашивает outbox по курсору («закладке») и доставляет записи в целевую систему. Курсор двигается **строго после** успешной доставки — краш между ними безопасен благодаря дедупу на приёме. Альтернатива транспорту — CDC/log-tailing (Debezium читает WAL): тяжёлая артиллерия для больших потоков; на типичном SaaS-объёме хватает поллинга.

**C3. Idempotent Consumer / Inbox.**
Зеркало outbox на потребителе: таблица обработанных ID + идемпотентные эффекты (условные апдейты, upsert, «сделано → skip»). Доставка at-least-once + идемпотентное исполнение = **effectively-once** — инженерная замена несуществующей exactly-once.

**C4. Ключ дедупа = идентификатор факта.**
Центральный трюк: `jobId = eventId`. Очередь (BullMQ и аналоги) не принимает job с существующим ID ⇒ повторная доставка физически отсеивается. Симметрия: для HTTP та же идея — claim-таблица идемпотентности (Stripe-стиль). Один принцип — «транзакционно захваченный ключ» — два применения.

**C5. Курсор по монотонной sequence.**
Нюанс, на котором горят: UUIDv7 **не строго** монотонен между инстансами (коллизии миллисекундного окна) ⇒ возможен пропуск события при курсоре по id. Канонический outbox использует `BIGSERIAL` от БД — строго монотонный. Существующий event log достаточно дополнить колонкой `seq`; курсор — сайдкар-таблицей, чтобы не ломать append-only лога.

**C6. Три барьера против дублей — по слоям.**
(1) курсор+seq — не теряем; (2) jobId-дедуп очереди — не дублируем доставку; (3) inbox/идемпотентность — не дублируем исполнение. Убрать любой — система работает; все три — effectively-once.

### D. Гарантии и семантики

**D1. Таблица отказов — «доказательство» паттерна.**
Перебор точек: до COMMIT — ничего не было; COMMIT→poll — реле́й дочитает; enqueue→курсор — повторный add с тем же jobId отклонён; курсор→process — job ждёт; в работе — retry; эффект→inbox-пометка — редкий повтор эффекта (закрывается provider-id или принят). Единственная строка с платой — последняя, и она локальна.

**D2. Чего паттерн НЕ даёт.**
Порядка исполнения между разными событиями (только порядок доставки); exactly-once на внешних эффектах (только effectively-once — фундаментальное ограничение); он не заменяет синхронные read-модели — реле́й про внешний мир, не про согласованность данных. Реле́й — единственный писатель курсора: это не очередь работ, а линейное чтение.

### E. Примеры из разных доменов (одна и та же анатомия)

**E1. LMS: курс завершён → письмо ученику** (наш кейс eloomi).
Факт: `learning.progress` + событие в tx. Реакция: SMTP. T2 (внешняя) + T4-мягкое ⇒ after-commit, либо outbox, если письмо нельзя терять. Phantom-вариант: enqueue в tx + откат из-за хендлера Certification.

**E2. E-commerce: заказ оплачен → вебхук партнёру по фулфилменту.**
Факт: `orders.status=paid` (после подтверждения платёжки). Реакция: HTTP-пост в чужой API с их retry-контрактом. Lost = заказ есть, склад не знает ⇒ отгрузка не планируется. Здесь almost всегда выбирают полный outbox+inbox: потеря денег, а не удобства.

**E3. Поиск: цена товара обновлена → переиндекс Elasticsearch.**
Факт: `UPDATE products`. Реакция: `es.update`. Lost = в каталоге старая цена (клиент видит одну, платит другую). Варианты: outbox → indexer, или CDC (Debezium) — классическое применение лог-тейлинга. Альтернатива-костыль: periodic full reindex (= B3).

**E4. Кэш: профиль обновлён → инвалидация ключей Redis.**
Факт: `UPDATE users`. Реакция: `DEL cache:user:{id}`. Phantom-режим: удалили кэш, COMMIT откатился — безвредно (кэш перечитается). Lost-режим: закоммитили, не успели удалить — **стейл до конца TTL**. Мораль: не всякий dual-write страшен — оценивай цену каждого направления поломки; для кэша часто достаточно write-through/short-TTL вместо outbox.

**E5. Файлы: загрузка аватара → S3 + строка метаданных в БД.**
Зеркальный dual-write: внешняя запись *сначала*, транзакционная *потом*. Упало между — файл-сирота в S3 (утечка, не потеря). Решение: сначала грузим во временное имя, строку в БД со статусом `pending` → rename в финальное → `committed`; сирот чистит фоновая задача по `pending`-возрасту. Урок: outbox — частный случай общего принципа «транзакционная запись — истина, остальное догоняет».

**E6. Платежи: инвойс Stripe оплачен → выдать подписку.**
Inbound-вариант: внешний факт приходит вебхуком. Опасность — двойная обработка одного вебхука (они приходят повторно!). Ответ тот же: claim по идемпотентному ключу (`event.id` провайдера) в транзакции выдачи. Направление зеркально, анатомия идентична C4.

**E7. Микросервисы: пользователь создан → событие в Kafka для трёх потребителей.**
Канонический учебниковый кейс: `COMMIT users` + `publish UserCreated`. Lost = сервис уведомлений никогда не узнает о юзере. Outbox+relay (или CDC) — стандарт; на стороне потребителей — inbox. Именно этот кейс породил имя паттерна.

**E8. Auth: смена пароля → отзыв всех сессий.**
Факт: `passwords` rotate. Реакция: `DEL redis sessions:{user}`. Lost-режим и окно безопасности: старые сессии живут до таймаута. Если недопустимо — сессии в БД или outbox-ревокация. Пример «dual-write с секьюрити-ценой», а не UX-ценой.

### F. Агентно-специфичное

**F1. Запреты — текстом и линтером.**
«Enqueue внутри PG-транзакции порождает phantom jobs» — правило, которое агент выучит только из ADR; lint на импорт очереди вне `shared/jobs` — правило, которое агент не сможет нарушить ([[Database-Drift-Prevention]] E2: чем ниже уровень энфорсмента, тем меньше агент может сломать).

**F2. Механизм — один и в одном месте.**
Реле́й, курсор, jobId-пробивка — живут в `shared`, контексты видят порт `JobQueue.enqueue`. Агент не должен (и не может) имплементировать outbox по месту — иначе получим пять релеев с пятью багами.

**F3. Обработчик — каноника из трёх строк.**
inbox-проверка → «цель исчезла → skip» → эффект → пометка. Эта форма записывается в AGENTS.md как обязательный скелет job-хендлера: ловит и дубли, и stale-яды (не ретраить удалённое!).

**F4. Явный продьюсинг и честные имена обёрток.**
Продьюсинг событий — **видимая строка в теле команды**, а не «магия» внутри обёртки или `save()`: `uow.dispatch(aggregate.pullDomainEvents())` последним выражением, скелет команды — load → mutate → save → dispatch. Обёртки названы по работе, которую делают: `withTenant` — только тенантность + tx (путь чтения/queries); `unitOfWork` — транзакция + обе фазы событий, внутри ровно один `withTenant` (путь записи/commands). Мораль: невидимый продьюсинг агент «не замечает» и пишет команды без диспатча — и ни один тест этого не ловит; вводящее в заблуждение имя обёртки — агентская мина, API — первый инструмент энфорсмента. Закрепление линтером: `queries → withTenant`, `commands → unitOfWork`, прямой `withTenant` из команды — ошибка.

## ✅ Чек-лист (внедрить на новом проекте)

- [ ] Тест размещения T1–T5 в AGENTS.md: какие реакции в каком контуре
- [ ] Явный продьюсинг: `uow.dispatch(...)` последним выражением команды; queries → `withTenant`, commands → `unitOfWork` (линт)
- [ ] Запрет enqueue внутри транзакции (текст ADR + линт на импорт очереди)
- [ ] Event log транзакционный (в той же tx, что факт) — уже есть ⇒ это твой outbox
- [ ] `seq BIGSERIAL` в event log + индекс (курсор только по нему, не по UUIDv7)
- [ ] Курсор — сайдкар-таблица; advance строго после доставки; условный UPDATE
- [ ] Реле́й: один инстанс, batchSize ~100, poll-интервал 1–2 с
- [ ] `jobId = eventId` для всех событийных job'ов; `removeOnComplete: {age}` шире окна пиков
- [ ] Скелет идемпотентного хендлера (inbox → stale-skip → эффект → пометка)
- [ ] Таблица отказов покрыта интеграционным тестом (краши в четырёх точках — доставляется ровно один раз)
- [ ] Reconciliation-джоб как страховка (B3) — осознанно, не как архитектура
