# 🧠 Topic: Postgres RLS и мультитенантность — изоляция арендаторов на уровне СУБД

> [!abstract] Executive Summary (ELI5)
> Одно приложение и одна база обслуживают много компаний-клиентов (арендаторов). Каждый ряд данных помечен владельцем (`tenant_id`), и база **сама**, на уровне каждой строки, пускает к данным только их владельца — независимо от того, что написал программист. Механизм называется **Row-Level Security (RLS)**. Он превращает забытый фильтр арендатора из «утечки данных» в «физически невозможную операцию».

---

## 🎯 The "Why"

**Проблема.** Мультитенантное приложение обязано изолировать данные арендаторов. Исторический подход — фильтровать в коде приложения: каждый запрос получает условие `WHERE tenant_id = X`. Корректность тогда зависит от того, что **каждый** разработчик **каждый** запрос написал правильно.

**Легаси-пример (боль):** eloomi (Laravel) держал фильтры арендатора в PHP — глобальные scope'ы Landlord. Один забытый scope = запрос видит чужие данные, и никакой тест это не заметит. ADR-005 переписывания прямо называет это мотивом: сделать класс багов «забытый фильтр» невозможным.

**Решение:** перенести фильтрацию в СУБД. Роли приложения не «видят таблицу и сами фильтруются», а физически не могут получить чужие строки — их не выдаст даже рукописный SQL в psql.

Связанная тема: [[Dual-Write-Problem-and-Transactional-Outbox]] — там defense-in-depth для событий; здесь defense-in-depth для изоляции: RLS — **единственный** фильтр аренды (правило ADR-006: второй механизм = вторая точка расхождения = место утечки).

## 🏗️ Механика

### 1. Политика (policy) — единица RLS

Политика — именованное правило, прикреплённое к таблице. У неё два фильтра:

| Фильтр | Что проверяет | Операции |
|---|---|---|
| `USING` | какие **существующие** строки видны | SELECT, UPDATE, DELETE |
| `WITH CHECK` | какие **новые** строки допустимы | INSERT, UPDATE |

Ключевое свойство Postgres: для политики `FOR ALL` (все операции сразу) с заданным только `USING` СУБД **автоматически** использует то же выражение и как `WITH CHECK`. Отсюда наблюдаемая асимметрия:

| Операция без контекста | Фильтр | Результат |
|---|---|---|
| `SELECT` / `UPDATE` / `DELETE` | `USING` | **0 строк, молча** (строки «не существуют») |
| `INSERT` | `WITH CHECK` | **ошибка** `new row violates row-level security policy` |

Оба поведения — fail closed (нет данных о «кто ты» → доступ запрещён), но семантика разная: читатель видит пустоту тихо, писатель падает громко.

### 2. Выражение изоляции — по частям

```sql
tenant_id = current_setting('app.tenant_id', true)::uuid
```

- `current_setting('имя')` — читает параметр конфигурации сессии (именованная ячейка памяти соединения). Имя `app.tenant_id` — собственное (точка в имени = пользовательский параметр).
- Второй аргумент `true` = missing_ok: параметр не установлен → вернуть **NULL**, а не бросать ошибку.
- `::uuid` — приведение текста к типу UUID (параметр сессии всегда текст).
- Сравнение с NULL даёт NULL (не true/false!) → в фильтре трактуется как «строка не проходит».

Цепочка: *не установил контекст → NULL → сравнение NULL → не видно ни одной строки*.

### 3. Как контекст попадает в базу: `set_config` + транзакция + пул

```ts
// eloomi-next: apps/api/src/shared/tenancy/with-tenant.ts (шаг 4 — единое место записи)
await tx.$queryRaw`SELECT set_config('app.tenant_id', ${ctx.tenantId}, true)`;
```

Третий аргумент `true` = **локально в транзакции**: при `COMMIT`/`ROLLBACK` значение стирается. Это обязательно из-за **пула соединений**: соединения переиспользуются, и параметр, переживший транзакцию, достался бы следующему запросу — контекст *чужого* арендатора. «Стереть за собой» — единственная безопасная дисциплина. (Мост: `SET LOCAL app.tenant_id` ≈ React-context-провайдер, скоуп которого — транзакция, а не рендер.)

### 4. FORCE: исключение для владельца закрыто

По умолчанию Postgres освобождает от действия RLS **владельца таблицы** (роль, создавшая её). `FORCE ROW LEVEL SECURITY` отменяет исключение — политики действуют и на владельца.

В eloomi-next владелец всех таблиц — `eloomi_owner` (роль миграций: она создаёт таблицы, значит владеет ими). Без FORCE миграции и seed-скрипты молча видели бы **всех** арендаторов — тихий обход изоляции, встроенный в штатные операции. С FORCE: `SELECT count(*)` под владельцем без контекста → `0` (проверено живьём, шаг 3).

Контраст по привилегиям: `eloomi_system` (BYPASSRLS) — единственная легальная «над-RLS» роль, инвентарь которой закрыт: seed и rebuild, каждое использование — review-маркер (ADR-005).

### 5. Каноническая функция: один producer, все callers

Политик будет много (таблица на каждый контекст). SQL каждой писать руками = дрейф (забытый FORCE, изменённая формулировка). Решение — функция в схеме `platform`, порождающая все политики; требование ADR-006 «byte-identical» = все политики проекта рождены одним текстом.

```sql
-- eloomi-next: apps/api/src/contexts/platform/prisma/migrations/20261013114914_init_platform/migration.sql:48-58
CREATE OR REPLACE FUNCTION platform.apply_tenant_rls(schema_name text, table_name text)
RETURNS void AS $$
BEGIN
  EXECUTE format('ALTER TABLE %I.%I ENABLE ROW LEVEL SECURITY', schema_name, table_name);
  EXECUTE format('ALTER TABLE %I.%I FORCE ROW LEVEL SECURITY', schema_name, table_name);
  EXECUTE format(
    'CREATE POLICY tenant_isolation ON %I.%I FOR ALL USING (tenant_id = current_setting(''app.tenant_id'', true)::uuid)',
    schema_name, table_name);
END;
$$ LANGUAGE plpgsql;
```

plpgsql-механика: DDL нельзя выполнить статическим планом, когда имя — параметр → динамический SQL `EXECUTE format(...)`; `%I` — безопасное квотирование идентификатора; `''` — экранированная кавычка внутри строкового литерала.

**Карта вызовов:**
- сегодня: `migration.sql:60-61` — по строке на каждую tenant-таблицу (`domain_events`, `idempotency_keys`);
- будущее: одна строка в миграции каждого нового контекста — `SELECT platform.apply_tenant_rls('learning', 'courses')`;
- страховка от забытого вызова: инвариант-тест (шаг 10, `invariant.spec.ts`) проверяет по каталогам `pg_class`/`pg_policies`: таблица с `tenant_id` без политики или без FORCE = красный тест. Правило исполняется инструментом, не памятью.

### 6. GRANT и политики — два независимых слоя

| Слой | Регулирует | Пример |
|---|---|---|
| GRANT | какие **таблицы** роль может трогать в принципе | `GRANT SELECT, INSERT... ON ALL TABLES IN SCHEMA platform TO eloomi_app` |
| Политика RLS | какие **строки** внутри таблицы видны | `USING (tenant_id = ...)` |

`eloomi_app` (весь рантайм) имеет гранты — иначе `permission denied` ещё до RLS — и находится под политиками. `ALTER DEFAULT PRIVILEGES` распространяет гранты на будущие таблицы схемы. Уровни строго разделять: **политика работает со строками (DML); создание таблиц (DDL) — территория GRANT и владения, политики её не касаются**.

### 7. Глобальные таблицы: у кого политик нет

`platform.tenants` (реестр арендаторов) — без политики намеренно: логину нужно найти арендатора по коду компании *до* того, как контекст известен. Таблицы без `tenant_id` обязаны быть в константе `GLOBAL_TABLES` (ADR-005) — инвариант-тест проверяет обе стороны правила (tenant-таблица без политики = ошибка; таблица без `tenant_id` вне списка = ошибка):

```ts
// eloomi-next: apps/api/src/shared/tenancy/global-tables.ts (шаг 4)
export const GLOBAL_TABLES: readonly string[] = [
  'platform.tenants',          // реестр арендаторов
  'public._prisma_migrations', // книга миграций Prisma — живёт в public, не в platform!
];
```

## 💥 Боли и грабли (реальные)

1. **`permission denied for schema public`** (пойман в шаге 3): PG 15 (2022) отобрал право `CREATE` в схеме `public` у псевдороли PUBLIC (харденинг). Prisma пишет книгу миграций в `public` → роль миграций упёрлась. Лечение: `ALTER DATABASE eloomi OWNER TO eloomi_owner` — в PG15+ `public` принадлежит `pg_database_owner`, владение БД дало владение схемой.
2. **Асимметрия fail-closed**: забытый `SET LOCAL` на чтении = тихий пустой результат (легко принять за «данных нет»), на записи = громкая ошибка. Тихая ветка опаснее для отладки: «пустой список» выглядит как баг данных, а не как пропущенный контекст.
3. **Пул соединений** убивает любые «запомнить тенант в соединении» схемы: только транзакционно-локальная установка.
4. **Направление FORCE**: не «обходит доступ», а **закрывает обход** — инверсия, в которой легко запутаться при чтении чужого кода.

## ⚖️ Альтернативы и почему нет

- **Фильтры на уровне ORM** (Landlord в легаси; в Prisma — `$extends`): корректность зависит от каждого запроса; ADR-006 запрещает — второй механизм поверх RLS = точка расхождения.
- **Отдельная БД на арендатора**: абсолютная изоляция, но N миграций, N пулов, N бэкапов — эксплуатационный ад для MVP.
- **Ручной SQL политик по миграциям**: дрейф; заменён канонической функцией.
- **`current_setting` без missing_ok**: тоже fail-closed, но ошибкой; ADR-005 фиксирует семантику «query sees nothing».
